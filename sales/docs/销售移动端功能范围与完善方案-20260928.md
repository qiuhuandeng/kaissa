# 销售移动端功能范围与完善方案

日期：2026-09-28。状态：第1组客户意向→产品／AI→预订资料承接已实施验收，其余组未实施。依据用户最新要求，保留现有五入口、绿灰色UI、小程序式标题栏、紧凑产品和订单列表；订单列表不恢复开单按钮。

第1组实施证据见[实施与验收](实施与验收.md)：34项规则测试、语法检查及320／390宽浏览器验证通过。以下现状表保留实施前基线，不能据此覆盖本次进度；M02品类、M05后续报价办理及其他组继续按下表推进。

## 一、本轮结论

移动端应让销售顾问围绕“一个客户的一次出行”持续完成接待、推荐、成交与订单服务。它需要覆盖销售每天随时会发生的查看、录入、申请、补充和结果查询；复杂批量处理、产品维护、资源确认及财务执行继续由后台和相应岗位承担。

merchant已有较完整的功能分布，但不能把菜单数量当成销售权限，也不能把按钮存在当成业务已经可用。当前移动端已具备标准预订和日本亲子定制两条代表路径，仍不足以代表销售日常全流程。下一阶段重点是补业务条件、信息承接、异常处理与明确结果，不重做视觉框架。

主流程为：接待客户 → 记录本次需求 → 推荐现成产品／制作定制方案 → 核对预订或提交已确认项目 → 订单办理 → 出行服务 → 售后与再次出行。收款、合同、资料通常并行办理，不能硬排成“收齐款才能签合同、签完才能补资料”的固定顺序。

上游是客户咨询、分配线索、客户历史、可售产品与具体日期、价格和服务规则；销售维护客户事实、成交依据和申请；下游分别交业务审批、产品／计调、合同经办、签证岗位和财务。销售随时能查看下一岗位、缺少的材料和返回结果。

## 二、merchant中销售岗位现有功能

下表“已有”指本轮从源码中找到页面、字段或处理分支，不等于本轮重新做过浏览器验收，也不等于正式接口已经接通。

| 业务场景 | merchant入口和已表达能力 | 销售职责与手机取舍 |
|---|---|---|
| 每日工作 | 销售顾问工作台：本人客户订单、今日回访、意向到期、近期出发、快捷预订、AI | 手机完整承接本人待办和直接办理入口；不照搬全店／集团指标 |
| 线索与意向 | 电销意向：来源、顾问、回访、分配、转预订；意向订单：个人／企业、多品类需求、日期明确度、预算、跟进 | 手机接收本人线索、记录意向、回访和转预订；主管批量分配与团队管理留后台 |
| 客户档案 | 散客会员：档案、来源、同行游客、历史订单、权益；企业客户：联系人、合同与开票资料、关联项目 | 手机使用业务必需资料和本人客户；会员规则、积分管理、批量合并不搬入 |
| 查产品 | 产品预订：目的地、出发地、日期、品类、预算、天数、余位、销售状态、方案与具体日期 | 手机保留高频筛选、规格价格、退改和材料截止；产品编辑及定价留产品岗位 |
| 预订下单 | 新建订单：不同品类规格、联系人、销售归属、草稿／预留／占位／待确认／确认、收款计划、费用摘要 | 手机可独立完成常见预订；实际可用动作由产品、公司授权、资源和付款条件决定 |
| 订单处理 | 订单列表与详情：状态、转确认、增人、释放、取消、游客、应收收款、合同、附件、履约和操作记录 | 手机以订单详情为主办理页；特殊变更须按主状态和权限判断，不显示一套所有订单通用按钮 |
| 应收与服务变更 | 订单应收调整及共享脚本：新增收费项、原项目数量／单价变更、免费服务、计调确认、业务审批 | 手机提交申请、看差额和结果、补充退回材料；销售不直接改已生效金额、不代计调确认服务 |
| 收款认领 | 收款认领：到账流水、凭证、付款方、分配订单、待复核、已确认、退回；详情内有收款入口 | 手机以单笔订单登记和补材料为主；跨多订单分摊、OTA账单解析等复杂工作留后台 |
| 合同 | 合同管理及共享模型：模板适配、签署人、按人分签、附件、审核、签署进度、异常、变更、撤销／解除、企业线下归档 | 手机完成普通签约及看进度、补件；复杂分拆和企业变更可后台继续，但手机须能看到办理状态 |
| 游客与出行 | 订单游客资料、按业务区分的材料、签证承接、资源确认、保单和出团通知附件 | 手机补资料、看缺口、看已发布结果；签证审核、出票、分舱分铺和出团发布归履约岗位 |
| 售后 | 原订单申请及售后处理：转团／改期、退团／退订、退款、转款、撤回、补充、审批结果 | 手机发起常见诉求和追踪结果；资源扣损由计调确认，退款／转款由财务执行 |
| 审批 | 待我审批、我发起的、抄送我等入口 | 普通销售首要是“我发起的”和退回补充；只有兼任审批岗位才出现待我审批 |
| 门店经营与管理 | 门店成员、预存、门店对账、电销顾问与业绩等 | 不属于普通销售默认功能。店长／合伙人可另按授权增补，不能全部开放给店员 |

## 三、销售实际会在手机上完成什么

| 当天场景 | 打开后先看什么 | 销售动作 | 结果和下一岗位 |
|---|---|---|---|
| 客户微信说“11月带孩子出去，预算3万” | 是否老客、同行人、现有需求 | 新建本次需求，允许日期／预算部分待定，补回访时间 | 形成可继续跟进的需求，不占名额、不计成交 |
| 客户问“周末出发还有没有位” | 对应日期、余位、价格、二次确认要求 | 查产品、选择规格，整理两三个可选方案 | 客户确认后进入预订；无位明确提供换期或替代产品 |
| 客户要一条定制路线 | 本次人数、日期、预算和偏好 | 用AI整理、生成并修改行程，比较版本，采用有依据报价 | 客户确认指定版本；提交已确认项目审核，交产品／计调承接 |
| 客户先留两个位置 | 是否允许预留／占位、截止时间、付款条件 | 按本单条件提交，必要时申请延期或释放 | 显示名额占用与截止；未满足条件不冒充已确认 |
| 客户发来转账截图 | 本单收款公司、应收、已确认收款、待复核记录 | 填金额、付款人、流水及代付说明，上传凭据 | 待财务复核；退回仍从原记录补充，避免反复填同一笔款 |
| 一家三口准备签约 | 谁签、覆盖哪些游客、缺哪些附件 | 核对签署资料、预览、提交审核／发起签署，查看进度 | 以逐方签署和公司签章结果判断；部分完成不等于全单已签 |
| 客户补护照／提出联运 | 哪位游客缺什么、哪项服务未确认 | 补资料；另发联运或升舱申请，核收费／免费 | 资料交签证／计调；免费联运也要有明确接收和确认结果 |
| 明天出发，客户问集合地点 | 最新出团通知、交通、领队及集合信息 | 查看已发布资料，预览或复制对客内容 | 使用已发布版本；未发布显示负责岗位和当前状态 |
| 客户要求换团、退款 | 原订单、适用规则、原款和已处理记录 | 选择游客／项目、目标团期或诉求、原因和确认依据 | 业务审核与资源核对后交财务；销售能看进度和退回原因 |

## 四、保持五个一级入口，补齐内部功能

### 1. 工作台：今天要处理什么

- 待办分为今日回访、保留临期、款项到期／认款退回、合同未完成、资料临期、资源异常、申请退回。优先显示客户／订单、截止时间和可核对缺口。
- 从待办直接进入相应客户需求或订单办理分区，返回保留原筛选；不先绕到全量列表重新找对象。
- 继续未完需求、方案和预订草稿；草稿按客户与需求区分，不能只允许全应用保存一笔草稿。
- 消息分清“需要我处理”和“结果通知”，同一事项避免在待办中重复堆叠；消息读取不等于业务完成。
- “我发起的申请”聚合改价、服务变更、售后、合同等申请，能查当前岗位、退回原因和历史结果。处理仍回原申请。
- 本人订单数、已确认收款可轻量展示，但必须按所选期间及日期依据计算，不把全部历史累计冠以“本月”；奖金与提成暂不推算。

### 2. 客户：客户关系与本次需求分开

- 保留紧凑客户列表；增加“客户／意向”页内切换。待回访是筛选条件，客户等级不代替某次出行的销售阶段。
- 新客快速登记、手机号查重、老客复用、常用同行人、历史订单和备注。客户资料不因一笔订单改期被覆盖。
- 本次意向记录来源、出发地、目的地、日期或月份、天数、人数结构、预算范围、产品偏好和下次回访；日期未定可保存，成交前再补齐。
- 意向阶段可建议为新需求、跟进中、方案沟通、待成交、已转订单、已关闭；“资料待补、今日回访”作为提示或筛选，不混入主状态。
- 需求详情统一承接跟进记录、候选产品、当前方案、关联订单、关闭原因和恢复；进入产品预订仍保留本次需求。
- 企业客户补联系人和项目需求；复杂企业主档、批量联系人管理可后台完成。转交只向授权接收人发起，未接收前保留原责任。

### 3. 产品：快速找到能卖、能准确报价的产品

- 保留紧凑列表，完善名称／业务编码、目的地、出发城市、日期范围、类型、预算和余位筛选。常用筛选直接显示，其余放筛选面板。
- 详情先看实际可售日期、报价对应规格、余位和确认方式，再看行程、费用、退改、证件／签证材料及截止时间。
- 提供“推荐给当前客户”和“预订”。推荐形成对客预览或候选记录；进入预订必须选日期与规格，不拿起价当成交金额。
- 收藏／最近查看可作为轻量效率增强，不优先建设营销素材商城。
- 已发布标准产品只能选择现有方案与规格；AI不能直接改成一条仍以原产品名销售的新路线。

### 4. AI助手：以可继续办理的结果卡片服务成交

- 顶部始终明确当前客户及本次需求，切换客户不得串方案、报价、确认和会话。
- 快捷场景控制在“整理需求、推荐产品、定制行程”三个主要入口；产品比较、版本调整、报价说明和开单核对由当前结果承接。
- 保留commerce-agents的产品、对比、每日行程、检查清单与开单卡片交互。页面列表紧凑化不等于AI结果退化成纯文字。
- 已有会话仍应能找到常用工具入口；结果卡片绑定本次对象和版本，历史卡片可回看。实施前曾仅在无消息时展示快捷卡片；第1组已改为三个常驻入口，并验证已有会话仍显示原方案与推荐卡片。
- 产品／订单详情内的“问AI”带当前产品或订单；普通业务操作继续有明确按钮，不要求销售通过聊天才能填资料、认款或签合同。

| AI能力 | 需要的业务依据 | 应返回的内容／卡片 | 销售下一步 |
|---|---|---|---|
| 沟通转需求 | 销售粘贴的沟通、已有客户资料 | 提取字段、待问问题、与原需求的差异 | 销售核对后保存，不能默默覆盖 |
| 推荐与比较 | 授权可售产品、日期、规格、价格及规则 | 2—3个候选、匹配理由、不满足条件、差异比较 | 选日期规格，加入候选或预订 |
| 定制路线与修改 | 本次需求、可用服务依据、当前方案版本 | 按天行程、改动摘要、参考预算、未确认项 | 比较版本，保留旧版，进入业务核价 |
| 对客报价说明 | 本版有效报价、费用与退改约定 | 客户版行程及报价，明确日期人数和有效期 | 预览、复制／分享，另记录客户确认 |
| 开单前检查 | 选定版本、报价、客户确认、预订资料 | 可核对清单、缺项与对应办理入口 | 销售核对后提交；不会因一句“可以”自动开单 |
| 订单问题解释 | 本单资料缺口、认款／签署／资源／售后结果 | 问题摘要、证据、办理入口、客户回复草稿 | 进入原业务办理或核对后使用回复 |

当前AI是本地关键词与固定场景，不是完整模型能力。后续原型可用代表场景完成上述交互和正常／缺资料／失败状态；正式模型、产品检索和接口接入另行实施，不将其混报为已完成。

### 5. 订单：成交后的主要办理页面

订单一级页继续以查询为主，不放开单按钮。状态筛选逐步覆盖预留、占位、待确认、已确认、出行中、已完成、已取消；资料缺失、认款退回等作为辅助筛选。列表只展示一个主状态和少量判断字段。

订单详情沿用“概览、收款、合同、资料、出行、售后”六区，在现有结构内补功能：

| 分区 | 要补齐的业务细节 | 完成后应看到什么 |
|---|---|---|
| 概览 | 费用明细、预留／占位截止、确认条件、当前缺口、订单所属与签约／收款公司；按状态提供延期、释放、转确认或取消等适用动作 | 当前状态、限制原因、操作记录；已收款／签约／确认资源的订单不能随意释放或作废 |
| 收款 | 应收项目、付款节点与到期日、已确认／待复核／未收分开；收款方式、凭据、代付依据、原申请退回补充；应收调整入口 | 认款申请进度与财务结果；业务价格批准前原应收不变，不把申请金额算作实收 |
| 合同 | 按业务匹配合同或确认书，核覆盖游客、签署人、监护／代签关系与附件；预览、审批、签署入口和逐方进度 | 受理失败／未知、部分签署、我方签章、签署完成分别表达；变更后能查新旧版本 |
| 资料 | 常用游客带入，按本产品要求补证件、实名和材料；支持附件、缺口数量、截止及退回原因 | 完整度和办理岗位明确；录入完整不等于签证审核通过或已经出票 |
| 出行 | 分项资源确认、拒绝／补差结果、联运升舱等服务申请、交通酒店确认资料、出团通知、集合及领队信息 | 申请／已确认／不支持分开；只看已发布通知，销售不能手工改成资源已确认 |
| 售后 | 改期／转团、退订、退款、转款；选涉及游客／项目、原款、目标、依据；查看、撤回及退回补充 | 原订单、费用处理、合同处理和财务执行结果分别可查，申请通过不表示钱已退 |

应收调整、免费服务、转团、退款不是四处重复的新模块：以原订单为主入口，由申请详情承载核对与退回处理；工作台只提供带对象的待办入口。

## 五、不同产品不能全部套“成人＋儿童”

| 业务 | 手机应支持的差异 | 实施建议 |
|---|---|---|
| 普通参团游 | 团期、成人儿童条件、占床、房型、单房差、联运、材料和收款计划 | 第一轮完整代表场景 |
| 小型定制 | 需求、方案版本、报价依据、客户确认、项目提交及审核结果 | 第一轮完整代表场景；不新建供应商询报价系统 |
| 自由行 | 出行日期、套餐、房型／间夜、航班或接送需求、二次确认 | 第二轮；当前自由行样例沿用人数计价，尚未覆盖完整规格 |
| 邮轮 | 航次、舱型、舱房数、同舱关系、第3／4人、税费和护照 | 第二轮代表场景，不复用普通跟团人数算法 |
| 专列 | 班期、车厢／铺位、上下铺、占铺条件、上下车站、实名 | 第二轮代表场景 |
| 单项服务 | 服务类型、使用日期、人数／份数、所需材料和交付结果 | 第二轮；不强制关联团期，由授权服务产品进入 |

## 七、不能照搬的现状及规则冲突

1. **电销转预订提前记成交。** `call-center/intents.html`的保存跟进分支把“转产品预订”映射为“已转订单”，并填示例订单号。移动端要区分打开预订、保存草稿、提交形成订单；仅有已提交订单依据才记录已转订单，已转订单也不直接等于业务已确认。
2. **意向保存提示不代表完整承接。** `orders-intent.html`的`saveIntent`主要校验后提示成功，跳预订仅传类型。手机要能回到所保存意向、带入当前客户与需求，不能只弹成功。
3. **应收调整职责以较新规则为准。** 培训材料仍有“审批和财务复核后生效”旧句；销售流程2026-09-26补充及`order-amendment-model.js`明确：计调确认相关服务，业务审批金额，批准后应收生效；财务复核实收，不再替业务审批价格。具体审批岗位仍待配置。
4. **AI前置定制与后台完整询报价分开。** 用户已明确要求手机AI定制到开单；这增加销售前置方案能力，不恢复旧意向／企业页中的完整计调询报价系统。采用本版业务报价、客户确认后接已有项目审核。
5. **保护规则不等于统一制度。** 预留期限、定金比例、合同放行、优惠与退款、跨公司承接按有依据规则表达；未定时提示缺哪项条件，不硬写全公司24小时、30%定金或必须收全款。
6. **权限配置存在不等于全部页面已接通。** 菜单不是销售权限清单；手机默认本人客户订单，不恢复曾撤回的销售结算价展示，不给普通销售门店余额、成本、公司间对账或财务执行权。
