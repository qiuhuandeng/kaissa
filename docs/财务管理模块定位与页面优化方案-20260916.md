# 财务管理模块定位与页面优化方案

日期：2026-09-16。状态：方案待用户确认，未实施页面改造。

## 一、结论与本次范围

财务管理定位为：**围绕旅行业务单据，完成款项确认、收付执行、结算核对、核算确认和期间控制的业务财务办理中心。**

财务人员进入后应知道：今天处理哪些单据、依据是否齐全、金额是否一致、可以做什么、完成后交给谁。经营结果分析不能替代这些办理动作。

本次静态核对主业务端财务导航23个入口及页面结构、关键处理逻辑，结合三份财务流程确认稿、多主体责任基线及数据中心既定范围提出方案。页面已有结构不等于正式服务已实现；本轮没有执行资金、审批、财务确认或NC推送，也未做浏览器流程验收。历史审计只作问题线索，本次明确复核的代码问题单独列证据。

建议保留现有23项业务能力，资金池调整为账户对账，新增核算确认、内部结算两个入口，形成25个菜单。新增方案未获批准前仍维持现状。门店并行办理线不纳入本轮改造。

## 二、谁使用、负责到哪里

| 角色 | 当天主要任务 | 主要入口 | 办理结果 |
|---|---|---|---|
| 收款财务 | 核实到账，审核销售认款，处理分配差异 | 到账流水、认款复核、应收、预收 | 已确认收款及对应应收核销记录 |
| 应付财务 | 核对供应商账单，确认负债及可申请付款金额 | 供应商账单、应付、预付 | 应付确认、预付冲抵及付款依据 |
| 出纳 | 执行已批准收退款、付款和调拨，核对银行结果 | 退款执行、付款执行、回单核销、付款退回、账户对账 | 实际资金结果及差异处理记录 |
| 结算财务 | 核对团期、项目、渠道、门店和公司间结算 | 业务结算、渠道结算、门店对账、内部结算 | 经核对的结算结果及未解决差异 |
| 核算会计 | 确认收入成本及期间，处理调整、核对凭证 | 核算确认、发票、NC推送、期间关账 | 可入账依据、凭证承接结果及期间状态 |
| 财务负责人 | 审批权限内事项，检查例外和关账条件 | 审批中心、各财务业务页、期间关账 | 审批意见、例外处理及关账决定 |

主体是承担法律或记账责任的公司；核算主体是实际记录这笔账务的公司或账套。合同、销售、产品、收款和成本承担公司可以不同，不可用一个“所属公司”覆盖。

主数据与合同、产品和实际履约事实来自上游。采购、计调确认供应服务和数量；财务确认金额、结算责任及入账依据。财务不能在结算页直接改游客人数、履约日期或供应商服务数量以消除差异。

审批中心承接授权审批，来源单据保留财务审核及审批结果；不能让同一事项在财务页与审批中心各审批一次。集团财务核算系统（以下简称NC）与本系统的正式记账分工仍须财务确认，本方案不默认在旅游系统重建总账。

## 三、按旅行社实际业务组织流程

### 1. 收款流程

订单及合同约定应收 → 实际到账 → 认款申请 → 财务复核 → 应收核销或预款入账 → 凭证承接。

到账与认款是两个对象：一笔到账可以分配多个订单，一个订单也可以多次收款。保留原银行流水及每次分配，不能拆成多笔虚构到账。预收是已收但尚待按指定业务使用或确认的款项；预存账户是按约定用于后续业务扣款的账户，两者不能重复记余额。

### 2. 成本及付款流程

合同付款节点／已确认采购及履约依据 → 供应商账单核对 → 应付确认或预付款申请 → 审批 → 付款执行 → 银行结果及回单核对 → 应付核销或预付登记。

存在先付定金、后履约结算的真实场景，不能要求所有预付款先有最终成本。付款申请占用的是可申请额度，付款成功才形成相应实际资金结果；预付冲抵也不能再次计作实际付款。

### 3. 完成、结算及核算流程

实际履约完成 → 业务结算核对 → 收入／成本核算确认 → NC凭证承接 → 期间关账。

上述是责任承接顺序，不是所有事项必须等待整团最终结算的硬性串行条件。阶段验收、符合批准政策的暂估成本可以有独立确认依据。暂估指服务已发生、最终结算金额尚未取得时，按批准依据暂时确认成本。

实际回团不能等待开票、收款、付款全部完成才成立；业务结算完成也不自动等于收入已确认。收付、票据与核算按各自业务条件推进，在结算和关账时核对。

## 四、逐页优化方案：现有23个入口逐一处理

下表中“建议”均是待实施设计，不表示现有页面完全没有相关字段或动作。

|---|---|---|---|
| F01 到账流水 | 来源、银行账户、到账金额、识别对象、未识别金额，登记及导入 | 围绕一笔真实到账办理；列表突出收款公司、原币金额、未分配金额及状态；详情核对一款多单、重复导入、非订单款归属，识别业务方向后交认款复核 | 重复导入不新增到账；已分配与未分配可以核对，截图不能代替银行到账 |

| F04 预收管理 | 预收单、已用可用、用途、冻结退款 | 表达与指定客户／订单关联的预款使用，核对来源、可用范围、转用、退款；明确不与预存账户重复入账 | 同笔款进入预收或预存的归属明确；使用与退回均能解释余额 |

| F06 退款执行 | 批准退款、退款对象、原款、执行及回单 | 只执行已有批准依据的退款；区分原路、其他批准账户及平台已退；清楚展示可退余额与执行结果 | 平台已退不能再次付款；退款失败不抹去已批准的业务调整 |
| F07 转款处理 | 原新订单、转款额、差额及处理记录 | 定义为已确认款项重新分配；原收款历史保留，跨公司转款展示内部结算承接；差额退款另交退款执行 | 转款不产生新银行收入，不重复累计订单实收 |
| F08 供应商账单 | 上传、关联业务、成本核对、差异及应付结果 | 一张供应商账单为主对象，明细分配到团期／项目／服务；业务确认数量和服务，财务确认结算金额及付款资料；拒绝差异回到来源 | 多团账单分配合计等于确认总额，未解释差异不能静默覆盖 |
| F09 应付管理 | 应付来源、成本、金额、已付可付和付款进度 | 显示应付公司、供应商、原币、到期节点、未结清、申请占用及可申请；区别负债余额和可申请付款额度 | 已付、已冲抵、申请占用分别扣减对应口径，不重复扣款 |
| F10 付款申请 | 依据、原币及人民币、预付冲抵与净付、审批承接 | 围绕申请对象和付款依据办理；区分预付、应付及其他批准类型；提交前校验账户与额度；审批仍回审批中心 | 撤回／驳回释放占用；同一应付不能超额申请 |
| F11 付款执行 | 付款单、申请、双方账户、付款进度、回单 | 出纳只处理已获批准的付款；区分待执行、银行处理中、成功、失败、结果待核实；异常后先查结果，再决定重试 | 银行结果未知不能作为失败直接重付；上传附件本身不等于付款成功 |
| F12 回单核销 | 回单导入、匹配、校验、核销、凭证承接 | 匹配银行结果与已存在付款；处理合并扣款、分次付款、手续费及币种差异；与付款页共用同一确认结果 | 一张回单不能重复核销；执行页已确认资金不得再次计出账 |

| F14 预付管理 | 预付、分配、冲抵、余额、退款及关闭 | 同一预付款详情中区分使用范围分配与抵减应付；资源采购跨团分配以业务依据为准；退款、转用及余额更正各有依据 | 分摊资源成本不自动消耗预付；预付冲抵不重复形成成本 |
| F15 业务结算 | 团期／项目核对、收入成本差异、毛利、结算及NC提示 | 聚焦业务结算资料与确认结果；建议主题Tab为结算办理、结算调整。核算确认迁入独立入口；详情分收入依据、成本依据、差异、确认记录 | 结算确认不直接替代会计确认；差异退回正确来源，不能只修改汇总数 |
| F16 渠道结算 | 渠道账单、订单优惠、平台扣款、应收及到账差异 | 针对线上平台、同业等结算账单逐单核对订单、账单与银行净到账；平台费、优惠承担和退款分别确认 | 净到账不能直接当营业收入；已确认费用不能再在贡献报表重复扣减 |

| F18 期间关账 | 收入应收、应付成本、发票、NC缺口及关账 | 移入核算票据分组；检查项分阻断、待批准例外、提示三类，逐项展示原因及责任入口；支持批准后的重开或后期调整表达 | 正常待收、待付、预付余额不一律阻断；真正缺失的确认依据按政策阻断 |
| F19 资金池 | 余额、可用、未识别、冻结、资金变化，当前主要只读 | 建议更名账户对账；主题Tab为账户核对、银行对账。以账户及对账期间核对银行流水与系统记录，处理未达和差异；保留必要余额，跨账户分析归数据中心 | 预存余额不是银行现金，不能与银行余额相加；若正式银行对账由NC负责，这里仅承接其结果及来源差异 |
| F20 资金调拨 | 转出转入账户、用途、金额、申请及确认 | 区分同公司账户划转和跨公司资金往来；明确审批、转出、到账、退回各阶段；双方公司资金结果分别确认 | 转出完成不等于转入完成；内部调拨不形成经营收入成本 |
| F21 发票管理 | 开收票、查验、税额、红冲、来源匹配及NC | 建议销项发票、进项发票两个主题Tab；分别对照业务依据与已确认核算记录；票据更正和业务退款分开处理 | 开票不重复确认收入，收票不重复确认成本，红冲只影响其有依据的事项 |
| F22 NC推送 | 待推任务、失败、历史、档案修复、借贷分录 | 改为核算确认后财务事项的校验及传送；校验公司账套、期间、借贷、科目及辅助资料；区分未送、结果未知、明确失败、成功、已冲回 | 未知结果先查询；借贷不平不能通过；修档案不等于可以批量重推所有任务 |
| F23 收付款配置 | 资金账户及收付款相关规则 | 保留NC推送之后的独立入口；维护账户基础资料、收付用途及权限，不承载日常余额分析；供应商账户审核与资源准入区别表达 | 历史单据保留当时使用资料；账户停用不破坏历史，未审核资料不能用于付款 |

## 五、需要补足的两个独立页面

### 1. 核算确认：补上“核对完成”到“可以入账”之间的处理

主要使用者：业务核算会计。上游为履约及阶段验收、结算依据、已批准调整；下游为NC财务事项和数据中心已确认收入成本。

建议三个主题Tab：**收入确认、成本确认、核算调整**。收入和成本是不同确认主题，不塞入“显示内容”下拉。各Tab默认按主状态筛选，不再多排一套无必要状态Tab。

列表核心内容：核算公司、团期／项目／服务、业务完成日期、确认期间、依据金额、本次确认金额、未确认金额、主状态。收入补清主责或代理的认定依据；成本补清正式结算或暂估来源。主责／代理指公司承担主要服务责任还是仅提供代理服务，不由产品名称推断。

详情中展示来源、确认金额及税额依据、成本或收入分配、调整历史和NC结果。财务执行确认、退回、撤销未入账确认或发起已入账调整，权限与已关闭期间检查分开。

不让财务随手改一个“收入总额”覆盖来源，也不把NC回传的已入账费用再生成一份成本。管理费用、分摊费用若由NC负责，旅游系统只承接结果及业务对应；本轮不新增整套报销系统。

验收：已回团但成本未齐、符合政策的暂估、部分阶段确认、已入账后补差四种场景；没有获批的收入、税务、暂估政策时显示待确认，不给默认通过。

### 2. 内部结算：满足集团多公司业务

主要使用者：各公司往来会计及集团结算财务。内部往来是集团两家公司之间因供货、代收代付或资金划转形成的应收应付。

建议主题Tab：**内部供货、代收代付、差异调整**。资金划转的执行仍在资金调拨，本页只处理对应往来责任和核对。

列表核心内容：双方公司、结算期间、结算单号、来源类型、我方确认、对方确认、差异金额、主状态。原币不同不直接对比合计。详情逐笔核对合同责任、原订单／供应账单／资金记录、双方确认和差异理由。

动作：发起核对、确认本方、退回差异、发起调整。不能替另一公司确认；不能因单边确认就给双方各生成一笔没有依据的负债。

同法人部门协作不作为公司间应收应付。集团抵销指合并报表中排除集团内部交易的重复影响，由集团既定核算流程处理；本页核对内部交易，不直接替代合并抵销。

验收：A公司销售、B公司提供产品、C为外部供应商；A代B收款；公司间跨币种；对方未确认；已关账后差异五种情况。

## 七、适用于凯撒复杂业务的设计要求

| 业务场景 | 财务必须能完成什么 | 对应页面 |
|---|---|---|
| 自营组团、外采整包、代理销售并存 | 分清服务责任、采购成本、销售公司与核算公司，依据批准政策决定总额或净额确认 | 供应商账单、业务结算、核算确认、内部结算 |
| 包机、邮轮切舱、专列采购跨多个团期 | 核对合同定金尾款、实际资源使用及损耗、预付分配与应付冲抵；未使用资源不能为了分完而随意摊给已出团业务 | 预付、供应商账单、应付、业务结算 |
| 平台净额打款 | 把订单成交、平台费、优惠承担、退款和到账分别解释，避免净到账当收入 | 渠道结算、到账、认款、核算确认 |
| 会奖项目分阶段验收 | 收款节点与履约确认分开；一期已验收可按获批政策确认，不能强制等整项目结束 | 应收、业务结算、核算确认 |
| 门店预存加分润 | 预存资金与应付分润分开；分润规则确认后形成结算依据，再走应付付款；本轮不重构门店线 | 预存、门店对账、应付、付款 |
| 回团后补成本或退款 | 保留原结算及原期间结果，根据批准规则形成差额调整；不覆盖历史报表 | 业务结算调整、核算调整、期间关账 |
| 境外供应商付款 | 原币、汇率及人民币分开；识别手续费及汇差承担；不同币种不直接相加 | 应付、付款、回单、核算确认 |

## 八、页面交互统一规则

1. 办理页以一类主业务单据为主表，默认突出待处理及异常；可保留当前范围金额合计。历史已完成单据保留查询，不删台账。
2. 独立主题用Tab，同一主题的汇总与明细才使用切换。状态使用Tab或筛选之一，避免主题、状态、显示层级堆三层切换。
3. 主表不平铺多个独立报表。详情中的原款、分配、核销、凭证属于同一对象的证据，可按详情Tab展示；必要的左右对照可以保留，不能为了“一页一表”拆散核对动作。
4. 列表由主流程状态决定稳定动作；缺资料、差异、临期是判断信息，不生成每行不同的随机按钮。对账处理允许并列展示银行与系统记录，核对对象保持明确。
5. 涉及资金的动作明确区分申请、审核、执行、确认结果和查看记录；已完成的按钮使用“查看付款／回单”等查看语义。
6. 详情集中呈现本单依据、金额组成、状态记录、关联上下游。高频承接可保留直接入口，低频跨菜单操作放详情关联单据。
7. 搜索沿用已确定左侧标题、明确默认值、自然换行、紧随末项的更多筛选；表格标题、字段设置及结果切换遵循既有统一规则，不恢复已撤回排序改造。
8. 不增加全局利润趋势、账龄结构、预算完成率等重复报表。办理所需待收、可退、可付、待核销等余额仍保留，必须与对应单据同口径。

## 十一、实施顺序与验收

方案批准后建议按以下次序推进，每步包含当前页面与直接入口范围的原型修改、正常／异常场景验收及记录，不追求浏览器模拟数据的生产闭环。

1. **结算与核算边界样板**：业务结算、核算确认、NC推送、期间关账。先把确认责任与关账阻断规则表达正确，验收实际完成未结算、成本暂估、已入账调整、结果未知四场景。
2. **收款应收链**：到账、认款、应收、预收、退款、转款；门店预存只核对承接边界。验收一款多单、部分退款、跨公司转款。
3. **成本应付链**：账单、应付、预付、申请、执行、回单、退回。验收定金先付、跨团账单、预付冲抵、失败退回与供应商退款。
4. **集团与渠道结算**：内部结算、渠道结算；门店仅在另行授权后纳入。验收双方不一致、平台净额到账及重复费用防止。
5. **资金与票据收尾**：账户对账、调拨、发票、配置；对全部25入口做角色及异常路径回归。

每页验收必须回答：上游是哪张单据；谁可以确认；确认哪个金额及期间；主状态如何变化；下游接收什么；异常退回哪里；重复操作是否会重复生成资金或核算结果。原型只证明这些表达成立，不能据此宣布已对接银行、税务或NC。

## 十二、需要确认的范围和政策

页面方案取舍：是否采纳23→25入口；资金池调整为账户对账；核算票据分组；首步从结算与核算样板开始。

待财务批准的政策：主责／代理及收入总额净额、税务处理、暂估及转回、跨期调整与重开条件、内部结算定价和双方确认规则、外币汇率与汇差承担、平台优惠和费用承担、门店可分配基础及正式分润规则。

待系统职责确认：NC承担的正式总账、银行对账、凭证生成及期间控制范围；本系统哪些提供确认依据、哪些只接收结果。先选唯一正式责任系统，不让两套系统同时确认同一笔账。

唯一下一步：用户审阅本方案，明确页面范围取舍；取得实施指令后先推进第1步，不自动修改23个现有办理页。
