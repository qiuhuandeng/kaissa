# 审批中心配置与流程页面增改方案

日期：2026-09-24。方案已获用户执行授权；本文件保留整体设计，当前实施证据见《审批配置首批实施记录-20260924》。用户补充确认：配置仅保留“审批模板、审批人员”两个 Tab，临时代办放审批人员操作抽屉。第一批已实现并完成规则及 DOM 检查，浏览器视觉仍待验，不代表第二、三批完成。

## 一、业务位置与现状结论

审批中心承接产品、团期、订单、合同、收付款等业务页面提交的申请。业务人员在来源页面办理业务；审批人集中核对依据并作出决定；审批管理员配置适用流程和处理人员异常。审批结束后，来源模块承接业务结果；付款执行、签署、归档、财务确认及 NC 推送仍由对应模块处理，审批通过不代表这些动作已经完成。

目前已有审批事项、五个导航入口及部分业务专属详情，但尚未形成统一的可配置审批能力。

| 源码证据 | 现有能力 | 缺口 |
| --- | --- | --- |
| `shared/nav-merchant.js`，审批中心五个入口 | 待我审批、我发起的、抄送我、审批总览、审批配置 | 导航已足够，不必增加一级菜单 |
| `merchant/approval/approvals.html`，`configs`、`openConfigModal` | 通用配置为固定事项、节点描述及只读弹窗 | 缺新建、编辑、条件分支、适用范围、试跑和发布 |
| 同文件，`matterOptions`、`configs` | 可筛选审批事项与配置行分别维护 | 两者未一一对应，不能据此认定所有场景均已接入 |
| 同文件，`approve`、`updateApprovalStatus` | 通用审批点击通过即标整单通过 | 缺当前节点完成后进入下一节点的表达；待办不能仅按示例范围筛选 |
| `shared/contract-approval.js` | 六类合同事项，可编辑少量公司、固定审批人等配置 | 需要保留合同差异，接入统一配置及节点流转方式 |
| `admin/org.html`、`merchant/system/my-org.html`、`merchant/system/staff-management.html` | 公司、部门、负责人、员工任职、角色和数据范围 | 可复用人员与组织来源，但尚无完整的按公司找审批人员规则 |
| `admin/merchant-roles.html` | 已有审批操作、配置等粗粒度权限 | 需区分维护、发布、审批人员管理、异常处理与可见范围 |

供应商准入、供应商资料变更和供应商协议已按 2026-09-21 文档改为管理端办理、致远审批；供应商账户变更仍有内部审批。本方案不直接撤销已确定的分工。若后续要求将上述致远场景也迁回系统内，须另行明确切换范围及在途单据处理，避免重复审批。

参考腾讯官方《审批流配置》所列企微模板、规则设置、审批节点、抄送节点、条件分支和多人审批方式，借鉴其简单配置交互，不照搬通用办公表单，也不据此宣称本项目已具备企微能力。参考：https://qian.tencent.com/document/77772/

## 三、审批配置怎样使用（按用户补充简化）

### 1. 审批模板

页面右上角只突出“新建模板”。筛选为业务场景、公司、状态及名称搜索；不设置统计卡，不把几十个审批事项展开为顶部 Tab。

列表六列：模板名称、业务场景、适用公司及部门、流程摘要、状态、操作。状态为草稿、已发布、已停用；已发布模板另有修订草稿时，用弱文本说明，不并列堆状态标签。

草稿支持编辑、删除；已发布支持查看、修改，复制、停用、版本记录放更多；停用模板支持查看、修改并重新发布。发布后的修改先形成修订草稿，发布前仍执行原版本。被历史单据引用的版本不可删除。

新建先选择业务场景，自动带出该场景可用的审批内容和默认流程示例；示例明确待配置、待发布，不自动生效。相同规则覆盖多公司时共用模板，有差异再复制调整，不按每个部门或每档金额机械拆模板。复制时重新核对公司和指定成员，不静默沿用失效人员。

### 2. 审批人员

解决“这家公司的财务负责人是谁”等问题，不复制员工档案。列表按公司、审批职责查看现有人员及生效时间，抽屉维护人员安排。

支持两种来源：直接使用组织中已维护的部门负责人、上级部门负责人；按公司维护财务审核、合同审核等审批职责对应的员工。审批职责用于找到办理人，系统角色用于决定操作权限，两者不混为一谈。

只选择既有在职员工及有效任职。跨公司人员必须有明确授权，不能因同属集团就默认可审批。兼职人员按本次业务所对应的任职匹配，不能只按默认任职判断。组织里的法人代表不自动等同业务负责人。

### 3. 临时代办（审批人员操作抽屉，不单列 Tab）

列表展示原审批人、代办人、适用公司和事项、生效期间、状态。抽屉填写代办原因和时间；到期自动停止接受新代办任务。

代办不扩大可见及审批范围，记录原审批人、实际办理人和代办依据。禁止循环代办。新生效设置默认用于后续到达的任务，是否转交已有待办须明确选择并留痕；到期后的未办任务回到有效的原审批人，原人员已失效则进入人员异常处理。

## 四、流程编辑页：四步完成

二级页采用现有后台样式，左对齐内容宽度不超过 1216px；顶部只保留一组标题和操作。复杂流程区内部可滚动，不撑破外壳。节点用纵向卡片，点击后右侧抽屉编辑；不要求用户拖线绘图。

| 步骤 | 填什么 | 简化方式 |
| --- | --- | --- |
| 适用范围 | 模板名称、业务场景、适用公司、部门、是否含下级部门 | 公司含义随场景解释，避免万能“所属公司” |
| 审批内容 | 审批人需要核对的业务资料、补充说明和附件 | 自动带出业务单据字段，核心内容只读且不可删除，不重建业务表单 |
| 审批流程 | 审批人、条件分支、抄送人 | “＋”只显示三种节点，选中节点用抽屉配置 |
| 其他规则 | 退回补充、撤回、办理时限、允许的转交方式 | 常用项直接显示，低频规则折叠 |

审批人可选择：申请人的部门负责人、上级部门负责人、该业务负责人、指定公司的审批职责人员、指定成员。“该业务负责人”按事项显示具体名称，例如产品负责人、团期负责人，不能留成没有来源的泛称。

多人办理用业务语言呈现：全部同意、一人同意、依次审批。流程图直接写明办理方式；全部同意或依次审批中，一人拒绝则本轮结束，其余未办任务关闭。退回补充与拒绝区分，退回进入补充重提，拒绝结束本轮申请。

条件用“字段—条件—值”设置，只提供该事项实际能取到的字段，如申请金额、业务类型、产品类型。金额条件同时限定币种，不将不同币种直接比较。先展示简单条件，多条件时再展开“全部满足 / 任一满足”。

条件分支顺序明确，按顺序采用第一条满足的分支，最后保留其他情况；发布前检查明显重叠和缺失。必要字段未提供时阻止提交或试跑，不当作不满足而落入其他情况。部门、公司等通常先用于适用范围，确需不同节点时再用于分支，避免重复配置。

建议默认不允许申请人批准本人申请、不允许找不到人员时自动通过、超时仅提醒不自动通过。同一人员担任不同职责不能一概跳过审批；如允许合并重复节点，必须有明确规则和可见记录。这些是待公司确认的建议规则，不将现有演示阈值视作正式政策。

## 五、公司、部门与流程如何匹配

先确定审批的是哪笔业务，再确定责任公司、业务部门和申请人。申请人登录公司不能替代业务责任公司，产品归属公司、签约公司、收款公司也不能一律互换。

| 场景 | 优先核对的公司及负责人来源 | 下游承接 |
| --- | --- | --- |
| 产品发布、价格调整 | 产品或团期业务归属及负责部门，按对应业务规则确认 | 产品或团期发布、价格生效等业务办理 |
| 付款申请 | 付款申请上已明确的付款公司及申请责任部门 | 财务付款执行；跨公司付款按既有结算关系核对 |
| 退款申请 | 原收款及退款申请确定的退款责任公司 | 财务退款执行 |
| 合同首次签约、变更、撤销、解除、企业归档、模板发布 | 各事项的合同主体、业务来源或模板使用范围 | 对应签署、变更、撤销、解除或归档办理 |
| 员工组织调整 | 当前与目标公司、部门及任职关系 | 组织权限管理员执行调整 |

上表是配置设计方向，实施前逐事项登记准确来源；已有业务规则优先核对，未确定的跨公司责任标记待确认。

匹配顺序建议为：业务场景 → 责任公司 → 部门范围 → 已发布且生效的模板 → 模板内条件分支 → 对应审批人员。公司专用流程与明确采用的集团通用流程需显示采用关系，不能暗中择一；同一优先层级的范围冲突应阻止发布。无匹配模板不能解释为免审批。

公司管理员只配置获授权的公司范围；集团管理员可维护通用模板。先复用角色和数据权限，再补“维护模板、发布模板、维护审批人员、管理代办、处理异常”的权限。拥有审批中心查看权不等于可以审批所有单据。

## 六、试跑、发布及版本

试跑选择示例申请人、公司、部门及本事项必要条件，直接展示匹配的模板、实际人员姓名、分支原因和抄送人。找不到负责人、人员离职、越权、自审、范围冲突、条件字段缺失等问题定位到具体节点；试跑不生成真实申请。

发布前同时校验范围、必备内容、每条可达分支及人员规则。维护权不等于发布权，发布人看到变更内容和影响范围后执行发布；不再为配置发布套一层无限审批。

新版本只用于新提交的申请；在途申请保留提交时的业务内容、流程版本和人员记录。停用模板只阻止新申请使用，不让在途申请消失。审批中人员权限失效时停止其办理并交管理员处理，不能因锁定版本继续允许离职人员审批。

退回后在来源业务页修改，重提形成新一轮申请、重新匹配流程，保留上一轮内容和审批记录；金额、公司等关键变化必须重新判断。审批中心不直接修改订单价格、付款金额或合同正文。

## 七、现有审批页面同步调整

待我审批只显示实际轮到当前用户或其有效代办的任务，事项作为筛选，不将所有事项堆为 Tab。申请主状态建议统一为审批中、已退回、已通过、已拒绝、已撤回；“待我处理”是任务视角，“超时”是提示，均不替代整单状态。

同意当前节点后，根据多人办理规则留在当前节点或进入下一节点；最后一个必要审批节点完成才显示整单已通过。待办操作由当前节点办理权与主状态共同决定，不再因整单文案为“审批中”就没有处理入口。

详情依次呈现业务摘要与核对依据、完整业务资料、实际审批流程、意见记录。节点显示应办人员、办理方式、已办结果和时间；合同保留正文、附件和版本比较，付款保留付款依据，不能全部压成通用说明字段。

底部突出同意、退回补充、拒绝；申请人按规则撤回。转交等低频动作放详情更多菜单并检查权限，必须记录原因。抄送我只读；我发起的支持查看进度及来源页补充入口；审批总览支持获授权的失效人员更换及处理记录，不提供管理员无理由直接通过。

来源页提交前展示简短流程摘要，确认后提交；公司或金额等影响流程的字段发生变化时更新预览。审批结果表达其业务后果与下一步入口，如“审批已通过，待财务付款”，不模拟自动付款、自动生成全套财务单据或 NC 推送。

表格只保留判断和办理必需列，操作列定宽并固定右侧，横向滚动限于表格容器；详情承载完整信息，不增加大块说明卡或重复主入口。

## 八、三个代表场景

1. 付款申请：申请责任部门负责人 → 付款公司的财务审核人员 → 按申请金额决定是否增加财务负责人 → 完成后交财务付款。演示可使用“5 万元以上增加一级”，但须标记演示规则，正式阈值待确认。
2. 价格调整：团期或产品负责人 → 根据调价幅度及既有定价规则决定是否追加负责人审批。基础价、调后价、幅度由业务单据提供，不能在审批页重新填写。调价比例不能直接沿用旧配置的 3% 作为正式政策。
3. 合同审批：保留当前六类合同场景及各自核对材料，统一其适用范围、审批人员和发布方式；首次签约审批通过进入签署，撤销、解除、归档等按各自流程承接，不能统一解释为合同已生效。

## 九、实施顺序与验收

| 批次 | 页面范围 | 完成标准 |
| --- | --- | --- |
| 第一批：可配置 | 配置两 Tab、流程编辑页、必要组织权限入口；付款、调价、合同代表模板 | 新建、复制、编辑、试跑、发布、版本、停用及人员代办可操作，错误能定位；使用明确演示数据 |
| 第二批：可办理 | 审批五视图、详情及上述代表事项的直接提交入口 | 可展示逐级审批、多人审批、分支、退回重提、撤回及异常；来源与下游职责清楚 |
| 第三批：覆盖现有事项 | 核对其余审批事项、触发入口、资料和公司人员规则 | 一项一条登记与验收；保留外部审批边界，不将有配置行当作已完成 |

验收至少覆盖：同一事项两家公司不同负责人；不同部门命中不同流程；金额边界及不同币种；全部同意/一人同意/依次审批；无人、离职、自审、兼职及越权；无匹配与范围冲突；条件字段缺失；发布新版本后在途申请不变；停用后在途可处理；退回修改金额后重新匹配；代办生效、到期及已有待办处理；抄送只读；合同六事项差异；通过付款审批但尚未付款；来源记录可核对。

原型验收以页面内正常与异常交互、明确的角色及流向为准，不要求建设真实流程引擎、跨页面自动回写、外部审批集成或生产通知系统。实施时按批次做页面及浏览器验收，不为演示扩大业务链路。
