# 邮轮全流程业务完整性评估报告

评估日期：2026-10-24。范围：当前工作区的资源、产品、邮轮、履约、销售、合同、财务及数据中心原型。依据：用户已提出的邮轮需求、实际导航与页面、共享业务规则及现有实施记录。首次报告只评估；后续经用户授权实施的进展见下方更新。

**主链路结论：邮轮主功能框架基本齐备，但几个关键环节的承接还不完整，尚不能认定已经形成统一、连贯的产品销售结算流程。采购至销售、订单名单与原团期准备两步主要承接已补充验收；下一重点是采购履约结果进入原财务结算及航次经营核对。**

邮轮中心现有16个直接页面：舱位采购3页、航次库存7页、分房管理6页。原产品、订单、合同、售后和财务也已具备邮轮内容。这些成果应保留，但“页面齐全”和“连续业务可完整办理”需要分别验收。

## 当前评估范围：主流程和主功能链路

按用户最新要求，本轮先看一笔邮轮业务从筹备到结算能否顺畅交接，暂不展开细分规则和异常清单。下方既有场景证据保留为支持材料，不作为当前继续逐项扩查的计划。评估阶段使用原实际入口、代码与操作证据；后续实施证据见上方更新。原型承接要求是业务对象、办理结果和下一步入口清楚，不要求后台自动同步或真实记账。

**主流程有两种供给起点：**

- 包船／切舱：资源与产品筹备 → 采购合同／采购订单 → 船方确认及入库 → 航次舱位供给 → 产品／销售团期引用 → 销售下单。
- 散位代理：产品询价与客户需求 → 船方询位报价 → 按单采购确认 → 对应客户订单确认供给。

产品筹备和采购可以并行。两种模式从订单开始共同进入：**订单确认、合同与收款 → 名单分房及出团准备 → 实际履约 → 成本确认与财务结算 → 航次经营核对**。退改、转团作为贯穿订单和履约的分支，结果交回库存、合同、名单及财务。

| 主功能交接 | 当前判断 | 影响主流程的缺口及原页补充位置 |
|---|---|---|
| 资源资料 → 产品筹备、采购选船 | 已有承接基础 | 船只、舱型、线路可被引用；原资源档案的回显保存问题需修正，确保下游引用可靠 |
| 采购合同／采购订单 → 航次供给或指定订单 | 本步正常采购至入库及归属保护已验 | 公共采购形成航次供给；指定订单采购保留专属占用，其他客户无法再次保舱；已签合同变更及采购收尾仍按后续范围核对 |
| 航次库存与价格 → 产品／销售团期 → 销售预订 | 已关联航次的主承接已验 | 原产品／团期引用航次余量及审批生效价，原销售保舱占用同一供给；物理余量与本次可申请额度分别显示。年龄、促销等细分规则保留后续 |
| 销售预订 → 订单、合同与收款 | 共用流程已有，连续承接需核齐 | 保留原订单、合同和收款入口；原团期订单与销售入口已复用同一邮轮预订，下一阶段仍需核订单确认、合同签署与收款进度的分别表达 |
| 已确认订单 → 名单分房 → 团期执行 | 本步主要承接已验 | 邮轮中心集中接收、维护与分房；两处原订单及团期按本单／本团采用结果；原出团准备核名单提交、房号、船票值机与实际登船。历史未关联资料及完整售后不视为已迁移／办结 |
| 退改／转团 → 库存、名单、合同与款项处理 | 原办理入口已有，最终结果承接未完整验收 | 在原售后详情串起各项处理结果；申请提交后应能判断哪些已办结、哪些仍需继续办理 |
| 采购及履约结果 → 财务结算 → 航次经营核对 | 共用财务基础已有，邮轮收尾需补 | 原采购详情承接付款计划执行，原成本结算承接实际船费、未售损失和保底补差；原经营报表按同一航次汇总多团收入与共同成本，避免重复计算 |

**主链路优先顺序：** 先理顺“采购 → 航次供给 → 产品／团期 → 销售订单”，再统一“订单 → 名单分房 → 团期执行”，最后补齐“采购与履约 → 结算 → 航次经营结果”；售后在相应交接处一起核对。继续使用现有产品、订单、合同、履约和财务页面，在对应业务区域补充。前两步已按原页补充并验收，唯一下一步为采购／履约至成本结算及航次经营核对；后续仍先逐页确认改动点。

## 既有细分场景复核（实施前支持材料，暂不继续展开）

**对前版的校正：前版主要是功能覆盖审查、代码规则核查和局部异常复现，所列12个场景是后续验收要求，并没有全部逐条办完。不能据此宣布正常主流程已按岗位完整验收。** 本次改从“业务人员接到一件具体事情，能否作出正确决定并办到正确结果”判断；下方各模块的“基本具备”只说明已有功能承载，不能代替本节的场景结论。

### 1. 每个场景怎样才算满足业务

逐项核六件事：进入原工作入口能否找到这笔业务；是否拿得到作决定所需的价格、余量、条款和资料；能否表达客人或船方的实际选择；数量、金额、责任和状态的结果是否正确；异常后能否继续处理而不覆盖历史；下一岗位能否看懂结果并接着办理。还要看是否被迫重复录入、在多个菜单来回找同一个对象。

“点得动”“有记录”“出现成功提示”只证明交互存在。只有上述任务结果成立，才判断为符合。对于付款到账、船方回复等原型边界，可以明确登记结果并表达下一步，不要求真实接口，但不能把需要登记的业务结果省略。

以下分开标记：**符合（限定本场景／本阶段）**、**部分符合**、**不符合已知需求**、**待验或待业务规则确认**。不把未测试当通过，也不把待确认政策当既定标准。

| 场20 | 船方调整餐厅轮次、救生艇或集合站 | 以船方确认安排为准，保留旧安排和新依据，客人愿望不等于确认结果 | **分配操作已有、完整确认流程待验**；不能把旅行社自行填容量和分组当作船方正式安排 |
| 场21 | 同舱第三人退订，其余两人继续出行 | 只调整这名乘客、价格、税费、服务和名单，通常不释放整间；具体扣费按约定 | **已有正确场景表达，最终办理待验**；原售后记录及规则，不能仅看“退款按钮” |
| 场22 | 客户整舱取消，船方不允许退舱或只退部分税费 | 对客退款、船方成本、该舱能否转售分别判断 | **部分符合**；原退舱及扣损确认存在，不能把客户退款成功等同供应商退款或库存释放 |
| 场23 | 四岛变三岛／换船换航次，客户选择不一致 | 每笔订单独立决定，目标容量不足只影响对应订单，合同和款项依结果办理 | **申请阶段符合，最终办结待验**；B05。行程实质变化不能只改公共文案 |
| 场24 | 出发当天客人未登船或中途离船 | 实际人数、客人状态、服务完成和相关费用有依据，不机械按计划回航结算 | **待补完整结果表达**；原执行与资料区有基础，邮全12 |
| 场25 | 多航次定金池，其中一航次取消，要求转用 | 未使用预付可按确认条件调整用途；已冲抵款不直接当余额转走 | **本次同主体未使用部分的规则符合**；B06。客户实收转款是另一笔业务，不跟着供应商款自动移动 |
| 场26 | 保底未达、未售舱不能退，同时还有退舱罚金 | 区分已承担船费、额外补差和罚金；待船方确认项目单列，避免同一损失重复计成本 | **部分符合／规则待确认**；已有条款和损耗基础，未形成完整保底核对；邮全07、13 |
| 场27 | 京沪共用船费，回航结算后又来一笔账单 | 航次总额与各团承担可核，原结算保留，新差额独立处理 | **独立算例有基础，航次整单场景未通过**；原财务实施记录，不将单项计算通过当完整经营核对 |
| 场28 | 同一位游客第二次出行换证；其他产品继续正常下单 | 识别实际游客而非只认付款会员；历史资料保留；跟团专列仍用原流程 | **客人关系待补、通用业务需随修改回归**；本轮不宣称已重验所有产品及跨航次身份场景 |

### 4. 对产品设计是否合理的判断

- **应保留的设计**：统一产品和订单流程、按间入住与按人收费分开、船方房表内分配、建议后人工确认、批量变更按客户逐单决定、预付用途与实际冲抵分开。这些设计服务具体业务，不需要推翻。
- **应修正的设计**：散位代理和买断切舱在入库后使用同一公共可售处理；服务参与者默认等于全单游客；价格配置与销售计算分叉。这些会改变实际成交、供给承诺或履约名单，优先于增加页面和补装饰性字段。
- **应先明确规则再落实的设计**：完全共享还是带额度共享、儿童计龄和入住限制、收款未认领时如何保舱、保底的累计范围、船方安排的确认责任。对这些应给可选择且结果清楚的原型，不替业务人员默认一种政策。
- **不能用单个按钮代表完成的事项**：订单确认、名单提交、航次完成、退舱、结算。每项都要说明确认了什么事实、尚缺什么、影响哪笔业务、失败后在哪里续办；超级管理员也不意味着可以把未完成事项直接当完成。

**修订后的交付判断：可以用于讨论已有的正常办理步骤，但还不能作为邮轮业务“已满足实际使用”的完整原型验收。** 后续验收应逐条保留上述场景的正常结果、异常结果及恢复路径；本次只补评估，未修复业务页面。

## 一、评估标准与全流程分工

本报告按业务原型评估：业务人员能识别对象，正常与异常场景有处理路径，操作前后状态清楚，下一环节知道承接什么。没有连接船公司接口、没有后台自动运行、独立页面的演示数据没有自动同步，不直接算成功能缺失；但同一业务出现两套计价规则、两个未说明分工的修改入口，属于原型本身的问题。

岗位仅解释职责，原型仍使用超级管理员，不增加岗位切换限制。

| 环节 | 主要使用人／处理对象 | 上游输入 | 本环节应完成什么 | 下游承接 |
|---|---|---|---|---|
| 资源维护 | 资源、产品／船公司、船只、舱型、港口、模板 | 船方资料、供应商合作资料 | 维护稳定、可复用且可核对的档案 | 产品引用、采购选船、航次排期 |
| 采购 | 采购／采购合同、采购订单 | 合作条件、采购计划 | 核数量与成本、付款和退改条款，审批、签订、接收入库 | 航次舱位供给、付款申请及后续对账 |
| 航次与供给 | 邮轮团控／船方航次、各舱型库存 | 入库结果或经确认的特殊排期 | 管可售、保舱、占用、共享、调拨及当期价格 | 统一产品销售及团期执行 |
| 产品组织 | 产品人员／产品、线路方案、销售团期 | 船只、航线、可销售航次 | 组织出发地、岸上方案、包含服务和销售资料 | 销售选择正确的产品与方案 |
| 销售签约 | 销售／客户订单、合同、收款计划 | 产品方案、航次、舱型、当期售价 | 按间安排入住、按人计价，询位、锁位、确认、签约 | 名单、履约和财务收款 |
| 出团准备 | 计调、名单人员／游客、同舱组、船票及执行安排 | 已确认报名、船方回执、客人资料 | 核资料、分房分组、名单提交、船票与值机、出团资料 | 实际登船及带团执行 |
| 变更售后 | 销售、计调／原订单及变更申请 | 客人或船方变更 | 分别处理客人选择、供应商结果、库存、合同和补退款 | 原售后、合同、库存及财务入口 |
| 回航结算 | 计调、采购、财务／履约结果和结算单 | 实际登船、船方账单、损失和费用依据 | 核实际成本、预付冲抵、未售损失、差异和最终余额 | 统一财务核算与经营分析 |

需要始终区分五个对象：**船方航次**是一条船的一次实际出航；**销售团期**是北京、上海等产品的出行安排；**产品方案**是岸上行程和服务组合；**同舱组**是一间房内的入住游客；**采购合同／采购订单**是取得舱位和承担成本的依据。一个航次可以对应多个销售团期与方案，但物理舱房及共同采购成本不能因此重复计算。

“基本具备”只表示该环节正常主流程已有可操作原型；“部分具备”表示有可保留的功能，同时还有影响完整办理的缺口；“待补”表示当前相关页面没有完整表达该项能力。

## 三、优先处理的问题及原页补充方式

优先级说明：P0＝整体业务原型验收前应先解决的规则冲突；P1＝完整经营流程需要补齐的能力；P2＝效率增强或后续接入。优先级不代表本轮已开始修改。

### P0：先让同一业务只有一套规则

**邮全01：新旧办理入口尚未收敛。**

原团期订单“新建订单”仍进入旧预订页，能搜索到“阳台舱岸上全含线路”；旧页使用成人／儿童／第三第四人分列数量，处理方式仍写“预留24小时、人工占位不自动释放”。销售中心的新预订已改为逐间游客和临时保舱，两者规则不同。原团期名单和新房号管理也都保留了“分房／换房”办理入口。这里的问题不是模拟数据没同步，而是业务人员无法判断同一动作应以哪处为准。

**建议**：保留团期订单的新建入口和原抽屉体验，复用同一邮轮预订规则；原团期仍保留本团名单及处理上下文，航次中心承载跨销售团的统一分房工作范围，两个入口调用同一套分房动作和确认结果，或明确其中一处仅查看。旧采购库存保留有效的退舱、供应商确认和历史记录，收敛重复的日常配额修改，不直接删除旧页。

**邮全02：配置价格与销售计价尚未统一。**

销售预订现有规则将第2人价直接等于第1人，第4人价按第3人减2,000元推导；单人附加费和部分税费也使用固定示例值。年龄仅参与显示，选择儿童价时，2岁和15岁均可按同一儿童价计算。新价格日历的独立人次价格及年龄范围因此不能代表销售端已经具备同样能力。

**建议**：原价格日历维护航次＋舱型＋渠道的规则；原销售预订展示实际命中的人次价、儿童年龄档、促销和税费；订单保留成交时的价格明细。增加同一组业务算例进行比对即可，不要求本轮建设后台价格系统。儿童年龄边界、计龄日期及促销叠加顺序由业务确认，不能把示例常量当政策。

**邮全03：库存占用、付款与分房应区分表达。**

现库存看板已经包含临时锁定、订单占用、已售、已分房等状态，但不能仅凭“已分房”推断已付全款，也不能因为临时锁位释放就视为客户订单取消。新库存页能操作锁定／释放和调拨，尚缺同一订单从锁位到成交、分房、售后的完整对应说明。

**建议**：库存主状态说明是否占用及占用来源；详情另列订单确认、订金／尾款、船方确认与房号情况。沿原订单／财务动作解释何时转为订单占用、何时允许释放；明确未付款临时保舱、已收订金、已分房退订三类差别。数量统计不能把已售与已分房重复累计。

**邮全04：名单“资料齐全”与“可用于出行”没有分开。**

本轮实际操作发现：名单已导出并登记提交后，仍可修改护照；原提交文件保留正确，但列表没有提示“资料已变更、需核对是否补报”。把护照有效期改为2020年仍显示资料已齐，因为检查主要判断是否填写。名单版本留档已有，应保留并补后续控制。

**建议**：原名单页区分缺资料、有效性待核、船方已接收、提交后有变更；显示变更客人、字段与对应已提交版本。截止后更名、换人、证件修改分别表达船方结果和是否收费。原型仍允许默认演示和继续操作，业务异常以标记、核对与处理结果表达，不增加阻断式必填流程。

### P2：效率增强及后续接入

拖拽分房、适合手机的分房与名单操作、船公司实时查价下单、正式名单／房表格式及真实回执接入可以分期。前两项是原始需求中尚未完整交付的操作能力，应保留在清单；后几项需要船方资料，不能把当前明确标注的示例模板或接口核对页面称为正式对接完成。

## 四、需要保留的现有能力

1. **采购已不是空白**：合同、采购订单、入库、审批、分批交付与异常处理均已有；无需再增加一套采购创建流程。
2. **共享库存已不是空白**：多产品／出发地／渠道共享、先到先得／优先级／配额、调拨、锁位、预警已存在；需要统一与原团期供给的职责。
3. **分房已不是空白**：房表导入、自动建议、人工调整、偏好、饮食、各类分组、名单导出及提交留档已存在；需要补提交后的控制和原入口融合。
4. **售后已不是空白**：整舱退订、单个乘客退订、批量转团、保留原款原占用已有表达；应完善分支，不另建邮轮售后中心。
5. **财务已不是空白**：预付分摊／冲抵／转用、共同采购成本分摊、舱损风险、结后差异单与通用报表已有；重点补采购依据、保底结算和航次汇总，不另建邮轮收付款及核算流程。
