# 会奖项目业财流程规则与数据关系开发说明

编写日期：2026年10月9日。面向产品、前后端开发、测试及财务接口开发人员。

本文与[按页面顺序操作说明](会奖项目按页面顺序操作说明-20261009.md)配套：操作说明用于对着页面办理，本文用于明确**一个操作为什么发生、满足什么条件、改变哪些记录、影响哪些金额、由哪个模块接着处理**。旧文档保留。

本次交付是开发业务设计说明，不是已完成的接口或数据库设计，也不代表生产链路已经接通。正文先讲业务事实与责任；第十一、十二章才给技术关联、操作契约和一致性要求。

本文使用三种标记：**【现状】**为当前原型代码可核对的行为；**【开发约束】**为正式开发应实现的数据关联和控制设计；**【待确认】**为公司业务或财务政策尚未确认的选择。开发约束不表示当前原型已经实现，不替代政策批准。

## 一、先确定整条链路各自确认什么

### 1.1 五条相互关联的流程

```text
客户委托 → 项目 → 项目分工 → 项目团草稿 → 日程、名单、资源 → 实际服务完成
                         │
                         ├→ 报价及客户确认 → 客户订单 → 合同、收款计划
                         │                       ├→ 到账认领 → 财务认款 → 收款及核销
                         │                       └→ 开票申请 → 财务办理 → 发票结果
                         │
                         └→ 采购费用 → 服务及费用确认 → 应付核对
                                      ├→ 供应商对账及差异处理
                                      └→ 付款申请 → 财务复核 → 审批 → 实际付款

实际服务完成＋客户认可＋本次费用范围 → 业务结算 → 财务核算确认 → 会计事项 → NC
项目全部业务收尾及获准款票遗留安排 → 项目结项
```

图表示来源和交接，不要求所有动作严格从左到右串行。签约、采购、订金和开票可依有效条件穿插；财务核算确认、核销及NC属于正式财务承接，当前会奖原型没有完整实现这些后段。

**【现状】建团与执行确认有不同门槛：**项目团可以先存草稿供报价引用；提交项目团核对／确认执行时，当前校验要求有覆盖本团的已确认报价单、客户委托凭据和完整服务资料。引用框架时还核签署及有效期。不能把“先建草稿”写成“未确认报价即可执行”。是否允许特殊先执行后定价，应另有批准规则。

### 1.2 业务和财务的确认不能合并

| 确认动作 | 确认的事实 | 下游使用 | 不能据此认定 |
|---|---|---|---|
| 客户确认报价 | 客户接受哪版服务与计价方式 | 形成或关联订单、合同及收款计划 | 已到账、已交付、已确认会计收入 |
| 计调确认完成 | 我方实际交付了哪些服务 | 客户对账、业务结算、完成业务查询 | 客户无争议或费用已结清 |
| 客户对账确认 | 客户认可的服务、数量和金额，以及争议 | 应收核对、价款变更、业务结算 | 另生成一次成交或已经收款 |
| 业务确认采购费用 | 支出范围、金额和采购依据已核清 | 财务核应付、付款条件及成本 | 已付款、已取得合法抵扣或已结转成本 |
| 财务认款 | 到账事实及订单归属已核准 | 订单实收及正式收款、核销记录 | 订单增加收入或合同履约完成 |
| 付款成功 | 资金确已付出 | 实付、应付核销或供应商预付 | 采购金额增加或全部服务已交付 |
| 发票开具成功 | 已有可核对的发票结果 | 已开金额、票款核对 | 已认款或已确认会计收入 |
| 业务结算批准 | 本次服务及费用承担范围已确认 | 财务继续核收付、税额与核算 | 整个项目结项或所有会计事项完成 |
| 财务核算确认 | 哪个核算主体、哪个会计期间确认什么金额 | 会计事项、凭证及NC结果 | 改写原成交、原交付或原银行记录 |

“核销”是把已确认收付款或预款余额逐笔抵到对应应收、应付；“核算主体”是负责这笔会计账的公司或账套主体；“会计期间”是财务记账归属的月份或期间。NC是财务核算系统。以上概念均不能用一个“已结算”状态代替。

## 二、业务记录之间的关系和归属

### 2.1 核心关系

| 记录关系 | 数量关系及业务含义 | 关系由谁建立 | 业财使用规则 |
|---|---|---|---|
| 客户—项目 | 一个客户可有多个项目；一个项目对应一项整体委托 | 销售建档 | 不把客户年度全部成交混成一个金额；项目不是收费单 |
| 项目—项目团 | 一个项目有零个或多个团；一个团只属于一个项目 | 负责人／授权计调建团 | 项目汇总执行范围；建项目不自动建首团 |
| 项目—分工 | 一个项目可交办多名员工，每人有期间、城市、服务及办理范围 | 负责人 | 约束建团、报价和客户确认，不产生财务金额 |
| 项目团—主责及移交 | 当前一个主责计调，历史可多次移交 | 负责人 | 当前待办找现主责，历史操作保留原经办 |
| 项目—参与人员 | 可按项目总体或具体团登记实际参与 | 负责人 | 与操作授权分开；不自动计算奖金或分配毛利 |
| 框架合同—报价 | 一个框架可供多次报价引用；报价可以不引用框架 | 销售 | 上限／预估／承诺分别判断；框架金额不直接计成交 |
| 报价—项目团 | 一份报价可覆盖一个或多个团；同团可以有不同服务范围的报价 | 销售／授权计调 | 按实际服务范围防止重复报价和重复收费，不只按团号判断 |
| 有效报价—订单 | 当前同一报价确认形成或关联一个原订单 | 报价确认及适用审批结果 | 同一成交只计一次，重复确认不能再生一单 |
| 订单—项目团 | 一个订单可覆盖多个团；同团可被不同服务成交覆盖 | 报价覆盖关系带入 | 关联用于说明服务范围，不表示已经分配各团收入 |
| 订单／框架—合同文件 | 可有主合同、补充协议和历史版本 | 合同经办 | 文件版本不是新收入；当前有效内容与原成交对应 |
| 项目团—资源—采购 | 一个团有多项资源；资源可转采购，项目采购也可直接建立 | 计调／采购 | 资源落实和费用确认分开；已转费用应回原采购 |
| 原采购—承担范围 | 单团直接承担、多团分配、项目承担分别记录 | 采购经办 | 项目计原采购一次，团计明确承担；未分配不能当零 |
| 到账流水—认领—订单及收款阶段 | 一笔流水可多次分配，一次认领可含多订单；订单可分次收款 | 业务提交、财务确认 | 资金总额、订单分配、阶段分配分别守恒 |
| 采购—付款申请—付款结果 | 一笔采购可多次申请，一份申请可分次付款 | 业务、财务、审批、出纳 | 申请占用与成功付款不能重复扣可用金额 |
| 开票申请—订单 | 一次申请可分配多个相容订单，一个订单可多次开票 | 业务提交、财务办理 | 逐单占用可开金额；整张票不能在每单重复计全额 |
| 客户对账—订单及交付范围 | 一次对账可核多单；整包可按不同交付范围确认进度 | 销售 | 不产生新订单，不自动更改原订单总额 |
| 供应商对账—原采购 | 一次对账有多条原采购，可留差异和版本 | 我方采购、供应商 | 对账认可与原成本不同应留差异，不能覆盖来源 |
| 业务结算—团及费用承担 | 一次可结部分团、全部团或项目承担费用 | 计调／负责人 | 每次记录本次范围；审批中及已确认范围不能重复纳入 |
| 变更调整—原单及原结算 | 一个原单可有多次调整，每次说明原版本和本次增减 | 原业务岗位及审批人 | 保留原结果，新增变化；退款、补付另由财务处理 |

同一对记录有多种关系时必须分别保存。例如“这笔采购服务了哪些团”与“各团分了多少钱”是两种关系；“订单覆盖了哪些团”与“各团有多少已确认收入”也不能共用一份关系。

### 2.2 公司、客户、供应商和人员归属

**【现状】**会奖以项目的我方公司和客户作为报价订单的主要签约关系；采购和财务申请另带公司、供应商、币种。集中认领／开票按同客户、同公司、同币种挑相容订单，可能跨项目；单团原位办理则限定所选订单。

**【开发约束】**签约公司、履约公司、实际收付款公司和核算主体分别保留。常规同公司场景可以相同，不能只留一个“公司”然后推断其他责任。跨公司代收代付要增加明确的内部结算关系，不能把A公司银行流水直接抵B公司应收。

主数据名称修改只改变显示名称。已确认订单、费用、资金及结算应保留发生时的公司、人员、部门和渠道归属。人员移交后，新增办理归接手人；旧批准、原交易及历史业绩不得全部改成接手人。正式员工任职及会奖汇率承接仍在原第4步范围。

## 三、金额、日期和范围的共同规则

### 3.1 金额从哪里来

| 金额 | 可信来源及形成时点 | 谁可以确认或改变 | 使用位置 |
|---|---|---|---|
| 计划成交／预算 | 项目分工、团预算及预计调整 | 负责人／计调按权限 | 事前预计与超支观察；不形成应收或实际成本 |
| 客户确认金额 | 有效报价及订单，后续加已批准价款调整 | 销售取得客户依据并完成适用审批 | 订单成交、业务应收参考、收款及开票额度 |
| 最终数量结算金额 | 客户认可数量×有效单价，另核优惠、追加及取整 | 销售确认、审批及财务核对 | 最终订单和收款阶段；当前专门路径尚未完整 |
| 实收 | 财务已确认归属的真实到账分配 | 收款财务 | 订单及收款阶段已认款；正式系统仍需收款／核销明细 |
| 原采购金额 | 一笔已确认采购及关联增减费用 | 采购业务确认、批准调整 | 项目成本来源与付款资格依据 |
| 本团承担 | 直接费用，或原采购下明确分配给本团的金额 | 采购经办；已结部分通过调整处理 | 本团费用、业务结算和经营结果 |
| 实付 | 成功付款结果逐笔合计 | 出纳登记或已核准支付结果 | 原采购已付、申请已付、应付核销或预付 |
| 已开票 | 成功发票按订单分配，红冲另留反向记录 | 开票财务 | 票款核对、剩余可开金额；当前会奖未完整承接红冲 |
| 财务确认收入、成本 | 财务确认记录及会计期间 | 核算财务 | 正式损益和NC；不由业务结算按钮直接生成 |

客户应收是客户欠我方的钱，应付是我方欠供应商的钱。订单确认金额与正式财务应收可能因成立时点、争议、调整或款项分类而不同；原型中显示“订单金额－已认款”不能替代正式应收账。

### 3.2 四组守恒关系

以下均按同一公司责任、币种、有效范围计算；没有金额依据时保留待确认。

```text
已明确订单总额 = 各收款阶段金额合计（包括有效价款调整）
本次认领金额 = 本次逐订单分配合计 = 本次逐订单收款阶段分配合计
原采购总额 = 各团承担合计 + 项目承担 + 未分配
开票申请总额 = 各订单本次开票分配合计
```

**【开发约束】**“未确认”“明确为零”“不适用”分别保存；没有费用明细不等于零成本。零价订单应有免收依据，无费用结算应有无费用说明。正式财务待收、待付余额不能以负数混入普通欠款；出现超收、超付，单列未核销款或应退款。

### 3.3 占用与实际结果

**【现状】**会奖原型的主要可用金额计算如下，正式开发仍需以逐笔事实及确认记录复算：

| 计算 | 当前规则 | 开发时特别处理 |
|---|---|---|
| 流水可继续认领 | 到账金额－有效认领分配；待财务认款也占用，退回／撤回释放 | 财务确认时把占用转为已确认归属，不再次扣一遍 |
| 订单可认领 | 已明确订单金额－财务已认款－其他待财务认款分配 | 订单改价或阶段调整后，财务确认前重新核额度 |
| 阶段可认领 | 阶段金额－阶段已认款－其他待认分配 | 阶段名称不能充当唯一关联；重名或改名不能错抵 |
| 采购可申请付款 | 采购有效付款上限与已满足条件上限取较小值，再减已付、有效申请未付部分及已冲抵 | 采购减费和付款条件变化需重核；不是所有采购金额都立即可付 |
| 可申请开票 | 订单金额－已开金额－有效未完成申请占用 | 开票中／结果待查继续占用，明确失败／退回按流程释放 |
| 人员／框架剩余额度 | 适用上限－相关已确认成交－审批中报价占用 | 草稿和已报价不算成交占用；未知金额不能当零越过硬限制 |

付款失败后原申请仍可重试，当前会奖原型保留该申请未付占用；“申请被退回”与“银行付款失败”不能使用同一个释放规则。结果未知的支付也不应释放占用后另发一笔付款。

### 3.4 日期各管一件事

| 日期 | 来源 | 主要用途 |
|---|---|---|
| 项目服务期间 | 客户整体委托 | 约束具体团及分工的安排范围 |
| 项目团计划日期 | 计调排期 | 资源、名单、计划完成提醒；当前四个会奖报表月份筛选按计划开始月 |
| 项目团实际完成日期 | 计调确认完成 | 履约完成事实、回团／完成业务分析 |
| 客户确认日期 | 报价或客户对账依据 | 区分成交确认与交付后认可 |
| 到账／付款日期 | 银行或已核实资金事实 | 实际资金发生；不是申请日期 |
| 结算确认日期 | 本次业务结算批准 | 表示本次范围何时确认，不替代实际完成日期 |
| 原服务日期、调整日期 | 原业务及本次调整 | 解释后补费用与跨期变化 |
| 会计期间 | 财务核定 | 正式收入成本、凭证及关账控制 |

不得用结算截止日替代会计期间。“维护结算期限”目前只计算提醒日期，建议从项目日常维护中移除；删除时一并处理既有截止日期和提醒来源。是否保留统一时限、采用几天，仍待确认。

## 四、操作规则与数据变化：从建档到成交

以下“写入”指业务记录的变化，不指定数据库物理表。操作详情见配套页面说明；开发和测试按规则编号核对前后结果。

| 编号／操作 | 岗位、前置条件与校验 | 写入或改变的记录 | 下游读取及不应产生的结果 |
|---|---|---|---|
| 规01 建立项目、提交核对、确认启用 | 销售／负责人核客户、公司、部门、人员、服务范围与日期；已有成交后不得直接换签约客户或公司 | 项目草稿→待确认→进行中，保留来源需求 | 项目分工、建团及报价读取；不自动建团、订单或应收 |
| 规02 新增／维护／结束项目分工 | 负责人核员工已有任职、负责期间、城市、服务、建团及报价范围；硬限额必须有有效依据 | 分工及变更历史；当前同人同项目只保留一条有效分工 | 建团、报价提交及审批生效时核有效范围；结束分工不自动移交旧团 |
| 规03 新增／批量建团 | 两个入口使用同一规则；核项目范围、员工权限、团名、日期和客户委托编号；已结束项目禁止新增 | 各团独立草稿；批量生成只是准备，整批校验通过才保存 | 报价引用草稿团，计调补安排；不增加客户成交或费用 |
| 规04 分配／移交计调、补成员 | 分配针对已建未完团；移交保留原人、生效日、原因；成员登记只补实际参与 | 团主责及移交历史，或独立参与记录 | 当前经办及人员导出读取；不改旧财务经办、不授予付款权 |
| 规05 登记框架、办理合同 | 销售核双方、范围、期间、金额性质和有效签署依据 | 框架及合同文件版本、签署／归档记录 | 报价核适用范围、上限和期间；框架金额不累计为订单收入 |
| 规06 保存报价／登记已报价 | 有报价权限的经办核所选团及服务、计价和版本；固定总价、确定数量单价、按实际数量分别处理 | 报价草稿或已报价，准备收款阶段及税费测算 | 提供客户沟通和后续确认依据；不形成已确认成交 |
| 规07 登记客户确认／提交报价审批 | 核客户凭据、覆盖团、计价、阶段合计、人员权限、框架期间及金额占用；适用审批未定只能留草稿 | 不需内部审批或有本版外部批准时确认；需要审批时为待审批并留审批来源版本 | 批准后才进入规08；待审批报价占用适用额度，不计实际收入 |
| 规08 报价确认承接订单 | 复核当前版本与办理范围；已有同一成交时校验原订单的公司、客户、币种、金额及覆盖范围 | 新建时带入计价、覆盖团、收款阶段、报价来源及预计税费；关联已有单时保留原结果，不覆盖其收付 | 合同、收款、开票、执行及报表读原订单；重复执行返回原单 |
| 规09 项目团提交核对／确认执行 | 【现状】完整执行资料及委托凭据、覆盖本团的已确认报价；引用框架须有效 | 草稿→待确认→准备中 | 计调进入执行安排；不再次生成订单，不代表已收款 |

**报价和订单的边界：**确认前修订报价，确认后价款变化从原订单办理。报价历史说明当时谈了哪版，订单说明当前有效成交。已确认订单不应随报价页面重新保存而被无记录覆盖。

**批量办理边界：**当前批量建团要求整批核对通过；批量维护及逐团报价可仅处理有效行。正式结果须逐行返回成功记录、失败原因和未处理项；重试失败行不能重复处理已成功行。原型示例缩到少量数据不意味着业务数量上限。

## 五、操作规则与数据变化：执行、采购及供应商链路

| 编号／操作 | 岗位、前置条件与校验 | 写入或改变的记录 | 下游读取及控制 |
|---|---|---|---|
| 规10 日程、名单、资源维护 | 计调按会议／旅游／混合服务及实名需要办理；已完成／取消团的原执行资料受保护 | 本团日程、人员、资源及确认依据 | 现场执行、采购、完成确认读取；人数更新不直接更改成交 |
| 规11 资源转费用／直接新增采购 | 经办核供应商、公司、币种、服务日期、采购总额和归属；原资源已转费用时继续原采购 | 新原采购及来源资源关系，或原采购补正 | 同一采购进入团费用和集中台账；不能因多入口生成重复成本 |
| 规12 确认费用及采购交付 | 经办核实际采购依据、服务范围、交付及付款条件；费用确认和服务交付分别记录 | 费用确认状态、金额、依据、交付结果；预算及最新预计另存 | 财务核应付；供应商对账按交付条件取数；不得把预付款当最终成本 |
| 规13 分配跨团／公共费用 | 核明确受益范围、各团承担、项目承担、未分配及依据；已结范围禁止覆盖 | 同一原采购下的承担明细和版本 | 本团结算取承担，项目取原采购；管理分摊不能再次增加项目成本 |
| 规14 申请付款 | 经办核已满足付款条件、可申请额、未付占用、用途及依据；供应商收款账户交财务核 | 付款申请为待财务复核，申请额占用 | 财务复核→审批→出纳；不增加原采购已付 |
| 规15 财务复核与付款审批 | 财务核原采购、公司、可付范围、经审核账户；审批人核本次版本且不得自审 | 退回则释放适用占用；送审后审批中；批准为已批待付 | 出纳使用本版批准申请及核准账户；不能复活已撤回旧申请 |
| 规16 登记付款结果 | 出纳核批准范围、实际金额、账户、银行交易号及结果；支持分次 | 成功记录及原申请／采购已付增加；部分付款保留余款；失败／待查不增已付 | 正式系统形成付款、回单及核销或预付；原申请和原成功付款保留 |
| 规17 撤回未付申请 | 经办说明原因；【开发约束】已发支付指令或结果待查先查清，不能直接释放 | 只终止可撤回的未付部分及其占用 | 成功已付不撤销；在途审批同时失效。当前原型此项控制不足，见缺口表 |
| 规18 发起／确认供应商对账 | 我方按公司、供应商、币种、服务期间和采购依据选原采购；直接团需完成，共同采购需交付确认 | 对账明细、版本、双方确认／差异、当前盖章资料 | 应付核验读取当前双方认可版本；旧确认不证明新金额已认可 |

供应商认可金额与原采购不一致时，保留双方数和差异处理。业务认可应增减费用的，先落原采购的调整；财务依据有效来源核应付变化。对账不能悄悄覆盖原采购，也不能把对账总额再新增为一笔成本。

**【现状】**供应商对账不是会奖每笔付款申请、每笔业务结算的统一强制前置。付款主要核当前采购付款条件；对账候选另核交付条件。正式制度若要求某类尾款必须对账，应按费用类型、付款阶段及批准规则设置，不能直接把所有订金一律阻断。

## 六、操作规则与数据变化：收款、开票及税额

| 编号／操作 | 岗位、前置条件与校验 | 写入或改变的记录 | 下游读取及控制 |
|---|---|---|---|
| 规19 提交收款认领 | 业务选已登记到账，核同公司、客户、币种，订单和阶段剩余额；最终金额未定订单当前不能申请 | 原流水下的认领、订单分配及阶段分配；状态待财务认款 | 占用可认金额；不增订单已认款，不重复新增银行到账 |
| 规20 确认／退回认款 | 收款财务核银行事实、归属及当前有效金额；【开发约束】重核所有订单和阶段版本 | 确认后逐单、逐阶段增加已认款；退回释放占用并留原因 | 正式收款及核销记录承接；已认款改错必须反向更正，不能直接改关联订单 |
| 规21 提交／修正开票申请 | 业务核购买方、销售方、币种、开票项目、备注原文、收票方式及逐单可开金额 | 开票申请及订单分配，状态待财务办理 | 占用额度，交财务；合并多单的修正核全单，不只改某一团 |
| 规22 审核开票、查询、重试 | 财务核最新订单及可开额；结果未知只查原请求，明确失败才允许重试 | 待财务办理→开票中→已开具／开具失败／结果待查；留每次请求及结果 | 成功才增加订单已开金额；查询不再次开票，重复成功通知不重复计票 |
| 规23 预计税费与财务核定 | 业务维护预计依据，财务核定收入税额及成本可扣税额；共同费用按明确承担核分团税额 | 预计与核定结果分开，带公司、币种、来源金额及版本 | 业务毛利读取适用一套口径；不能用识别票面税额直接代替可扣税额 |

**【现状】**认领和开票共用相容订单选择，但合并申请的主记录仍使用起始订单的项目作为页面上下文。**【开发约束】**实际归属必须沿每条订单分配找到各自项目，不能只按申请头的项目编号汇总，否则跨项目收款、开票会漏算或全算到第一个项目。

订单改价后，当前原型会清除需重核的财务销项税额及手工预计税额；历史结果保留。正式开发还要重新检查待认款、未完成开票申请和原票是否需要红冲。价款减少不意味着银行退款已发生，发票红冲也不等于退款。

## 七、操作规则与数据变化：客户认可、业务结算及结项

| 编号／操作 | 岗位、前置条件与校验 | 写入或改变的记录 | 下游读取及控制 |
|---|---|---|---|
| 规24 开始执行／确认完成 | 主责计调核真实开始／结束、实际人数、完成依据和交付材料；真实未交付须先处理 | 团执行状态及实际完成事实；有期限依据时计算结算截止日 | 销售客户对账、业务结算、完成业务查询读取；不增加认款或成本 |
| 规25 客户价款及服务对账 | 销售按原订单核全部覆盖团已完成／取消，确认认可、争议及原因；按实际计价补数量单价 | 客户对账行、原订单引用、认可／争议及相关团认可状态 | 交业务结算及订单价款调整；不直接更改原订单总额 |
| 规26 整包交付进度确认 | 整包未全部完成时，销售选择本期间已完成且未重复认可的交付范围 | 原订单下的已认可交付范围，金额不作整包分团收入 | 已认可的本团可按当前规则办理业务结算；最终项目收尾另核完整认可 |
| 规27 保存／提交业务结算 | 计调／负责人选本人可办范围；团完成或适用取消、客户认可、费用确认及承担明确；无费用须有依据 | 结算范围、来源费用及版本、服务结果、本次承担、遗留；提交形成审批中记录 | 审批读取本次提交时的依据；同一团或项目承担范围不得在有效结算重复出现 |
| 规28 批准／退回业务结算 | 审批人核来源版本；当前还比较提交时与此刻的服务及费用依据 | 批准保存本次结算确认记录；退回留原因，再补原资料重提 | 财务读取已确认范围；历史确认金额不能随原采购最新值漂移 |
| 规29 项目结项检查／申请／批准 | 负责人核服务、客户完整认可、费用、结算、争议和未完变更；款票例外须有有效依据和责任安排 | 进行中→待结项→已结项，或退回进行中；保存遗留事项及责任人 | 停止新增普通业务；获准遗留仍须有财务办理路径，不能只留下文字 |

**结算范围要记录到“哪笔原采购的哪部分承担”。**只存采购编号和全额，会让跨团采购在多次结算中重复出现全额。已确认结算应保存本次团、项目承担标记、原采购版本、原总额、本次承担、分配依据和服务认可记录。

**【现状】**业务结算允许“进度已认可”的整包子团先结；项目结项检查要求已完成团达到完整“已认可”。因此中间交付确认与最终认可必须分开，不能中途将年度项目直接结项。

业务结算不是财务收入确认。原型目前主要固定服务结果及费用承担，尚未形成完整的订单、应收应付、收付、票据和会计确认整套结算资料。正式开发需按第八章承接，不应把当前结算记录结构当完整会计底稿。

## 八、从会奖业务数据交给财务的接口边界

这一章描述业务交接，不预设具体接口路径。财务模块复用统一单据及规则，会奖提供来源与范围，不再另造一套财务账。

| 交接事项 | 会奖提供什么 | 财务核什么、形成什么 | 必须回传的关联结果 |
|---|---|---|---|
| 客户应收 | 订单、有效报价／合同版本、客户及签约公司、币种、收款阶段、覆盖服务及有效改价 | 按制度确定应收成立时点，形成应收／调整及到期安排 | 应收及调整编号、金额、状态、未核销余额、来源版本 |
| 客户收款 | 原到账、付款方、订单及阶段分配、归属依据 | 确认真实收款、客户和主体；形成收款及逐笔核销 | 认款／收款／核销编号、分配金额、成功时间及冲销关系 |
| 供应商应付 | 原采购、实际服务／合同条件、供应商、承担明细、对账及差异、原付款 | 区分采购确认、实际成本、应付成立及预付；形成应付或调整 | 成本确认、应付、调整、预付冲抵的编号与金额 |
| 付款 | 原申请、当前可付依据、批准版本及经核准账户 | 支付执行、银行结果、回单，确认应付核销或预付去向 | 付款编号、交易号、逐笔金额、银行状态、回单及核销／预付编号 |
| 销项发票 | 原订单、逐单金额、客户抬头税号、开票项目、完整备注及收票方式 | 审核、开具、查询、更正及红冲 | 申请、请求、发票编号、成功金额、分配、文件及原票关系 |
| 进项票据 | 原采购、供应商票据、票面及服务信息、分配依据 | 发票核验、认证或其他适用处理、可扣税额确认 | 票据及核定编号、核定税额、分团金额、核定版本及依据 |
| 收入成本确认 | 实际履约、客户认可、原订单及调整、实际成本、结算确认及遗留 | 按已批准政策确认收入、成本、核算主体和会计期间 | 确认记录、确认范围、金额、期间及后续会计事项 |
| 核算系统推送 | 已确认会计事项及完整来源关系 | 财务组织凭证、校验和推送NC，处理退回／冲销 | 推送批次、凭证编号、状态、失败原因及更正对应 |

“预收”是已收但暂未形成或明确对应应收的款；“预付”是已付但尚未形成可核销应付的款。客户预存则是客户同意留存、以后可重复使用的余额账户，不能把所有超收自动转为预存。

**【开发约束】**预收、预付、退款、转款、核销及冲销保留独立明细。先付款后交付可以形成供应商预付，不能先造最终成本来凑付款条件；按实际数量金额未定但客户已打订金时，应由财务预收等适用流程承接，不能用零元订单或临时虚构总价绕过限制。会奖这两类完整承接尚未验收。

**【待确认】**应收应付成立时点、提前收付分类、暂估、收入按总额还是净额、税务及跨期处理由财务明确。“暂估”指依据已发生业务先估计确认、后续据正式依据调整。本文不指定会计分录、税率或入账日期。

## 九、变化、异常和历史数据如何处理

### 9.1 三种业务调整

| 变化 | 当前数据处理 | 正式开发需要继续衔接 |
|---|---|---|
| 项目团改期 | 保留原日期、日程、资源；改新日期，日程标待重核，原资源确认号不沿用 | 重核报价／合同期间、供应商安排及需补退费用；不自动改客户价款 |
| 取消项目团 | 团变已取消，资源变取消待核对，登记损失及客户／供应商退补安排 | 损失确认进费用；客户折让改原订单；已付款追退、客户退款另走资金结果 |
| 订单增减价 | 批准后原单金额变动，保留价格历史，增加价款调整阶段，税额重新核 | 应收调整、收款阶段重排、未完认领／开票重验、超收和红冲分别处理 |
| 费用追加／减费 | 批准后新增关联原采购的正／负费用，原采购保留；减费同步影响原单可付范围 | 明确新费用各团及项目承担、应付调整、已付待追回和税额调整 |

调整申请需记录“原单当时什么版本”和“本申请第几版”。审批时来源已改变，应退回重核，不能直接在已变金额上重复加减。原型已对调整生效设置重复保护，但不能把浏览器内的保护当成正式并发控制。

**【现状限制】**费用调整目前按同项目找已确认结算，未确保一定找到包含该笔采购承担的结算；跨团追加费用也需要重新明确承担。开发必须按实际来源明细反查原结算，不能取项目中第一张结算单。

### 9.2 不应靠改原金额解决的异常

| 异常 | 正确的数据处理方向 | 当前边界 |
|---|---|---|
| 认错订单或重复认款 | 未生效退回修正；已生效冲销原分配再建立新归属，保留原流水 | 会奖有退回修正，完整冲销／转款未接通 |
| 银行结果未知 | 保留原支付及占用，查询原交易；查清前不再发同一款项 | 当前可登记待查，撤回与再次付款的完整控制待补 |
| 付款成功后银行退回 | 原付款历史保留，新增实际退回到账和待处理余额 | 不可直接改原付款为失败；会奖来源接续待验 |
| 客户只认可部分金额 | 留认可、争议及原因，按原订单办有效让价或补服务后重新认可 | 整笔等额争议减价已有处理，部分处置及再次认可待验 |
| 按实际数量最终定价 | 留最终数量、单价、计价依据及批准；确认原订单最终金额并形成可核平阶段 | 当前对账不回写总额，通用改价不能当作已完善的最终定价功能 |
| 减费后已经超付 | 降低有效应付或形成供应商应退款，待实际回款再减资金占用 | 负费用不能假装已有供应商退款到账 |
| 结算后追加成本 | 关联原采购、承担范围和原结算形成调整／补充确认 | 保留原结算确认金额，禁止报表用新值覆盖旧确认 |
| 已关账或已推NC | 在允许期间形成调整或冲销，并关联原确认及原凭证 | 财务政策、期间权限及真实NC接口待落地 |
| 结项仍有获准款票 | 只允许办理批准范围内的遗留，有责任人、额度及原单关系 | 当前新认领／开票被项目结束规则阻止，尚不能视为完整收尾 |
| 复制项目／项目团 | 复制允许复用的资料，新业务重新取得成交、交付和资金结果 | 当前有整条记录复制再清理的写法；正式开发应使用明确复用清单，防止带入旧完成／结算结果 |

### 9.3 税额与汇率变化

收入预计税额、财务核定销项税额、成本预计可扣税额、财务核定可扣税额分别保存。销项税额是对客收入相关税额；可扣税额是财务确认可按适用规则扣除的采购税额，不等于票面全部税额。

在适用的一般价税测算下，含税金额除以“1＋税率”得到预计不含税金额；特殊或混合计税按明确依据人工核定，不能统一套一个税率。公司配置中的示例税率仅供原型选择，不作为适用政策。

预计业务差额＝客户确认金额减预计收入税额，再减“明确成本减预计可扣税额”；核定业务差额改用财务核定税额。任一必要金额未明确时保留待核；整包未分团收入时不出虚构的本团毛利。该差额仍不是公司净利润，也不代替会计收入与成本确认。

外币业务保留原币金额、币种、汇率方向、来源日期、用途、批准依据和折算结果。预算汇率、合同固定汇率、付款实际汇率、财务核算汇率分别记录；不能用最新参考汇率覆盖旧订单或已结算结果。收入端固定汇率、全局来源和取值时点仍属原第4步待完善内容。

## 十、报表怎样沿同一批数据复算

### 10.1 分清统计粒度

| 查询结果 | 每行主要代表什么 | 汇总来源和排重规则 |
|---|---|---|
| 项目结果 | 一个项目在所选范围及币种下的经营情况 | 订单按原单计一次，成本按原采购及调整计一次 |
| 项目团结果 | 一团的执行、明确成交及承担费用 | 整包覆盖不等于分团定价；费用取直接费用及明确承担 |
| 订单明细 | 一份有效客户成交 | 月度对账、合同份数、开票次数不增加订单成交额 |
| 回团／完成业务 | 一次实际服务完成 | 实际完成日与计划日分别提供，不把未完成日期当实绩 |
| 资金报表 | 一次真实收付及分配 | 银行原金额和逐订单分配不能混在同一层相加 |
| 业务结算记录 | 本次确认范围及来源版本 | 用本次确认记录核历史；后续调整单独列示 |
| 正式财务损益 | 指定核算主体和会计期间的确认结果 | 取财务确认及调整，不直接取订单总额或实收 |

**【现状】**会奖四个相关报表按项目、计划开始月份、计调和币种查询，属于业务原型只读视图；当前不提供单元格点击下钻。不能把其月份筛选叫会计期间。按部分团查询时，未明确分团的整包收入应提示范围不足，不平均拆分。

### 10.2 必须可反查的来源

```text
一笔客户已认款
→ 订单分配及收款阶段 → 财务认款记录 → 原认领 → 原到账流水

一笔本团承担费用
→ 分配明细及版本 → 原采购／关联调整 → 服务与供应商依据
→ 原付款申请 → 成功付款 → 核销或预付去向

一张业务结算
→ 本次范围及确认版本 → 客户认可、服务完成、逐笔承担费用
→ 原订单及采购 → 对应收付、票据、财务确认与调整
```

“可反查”是数据关系及服务查询要求，不等于必须给只读报表新增点击下钻。报表导出应带必要原单编号、范围、币种、日期口径、金额确认状态及调整依据，使财务能核同一数字。

## 十一、技术附录：逻辑数据结构与当前代码对应

以下技术名称用于开发定位。它们是当前原型集合或**建议的逻辑记录**，不是已存在的生产数据库表；物理表、索引及接口由开发在业务关系评审后确定。

### 11.1 当前原型记录

| 业务含义 | 当前代码记录及关键关联 | 正式开发要保留的关系 |
|---|---|---|
| 项目 | `projects`；`id`、`company`、`customer`，内含`frameworks`、`delegations`、`members` | 公司、客户用稳定标识；名称及发生时归属留存；项目与各子记录独立关联 |
| 项目团 | `activities`；`projectId`，`planner`，`commitmentId`，内含`agenda`、`roster`、`resources`、`completion`、`acceptance` | `projectId`指向唯一项目；人员、日程、资源、完成及客户认可分别有可追溯来源 |
| 报价及覆盖团 | `commitments`；`projectId`、`activities[]`、`frameworkId`、`workAssignmentId`、`orderId`、`version` | 报价版本、服务覆盖明细、分工与框架引用；团的单个`commitmentId`不能替代全量覆盖关系 |
| 客户订单及收款阶段 | `orders`；`commitmentId`、`activities[]`、`nodes[]`、`received`、`invoiced` | 订单引用成交版本；阶段要有稳定ID；已认款／已开票由有效分配明细汇总 |
| 采购及分配 | `costs`；`projectId`、`activityId`、`activityIds[]`、`allocations[]`、`commonAmount`、`scopeType` | `direct/shared/common`分别为直接、跨团、公共；保留覆盖范围、承担金额及分配版本 |
| 费用调整 | 新费用的`originalCostId`、`adjustmentId`，原费用的`adjustmentTotal`、`paymentReduction` | 调整链只计一次；原费用累计辅助值不能再与关联增减费用相加计成本 |
| 供应商对账 | `reconciliations`；明细`lines`引用原采购，带公司、供应商、币种、版本和确认资料 | 按来源费用逐行匹配，保留双方金额及差异，不以项目编号代替采购明细 |
| 到账及认领 | `moneyFlows`、`claims`；`flowId`、`allocations[].orderId`、`nodeParts` | 流水→认领→订单→阶段多层明细；生产补收款、核销与冲销记录 |
| 付款申请及结果 | `requests`；`costId`、`projectId`、`version`、`verifiedAccount`、`payments[]` | 每次付款结果有独立记录，原申请、核准账户版本、银行交易及核销去向可追溯 |
| 开票申请及结果 | `invoices`；`allocations[].orderId`、`submissionRef`、`invoiceNo`、`resultFiles` | 申请、发送尝试、最终发票和红冲分开；不能把申请编号当发票编号 |
| 客户对账 | `customerSettlements`；`lines[].orderId`、`activityIds`、`accepted`、`dispute`、`mode` | 每行保存本次订单及交付范围、认可和争议；最终定价应另有明确生效记录 |
| 业务结算 | `settlements`；`activities[]`、`includeProjectCosts`、`submittedRecord`、`confirmedRecord` | 保存提交及确认时依据；`confirmedRecord.costs`必须含原采购、本次承担、版本、分配依据 |
| 变更调整 | `adjustments`；`type`、`targetId`、`targetVersion`、`settlementId`、`version`、`applied` | 原单版本和申请版本分别校验；原结算须按实际包含来源匹配 |
| 审批 | `approvals`；`sourceId`、`type`、`projectId`、`version`、申请人和决定 | 来源类型＋来源ID＋来源版本明确唯一；批准不直接等于资金结果 |
| 合同 | `contractRecords`及合同工作流；框架／订单上下文由合同桥接脚本提供 | 区分框架和订单来源、签约方、有效文件版本；生产不依赖浏览器临时草稿 |

**【现状】**浏览器会话保存只是演示机制，集合名`activities`在业务上已经统一叫“项目团”。不能因为内部名称未改，把页面或正式业务说明重新叫“活动”。

### 11.2 建议的关联记录与约束

| 逻辑记录 | 核心关联与必要内容 | 一致性约束 |
|---|---|---|
| 报价覆盖／订单服务明细 | 报价或订单ID、版本、团ID、具体服务范围；只有有依据时填分团价 | 不以团数平均分总价；同一有效服务重复收费须被识别 |
| 采购承担明细 | 原采购ID、分配版本、承担类型、团ID或项目ID、币种、金额、依据 | 直接费用唯一归团；各项合计不超原金额；已结部分不覆盖 |
| 收款阶段及认领分配 | 订单ID、阶段ID、原认领ID、原流水ID、金额、状态 | 名称不是键；逐层金额守恒，已生效重分配留反向记录 |
| 开票分配 | 申请ID、订单ID、金额，结果另关联发票ID及原票ID | 每单申请占用和成功金额分别统计；跨项目按行归属 |
| 结算范围／依据明细 | 结算ID、版本、团ID或项目承担范围、来源类型／ID／版本、本次金额 | 正常结算范围不重叠；后补调整引用原结算，不伪装第二次普通结算 |
| 财务来源关系 | 财务单据类型／ID、来源类型／ID／版本、来源行ID、责任主体、币种、金额 | 一笔财务单据可以对应多来源；一来源可分次确认，累计不能重复 |
| 反向更正关系 | 原生效记录ID、本次冲销／退款／红冲ID、金额、期间、原因和批准 | 原记录不删除，原影响与反向影响可复算；资金、金额及票据分别更正 |

所有金额使用明确币种和十进制精度。原币、折算币、汇率方向及精度分别定义；原型的JavaScript浮点数和两位取整只供演示。分配尾差须有统一处理规则及落到哪条明细的记录，不能每次汇总出现不同结果。

## 十二、技术附录：提交、审批、回传的一致性

### 12.1 操作契约

下表是一项操作应一次完成的业务结果。若数据库提交中途失败，不能只完成其中一半；外部银行或开票服务的发送与返回另留可恢复状态。

| 操作 | 请求需要识别的对象 | 服务端重验 | 同次完成的写入 | 返回结果 |
|---|---|---|---|---|
| 报价生效 | 报价ID及版本、确认／审批依据、防重复标识 | 有效权限、覆盖、计价、框架及在途占用 | 报价状态、原订单关联、覆盖与阶段、审计记录 | 原报价及订单ID、有效版本；重复请求返回同一结果 |
| 财务认款 | 原认领ID及版本、确认意见 | 流水余额、每单及阶段当前金额、公司币种、未被处理 | 认款决定、收款及分配、适用核销、占用转正式结果 | 收款／核销关联、逐单金额和当前余额 |
| 付款申请提交 | 原采购ID及版本、本次金额、条件依据 | 当前有效费用、付款条件、已付及所有在途占用 | 原申请、占用、经办及来源版本 | 申请ID、待复核状态及剩余可用金额 |
| 批准付款 | 原申请ID及版本、审批来源及意见 | 申请仍有效、账户与来源未变、可付资格和适用权限 | 审批决定及批准范围；不写实际付款 | 已批待付状态、批准版本及可执行范围 |
| 确认支付成功 | 支付指令／结果ID、银行交易号、金额和结果版本 | 来源仍对应、结果未重复、币种账户及金额一致 | 成功付款、原申请已付、采购关联、核销／预付、占用释放 | 同一付款ID及逐笔资金结果 |
| 确认开票成功 | 原请求ID、发票号、逐单金额及文件 | 对应发送请求、结果未处理；异常差异进入核对 | 发票及逐单分配、申请成功状态、占用转已开 | 发票与订单关系、文件及办理状态 |
| 提交／批准业务结算 | 结算ID、版本、本次范围及来源明细版本 | 范围未被其他有效结算占用、服务及费用依据未变 | 提交依据和审批，或确认依据与状态 | 本次结算ID、版本、来源及承担金额 |
| 调整生效 | 调整ID、申请版本、原单版本及依据 | 未重复、原单未变化、金额合法、适用期间与权限 | 原变化历史、关联调整／财务待办、版本递增 | 原单当前版本、调整及应承接事项 |

这里的**防重复标识**在接口中可称`idempotencyKey`，作用是同一业务请求因重试到达多次时仍只办理一次。它应和来源、动作、版本及结果记录共同使用；只让前端按钮变灰不能防并发和重复回调。

### 12.2 必须在服务端执行的控制

1. **身份与范围。**读取、提交、导出、审批、结果回传均校验当前租户、公司、角色、任职及业务范围。页面参数、隐藏按钮和浏览器演示身份不能作为授权依据。
2. **版本。**订单、报价、采购分配、收款阶段、结算和调整各有版本；用提交者看到的版本检查并发修改。审批版本只说明批准哪份申请，还要核来源记录仍有效。
3. **额度。**同一流水、订单、框架或原采购的并发申请必须按实际占用执行原子校验；不能两个请求都读取旧余额后分别通过。
4. **在途终止。**来源撤回、作废或重提时，旧审批和未执行指令一并终止或明确失效；在途银行结果先查清，不能释放占用后仍允许旧审批通过。
5. **成功回传。**银行或开票的真实成功不能因为业务记录后来变化而丢弃。保存原结果事实，金额或状态冲突进入核对，再决定退款、冲销或红冲；绝不重新发送同一经济事项来“补数据”。
6. **派生合计。**已收、已付、已开、分配及占用从有效明细复算。可以保留快速查询合计，但必须能与明细对平，不能把多个页面各自累加的数字当最终账。
7. **操作追溯。**保存实际操作者、办理时间、原版本、原因、附件及批准来源；批量操作保留逐行结果。不能只把项目负责人写成所有申请的实际提交人。
8. **跨模块恢复。**采用可靠的待处理记录或消息机制保存已发生事实；接收模块按同一来源版本防重复消费。失败后重新交付同一事项，不重新创建原订单或原付款。

**【现状限制】**当前审批主要核申请版本，财务认款主要复核流水合计；这些不能代替上述全面校验。当前收款阶段按名称对应，开票占用还用历史已开合计与已开记录取较大值避免演示数据重复。生产应完成历史来源对齐、稳定阶段ID和逐笔账，不照搬这类演示兼容算法。

## 十三、开发与测试共同验收的场景

下面是拟验收标准。本次只检查文档和来源，没有执行新的页面或生产接口测试。

### 13.1 三个可复算例子

**例一：整包多团与公共采购。**一个订单100,000元覆盖五团；一笔采购30,000元，其中第一团6,000元、第二团4,000元、第三至五团各3,000元、项目承担9,000元、未分配2,000元。分配合计19,000元，19,000＋9,000＋2,000＝30,000元。项目成本计30,000元；第一团结算只取6,000元。按第一团看收入时仍为“整包未分团”，不能填20,000元。项目承担费用最终结算前，剩余2,000元须明确归属或保留缺项。

**例二：认领占用转认款。**订单12,000元，订金3,000元、尾款9,000元；到账5,000元。本次认领5,000元，其中订金3,000元、尾款2,000元。提交后流水可认0元，订单已认款仍0元；确认后订单已认款5,000元，尾款未认7,000元，流水可认仍0元。重复确认不再增加任何金额。

**例三：付款及减费。**原采购30,000元，已满足付款条件上限12,000元；历史实付2,000元，另有未付有效申请3,000元，可新增申请7,000元。新申请7,000元提交后可用0元；其中成功付4,000元后，原采购已付6,000元，其他申请未付3,000元、本申请未付3,000元，可用仍0元。以后批准减费5,000元，成本以30,000－5,000＝25,000元体现，不能再减一次原采购的累计调整辅助值；条件额度和在途申请重新核，不自动生成退款到账。

### 13.2 正常与异常验收清单

| 编号 | 场景 | 应检查的结果 |
|---|---|---|
| 验01 | 项目建档、两个入口建团 | 新建项目无自动首团；两入口同记录、同办理范围；重复提交不重复创建 |
| 验02 | 分工、任职、移交与成员 | 成员不扩大操作权；分工结束后旧团责任有明确处理；历史经办不被改写 |
| 验03 | 报价确认、审批及重复重试 | 已确认报价产生或关联一个原订单；草稿／待审批不多计成交；客户依据及版本可追溯 |
| 验04 | 同一上限的并发报价 | 已确认＋在途＋本次不越硬上限；未知金额不按零通过 |
| 验05 | 团先建草稿再确认执行 | 草稿可供报价选取；无有效覆盖报价不能通过当前执行确认条件 |
| 验06 | 例一及分批结算 | 项目成本30,000元、第一团承担6,000元，不能复制整包收入或采购全额 |
| 验07 | 同一范围并发提交结算 | 一份团／项目承担范围只能有一份有效普通结算占用；另一份明确失败 |
| 验08 | 审批中费用或认可依据变化 | 旧结算批准被阻止，退回补新依据；已确认结算保持原版本金额 |
| 验09 | 例二及跨项目合并认领 | 逐流水、订单、阶段都核平；各项目按分配行归属；重复认款不加钱 |
| 验10 | 待认款期间订单减价 | 财务确认重核当前订单及阶段额度；不能只核流水够不够 |
| 验11 | 例三及付款条件变化 | 占用与实付转换不重复；变更后超出资格的未付申请进入核对 |
| 验12 | 付款在途、撤回及旧审批 | 结果未知不重复支付；撤回不能留下仍可批准生效的旧来源 |
| 验13 | 供应商差异重提 | 新版认可及盖章材料对应新金额，旧版失效；采购和对账差异不直接覆盖 |
| 验14 | 开票失败、未知、成功重复回传 | 未知继续占用，失败按流程重试，成功只计一次；保留实际发票及订单分配 |
| 验15 | 客户部分认可及最终数量定价 | 不重建月结订单；最终金额与阶段合计一致，争议按实际处置结果解除 |
| 验16 | 取消、追加费用及跨期 | 服务、订单、采购、退款／追退分别留依据；原结算和原银行结果不覆盖 |
| 验17 | 项目结项与获准款票遗留 | 业务缺项不能例外绕过；批准遗留确有后续办理入口和额度范围 |
| 验18 | 财务后段与报表 | 应收应付、预收预付、核销、财务确认、NC能回原来源；同金额不因合同／对账／票据重复计入 |
| 验19 | 外币、税额、空值和历史归属 | 各币种分开，预计与核定分开，未知不补零，人员和汇率变化不重写历史 |
| 验20 | 复制与演示数据迁移 | 新业务不携带旧交付、认款、付款或结算结果；样例数量变化不改变业务限制或用户数据 |

## 十四、当前缺口、待确认政策及开发接续

### 14.1 已有原型与正式开发之间的差异

| 编号 | 当前事实／缺口 | 开发承接要求及归属 |
|---|---|---|
| 待01 | 当前会奖数据主要在浏览器会话中；普通到账及部分财务菜单和会奖视图未统一取数 | 应用与财务开发统一来源、权限及工作入口；不把链接存在当数据交接成功 |
| 待02 | 按实际数量对账不更新最终订单金额；通用改价把未知金额作为零累加不够完整 | 订单／销售模块定义专门最终定价及阶段确认，财务核提前收款分类 |
| 待03 | 付款退回后业务统一修订入口不足；待查申请撤回、旧审批生效控制不足 | 采购、审批、支付共同补原单修订、版本失效和在途款保护 |
| 待04 | 认款确认未完整重验订单及阶段额度；阶段按名称匹配 | 财务及订单模块补稳定阶段ID、当前金额复核和并发占用 |
| 待05 | 部分争议／补服务后的重新认可未完整；整包进度与最终认可有不同要求 | 客户对账保留处置明细及最终认可，不以任意改价自动清争议 |
| 待06 | 结算确认记录主要包含服务及成本承担，未包含完整财务来源 | 结算与财务模块按本次范围补订单、款票及财务确认引用，保留历史版本 |
| 待07 | 费用调整原结算可能按同项目误选；跨团追加需重新明确承担 | 按实际费用及承担明细找原结算，验证关联与金额，不取第一张同项目结算 |
| 待08 | 获准未清款票结项后，新认领／开票仍被项目结束限制拦截 | 产品与财务确定例外业务范围，开发提供受控遗留办理；未完成不报收尾闭环 |
| 待09 | 任职、历史责任归属、收入端锁定汇率、统一汇率来源和完整输出未收口 | 保持原第4步范围，按正式生效期间及来源版本承接 |
| 待10 | 成员没有逐条修订入口；结算期限日常配置被建议移除；复制使用整条数据后清理 | 成员记录与授权分开完善；期限删除连同提醒来源处理；复制采用允许复用清单 |
| 待11 | 正式预收预付、核销、退款、红冲、财务收入成本确认及NC未由会奖完整承接 | 复用统一财务对象，逐来源做接口与对账验收，不能由会奖页面直接写财务余额 |
| 待12 | 会奖有独立演示审批，正式已发布审批配置的接续不能仅凭同名认定完成 | 审批开发绑定事项、有效规则和来源版本；不得把固定演示人员或免审选项当正式制度 |

### 14.2 需要业务／财务明确的选择

待确认内容包括：特殊先执行后定价条件；人员及框架限额依据；应收应付成立时点；提前收付及超收超付分类；按实际数量的最终确认责任；价款减少后的阶段重排；无票付款及预付条件；税费、汇率和尾差处理；财务收入成本确认、跨期及关账规则；结项款票例外和统一结算时限。

这些项目须分别记录确认人、适用公司／业务、有效日期、规则版本和批准依据。没有依据时，不把演示金额、税率、审批人或日期变成硬编码制度。
