# 单团会奖全流程业务需求核对与改进建议

> **2026-10-24当前主线补充已实施：** 项目详情现为项目总览、项目团、报价与合同、开票收款、费用总览、项目资料六页签；执行八页签／结算十页签及独立采购保留。父子团、操作额度、OA合同、询价成本及款票的最新操作与验收见[本轮实施记录](单团会奖主线原型补充实施-20261024.md)。下方旧步骤与全量待办需按该记录区分，报价流程保持原样。

核对日期：2026-10-24。依据：本轮用户提供的两种业务场景、标准节点及五组产品需求；merchant 当前导航、页面和共享脚本；现有会奖流程、实施记录及业财规则。

本轮交付是业务复核与改进建议，未修改业务代码、报价流程或浏览器中的业务记录。以当前代码判断已有能力，以本轮需求判断目标；旧方案和历史测试不能代替本轮验收。

## 一、总体判断

现有系统的基本组织方式是成立的：**一份单团项目统筹多份项目团，以原订单承接客户收入，以原采购承接供应商费用，各团分别执行和办理业务结算，项目层汇总。** 不需要再建一套“大团—子团”模块，也不应把执行详情、采购和结算合成一个大页面。

但目前还不能判断“这份需求已经全部走通”。主要问题集中在以下方面：

1. **年框项目的人员金额与支出预算不是同一套控制。** 现有人员金额限制检查报价、订单及审批中占用；费用预算仍为参考，并没有按人员统一管理采购支出额度。
2. **按实际数量结算的最终定价没有完整办理路径。** 客户对账可记认可数量、单价和金额，但不使原订单正式定价；直接用通用增减价替代，会把未知原价当零处理。
3. **子团业务结算已经具备，大项目财务最终核对不足。** 财务当前主要列出各业务结算及来源，项目费用总览和项目结项不能代替整体财务复核。
4. **统一审批配置与会奖业务审批尚未真正衔接。** 配置有自动找人和免重复审批的试运行能力，会奖实际申请仍大量使用固定演示审批人；自动知会没有完整承接。
5. **分类、项目成员维护、提醒及正式财务承接仍有缺口。** 其中一部分应补原型，一部分只需明确正式接口边界，不能混作“原型都没做”。
6. **存在应先修复的入口问题。** 本轮复现会奖示例脚本缺少依赖造成多个入口初始化异常；结算提醒的旧链接仍进入执行总览。

现有“执行八页签／结算十页签”、独立项目采购、原报价确认和订单生成方式均应保留。

## 二、先统一业务对象和主流程

### 2.1 “大项目团”建议在系统中仍称“项目”

| 业务对象 | 应承载的内容 | 不应混入的含义 |
| --- | --- | --- |
| 客户单位 | 客户身份、类型、联系人和开票资料 | 客户不是某一次项目，也不是订单 |
| 单团项目（父级） | 客户委托、销售归属、框架、总预算、项目分工及总体结果 | 父级不是另一个需要重复计收入成本的履约团 |
| 项目团（子级） | 一条旅游线路的一次交付，或一场会议；日期、地点、人数、计调、资源和完成事实 | 不等于订单；按人数交付的会议不必强制实名游客资料 |
| 客户订单 | 客户实际确认的服务和价款，承接收款、开票与改价 | 框架金额和项目预算不能直接生成同额收入 |
| 原采购及费用分配 | 我方向供应商采购的服务，各团承担及项目承担 | 供应商付款金额不能直接代替成本；跨团分配不能再新增一份采购 |
| 业务结算 | 某次已完成／取消收尾范围的单据、金额、税额和依据核对 | 不等于银行款项全部结清，也不等于会计期间收入成本已确认 |
| 项目财务核对／项目结项 | 前者核总体金额及未结事项，后者确认业务收尾和责任移交 | 两者不能互相替代，不再把全部子团金额当第二笔成交 |

一项目可以一团，也可以多团。一份订单可以覆盖一团或多团，同一团也可能有不同服务范围的订单。**“子团／订单”不能作为同一种记录设计。** 同一笔服务的收入和成本，在项目合计中只计一次。

客户类型与项目类别同样应分开：政府／企业等回答“客户是谁”；奖励旅游／团建／会议／考察等回答“本次做什么”。不能把奖励旅游等直接作为企业或政府的下级客户类型。

### 2.2 主线应补出成交依据与客户认可，并允许款票穿插

```text
销售：客户资料 → 建项目 → 关联框架／合同及金额性质 → 登记项目分工
                              ↓
销售或操作：建立项目团草稿 → 原报价与客户确认 → 原订单 → 确认建团
                              ↓
操作：执行安排、名单和资源 → 原采购及本团成本 → 实际服务完成
                              ↓
销售：客户交付／价款认可 → 必要时完成原订单最终定价或金额变更
                              ↓
操作：团期结算核对本团承担、收入、税额及依据 → 原审批 → 结算确认
                              ↓
财务：按项目汇总已确认结算、公共费用、款票及差异 → 总体核对
                              ↓
负责人：项目结项 → 数据按项目、团、人员、期间分别归集

贯穿执行过程的两条支线：
客户侧：订单／合同 → 按约定申请开票、认领收款、预收分配、退款及红冲
供应商侧：采购／付款条件 → 申请预付或付款 → 财务复核、审批、支付与核销
```

合同可以是先签年框，也可以随具体成交办理。开票不一律在收款前或收款后，采购款也可能先付订金；这些按约定和已确认制度办理，不应排成必须逐步完成的单一串行流程。

当前报价维持原状：登记客户线下确认；适用内部审批通过后或已有有效批准依据时，形成或关联原订单。本轮不恢复已撤回的“新增销售确认报价”改造。操作负责报价准备还是也能登记客户确认，由业务分工明确；销售统管收入不等于必须由销售重复录入每场资料。

## 三、用两种场景核对能否走通

### 3.1 保险开门红：少量大金额项目团

1. 销售建立一个年度奖励旅游项目，保存总合同及总体服务范围。
2. 为五条线路分别建立项目团，分配计调，分别确定日期、人数及服务。
3. 每条线独立成交时使用五份报价及五份订单；若客户只接受一个整包成交，则使用一份覆盖五团的订单，不能复制五份同额订单。
4. 各团在执行详情维护交付；直接费用从团期结算“维护成本”办理，共同设计、统筹及跨团采购从项目采购办理，引用同一原费用。
5. 服务完成后销售登记客户认可，操作分别办理团期结算。未分团的整包收入暂不计算单团毛利，项目层仍核整单金额。
6. 财务汇总五团、项目承担费用及未清款票，再做整体核对，最后办理项目结项。

**判断：前五步的主要原型已有。** 缺口在最后的项目财务汇总核对，以及整包收入需要分团分析时的明确分价依据。后一项没有客户或财务确认依据时应保持“未分团”，不自动平均。

### 3.2 医药年框：大量小金额会议

1. 销售建一个年度项目，登记500万元年框，并明确这是合同上限、预计金额还是其他约定，不直接记500万元收入。
2. 负责人给A、B等操作登记期间、地区、事项和金额。**A的10万元、B的50万元要先明确是承接业务金额还是可支出成本预算。** 两种金额可以同时有，但不能共用一个剩余额度。
3. 操作可从项目团控新增或批量建立本项目的会议团，无需销售逐场建团；原项目分工和报价功能继续使用。
4. 每场按原流程完成报价与成交承接。月底合并客户对账、收款或开票，应引用这些原订单，不再新增一张“月结销售订单”重复计收入。
5. 按约定实数结算的会议，完成后需要明确“认可数量和单价 → 最终订单金额 → 收款阶段 → 后续款票”的承接。
6. 操作逐团维护成本和提交结算，其他团继续新增和执行；项目层随时汇总本年度已成交、已完成、已结算、未清款票及费用。

**判断：自主和批量建团、分工、逐团报价、按月对账的基础已有；“按支出额度受控执行”和“实际数量最终定价”尚未完整。** 这是本次比场景一更重要的流程缺口。

目前医药年框示例中的三位操作采用“计划参考”，人员金额各1,666,666.67元，费用预算参考各20,000元；它没有证明A10万元、B50万元的支出授权已落实。该示例只用于展示分工，不能作为公司额度制度。

## 五、四个需要明确的业务口径

### 5.1 人员10万元到底控制什么

如果是**承接客户业务额度**，应看已生效成交及在途确认；现有实现基本沿这一方向。若是**支出预算**，应看经批准预算与已承诺采购／明确承担的占用，不能只扣已付款，更不能扣客户订单金额。

例如A的支出预算10万元，已确认采购8万元但只付2万元，不能因为“还没付款”就把可用预算当8万元。采购占用何时形成、在途申请是否占用、取消和退回如何释放、跨团费用算谁、已完成团移交后责任怎么算，均需要统一规则。项目预算是否允许人员之间调剂，以及超支是提示、审批还是禁止，也应有批准依据。

当前没有确认这些制度，本报告不把任何一种算法写为既定财务政策。

### 5.2 税前税后建议使用明确名称

页面继续使用“含税金额／预计扣税后／核定扣税后”，避免将这里的“税后”理解为扣除企业所得税后的净利润。财务核定需要分别确认对客销项税和采购可扣税额；有票、开专票或识别成功均不等于全部可抵扣。[增值税法第十六、二十二条](https://fgk.chinatax.gov.cn/zcfgk/c100009/c5237365/content.html)分别规定扣税凭证及不得抵扣情形。

用于本业务测算的关系为：

```text
含税业务毛利 = 同范围含税客户金额 − 同范围含税成本
核定扣税后收入 = 含税客户金额 − 核定销项税额
核定扣税后成本 = 含税成本 − 核定可扣税额
核定扣税后业务毛利 = 核定扣税后收入 − 核定扣税后成本
各口径毛利率 = 本口径业务毛利 ÷ 本口径收入
```

收入为零或未知时，毛利率显示不适用／待确认；税额未知时不能填0。具体财务收入成本确认另按财务规则办理。

适用单一价税计算的例子：含税10,600元、税率6%，票面未税金额10,000元、税额600元；若财务只核定300元可扣，业务核对成本为10,300元，而不是10,000元。价税换算依据见[增值税法实施条例第十六条](https://fgk.chinatax.gov.cn/zcfgk/c100010/c5246349/content.html)；本例只是算术说明，不批准任何实际交易抵扣。

当前税率配置默认0、1%、3%、6%、9%、13%，并非这些选项对所有公司和服务均适用。用户材料中的17%不能直接加入当前常用税率；若要承接历史票据，应保留历史税率和有效期，另由财务确定配置。[现行增值税法第十、十一条](https://fgk.chinatax.gov.cn/zcfgk/c100009/c5237365/content.html)是核对法定税率和征收率的依据，特殊政策及实际适用仍须分别核实。

### 5.3 子团业务结算与父项目最终核对

操作提交子团业务结算，核的是本次完成事实、客户认可和费用承担。财务项目总体核对应至少覆盖：所有子团结算范围和版本、未结团、原订单及整包收入、直接与公共采购、未分配费用、销项及可扣税额、款票未清和调整记录。

项目总体核对只汇总、解释差异并保留确认依据，不把各团已确认金额再新增为一笔订单、成本或资金单据。项目结项则核“是否再新增服务、未完事项如何接手”。已批准保留未清款票时，必须能继续办理允许的收款、开票及后续事项；现有结束项目限制会阻止部分新申请，这条例外路径还需补齐。

### 5.4 同一人审批一次的范围

建议限定在**同一份申请、同一业务版本、同一审批轮次**内复用同意结果。一个人先批准合同，不代表之后对该项目付款、应收变更、开票都免审。退回重提且金额或范围变化时，按新版本重新核对。后续同人节点应留“免重复审批的原同意依据＋知会记录”，不能无记录消失。

## 七、本轮新复现的问题与证据

### 7.1 示例资料加载依赖遗漏：先修

独立浏览器会话首次打开项目列表，出现 `Cannot read properties of undefined (reading 'split')`。列表得到12个项目、23个项目团，只有6团已完成，缺少华东三场新结算案例；直接打开项目详情／团期结算则得到13个项目、26个项目团。

原因可定位到共享示例新增调用税额计算，但部分入口未在示例脚本之前加载税额模型。随后只读核对10个具有同一依赖缺口的入口，均复现同类错误：工作台、合同、订单、售后、供应商对账、单团项目列表，以及四个相关报表。并不表示这些页面全部无法显示，而是它们可能展示初始化中断后的旧资料，不能证明同源完整。

这是前面结算示例补充后漏查的直接关联入口，本轮没有修复。不得继续以此前结算页测试通过推断全链路入口无异常。

证据：[依赖检查](evidence/mice-prototype/business-review-20261024/dependency-observations.json)、[10入口浏览器错误记录](evidence/mice-prototype/business-review-20261024/dependency-browser.json)。

### 7.2 结算提醒仍进入执行总览

工作台未结算提醒和部分结项检查仍生成执行页 `tab=settlement` 的旧地址。本轮打开有效项目团的该地址，实际选中“总览”，没有直接到团期结算。执行总览虽有结算查看链接，但仍多绕一次，且旧参数语义已不成立。应复用原团期结算地址规则，不能为兼容旧链接重新恢复执行页结算功能。

### 7.3 示例阶段与开发说明要分清

当前26个示例团全部已完成，是上一轮用户要求的结算演示设置，不应回退。存在客户认可待补、名单缺失和历史22万元费用差异等，仍保留待核。因此“有结算按钮”只表示能进入办理，不代表全部可以直接提交。

旧开发说明正文仍有“五页签”及已撤回报价建议，并与顶部新记录并列。原有证据不删除；后续需要把现行八／十页签和报价不变的说明放入正文，历史方案明确归入历史章节，避免开发按旧流程实施。本报告第二、六节为本次现行边界说明。
