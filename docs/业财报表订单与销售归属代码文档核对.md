# 业财报表订单与销售归属代码—文档核对

更新时间：2026-09-06

> 本文是阶段2第二个模块的审计结果。范围限于客户、下单、订单、合同、收款认领和销售发起的售后；本轮不修改业务页面，也不把静态页面、浏览器本地记录或操作成功提示误判为已经形成正式业务单据。

## 一、本轮要回答的问题

财务的订单口径、产品渠道分析和统一业绩明细，都要先回答同一件事：在某个日期，哪一张订单以什么状态成立，卖了什么产品和团期，归哪个销售、销售组、门店、分公司和渠道，成交金额是多少，后续取消、退款和变更又怎样影响原订单。

这一环节位于完整业财链路的中段：

`客户和销售机会 → 产品/团期 → 下单 → 客户订单 → 合同/应收/收款 → 履约 → 售后调整 → 结算和财务分析`

主要使用角色是销售顾问、门店店员、大客户销售和店长；履约人员需要从团期查看同一批订单，财务人员需要沿同一订单反查应收、收款、退款、合同、团期和最终结算。订单必须成为上下游共同使用的业务依据，不能由销售端和履约端各维护一套近似订单。

## 三、总体结论

当前系统还不能自动、稳定地生成财务要求的订单口径业绩和统一财务业绩明细。

业务文档对正确方向已经描述得比较完整：订单应保存产品、团期、客户、销售归属、责任公司、金额构成和当时适用的规则；订单提交不等于收款，售后申请不等于退款，生效后的变化不能覆盖原记录。这些设计可以继续作为改造依据。

代码的现状则是可操作原型：

1. 下单页只把部分订单信息保存到当前浏览器，合同、认款和售后等页面大多使用固定示例数据或操作提示。
2. 订单日期没有作为明确、不可随意改变的业务日期保存；订单详情又统一展示固定下单时间。
3. 下单时选择了渠道、分销商、分销员或平台，但保存订单时没有保存这些信息。
4. 只保存归属门店和销售姓名，没有销售组、部门、分公司、预算区域、人员任职版本和调整记录。
5. 产品和团期只保存名称、日期及一个混合字符串，没有完整保留产品归属、业务类型、旅游范围、目的地和责任公司。
6. 订单后续的确认、取消、归属调整、收款、应收调整和售后提交，大多只弹出成功提示，没有形成可持续追溯的记录。
7. 销售中心和履约中心存在两套近似订单页面，使用相同浏览器记录但复制了整套页面代码，已经出现功能分叉。
8. 履约中心订单详情在没有真实成本依据时会自动展示一条应付：普通订单固定为25,000元，单团项目按订单金额的62%计算，并自动指定供应商。这类金额只能作为演示，绝不能进入财务报表或应付流程。

所以当前页面能演示“业务应该怎样走”，但不能证明“订单事实已经形成、后续单据真实关联、历史归属能够复算”。直接在此基础上开发周报，会把固定示例、推断金额和当前人员资料误当成财务事实。

## 四、代码与文档五类核对结果

| 分类 | 已确认事项 | 对财务报表的意义 |
|---|---|---|
| 代码与文档一致 | 销售负责下单、合同、客户资料和售后发起；财务负责认款确认和退款执行；订单、收款、合同、履约应分别表达状态 | 角色边界和页面方向可以保留 |
| 文档已有、页面未完整承接 | 文档要求订单保留责任公司、产品团期、销售渠道、完整金额、版本和变化记录；代码只保存很少一部分 | 订单口径、渠道业绩和历史归属无法稳定生成 |
| 代码新于文档 | 页面已支持参团游、邮轮、专列、自由行、研学、单项服务和单团项目共用订单外观，也增加了优惠构成、多人/多资源销售构成等演示 | 统一订单对象的方向正确，但仍需形成共同保存和校验规则 |
| 代码与文档冲突 | 文档规定预估成本不能形成应付；履约订单详情却用固定金额或比例自动展示应付。文档统一使用“未收款/已收齐”，部分页面仍使用“待收款/已收款” | 会导致成本、应付和收款状态被误判，必须统一 |
| 代码和文档均待确认 | 有效订单从哪个状态开始计入业绩；取消、部分退款、全额退款和跨期调整如何冲减；归属调整是否改变历史业绩 | 没有这些规则就无法复算订单周报和人员业绩 |

## 六、当前页面之间为什么没有形成共同订单链路

### 6.1 下单只保存了浏览器局部记录

`merchant/sales/booking.html`把新订单写入浏览器本地记录`caesarOrderFinanceEvents`。保存内容包括订单号、产品名称、团期显示值、联系人、门店、销售、金额、优惠、初始状态和部分销售构成。

它没有保存下单时已经选择的渠道、分销商、分销员、线上平台和收款计划，也没有保存销售组、分公司、预算区域、合同主体、收款单位、履约公司、采购公司、收入核算主体和退款责任公司。

浏览器本地记录只服务当前原型演示，换浏览器、清理数据或进入其他数据来源后都不能保证一致，不能作为财务底表来源。

### 6.2 订单详情会用固定规则补出不存在的事实

销售订单详情会读取少量本地订单信息，但产品来源、渠道、客服、部门、责任公司、收款路径、成本承担和内部结算等大量内容来自页面固定规则。新建订单没有提供这些事实时，页面仍会显示完整结果，使使用者误以为系统已经做过判断。

履约中心订单详情的问题更严重：没有真实应付时，会自动生成一条固定应付编号、供应商和金额。普通订单统一显示25,000元，单团项目按订单金额的62%计算。根据现有业务文档，预估成本不能替代实际成本或应付，因此该逻辑只能作为临时演示，后续必须删除或明确标为预计成本，不得进入财务承接。

### 6.3 合同、认款和售后没有读取同一订单事实

- 合同管理使用页面固定合同行；从订单进入时没有生成、定位或更新对应合同。
- 收款认领可以根据网址中的订单号筛选，但可选应收仍是页面固定卡片；新建订单不会自动成为可认款应收。
- 售后处理列表全部来自固定行；订单详情或列表提交售后后没有形成售后单并进入该列表。
- 订单状态、归属门店和销售调整大多只显示成功提示，不保留调整前、调整后、原因、审批和生效时间。

因此页面之间的跳转证明了产品原型的操作方向，却不能证明数据已经贯通。

## 七、销售订单与团期订单两套页面的边界

当前两套页面的重复程度很高：

| 页面 | 当前差异 |
|---|---|
| 新建订单 | 两个文件各2,780行，只有约15处链接或标题差异 |
| 订单列表 | 两个文件各4,708行，主要是跳转路径和标题差异 |
| 订单详情 | 销售端2,165行，履约端2,270行；履约端单独增加了应付付款展示和推断应付逻辑 |
| 售后列表 | 两个文件各496行，只有标题差异 |
| 取消、退款、转款、转团兼容页 | 销售端与履约端各有4个19行跳转页 |

建议的业务边界是：

1. **客户订单只有一套共同记录。** 销售中心是下单、客户、合同、收款登记和售后发起的主要入口。
2. **团期订单是同一订单的履约查看方式。** 计调或团控从某个团期查看该团已确认、占位或售后的订单、游客和资源影响，不再生成另一套订单数据。
3. **如果履约人员确有代客下单权限，仍复用同一新建订单表单。** 只增加操作来源和权限记录，不复制页面和规则。
4. **财务结果只展示真实关联单据。** 订单详情可以反查应收、收款、应付和付款，但不能在订单页根据比例或名称自动造出财务金额。

这样既能保留销售和履约各自高频入口，又不会让同一订单因页面复制而出现状态、字段和金额差异。

## 八、需要形成的订单业务记录

### 8.1 订单基本信息

- 唯一订单号、来源系统和原订单号。
- 创建日期时间、提交日期时间、确认日期时间和当前状态。
- 客户、合同客户、付款方、联系人和游客之间的关系。
- 产品、方案、团期/航次/班期/营期/出行日期及其当时信息。
- 各产品类型适用的人数、数量和资源占用明细。

### 8.2 订单销售归属确认

订单确认时保留当时适用的：

- 销售公司、销售人员、销售组和部门。
- 门店、分公司、区域和预算区域。
- 渠道大类、具体渠道、分销商、分销员或线上平台。
- 产品经营公司、产品负责人和团控负责人。
- 归属规则来源及生效时间。

客户后来转交给其他销售、人员转岗或门店调整，不能自动改变已经发生订单的历史归属。确需改业绩归属时，应形成有原因、审批人、生效日期和调整前后值的归属调整记录。

### 8.3 订单责任和结算关系

系统应根据产品、门店、渠道、合同和集团规则自动判断，并在确认前让销售核对：

- 对客签约公司、客户款收取单位和对客开票公司。
- 主要履约责任公司、采购签约公司和收入核算公司。
- 客户退款责任公司。
- 集团内部产品提供方和接受方。
- 门店或渠道结算对象、结算方式和采用的规则版本。

这些责任不能由订单详情根据产品类型临时推断。判断冲突时应阻断确认并交给相应角色处理。

### 8.4 订单金额和费用明细

- 标准报价、人工调整和客户合同金额。
- 客户现金应付、非现金抵扣、优惠减免、第三方补贴和公司承担优惠。
- 代收代付、服务费、税费、房差、港务费等不同性质金额。
- 每项金额的支付方、取得方、承担方、币种、数量、单价和规则来源。
- 付款计划和各阶段应收条件。

订单总额必须由明细汇总。后续人数、服务或价格变化通过应收调整、退款或补充结算记录影响，不能直接覆盖原订单金额。

### 8.5 订单状态和变化记录

每次预留、占位、提交、确认、取消、作废、执行、完成都要记录发生时间、操作人、前后状态和业务依据。售后必须引用原订单及受影响的游客、服务、团期、收款和金额，并分别保留：

- 申请金额与最终批准金额。
- 未收部分冲减、已收部分退款和供应商扣损。
- 原团期释放与新团期占用。
- 原合同和补充协议。
- 调整所属的业务日期和财务期间。

## 九、建议的修改顺序

### P0：先建立一套共同订单来源

1. 收敛销售订单与团期订单的重复保存规则，明确销售主入口和团期履约视图。
2. 用同一订单记录承接下单、详情、合同、认款、售后和团期查看。
3. 清除订单详情中自动推断正式应付、收款和责任结果的逻辑；无真实记录时显示“未形成”或“待确认”。

### P0：补齐订单发生时必须保存的事实

1. 明确记录真实下单时间、确认时间、来源系统和原订单号。
2. 保存产品团期、销售组织、门店渠道和责任公司的当时归属。
3. 保存金额明细、付款计划、币种及价格规则来源。
4. 在确认前校验关键归属和金额是否完整，不能只校验联系人和人数。

### P0：打通变化和财务承接

1. 订单状态动作形成可追溯记录，而不是只弹成功提示。
2. 合同必须从订单生成并保持订单号、合同金额、签约主体和版本一致。
3. 订单达到应收条件后形成真实应收，认款从真实流水分配到真实应收并写回订单。
4. 售后形成真实售后单，审批通过后分别承接应收冲减、补差、转款或退款执行。

### P1：统一状态和编号名称

1. 统一“未收款、部分收款、已收齐、退款中、已退款”等收款状态。
2. 统一应收、认款、收款、退款等单据编号用途，不能在不同页面用同一前缀表达不同单据。
3. 将客户当前归属与订单历史销售归属明确区分。

## 十、需要财务和业务确认的事项

1. 订单从预留、占位、待确认、已确认中的哪个状态开始进入“有效订单业绩”；不同业务类型是否一致。
2. 取消订单、全额退款、部分退款、退差、转团和改期分别按原下单期间冲减，还是按变化生效期间记录调整。
3. 订单业绩按客户合同金额、客户现金应付还是财务确认的订单金额统计；优惠、积分、代收代付分别怎样处理。
4. 销售、门店和部门业绩以订单创建时、订单确认时、出团时还是回团时的归属为准。
5. 经审批修改销售或门店后，历史业绩是否跟随调整；跨月、跨年时是否允许追溯调整原期间。
6. 直客、门店、分销、线上平台、企业客户和全员营销的渠道层级及优先判断规则。
7. 同一订单含多个产品、多个目的地、多个供应方或多个销售协作人时，金额和业绩如何分配且不重复。

## 十一、旧文档时效判断

`docs/system-standard-group-link-walkthrough-report.md`证明的是原型页面入口和跳转方向基本存在，而且原文已经说明“不做真实跨页数据回写验证”。其中“通过”不能再解释为订单、应收、收款、合同、售后和财务报表已经使用同一套数据。

该文档仍可保留为历史页面链路验收记录，但后续判断报表能力必须以本文和总对照表为准。

## 十二、本轮边界与下一步

本轮没有修改业务页面，已经确认订单与销售环节存在P0数据链路缺口。门店、分公司、销售组、渠道层级和预算区域的来源及历史版本，还需要结合组织、渠道和预算页面继续核对。

唯一下一步是核对“组织、渠道与预算归属”模块，重点确认组织树、人员任职、门店类型、分公司、渠道层级、预算区域、个人/团队/门店/渠道任务，以及这些规则如何在订单发生时固定下来。
