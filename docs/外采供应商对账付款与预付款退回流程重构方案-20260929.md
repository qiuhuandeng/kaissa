# 外采供应商对账、付款与预付款退回流程重构方案

> 日期：2026-09-29  
> 状态：方案已确认；第1步独立对账、第2步独立付款、第3步预付款逐明细退回均已实施  
> 适用范围：体系外供应商；集团内部公司间对账继续使用“公司间对账”，不并入本方案

## 一、结论

本次应把“团期结算、供应商对账、付款”从一条串行流程改为三条有关联但互不互锁的业务线：

| 业务线 | 主要作用 | 主要角色 | 形成条件 | 是否互为前置 |
|---|---|---|---|---|
| 团期结算 | 核对团期收入、成本和业务毛利 | 计调、团控、业务结算人员 | 团期发生业务和成本 | 不作为对账或付款前置 |
| 供应商对账 | 双方确认实际服务和最终应结金额 | 我方计调、供应商管理员 | 已有外采成本项及可核对依据 | 不作为首次付款前置 |
| 付款与退回 | 按成本项申请预付或付款，并处理多付退回 | 计调、付款复核、资金、供应商管理员 | 团期已保存外采成本项 | 不等待团期结算或供应商对账 |

因此页面上不能再用“团期结算｜供应商对账”两个页签表达，也不能让付款申请继续藏在 `fulfillment-cost.html?view=payment` 中。

本次页面处理建议为：

1. 新增一个商户端直接页面 `merchant/tour/supplier-reconciliation.html`，在履约中心设置独立“供应商对账”菜单。
2. `merchant/tour/fulfillment-cost.html` 只保留团期结算，不再承载供应商对账和付款申请。
3. 将现有 `merchant/tour/fulfillment-payment-apply.html` 从跳转页改成真正的独立付款申请页，继续使用现有“付款申请”菜单，不新增重复地址。
4. 供应商端复用 `supplier/settlements.html`，去掉供应商主动“提交对账单”，改为处理我方发起的待确认对账。
5. 预付款退回复用 `merchant/finance/finance-prepayment-offset.html` 和现有付款退回页，不新增一个孤立的退款菜单或页面；在预付单上新增“预付款退回”处理，并按原付款明细填写退回金额。

本方案只确认业务流程和原型页面边界。正式会计入账时点、发票已开后的退回政策、跨币种退回规则仍须财务确认；这些未定规则不影响先完成本次原型。

## 二、实施前页面核对结果

| 当前页面或入口 | 当前状态 | 与本次流程的冲突 |
|---|---|---|
| `merchant/tour/fulfillment-cost.html` | 同一页包含“团期结算／供应商对账”页签，并承载付款申请模式 | 把三条独立业务线做成了串行关系，入口归属错误 |
| `merchant/tour/fulfillment-payment-apply.html` | 仅跳转到团期结算页的付款模式 | 导航看似独立，实际仍依附团期结算 |
| `supplier/settlements.html` | 供应商可点击“提交对账单”主动发起 | 与最新确认的“我方计调发起、供应商管理员确认”主流程冲突 |
| 商户端现有对账确认 | 能往返确认和处理差异 | 供应商最终确认不强制上传盖章件；已确认版本与盖章件没有形成完整对应 |
| `merchant/finance/finance-prepayment-offset.html` | 有冲抵、分摊、转款和泛化“退回” | 没有按原付款明细发起预付款退回，也没有清楚区分“申请退回”和“已收到退款” |
| `merchant/finance/finance-payment-return.html` | 已能承接付款退回和到账核对 | 可继续复用，但应接收预付款退回申请及供应商退款凭据，不应另造重复页面 |

此前原型中“供应商也可先提交账单”和“供应商主动发起对账”的能力，由本次用户确认覆盖。供应商可以提交账单、实际服务依据或差异材料，但这些是对账依据，不等于供应商创建双方对账单。

## 三、角色、上游和下游

### 1. 我方计调

- 上游：团期资源采购、供应商确认、实际服务记录和团期成本项。
- 高频任务：按供应商和费用范围发起对账；核对供应商异议；在已有成本项后发起预付或付款。
- 操作结果：生成待供应商确认的对账版本，或生成待财务复核的付款申请。
- 不承担：实际付款、退款到账核验、发票核验和会计处理。

### 2. 供应商管理员

- 上游：收到我方发起的对账单。
- 高频任务：逐项核对金额和依据；有异议时说明差异；一致时上传盖章件并确认。
- 操作结果：对账退回我方处理，或形成双方已确认的最终金额和盖章依据。
- 不承担：我方付款审批、资金付款或我方财务核销。

### 3. 我方付款复核与资金人员

- 上游：计调按成本项发起的付款申请；已确认对账产生的补付或应退差额。
- 高频任务：复核付款对象、金额、协议、账户和已有付款占用；执行付款；核对供应商退款到账。
- 操作结果：付款成功、付款失败待重办、退款部分到账或退款全部到账。
- 不承担：修改团期成本、代替计调确认实际服务或代替双方对账。

## 四、目标业务流程

### 1. 外采成本形成付款资格

只要团期保存了外采供应商成本项，就可以按该成本项发起预付或付款，不校验团期是否已结算，也不校验供应商对账是否已完成。

付款页必须核对以下内容：

- 采购公司、供应商、团期和成本项一致；
- 成本项未作废，金额和币种有效；
- 已付款、申请中、付款中和已退回金额各自清楚；
- 同一成本项不能因重复提交形成超过当前可付金额的占用。

对账完成前，成本项金额是当前付款上限；对账完成后，双方确认的最终金额成为新的付款上限。对账不是付款开关，只是修正最终应结金额。

### 2. 我方发起供应商对账

我方计调在独立“供应商对账”页面新建对账：

1. 选择采购公司和一个外采供应商。
2. 选择对账期间、团期／订单及成本明细。
3. 核对实际服务数量、单价、增减项、已付金额和本次对账金额。
4. 保存草稿或提交供应商确认。
5. 提交后生成不可直接改写的版本，状态变为“待供应商确认”。

跨公司、跨供应商或跨币种的费用不能放入同一张对账单。对账范围重复、费用已被其他有效对账占用或缺少实际服务依据时，应在提交时拦截并指出具体费用。

### 3. 供应商确认并上传盖章件

供应商管理员从“待我确认”进入本张对账单：

- 金额一致：必须上传与当前版本对应的盖章件，再确认。
- 金额不一致：逐项填写供应商认可金额、差异原因和附件，提交给我方处理；此时不要求上传最终盖章件。
- 没有盖章件、盖章件不是当前版本或文件上传失败时，不能完成最终确认。

建议盖章件支持 PDF、JPG、JPEG、PNG，原型中显示文件名称、上传人、上传时间、对应版本和备注。正式文件大小及病毒检测规则由开发阶段按公司安全规范确定。

供应商确认成功后，状态变为“双方已确认”。我方可以查看和下载盖章件，不再要求我方重复上传同一份文件或做第二次金额确认。

### 4. 差异退回与版本保留

供应商提出异议后：

1. 我方计调查看逐项差异和供应商材料。
2. 接受差异时调整本次对账金额；不接受时填写处理说明。
3. 重新提交形成新版本，再交供应商确认。
4. 旧版本、旧金额、旧附件和双方操作记录全部保留。

双方已确认后不能直接覆盖金额。如发生后补费用、减免或错误更正，应发起“对账调整”并形成新版本；已付款和已退回记录不随金额修改而消失。

### 5. 对账后的多退少补

对账确认后，系统按最终金额和实际净支付金额判断补付或退回：

```
实际净支付金额 = 累计付款成功金额 - 已核对到账的供应商退款金额
可付金额 = 最终确认金额 - 实际净支付金额 - 申请中及付款中占用金额
应退金额 = 实际净支付金额 - 最终确认金额
```

- 可付金额小于零时按零显示，并形成应退金额。
- 应退金额小于零时按零显示，不产生退款任务。
- “申请中及付款中”只占用可付金额，不能算作已经付款。
- 供应商只上传退款凭据时，不能直接减少实际净支付；须由资金人员核对实际到账后再减少。

金额示例：

| 场景 | 最终确认金额 | 已付款 | 已核对到账退款 | 申请中／付款中 | 结果 |
|---|---:|---:|---:|---:|---|
| 少付需补款 | 90,000 | 60,000 | 0 | 0 | 可付30,000 |
| 已有付款占用 | 90,000 | 60,000 | 0 | 10,000 | 可再申请20,000 |
| 多付需退回 | 90,000 | 120,000 | 0 | 0 | 应退30,000，可付0 |
| 退款已到账 | 90,000 | 120,000 | 30,000 | 0 | 实际净支付90,000，可付0、应退0 |

若尚未完成最终对账，则付款页按当前有效成本项金额计算，不因“待对账”阻断付款；页面只需弱提示“最终金额尚未双方确认，后续可能多退少补”。

## 五、商户端页面重构

### 1. 团期结算页

页面：`merchant/tour/fulfillment-cost.html`

保留：团期收入、收退、成本和业务毛利核对；成本项及其来源查看；进入团期、订单或成本详情的反查入口。

移除：“供应商对账”功能页签；隐藏在本页的付款申请工作区；“结算完成后才能对账／付款”的提示和校验。

详情中可以保留只读关联信息，例如“已发起2张供应商对账、付款申请3笔”，但这些不是本页主操作。

### 2. 新增独立供应商对账页

页面：`merchant/tour/supplier-reconciliation.html`

菜单位置：履约中心，与“团期结算”“付款申请”并列，名称为“供应商对账”。

主要列表字段：对账单号／供应商、对账期间、关联团期和费用数量、我方提交金额、供应商确认金额、已付金额和多退少补结果、主状态、操作。

主状态只保留一套：草稿、待供应商确认、差异处理中、双方已确认、已作废。盖章件缺失、存在差异、应补付或应退回属于数据结果或提示，不再额外堆一组状态标签。

| 主状态 | 主要操作 | 说明 |
|---|---|---|
| 草稿 | 编辑、作废 | 本页抽屉完成 |
| 待供应商确认 | 详情、撤回 | 未确认前可撤回并升版 |
| 差异处理中 | 处理、详情 | 在详情中逐项处理差异 |
| 双方已确认 | 详情、发起调整 | 补付或退回从详情的款项区域进入 |
| 已作废 | 详情 | 只读保留历史 |

新建和详情使用同页右抽屉；复杂差异处理可以进入本页二级处理区，不跳回团期结算页。

### 3. 独立付款申请页

页面：复用并重做 `merchant/tour/fulfillment-payment-apply.html`

付款申请的来源改为“有效外采成本项”，不是“已结算团期”或“已确认对账”。列表和抽屉至少显示：供应商、团期、订单或采购依据；成本项名称、成本金额和币种；当前付款上限及来源；已付款、申请中、付款中、已退回；本次可申请金额；对账状态弱提示。

计调可按一个供应商勾选多笔同公司、同币种成本项提交付款申请；每笔申请金额仍要落到原成本明细，不能只留一笔供应商总额。

## 六、供应商端页面重构

页面：复用 `supplier/settlements.html`，页面名称建议由“对账结算”改为“供应商对账”。

页面默认展示“待我确认”，不再放“提交对账单”主按钮。供应商账单或实际服务依据从相应采购订单、服务确认或账单入口提交，不在对账页创建双方对账单。

列表字段建议为：对账单号／采购公司、对账期间、关联团期／订单和费用数量、我方提交金额、主状态、操作。

处理抽屉分四区：对账摘要、费用明细、付款情况只读、最终确认。最终确认选择一致或有异议；一致时上传盖章件并确认，有异议时提交差异和材料。

供应商已确认后只可查看当前盖章件、历史版本、我方付款结果和退款处理结果。供应商不能进入我方付款审批、账户选择、核销或会计处理。

## 七、预付款逐明细退回

### 1. 入口和适用条件

入口放在 `merchant/finance/finance-prepayment-offset.html` 的预付单操作列，名称明确为“预付款退回”，不再用含义不清的“退回”。

同时满足下列条件时可操作：

- 预付款申请已通过；
- 至少有一笔付款明细已经付款成功；
- 该付款明细仍有未冲抵、未退回、未被其他退回申请占用的余额；
- 当前没有与这笔预付款关联的有效发票，或原发票已按财务要求完成作废／红字处理；
- 付款对象、币种和收款账户可以核对。

“审批通过但尚未实际付款”的明细不能退回；它应撤销付款安排或关闭未执行付款，而不是要求供应商退款。

### 2. 退回抽屉

抽屉按原付款明细逐行展示：

| 字段 | 业务含义 |
|---|---|
| 付款明细／付款单号 | 对应哪一次实际付款 |
| 付款日期和付款金额 | 原成功付款事实 |
| 已冲抵金额 | 已用于实际成本或应付的金额 |
| 已退回到账金额 | 财务已经核对到账的退款 |
| 退回处理中金额 | 已申请但尚未核对到账，防止重复申请 |
| 本次可退金额 | 付款金额减已冲抵、已退回和处理中金额 |
| 本次退回金额 | 本次填写，不能超过可退金额 |
| 退回原因 | 对账后多付、采购取消、服务减少、重复付款或其他 |

同一预付单可一次选择多笔付款明细，每笔单独填写退款金额；至少一笔大于零。不同币种不能合并，不能用后续应付款抵消后冒充现金已退。

### 3. 提交后的职责

提交“预付款退回”只生成退回申请并占用相应可退余额，不表示钱已到账：

1. 供应商管理员查看退回要求并上传退款凭据。
2. 我方资金人员在现有付款退回页核对银行实际到账，可一次或分次核对。
3. 只有实际到账核对后，才减少预付余额和实际净支付金额。
4. 退回失败、部分到账或凭据有误时保留原付款和处理历史，未到账部分继续待处理。

银行原路退回、账户错误导致的付款失败，继续按现有“付款退回”处理；它与供应商因多付主动退款不是同一种业务原因，但可以复用同一到账核对页面。

## 九、正常与异常验收场景

### 正常场景

1. 团期添加100,000元外采成本后，未结算、未对账也能申请30,000元预付。
2. 我方发起90,000元对账，供应商上传当前版本盖章件并确认，已付60,000元后可再付30,000元。
3. 已付120,000元、最终对账90,000元，显示应退30,000元；供应商分两次退回20,000元和10,000元，资金分别核对到账后结清。
4. 同一预付单包含两笔成功付款，可分别填写5,000元和8,000元退回，不影响未选择明细。
5. 供应商提出差异，我方处理后提交第2版；供应商只能对第2版上传盖章件，旧版本和旧附件仍可查看。

### 异常场景

1. 供应商未上传盖章件直接确认，系统拦截。
2. 供应商上传旧版本盖章件确认新版本，系统提示版本不一致。
3. 跨采购公司、跨供应商或跨币种费用放入一张对账单，系统拦截。
4. 对账未完成时付款申请被错误阻断，应判为失败。
5. 付款明细未实际成功、已全额冲抵、已全额退回或已被其他申请占用时，不能再次申请退回。
6. 供应商只上传退款凭据但资金未核对到账，预付余额和实际净支付不得减少。
7. 已确认对账被直接改写金额而没有形成新版本，应判为失败。
8. 付款成功100,000元、退款到账20,000元后，实际净支付应为80,000元，不能同时把原付款改成80,000元造成历史失真。

## 十、实施顺序

1. 先拆菜单和页面：新增商户端供应商对账页，团期结算只保留本职，供应商端改为只处理我方发起，并完成盖章件确认。
2. 再重做独立付款申请：付款资格改为成本项形成即成立，对账只更新最终付款上限和多退少补结果。
3. 最后补预付款逐明细退回：预付管理发起、供应商上传凭据、付款退回页核对到账，并回归原冲抵、付款失败和发票流程。

## 十一、仍需财务确认但不阻塞原型的事项

- 已开发票后发生供应商退款时，必须先完成何种红字或作废处理；原型先拦截快速退回并提示转财务处理。
- 外币退款按原付款汇率、到账汇率还是结算汇率处理汇兑差额。
- 退款到账确认后，正式系统减少预付余额和应付余额的具体入账时点。
- 供应商盖章件是否必须使用公司备案印章、是否需要电子签章验真。
- 一张对账单允许覆盖的最长期间及是否允许跨团期但同供应商、同币种合并。

这些事项均标记为“待确认”，不能在原型中假设为已批准政策。
