# 审批配置业务扩展设计

> 实施状态（2026-10-09）：第1步配置和试跑已实际落地，见[实施验收](审批配置第一步实施验收-20261009.md)。用户反馈后，“负责范围”在人员抽屉改为“审批哪些业务”，强调业务归属不等于审批人所在部门，产品部门候选不含门店／分公司。第2、3步仍待完成；未定制度不因本次实现而自动确认。

日期：2026-10-09。适用对象：集团流程管理员、业务和财务负责人、产品设计及开发人员。

本设计覆盖公司提供的15类审批场景。保留集团审批配置的“审批模板、审批人员”两个页签，在现有组织任职和流程编辑基础上，补齐按业务职责找人、按业务条件分流、明确免审依据及逐节点办理。销售、计调、财务继续在原业务页面发起申请；配置管理员维护规则，审批人核对并决定，业务和财务办理人员承接审批结果。

本轮交付为扩展设计，尚未修改业务页面。原型以配置、试跑、申请及正常／异常办理可操作为完成标准，不以真实后端、支付、签约、消息发送或跨模块自动回写为条件。

## 一 已确认的业务边界

公司现行审批路径以用户提供的15项表格为依据。本轮进一步确认：

1. 第9项“供应商”是外部合作供应商，负责确认价格，不能当作本公司员工审批人。
2. 不改变供应商结算价，只免结算价变更这一项内部审批；销售申请优惠仍按第15项办理。

对客金额和供应商结算价分别表示客户应付给我方的金额、我方与供应商约定的金额，不能混成一个“订单价格”。现有订单应收变更要求业务审批；本次不以结算价免审覆盖该要求。优惠导致对客金额变化时，原型关联同一次业务申请，并列明所需审批。仅在优惠流程已覆盖该次应收变更要求的审批职责、金额和版本范围时复用其批准，避免重复送相同审核；未覆盖时不能因优惠通过就取消原应收审核。非优惠的应收变更继续遵循既有流程。

审批通过不等于实际付款、退款到账、开票成功、合同签署完成或供应商已确认。未匹配流程、缺审批人、来源资料缺失与政策待确认均应明确提示，不能进入免审结果。

合同收款比例及限制时点、混合支付退款路径、领队借款与报销的具体核对规则、申请人与计调为同一人时如何处理等，仍按第十节标记待确认。配置功能可以先完成，未确认政策只允许保存草稿或以明确样例试跑。

## 二 页面归属与角色任务

| 页面或区域 | 使用角色与最高频任务 | 上游资料 | 操作结果及下一步 |
|---|---|---|---|
| 集团审批配置的审批模板 | 流程管理员找到事项，编辑、试跑并发布适用流程 | 公司、业务场景、已确认制度 | 新版本供新申请采用；旧版本保留 |
| 集团审批配置的审批人员 | 流程管理员安排某项职责在各公司、负责范围的人员 | 现有员工账号、有效任职及审批授权 | 后续任务按职责取人；人员异常由获授权管理员交接 |
| 模板编辑的审批流程 | 管理员设置适用范围、触发条件、审批人及分支 | 单据能够提供的条件与职责安排 | 试跑显示采用原因、实际人员和办理路径 |
| 模板编辑的审批内容 | 管理员选择该事项需要核对的资料 | 原业务单据 | 审批人看到完整判断依据，原单填写规则不受影响 |
| 模板编辑的审批规则 | 管理员设置退回、撤回、代办、重复审批等 | 公司批准的办理规则 | 办理时按规则控制动作，缺人不自动通过 |
| 集团基础参数的销售签约条件 | 合同／业务管理员设置签约前收款要求 | 签约公司、产品条件、销售渠道及制度依据 | 判断可继续、需例外审批或暂不可办理 |
| 原业务申请入口 | 销售、计调、财务提交当前单据 | 原订单、团期、款项、合同或结算 | 显示本次所需审批及下游处理，提交当前版本 |
| 审批中心详情 | 当前审批人核对、同意、退回或拒绝 | 本次提交内容、采用规则与实际流程 | 当前节点完成后进入下一节点，最终回原业务继续办理 |

集团导航维持“部门组织 → 审批配置”。模板编辑继续使用现有三个页签“审批流程、审批内容、审批规则”，不恢复历史四步页面，不增加审批一级菜单。供应商价格确认沿用供应商业务入口；付款、开票、到账核对留在财务。

## 三 审批人员配置

### 1 列表与操作

审批人员列表调整为：公司、审批职责、负责范围、审批人员、状态、操作。生效期间、代办明细和调整记录进入详情。主状态统一使用未生效、有效、已停用或已到期之一，不并排增加“缺人、风险、代办中”等状态标签。

筛选包含公司、审批职责、状态及人员名称，查询／重置跟在条件后，右侧为“新增”。列表操作按当前安排状态提供详情、编辑；停用、代办及调整记录放更多菜单。停用只影响后续取人，在途任务通过明确交接办理；已使用安排保留历史，不能直接删除。

表格内部横向滚动，操作列固定右侧并定宽164像素，负责范围列吸收多余宽度。每个单元格最多三层；人员较多时显示必要姓名与人数，完整名单进详情。状态、日期、人数和按钮不得裁切。

### 2 新增和编辑抽屉

使用现有标准右抽屉，按“职责安排、审批人员、生效安排”分区，不增加顶部说明卡。

| 字段 | 控件及联动 | 必填和校验 |
|---|---|---|
| 公司 | 单选现有公司 | 必填；变更后重新核对范围、人员及未保存内容 |
| 审批职责 | 下拉选择预置业务职责 | 必填；不同职责开放不同负责范围，不能只靠自由文本命名取人 |
| 负责范围 | 公司通用、指定业务部门、指定产品部门或指定渠道 | 每条安排选一种依据；不把不同依据的安排自动拼成一个审批人集合 |
| 部门或渠道 | 对应范围的搜索多选；部门可明确包含下级 | 非公司通用时必填；只选本公司允许使用的范围 |
| 审批人员 | 从现有员工搜索多选 | 须具备有效任职及相应审批授权；不新建一份通讯录 |
| 生效日期与结束日期 | 日期选择，结束日期可空 | 生效日期必填；时间倒置、同职责同范围同期间冲突阻断保存 |
| 调整原因 | 多行文本 | 修改已使用安排必填；保留修改前后人员和范围 |

底部为“取消／保存”。新公司或范围中没有合格人员时，保留已填内容并定位缺口，不能用离职人员补齐。多人是否全部同意或一人同意在流程节点设置，人员安排不重复维护第二套办理方式。

代办沿用既有抽屉，继续填写原人员、代办人员、公司、事项、日期和原因；代办不能扩大原审批职责和查看范围。

### 3 职责目录与取人依据

财务业务伙伴，以下简称财务BP，是负责某一业务范围财务审核的人员。审批职责决定由谁处理；账号角色决定能看什么、能做什么，二者分别校验。

| 职责 | 建议取人依据 | 不可替代的关系 |
|---|---|---|
| 部门经理 | 申请人本次任职部门负责人，仍用既有部门取人方式 | 不能一律取个人直属上级 |
| 负责计调 | 本订单对应团期、项目或已登记申请上的负责计调 | 产品负责人、派团领队均不能代替 |
| 渠道负责人 | 订单所属渠道的内部职责安排 | 分销商档案的外部联系人不能代替 |
| 渠道总监 | 订单所属渠道的内部职责安排，单独职责 | 不能默认等于渠道负责人 |
| 产品总监 | 本产品所属产品部门的职责安排 | 不能默认等于产品经办人或申请人上级 |
| 供应商管理审核 | 公司指定的供应商管理职责人员 | 不选择外部供应商账号 |
| 核算会计 | 对应公司及已安排的业务部门或产品部门 | 不与财务BP、财务经理合并为财务审核 |
| 财务BP | 对应公司及其负责的部门、产品部门或渠道 | 节点明确使用哪种负责范围，不同时混取不同依据 |
| 财务经理 | 对应公司职责安排 | 不通过猜组织层级找人 |
| 总经理 | 对应公司职责安排 | 法人代表不能自动代替总经理 |
| 开票审核人员 | 公司发票审核职责，如公司确有独立审核环节 | 开票专员实际执行开票仍由财务办理权限控制 |

保留原合同审核、法务审核、公司负责人、业务审核、组织审核等已使用职责。原“财务审核／财务负责人”的已发布模板不自动转换为核算会计、财务BP或财务经理；管理员修订时明确选择。

负责计调优先使用业务单据上的明确人员，不在审批人员页重复维护“每个团的计调”。单据未提供负责计调时显示具体缺项，不能自动改用部门负责人。一个申请覆盖多个团期、产品部门或计调时，先列明涉及范围；本期要求明确是否拆分申请或配置会签，未确定前不选第一人代替全部责任人。

### 4 匹配和人员变动

职责节点只采用一条有效安排。指定范围命中后，使用该安排中的人员；没有命中时，仅在节点明确允许“采用公司通用安排”且通用安排有效时采用，否则暂停。命中两条有效的专用安排属于配置冲突，不按第一条或多人合并处理。

公司通用与指定范围可以共存，但必须在节点中明确通用安排的使用方式。部门父子范围重叠默认阻止重复安排；若需要子部门例外，缩小原安排范围后单独设置，不增加隐含层级优先级。

每个职责节点显示公司取自哪份业务资料：产品总监通常使用产品所属公司，渠道职责通常使用销售责任公司，财务职责按付款、退款、核算等事项的责任公司。资料中只有一个“公司”时，不推断其他公司。跨公司参与还需对应授权；不能因同属集团或人员在另一公司任职就直接放行。

申请提交时保留采用的人员与安排依据。在途人员离职、任职结束或权限失效时暂停并交接，不因新安排生效静默改写已完成的审批。正式多公司授权和在途交接规则保留第十节确认范围，原型使用明确授权样例演示。

## 四 模板编辑交互

### 1 设置适用范围和触发条件

流程顶部现有“申请人”卡片实际维护模板名、场景、公司及适用部门。建议改为“适用范围”，点击“设置适用范围”抽屉；申请人由实际单据带入，不能用此卡片冒充已经配置了谁可以发起。

抽屉依次维护模板名称、业务场景、责任公司和适用部门。申请权限继续由角色及业务入口控制。普通业务仍可按公司及部门确定模板；同一场景、公司和部门范围不允许同时发布两份互相竞争的模板，渠道、款项性质等差异优先放在模板内分支。

在审批规则页增加“发起条件”，选项为“本事项均需审批”或“符合条件时审批”。仅开放该业务确有来源的字段；金额、人员和业务状态不能由普通申请人在审批页重填。已明确免审的情况记录“无需本项审批”及规则依据，不生成假同意记录。

合同收款例外的是否触发由销售签约条件判断，模板引用“收款要求是否达标／是否允许例外”结果，不再维护另一份比例。结算价变更以原价和申请价比较判断是否发生变化；不改变结算价时不发起该事项，优惠和其他应收变更单独判断。

免审只作用于当前事项。默认分支仍需有审批安排，不能在“其他情况”中放一个空流程绕过审核。新增免审规则必须带公司确认依据；政策未确认可存草稿和试跑，不能发布为正式适用规则。

### 2 设置审批人

保留现有选人方式，将“公司审批人员”扩展为“按审批职责”。新增明确的单据负责人选项，仅在事项已经提供对应人员时显示。

| 选择方式 | 抽屉填写项 | 示例 |
|---|---|---|
| 指定成员 | 有效员工、多人方式 | 特定事项指定两名审核人 |
| 指定上级或连续多级上级 | 现有层级、任职及终点 | 申请人直属上级 |
| 指定部门负责人或连续多级部门负责人 | 起始部门、层级、同层方式、缺人处理 | 申请人本次任职部门经理 |
| 按审批职责 | 职责、取人公司依据、负责范围依据、是否允许公司通用安排、多人方式 | 产品所属公司＋产品总监＋本产品部门 |
| 单据负责人 | 负责人类型只读、必要时明确业务范围 | 本订单负责计调 |

节点名称默认采用具体职责，例如“核算会计”，可编辑为业务名称，但改名不改变取人。流程卡片显示职责或已指定姓名及多人方式；完整取人依据在抽屉，实际人员在试跑和申请详情。预设职责不能默认为当前操作管理员。

申请人也是审批人时维持既有自审拦截；“计调发起后还需计调确认”不能未经制度确认就自动跳过。试跑应明确出现冲突的位置及处理责任。可由公司安排其他有权计调确认，或待确认提交是否已经完成该项确认，不能用通用免重复规则代替自审政策。

### 3 条件抽屉

沿用“条件名称、全部满足／任一满足、判断条件”结构，字段选择后联动控件：

| 字段性质 | 可用判断 | 值控件 |
|---|---|---|
| 金额 | 大于、大于等于、小于、小于等于、等于、区间 | 金额输入及币种；同一笔条件须采用明确的原币或已确认折算依据 |
| 比例 | 同上 | 百分比；原金额为零或比例依据缺失时不计算 |
| 业务类型 | 属于、不属于 | 该事项允许值的多选，如线上／线下支付 |
| 业务结果 | 是、否或明确状态 | 只读来源可提供的选项，如已回团／未回团；未知单独处理 |
| 结算阶段 | 首次结算、二次结算 | 单选或多选，来自原结算记录 |

条件字段缺失、未知或有冲突时进入“资料待补／待核对”，不按“不满足”进入默认分支。金额减少使用“调整方向＋差额金额”表达；按差额绝对值比较时名称明确写出，审批依据仍展示正负变化，不能丢失方向。

分支顺序沿用当前可调整方式；明显重叠、相同条件、区间端点冲突阻断发布。不同币种不能直接比较，跨币种但未提供确认汇率时暂停。首期只提供固定业务字段及标准判断，不开放业务管理员编写计算公式或程序表达式。

### 4 审批内容与办理规则

审批内容继续采用一次列出、直接勾选。每个事项的原单、公司、申请人、本次金额或变化、原因及关键确认结果为必显；隐藏可选字段不得隐藏本次发生变化的内容。付款、退款、合同、价格及结算分别使用自己的核对资料，不能仅展示泛称“业务依据”。

人员为空、离职、代办、重复人员、意见、签名、撤回、退回及转交继续使用现有配置。重复同人只能沿用本轮已经明确同意的结果；申请人提交不属于同意结果。退回重提清除本轮免重复依据，保留原记录。

## 五 业务场景与来源资料

下表是审批配置中的业务归类，序号对应公司原表。合并代表复用模板能力，不合并业务单据或资金性质。未确认事项只提供草稿。

| 原序号 | 配置事项及区别 | 必须带入的判断资料 | 公司和人员来源 | 审批后的承接 |
|---|---|---|---|---|
| 1 | 合同收款例外；其他首次签约审核保持 | 本合同范围、签约公司、渠道、适用收款要求、已核实收款、未达标金额、政策依据 | 签约公司及本单内部渠道负责人；跨公司授权另核对 | 返回合同准备，按批准范围继续办理 |
| 2 | 付款退回 | 原成功付款、付款公司、收款方、原因、本次金额、已退及处理中金额 | 原付款责任公司及对应财务BP | 付款管理继续核对实际到账 |
| 3、10 | 客户退款；线上与线下为条件分支 | 原收款明细及方式、退款分配、原路情况、订单渠道、产品部门、计调、扣损和金额 | 退款责任公司；本单计调、内部渠道和产品职责、财务BP；线下加总经理 | 财务退款执行 |
| 4 | 预付款退回 | 原预付与实际付款、供应商、已冲抵、可退余额、本次退回 | 原预付／付款责任公司及财务BP | 预付退回及资金到账核对 |
| 5、6 | 付款申请；预付与普通付款分别显示资料 | 申请性质、付款公司、供应商、原成本或预付依据、申请金额、产品部门 | 供应商管理审核→产品总监→核算会计→财务BP→财务经理→总经理 | 财务付款复核和执行，现行入口保持 |
| 7 | 领队费用申请；借款、报销、补付分开 | 领队、团期、费用性质、原借款、报销金额、本次需付或需退金额 | 对应公司核算会计→财务BP→总经理 | 财务办理；报销额不直接等同新增付款额 |
| 8 | 开票申请；预开票与普通开票分开 | 开票公司、购买方、税号、订单、申请金额、收款核对及开票资料 | 核算会计；开票专员是否另审核待确认 | 财务发票办理，结果为成功或失败等实际状态 |
| 9 | 订单结算价变更 | 原／新供应商结算价、变化、实际回团结果、供应商、产品部门及原因 | 回团后产品总监内部审批；回团前无该内部节点；两者均需外部供应商确认 | 原订单／供应商确认流程，未确认时不替换原价 |
| 11 | 结算确认；首结与二结分开 | 原结算版本、团期、收入及成本核对、本次调整明细、差额与原因 | 产品总监→核算会计→财务BP→总经理 | 原业务结算或结算调整，不覆盖原确认记录 |
| 12 | 订单转款 | 原收款、转出／转入订单、客户、公司、币种、可转余额与本次金额 | 对应核算责任公司核算会计；跨公司规则待确认 | 转款核销办理，不产生虚构的新收款 |
| 13 | 预付转款 | 原预付、转出／转入团、供应商、公司、币种、可用余额 | 对应核算责任公司核算会计 | 原预付分配／转款办理 |
| 14 | 单团合同审核；与合同归档分开 | 单团项目、本次合同完整内容及版本、公司、计调、客户与金额 | 申请人部门经理→项目计调→核算会计 | 合同准备／签署；已有合同另走归档 |
| 15 | 订单优惠 | 原对客价、优惠后价、优惠金额及比例、承担方、计调和产品部门 | 销售部门经理→本单计调→产品总监 | 原订单关联本次申请，核对所需职责和批准范围后采用；未覆盖的应收审核仍保留 |

订单渠道以该订单的销售渠道及负责组织为依据，不以付款方式、登录部门或外部联系人推断。付款方式以本次退款所关联的原收款明细为依据，不因订单来自电商就认定全部款项都是线上支付。

回团状态使用已经确认的实际履约完成结果，不以计划回团日期早于今天代替。单项服务、活动和分次履约的对应完成判断沿用来源业务；无法明确时保留待核对。

公司责任资料应能解释签约、销售、产品、付款、退款和核算各自归属。只有部门资料不能替代这些公司；本期不创建虚构公司，也不因模板需要字段而改变原业务责任。

## 六 合同收款条件

沿用集团基础参数中的销售签约条件，扩展适用渠道。合同规则页面仍主要决定采用什么合同模板，不在合同规则、审批规则两处各维护一次收款比例。

| 字段 | 设计 |
|---|---|
| 适用范围 | 签约公司、现有产品条件、销售渠道；公司通用与专用规则的采用关系必须明确 |
| 收款要求 | 不设收款前置要求、按订单付款节点、按确认比例；保留现有先签后收的业务含义 |
| 比例与金额依据 | 选择按比例时填写比例，并明确以订单金额还是本份合同金额为依据；分签不可重复占用同一笔收款 |
| 限制环节 | 按已确认制度选择生成正式合同或发起签署；未确认时不默认拦截其中一个 |
| 未达标处理 | 暂不可办理，或允许申请例外审批；两者择一 |
| 例外审批流程 | 仅允许例外时选择对应合同收款例外流程；采用内部渠道负责人职责 |
| 制度依据与生效期间 | 正式规则必填；修订保留原依据和使用记录 |

比例测试可使用“本份金额10,000元、要求30%”的独立样例：确认收款2,999元未达标，3,000元达标，3,001元达标。该数值仅测试边界，不是公司已批准的比例。

收款未认定、金额范围不清、退款后有效收款不明、分签未分配或币种不可比较时，不输出达标结论。关闭收款前置要求只取消该项收款例外审核，合同内容、单团合同等其他已配置审核继续判断。

收款要求变化或合同金额／范围修改后，旧例外批准不能无条件沿用。审批记录绑定批准时金额、收款情况、合同版本及范围，变更后回原业务重新核对，必要时重新申请。

## 七 四类代表流程

以下为设计核对案例，尚不是已通过的页面验收。姓名与金额均为独立原型样例；实际审批职责人员仍由公司安排。

### 1 六级付款

计调提交后，依次进入供应商管理审核、产品总监、核算会计、财务BP、财务经理、总经理。申请金额大小不擅自减少公司提供的节点。预付与普通付款可共用该路径，但核对依据不同。

| 核对情况 | 预期结果 |
|---|---|
| 同一计调分别提交欧洲产品和邮轮产品付款 | 产品总监及按产品安排的财务BP随业务变化，其他公司职责按安排采用 |
| 前五节点完成，总经理未处理 | 整单仍审批中，不能进入已批待付 |
| 会计与财务BP为同一人 | 按模板明确的重复审批规则处理，保留两项职责及采用依据 |
| 某职责无人或人员已失效 | 暂停并指出缺少哪家公司、哪一范围、哪项职责 |
| 最后节点批准 | 显示已通过及财务承接入口，实际付款状态保持待办理 |

### 2 线上和线下退款

销售或计调提交后，按原收款明细判断路径。线上：计调→渠道总监→产品总监→财务BP；线下：在上述路径后增加总经理。

| 核对情况 | 预期结果 |
|---|---|
| 同一电商订单包含一笔线上、一笔线下收款 | 展示本次退款分配；不按电商标签整体走线上流程 |
| 本次仅退明确的一笔线上原款 | 采用线上路径并保留原款依据 |
| 本次跨线上与线下原款 | 按公司确认的混合支付规则办理；规则未定时提示待确认，不自动取较短或较长路径 |
| 销售发起且订单计调明确 | 先到本单计调，再到本单渠道和产品职责人员 |
| 发起计调也是当前计调审批人 | 自审冲突显式提示，不能静默跳过；按已确认替代人或提交确认规则处理 |
| 非原路退款或原支付商户停用 | 保留异常及原款，不用普通线上分支直接放行 |

### 3 回团前后结算价变更

| 结算价是否变化 | 实际回团结果 | 内部审批 | 外部确认与后续 |
|---|---|---|---|
| 无变化 | 任意 | 不发起结算价变更审批；优惠、应收变更分别判断 | 不因该项免审就替换其他待核对结果 |
| 有变化 | 明确未回团 | 无产品总监这一内部节点 | 原业务进入待供应商确认，确认本次价格后继续 |
| 有变化 | 明确已回团 | 产品总监 | 内部通过后仍待供应商确认本次价格 |
| 有变化 | 未确认或冲突 | 暂不选择前后路径 | 来源页补充实际完成依据 |

供应商确认记录单独保留本次价格、版本、确认方、日期及结果。拒绝时回计调处理，不能标成内部审批拒绝；内部退回后改价，供应商此前对旧价格的确认不能替新价格生效。若一次调整同时包含优惠和供应商结算价变化，两项判断各自留结果，不默认合并或漏掉其中一项。

原型可以在来源处理区域演示供应商接受／拒绝及明确的供应商入口，不把外部供应商放进内部员工选人列表，也不要求真实供应商账号联调。

### 4 合同收款例外

先匹配本次签约公司、产品条件及渠道政策，确认本份适用的收款范围，再判断是否达标。达到要求按正常合同流程继续；未达到且允许例外时送内部渠道负责人；不允许例外则留在合同准备补足条件。

| 核对情况 | 预期结果 |
|---|---|
| 同渠道金额低于、等于、高于阈值 | 边界判断与批准制度一致，等于按达到要求处理 |
| 相同订单金额但渠道不同 | 采用各渠道已确认规则，无专用规则时按明确允许的公司通用安排处理 |
| 例外批准后变更合同金额或覆盖游客 | 重新核对适用范围，原例外批准不自动覆盖新内容 |
| 明确不设收款前置要求 | 不触发收款例外，其他合同审核仍生效 |
| 规则未确认或收款资料不完整 | 不伪装未达标或免审，显示待确认／资料待补 |

## 八 申请和审批办理

### 1 提交前核对

来源抽屉先显示当前单据及金额／版本，再显示本次所需事项、采用流程和人员。无需本项审批时显示依据，仍保留其他审批或外部确认要求。此处不能修改审批人或自行选择免审；业务资料变更后重新计算本次路径。

同一来源版本重复点击提交只保留一份当前申请。提交后来源资料按当前原型范围锁定，修改通过撤回或退回重提。审核人从审批详情返回来源查看完整资料，不直接在审批页改订单金额、合同正文或付款金额。

### 2 当前节点与整单状态

申请主状态沿用审批中、已退回、已通过、已拒绝、已撤回；人员异常作为审批中记录的异常原因。待我审批只显示当前实际有权处理的任务，抄送视图只读。

全部同意、或签、依次审批按当前节点规则结束，只有最后必要节点完成才能整单通过。未来节点无权提前办理；节点重复提交、版本不符、人员失效均拒绝处理。

详情保持业务摘要、核对资料、审批流程、处理记录。底部只放同意、退回补充、拒绝及当前允许的动作。付款通过后显示待财务办理；合同例外通过后回合同准备；供应商确认不使用内部同意按钮代签。

### 3 版本和退回重提

在途申请保留提交时流程版本、业务内容及审批记录；发布新模板不改在途。停用模板只阻止新申请继续采用，不撤销旧记录。

退回后修改金额、公司、渠道、产品部门、回团结果等会影响路径的内容，重提按当时有效规则重新匹配，形成新一轮记录。前一轮意见保留但不代替新一轮批准。若原版本已停用且无新流程，重提明确报缺流程，不能沿用旧模板静默放行。

此处修订现有模拟办理中“重提沿用旧模板副本”的限制；新规则实现时必须同步验证配置端模拟与日常办理，不能只改其中一处。

## 九 分步实施与验收

本次为审批扩展，原财务报表8批保持原验收状态。后续按下列三个边界清楚的步骤实施，每步包含必要来源核对、页面、规则及实际浏览器验收；不以文档中的拟验收场景当作已通过。

| 步骤 | 具体范围 | 完成条件 |
|---|---|---|
| 第1步 配置和试跑 | 两页签列表及职责范围抽屉；15场景目录和审批资料；职责／单据人员取人；真实业务条件、明确免审；合同签约条件；试跑及模拟办理 | 15场景均可配置对应草稿，四代表流程能显示实际路径；缺人、缺字段、冲突、免审和政策待确认均有可操作表达；桌面及窄屏通过 |
| 第2步 四类代表业务办理 | 付款、客户退款、订单结算价变更、合同收款例外的原入口及审批详情 | 采用发布版本、逐级办理、退回重提、撤回及异常交接；供应商确认、实际付款、合同签署分开；原直接业务回归通过 |
| 第3步 其余事项覆盖和收尾 | 付款退回、预付退回、领队、开票、结算、两类转款、单团合同及优惠直接入口 | 15项逐项有来源、资料、人员、正常／异常及下一步证据；既有合同、组织、会奖路径按真实改动范围回归，未确认政策单独交接 |

第1步不会因为正式人员或阈值未提供而停下：使用标明的样例完成配置及试跑，正式规则仍为待确认草稿。第2／3步仅在原页面及直接入口表达，不恢复已撤回的独立履约付款申请类型改造，不建设跨模块资金自动回写。

| 验23 | 单团签前审核与已有合同归档 | 两类目的、审批依据及后续入口不同 |
| 验24 | 发布新版本、停用和在途申请 | 新旧采用关系明确，在途不被覆盖 |
| 验25 | 退回修改关键资料后重提 | 重新匹配现行规则，上一轮批准不复用 |
| 验26 | 重复提交／重复同意、越级或过期链接 | 不重复生成有效申请，越权及版本错误被拦截 |
| 验27 | 无需本项审批与缺模板／缺人 | 三种结果不混用，免审有明确依据 |
| 验28 | 桌面、1024像素及窄屏 | 表格内部滚动、操作列定宽、短值不裁切，抽屉无无意义空白 |
| 验29 | 原产品、合同、组织及会奖流程 | 仅对本次真实影响的入口回归，既有独立事项不被误迁移 |

15项场景覆盖应同时对照第五节和上轮审评01—15，不能仅凭29个共同检查数量认定全部完成。

## 十 待确认事项与实施影响

| 事项 | 需要明确的业务决定 | 当前处理 |
|---|---|---|
| 各公司职责和负责范围 | 真实人员、产品部门、渠道及可覆盖公司；财务BP按哪种范围负责 | 完成功能和样例，实际配置保持待安排，不借外部联系人或财务通用岗替代 |
| 合同收款制度 | 限制生成还是发起签署；比例分母、有效收款、分签分配及是否允许例外 | 草稿及独立算例，未确认制度不能正式启用 |
| 计调发起又到计调节点 | 提交是否包含计调确认，还是需其他有权计调审核 | 维持自审拦截；页面给出可处理的人员异常 |
| 开票专员的职责 | 是核算会计审核后的开票办理人，还是另有批准责任 | 先分清审核和执行，两种流程可演示，正式安排待确认 |
| 混合支付和非原路退款 | 按原款拆分还是采用指定路径；非原路例外批准要求 | 不自行增加或减少总经理节点 |
| 跨公司及跨供应商转款 | 哪些情况允许、谁负责批准和核对 | 资料和异常可表达，无批准依据不放行 |
| 同申请多团多产品 | 拆分单据、会签或指定统筹人及金额范围 | 不自动选第一条；独立样例验证明确分工 |
| 再次结算及领队报销 | 再结审核全量还是差额；借款冲抵与补付的核对方式 | 原单、差额及资金结果分开，具体财务规则待确认 |

已确认的两项不再列为待确认：供应商为外部合作方；结算价未变不免除优惠审批。

正文已经说明业务事实、人员责任、金额含义及单据关系。本附录仅列开发实施位置，文件名与程序名称不进入业务界面。

| 业务变化 | 当前代码与拟修改位置 | 开发注意事项 |
|---|---|---|
| 职责与负责范围 | `shared/approval-config-model.js` 的职责安排及取人；`shared/approval-config.js` 的人员列表／抽屉 | 现有仅公司加职责，扩展范围、有效期间及唯一匹配；旧安排按原公司通用含义保留，不自动改职责 |
| 员工有效任职与权限 | `shared/approval-org-data.js`、`admin/employees.html`、`admin/org.html` | 复用当前资料；不因配置需要另建人员库，不改原组织层级 |
| 场景和审批核对资料 | `shared/approval-config-model.js` 的场景与内容目录 | 新场景按第五节补齐；价格调整现有产品职责不替代订单结算价变更；旧版本原样可读 |
| 条件与触发判断 | `shared/approval-config-model.js`、`shared/approval-config.js` | 扩展现有金额／幅度字段，增加明确类型；区分缺值、无需本项审批和需审批；不能简单删除最少审批节点校验 |
| 模板编辑入口与样式 | `admin/approval-template-edit.html`、`shared/approval-config.css`、`shared/approval-editor-page.css`、`scripts/build-approval-editor-css.cjs` | 保持三个页签及单一适用范围抽屉；专用样式按现有构建方式更新，无页面内联样式 |
| 签约收款要求 | `admin/params.html` 的现有合同设置入口、`shared/contract-admin-config-ui.js`、`shared/contract-settings-data.js`、`shared/contract-template-bridge.js` | 扩展销售签约条件；`admin/contract-rules.html` 继续负责合同选模，不再复制一份比例 |
| 模拟与日常逐级办理 | `shared/approval-rule-run.js`、`merchant/approval/approvals.html` | 公共办理规则区分节点完成与整单完成；重提重新匹配；不继续一次同意将整单通过 |
| 付款直接入口 | `merchant/tour/fulfillment-cost.html?view=payment`、`merchant/finance/finance-payment-apply.html` | `fulfillment-payment-apply.html` 当前为跳转壳；不恢复已撤回的独立申请页、类型区和批量拆单 |
| 退款与两类转款 | `merchant/sales/orders-after-sales.html`、`merchant/sales/orders-payment-transfer.html`、`merchant/finance/finance-refund-execute.html`、`merchant/finance/finance-transfer-records.html`、`merchant/finance/finance-prepayment-offset.html` | 以当前业务入口为准，区分申请和执行；审批原型不自动改资金余额 |
| 改价与优惠 | `merchant/sales/orders-detail.html`、`shared/order-amendment-model.js`、`shared/order-amendment-ui.js` | 原应收业务批准继续保留；优惠批准与本次应收变更关联，供应商结算价结果独立 |
| 合同日常办理 | `merchant/sales/contract-prepare.html`、`shared/contract-approval.js` | 保留正文／版本／签署平台及六类合同事项；配置承接不能降级原专属核对 |
| 会奖及其他专属事项 | `shared/mice-approval.js`、结算／开票等直接业务组件 | 当前项目审批另有来源版本和金额保护；先保持，后续仅按明确适配范围接入，不能强制换通用抽屉丢字段 |

新增职责、场景和示例模板按草稿进入，不替换正在使用的旧版本。配置端验证通过不等于日常入口已经接入；逐事项记录来源、采用版本、办理结果及直接承接证据。真实人员、正式制度和后端服务分别交接，原型完成状态据页面可操作范围认定。
