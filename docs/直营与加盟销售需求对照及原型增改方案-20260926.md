# 直营与加盟销售需求对照及原型增改方案

日期：2026-09-26。范围：两份销售需求申请单与当前原型的差异分析；本轮不修改业务页面。

## 一、结论与优先级

两份需求不是要求新建一套销售系统。现有原型已经覆盖产品预订、订单、合同、收款认款、售后、单项服务、门店预存和对账；主要增改在**已有页面的业务条件、提交结果和岗位交接**。

建议分三档处理：

| 等级 | 判断标准 | 本轮建议 |
|---|---|---|
| P0：首轮必须改 | 会把价格、资金或业务状态演示错，或使核心办理路径无法成立 | S01预订状态、S02优惠计价、S03意向承接、S04认款、S05退转款，共5组 |
| P1：对应业务场景必须补 | 基础销售可运行，但无法完整表达附件明确提出的场景 | S06首次预订附加服务、S07加盟资金与利润、S08跨地区及公司／门店权限，共3组；正式政策仍待确认 |
| P2：可加可不加 | 有人工或已有入口可完成，不影响当前原型主流程判断 | 抢单、智能分单、自动提醒、搜索增强、自动发券及营销工具等 |

P0/P1表示建议实施顺序，不表示本轮已获页面实施授权。每组只补当前页可操作示例、必要校验、状态结果和下一岗位；不建设后台、真实接口、跨页自动回写或全量规则引擎。

**不要重复新增：** 多人签约／一单多合同、未成年人等条件附件、扫码签署异常、企业线下合同归档、单房差、订单收费／免费服务变更、业务审批、计调服务确认、独立单项服务已有实现，保留并针对衔接复验。

**不要直接恢复：** 产品预订结算价查看已按2026-09-26用户要求撤回；系统内完整询价报价也在后续销售流程中排除。旧附件提出过，不代表本轮重新授权。

- 原始材料：`需求申请单-直营销售.pdf`、`需求申请单-加盟销售.pdf`各3页，均为扫描件；本轮渲染并查看全部6页。第1页为申请封面，第2—3页为会议正文。加盟封面与会议正文日期存在7月22日／23日差异，本轮不据此判断制度生效日期。

- 先盘点当前目录、`shared/nav-merchant.js`及销售、财务、营销、组织、门店入口，再对照当前页面和共享脚本；沿用历史清单的直01—23、加01—18编号方便核查，但重新判断当前覆盖情况。

- 本轮结论依据原始图片、源码和业务流程；**未进行新的全站浏览器点击验收，也未把历史验收记作本轮通过**。下文“验收”均为后续实施的标准，不是已修复结果。开始及收尾运行财务执行清单检查，该检查不替代业务验收。

## 四、5组首轮必须修改的页面

### S01｜P0：让门店预订的正常路径与异常路径都成立

**页面：** 销售中心→产品预订→[预订填写](../merchant/sales/booking.html)、[订单详情](../merchant/sales/orders-detail.html)；门店管理→[门店列表](../merchant/sales/store/index.html)、[门店详情](../merchant/sales/store/detail.html)仅配对核对规则示例。

**当前与缺口：** 已有草稿、待确认、预留、占位、确认和释放保护。`booking.html:2531`起把各门店的预留／占位小时数、释放方式和付款条件统一设为空；`submissionIssues`因此拦截门店预留／占位及直接确认。门店页面却有24／48小时的示例和已生效表达。缺口是示例条件不一致，不是应该删除保护或擅定24／48小时。

**最小修改：**

1. 预订页提供一组条件完整的演示门店和一组规则待确认门店；显示本单保留截止、资源是否确认、确认订单的付款条件。
2. 条件完整的示例允许预留／占位；资源、余位和付款条件均满足才可确认。待确认示例只能草稿／待确认并说明缺少哪项条件。
3. 订单详情沿用已有延期／释放／转确认保护；已收款、签约或出票不能一键按普通超时订单释放。

**验收：** 正常示例保留成功且显示截止和占用数量；余位不足、规则未定阻断；已收款超时不直接释放。只需要一致的原型示例，不要求门店配置真实跨页同步。

### S02｜P0：优惠采用有依据，成交价和承担金额分开

**页面：** [预订填写](../merchant/sales/booking.html)、[订单详情](../merchant/sales/orders-detail.html)；营销中心→[优惠券编辑](../merchant/marketing/coupon-edit.html)、[活动编辑](../merchant/marketing/campaign-edit.html)作为已有规则来源。

**当前与缺口：** 券配置已有产品／团期、渠道、领取资格、叠加及承担比例，不需新建营销模块。但`booking.html:1515`的优惠按“分销减800、参团满20000减1000、研学每生减300”等固定分支套用，没有核对应产品、日期、领取资格及互斥；订单详情还存在把全部优惠称为“本公司承担优惠”的表达。标准参团价目前不是任意可编辑，不应误报为销售可以随意改全部价格。

**最小修改：**

1. 当前页展示基础售价、产品早订价、营销减免、附加服务、客户应付；产品早订定价与营销券分栏说明，避免重复优惠。
2. 用少量明确示例表达可用券、不可用原因、叠加或互斥、非会员通用优惠；不符合条件不得默认扣款。
3. 明示本次优惠由谁承担及各方金额。比如优惠1000、总部70%／门店30%，分别700／300，不把1000全记门店负担。未定的收入和成本会计处理仍留待财务确认。
4. 销售要求额外优惠或改单价时，沿用已有订单业务审批；未批准前原价不变，不让财务认款页审批产品价格。

**验收：** 有效优惠按示例扣减；过期、错团期、资格不符不可用；互斥不重复；总部700＋门店300＝1000；拒绝价格申请后原应收不变。复用现有审批，不扩成新审批系统。

### S03｜P0：意向保存、转预订和已成单状态真实可演示

**页面：** [意向订单](../merchant/sales/orders-intent.html)、电销中心→[电销意向](../merchant/sales/call-center/intents.html)、[预订填写](../merchant/sales/booking.html)；[客户详情](../merchant/customer/detail.html)沿用已有历史入口。

**当前与缺口：** `orders-intent.html:1117`保存只检查客户、电话和需求主题，然后提示成功；人数、目的地、日期及预算未形成完整提交条件，当前列表也未新增本次意向。转预订只传类型，没有带客户需求。`call-center/intents.html:497`把跟进结果选为“转产品预订”直接记为“已转订单”。这些会误导销售和主管判断。

**最小修改：**

1. 必要资料包含客户／联系人、人数、目的地、出行时间、预算、来源和经办人；日期、预算确实未定时用明确“待定”表达，不能空值假装已收齐。
2. 保存后在当前页出现意向及其状态；转预订带入可复用的客户、人数和需求，不重复录入。只做当前操作所需的简单承接，不建设客户同步系统。
3. 进入预订只记“预订办理中”或保留意向阶段；有明确订单号才可显示已转订单，取消预订不能算成单。
4. 对旧“询价”入口按后续已确认范围收敛为需求记录／已确认项目承接；不趁本次恢复完整系统报价流程。

**验收：** 新意向保存可查；缺客户或人数不提交；转预订带入原资料；仅跳转或取消不出现已成单；老客户能引用既有资料，无需新建重复客户。

### S04｜P0：认款金额、付款人及财务职责必须核清

**页面：** 销售中心→[收款认款](../merchant/sales/payment-claim.html)，财务中心→[到账流水](../merchant/finance/receipts.html)、[认款复核](../merchant/finance/finance-matching.html)。

**当前与缺口：** 已有一笔款分多单、付款凭证和待复核页面。`payment-claim.html:862`只将差额标红，`:1038`提交直接关闭抽屉并提示成功，没有提交条件检查；任意上传文件还会固定选中同一条演示流水（`:1025`），容易被误解为已识别到账。财务复核仍有“生成补收应收”处理，和最新“业务改价经业务审批，财务只复核实收”职责需统一。

**最小修改：**

1. 选择原流水及可认余额，逐单分配；阻断空分配、负数、超过流水可用额、无效订单或主体不符。部分认款合法，剩余款保留待认，不能简单要求差额必须为0。
2. 第三方代付明确付款人、与客户关系及证明；金额或人员不匹配进入待补／待复核。
3. 提交后当前页出现本次申请和待复核状态，不能立刻成为已收。凭证上传只表示材料已上传，选择到账流水仍需人工确认；不需要真实识别或银企直连。
4. 财务可确认／退回／处理剩余款；涉及新增应收时交回原订单业务变更，不能在复核收款时直接决定额外销售金额。

**验收：** 可用10000分配6000＋3000后剩1000待认；分配11000、未选订单、负数均阻断；第三方付款可留依据送复核；退回保留原因；上传无关文件不显示已识别指定流水。

### S05｜P0：售后申请不能只提示成功，退转款不得越过原收款

**页面：** [订单详情](../merchant/sales/orders-detail.html)售后抽屉、[售后处理](../merchant/sales/orders-after-sales.html)、财务→[转款记录](../merchant/finance/finance-transfer-records.html)、[退款执行](../merchant/finance/finance-refund-execute.html)。

**当前与缺口：** 售后已有退改规则版本、扣损、计调确认和财务去向；并非没有售后模块。但订单详情退款金额仅有“不超过最大可退金额”占位提示，`:2384`通用提交处理直接关窗提示结果。优惠券编辑页已有“重算／整单恢复／失效／人工处理”选项，而订单详情`:2245`仍统一按退款占应收比例冲回优惠，没有采用本单具体券规则。转款页`:834`处理可直接把用户输入的金额存入并记“已核销”，未先核可转余额等数值条件。

**最小修改：**

1. 申请带原订单、原收款、已退／已转／申请中占用、本次可处理余额、原因和费用依据；提交后出现本页可查看的售后申请。
2. 改人数、改单价影响应收与实际退款分开；退订业务成立不等于钱已退。出团后或已结算的变化走调整，保留原记录。
3. 转款核原单余额、目标订单、客户或代付授权及收款公司；跨公司不能作为普通同公司转单直接核销，需单独确认流程。差价补收或余款处理给出明确去向。
4. 去掉无依据的通用按比例冲券结论；展示适用券规则及本次处理结果。政策未定时显示待确认，允许记录申请，禁止算成已确认退券／冲回金额。
5. 退款执行沿用原财务入口，复验原收款方式和账户、审批及失败处理；不在销售页假装已退款。

**验收：** 已收10000、已退2000、已转1000、申请占用1000，则本次最多可处理6000；申请7000阻断（已退、已转、占用须互不重复）。同客转款金额超限或目标无效不得核销；未定券规则不能自动按比例冲回。正常申请可查看，拒绝或撤回不改原实收。

## 七、待确认的政策：先保留业务位置，不写死规则

| 待确认事项 | 冲突／不确定性 | 对原型的处理 |
|---|---|---|
| 预留与占位期限、扣库存时点、付款锁位及保护 | 附件提出配置，但定金门槛未定；页面示例与预订条件不一致 | S01使用明确演示条件，不把24／48小时或某定金比例变成公司制度 |
| “退款原路原价”、券核销／返还及承担冲回 | 直营附件提出按原应收而非优惠后实付；现有财务流程要求受原实收可退余额约束，代码又使用通用比例冲回 | 原路退回是资金渠道；退款依据、实际退款额与优惠处理分开。绝不按标价无条件超实收退款；如存在补偿应单独确定业务依据及审批 |
| 加盟利润按出发确认、长线提前结算 | 加盟材料是倾向及讨论，尚非全公司批准政策 | 展示预计、待确认、已确认和调整；不要把出发自动转可支付余额 |
| 供应商尾款与门店利润自动拆分 | 涉及公司、供应商和门店不同结算关系 | 保留原采购／应付及门店对账，先核依据和责任，不模拟一笔自动付款替代三方确认 |
| 合伙人／店长审批额度及独立公司权限 | 天津／山西“可能独立”不能推导所有加盟门店都是法人公司；同品牌也不等于同收款方 | S08用明确示例；具体地区、公司资质、授权和审批条件待确认 |
| 早订价、优惠承担的收入／成本列示 | 会议讨论成本处理，当前规则也有分担示例 | 先让客户金额与承担金额相等可核；财务科目及期间确认另议 |

以上未定政策不阻止独立完成P0页面校验及P1角色表达，也不能被“待确认”替代整个已承诺功能。
