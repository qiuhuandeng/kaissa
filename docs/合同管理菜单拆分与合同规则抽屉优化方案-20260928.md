# 合同管理菜单拆分与合同规则抽屉优化方案

> 后续需求衔接（2026-09-28）：用户新增12301与第三方定制合同并用要求，本方案尚未实施的规则抽屉及匹配改造并入[多平台方案第1步](电子合同多平台协同与定制模板完善方案-20260928.md)。公司及产品条件选一份模板的核心保持，平台由模板确定；不新增销售自由切平台或重复平台路由规则。本条为计划更新，不表示下述待办已实施。

日期：2026-09-28。依据：用户要求集团端独立“合同管理”模块，将模板和规则两个Tab拆成菜单，并重新审视新增规则抽屉。

本轮菜单拆分已实施；下文抽屉、匹配规则及付款／审批分工为新建议，尚未修改原业务逻辑。它们不因菜单调整自动生效。

## 一、菜单与页面

集团admin独立一级模块“合同管理”，下设两个直接菜单：

- 合同模板：`admin/contract-templates.html`，维护正文、字段对应、附件、版本及发布。
- 合同规则：新增独立页面 `admin/contract-rules.html`，维护产品默认使用哪份模板。

系统配置中移除“合同设置”。两个列表不再用业务Tab切换，状态仍为各页下拉筛选。原集团 `contract-templates.html?tab=rules` 转到新规则页；模板详情和编辑返回模板列表，菜单归属同时跟随新模块。

商户销售中心的合同管理继续处理具体订单合同。12301接口配置继续在集团系统配置，维护连接、企业身份、授权和印章。两端同名“合同管理”按端口和职责区分，不搬动销售办理页。

## 二、规则的核心业务

**集团合同管理员配置：哪些签约公司，以哪些产品类型、旅游范围及必要条件经营的产品，默认使用哪一份合同模板。**

上游是组织档案的公司、产品分类与模板库；下游是产品的“沿用系统设置”和订单合同准备。日常任务是新增、调整、启停默认模板匹配，不是在每一条选模规则中重新配置销售流程。

公司指实际与客户签约的法人主体，不是产品所属公司、供应商或门店。当前“业务类型”选择的是参团游、邮轮、专列、自由行、研学、单项服务、MICE，建议改名“产品类型”，避免与自营、外采等经营方式混淆。自营／外采仅在确实影响合同文本且产品已有可靠分类时再作为条件，不默认新增必填项。

## 三、代码现状与问题

当前 `shared/contract-settings-ui.js` 的 `initRules` 抽屉同时要求签约公司、名称、业务、范围、客户类型、模板类别、省份、默认模板、草稿生成条件、内部审核、审批流程、付款条件、付款节点、起止日期、政策核对、负责人及确认依据。列表却主要展示付款条件，没有展示默认模板。

问题在于把“选用哪份模板”和“具体订单何时能签、如何审批”放进一个规则。模板类别又要求管理员先判断“全国示范／省级示范／推荐文本／企业自有”，它是模板属性，不是产品的独立业务事实，不宜用作普通管理员必须先填的条件。

## 四、建议的新增抽屉

标题仍为“新增合同规则”，按连续三个区域组织，不再增加Tab。

| 区域／字段 | 建议交互 | 业务含义 |
|---|---|---|
| 适用范围：签约公司 | 必填、可多选，选择已登记的法人公司 | 多家公司条件相同时可共用配置；按每家公司分别校验，不能默认包括未来新增公司 |
| 适用范围：产品类型 | 必填、单选，使用现有产品分类 | 一条规则对应一种产品类型，减少交叉组合；相似规则可复制后调整 |
| 适用范围：旅游范围 | 必填、单选，沿用产品现有分类 | 境内、出境等范围必须与模板适用范围相符 |
| 适用范围：签约对象 | 个人游客／企业，按场景提供合理预选 | 决定个人旅游文本还是企业服务文本；不按付款人或旅行社公司名称推断 |
| 采用模板：默认合同模板 | 必填，仅选一份；可查看正文和适用条件 | 候选需适用所有所选公司和本次产品条件，不能以任意一家适用就放行 |
| 采用模板：必要附加条件 | 按需展开地区、行程天数、服务形式 | 支持省级、一日游、包价旅游／代订代办差异；普通规则不显示无关项 |
| 生效设置：规则名称 | 按公司、类型、范围自动建议，可修改 | 便于列表识别，不作为程序匹配依据 |
| 生效设置：生效时间 | 默认立即生效、长期有效；需要时指定起止日期 | 控制新合同何时采用；选择日期不改变历史合同 |

模板类别、当前启用版本、维护人作为选择后的只读信息。规则维护人、操作时间进入记录，不让新增人再填一个“负责人”。抽屉底部使用“取消／保存草稿／保存并启用”；字段不完整可存草稿，启用前校验适用性和冲突。

附加条件不是任意表达式。只使用产品或订单已有、可判断的业务信息：

- 一日游模板自动要求行程为1天，不能套用于多日产品。
- 省级文本显示具体地区条件；按该文本已登记的适用依据核对，不能直接把公司注册省份当作产品适用省份。具体按出发地、服务地或其他条件判定，需要按采用文本逐项确认，未明确时标待确认。
- 自由行、单项服务确需区分包价旅游与代订代办时显示服务形式；不因产品名称包含“自由行”就自动使用代办合同。
- 选择模板带出其不可放宽的条件；管理员只能合理缩小适用范围，不能用规则突破模板或公司资格。

## 五、移出哪些字段，以及去哪里

| 当前字段 | 建议处理 | 原有要求如何承接 |
|---|---|---|
| 允许生成草稿 | 从选模抽屉移除 | 由订单状态和合同准备流程统一判断，不逐条模板规则重复定义 |
| 内部审核、审批流程 | 移出 | 归集团“部门组织 → 审批配置”的合同事项，按公司及业务条件确定审核；模板发布与具体合同审批分别保留 |
| 发起签署付款条件、订单付款节点 | 移出 | 建议在集团“系统配置 → 基础参数”增加“销售签约条件”配置区按公司维护；具体付款计划引用订单。该配置区当前不存在，属于后续迁移配套，不冒称已有 |
| 业务政策核对（演示）、政策确认依据 | 移出本抽屉 | 对应审批／付款政策的依据跟随其所属配置保存；模板选用变更保留操作记录，不再要求手选“已确认”才能完成普通选模 |
| 模板类别 | 改为选定模板后的只读属性 | 省级、全国、推荐文本等来自模板库，不要求新增规则重复分类 |
| 规则负责人 | 改为系统记录维护人 | 如需岗位权限，走已有后台角色及公司权限，不在每条规则重新指定 |

**移出不等于取消校验。** 实施时须连同现有审批／付款资料的承接一起调整；不能只隐藏输入框，却保留不可满足的旧必填，也不能删除字段后让具体合同默认免审或无付款条件。历史已提交合同继续保留当时依据，不用新配置覆盖。

公司能选用某份业务模板，与能否此刻通过12301发起是两个检查：选模规则不得扩大公司经营资格和模板适用范围；平台授权、印章及连接情况仍在接口配置和发起签署时检查，不把接口密码等搬回选模抽屉。

## 六、产品与规则如何配合

1. 产品选择“指定合同模板”：采用指定的一份，不再要求必须存在一条默认选模规则；仍检查实际公司、产品范围、模板启用及必要条件，审批和付款从各自配置判断。指定模板失效时明确提示，不静默改用默认模板。
2. 产品选择“沿用系统设置”：按实际签约公司和产品条件匹配。适用范围明确更窄的专用规则优先于包含它的通用规则，例如同公司境内参团游通用规则之下的具名地区一日游规则。
3. 同范围重复或交叉但无法确定优先的启用规则应阻止保存并列明冲突，不用“第一条”、最新创建或管理员手填优先级兜底。
4. 无匹配时提示缺少哪类规则；不自动使用出境模板、其他公司模板或同名模板。
5. 创建具体合同草稿时保留当时采用模板版本和匹配结果。后续调整规则或模板不覆盖已提交和已签文书；待修改草稿按既有显式更新和重新预览处理。

这里需要同步修正此前“指定产品也必须存在默认合同规则”的设计：默认选模规则负责提供默认模板，不能成为已明确指定模板的多余前提。原合同审核与付款控制继续有效，归独立配置承接。

## 七、规则列表同时调整

建议列：**规则名称｜签约公司｜适用产品条件｜默认合同模板｜生效时间｜状态｜操作**。移除主列中的签约付款条件，把模板名称及当前版本直接展示出来。省份、天数等作为适用条件的简洁辅助行，完整条件进抽屉。

筛选以公司、产品类型、旅游范围、状态、关键词为主。操作保留编辑、启用／停用，复制放更多；不再增加状态Tab或“资料缺口”主列。

示例仅说明匹配设计，不是正式公司政策：

| 签约公司 | 产品条件 | 默认模板 |
|---|---|---|
| 已获准的福建、北京公司 | 参团游＋境内＋个人游客 | 团队境内旅游合同 |
| 已获准出境经营的公司 | 参团游＋出境＋个人游客 | 团队出境旅游合同 |
| 获准公司 | 邮轮＋出境＋符合文本登记的地区条件 | 对应邮轮旅游合同 |
| 获准公司 | 研学＋境内 | 对应研学旅游合同 |
| 获准公司 | 参团游＋境内＋浙江文本适用条件＋1天 | 浙江省一日游合同 |

## 八、本轮边界及下一步

菜单本轮直接实施。抽屉、列表和匹配逻辑只交方案，没有改动现行审批、付款、产品和合同准备逻辑。下一步实施应作为同一个有界改造完成：规则抽屉与列表、按公司匹配和冲突检查、审批／签约付款条件迁移、产品指定与默认规则解耦、合同准备必要承接及回归；不扩展到门店、团期合同专用模块或真实12301接入。
