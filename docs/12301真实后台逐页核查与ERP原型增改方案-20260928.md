## 一、结论与本轮边界

**需要完善。现有原型已经有合同办理流程，但合同内容的来源、模板差异和多人签署仍不足以承接本次看到的12301后台。** 重点不是再增加几个状态，而是让销售能依据产品、团期和订单，准备一份内容齐全、签署关系明确、后续变更有依据的合同。

本次直接查看用户Chrome中已登录的[全国旅游监管服务平台电子合同后台](https://econtract.mr.mct.gov.cn/travel/index)，展开合同分类、模板填写步骤及部分条件选项，滚动长表单至后续条款和附件区域；再核对本地ERP页面、当前加载的共享脚本及对应业务文档，并查看浏览器中ERP合同模板编辑页。没有在真实后台保存草稿、提交审批、上传材料、发起签署或作废合同。

三类依据分别使用：

- **后台实见**：本次账户可见的页面、字段、选项、说明及列表状态。
- **ERP现状**：当前页面和实际加载脚本中已有的功能；旧版未加载脚本不作为现状能力。
- **建议／待核实**：根据业务承接提出的原型设计，以及账户权限、真实签署端或接口资料才能证明的事实。

不是所有内容都应填在线路页。正确分工是：**法务维护标准文本与可调整范围 → 产品维护可复用的服务及规则 → 计调确认本团实际安排 → 销售核对订单与客户选择 → 合同经办人完成本次文书 → 审批、各方签署 → 变更／售后和文件归档。** 这些动作不直接完成退款、收入确认或财务结算。

2026-09-24已验收的是通用配置、签约、审批、变更和归档流程。本次取得真实后台后发现的新差距列为下文C01—C10；旧验收继续保留，但不能据此认定已经覆盖各真实模板的全部合同内容。

### 2.4 多人签署的关键事实

后台游客列表每行有“签署”选择项；展开说明明确：**被选中的游客全部签署后合同才生效，作废也需要同时确认。** 这是本次后台说明的业务表达，不代表本次已经验证真实签署端或法律效力判断。

因此至少应区分：

| 内容 | 意义 |
|---|---|
| 合同覆盖游客 | 这份合同为哪些人提供服务 |
| 游客代表／联系人 | 联系及代表信息；可能不参团，不自动取得全部游客代理权 |
| 必要签署人 | 本份文书要求完成签署的实际人员 |
| 代表／监护／代理关系 | 实际签署人代表谁，凭什么材料 |
| 多人签一份合同 | 同一正文、金额和合同号，多个必要签署人分别完成 |
| 按人分别签合同 | 多份合同，分别有覆盖范围、金额和结果；平台是否支持批量创建需另核 |
| 作废／解除确认人 | 本次结束办理要求哪些人确认、各自是否完成，不能只有“各方已确认”一个总开关 |

代理人代表多人时平台发几个签署任务、未成年人如何认证、企业代表如何签、签署先后顺序及作废具体确认方式，本次没有真实操作证据，继续列为平台待核实项。

| 对接方式 | 接口配置已有“电子签署及备案／仅编号及备案”概念 | 办理界面尚未充分区分两种路径；不能在仅上传监管资料时演示成已在12301发起游客签署 |

## 四、合同要的信息应该放在哪里

| 合同内容 | 主要维护位置／角色 | 签约时如何采用 |
|---|---|---|
| 公司名称、许可证、经营范围、地址 | 集团组织架构／公司资料，组织管理员 | 读取实际签约公司；产品经营公司、销售公司、供应商不能互相替代 |
| 投诉电话、受理地区、地址、邮箱 | 公司签约资料，合同管理员 | 按模板带入，补齐所需项；不只存一句“客户服务中心” |
| 经办人、服务网点、签订地点 | 公司／门店资料及本次合同经办人 | 网点、经办人带入；本次签约地点补充确认 |
| 合同固定正文、不可抗力和违约基础条款 | 合同模板，法务／合同运营 | 获准版本只读使用；模板允许的参数才逐单确认 |
| 默认模板及允许选用范围 | 产品或具体方案，产品负责人；公司规则限制 | 用于推荐和过滤，不能突破公司资质、法务模板及门店权限 |
| 每日行程、交通餐住和服务标准 | 产品方案；团期实际安排由计调确认 | 合同取本单对应团期／服务的确认版本；未出具体房号不等于不能签约，按模板要求的标准判断 |
| 研学课程、课时、场所及费用分类 | 研学产品／营期，产品和计调 | 带入本营期课程及本单费用；不能仅以营费总额代替所需分项 |
| 邮轮港口、舱等、岸上安排及餐住 | 邮轮产品／航次；本单选舱在订单 | 航次给共同安排，订单给客户实际所选；不可把船司采购协议直接当对客条款 |
| 成团最低人数 | 产品可给默认值；本团实际门槛在团期 | 合同引用本团人数；总名额、当前报名数、最低成团人数是三个不同值 |
| 不成团通知及可提供方案 | 模板获准规则＋团期计调安排 | 合同展示可选项；客户对延期、改线、转社、解除分别确认，不能代为全部勾“同意” |
| 拼团／委托组团／地接社 | 产品组织方式给默认；本团实际旅行社由计调核对 | 合同填实际名称、许可证／联系等模板所需内容；客户同意仍在本份合同确认 |
| 保险名称、计划及可售条件 | 产品费用与服务说明，可引用现有保险服务资料 | 合同按本次委托购买／自购／放弃等选择记录；邮轮两类险分开，浙江按需人数／保费／保额 |
| 被保险人、保单及投保进度 | 订单保险服务与团期名单／资源执行 | 复用已有履约表达；合同选“委托购买”不能自动变“已投保” |
| 本单游客、证件、健康及分房需求 | 订单游客资料，销售维护 | 合同引用必要资料；联系人可不参团，游客代表和必要签署人另设 |
| 成交金额、成人儿童费用、导游费、支付约定 | 订单及已确认费用／收款安排 | 金额取本单，不取产品参考起价；约定付款时间不等于实际到账 |
| 游客解除费用、必要费用 | 公司获准条款＋产品退改规则＋本次确认 | 签前检查一致性，冲突需处理；售后使用已签版本并核对实际损失依据 |
| 旅行社违约、退款期限、特定不可抗力处理 | 法务模板默认及可调整参数 | 允许变动的值在合同里确认，超范围送审；不要求产品经理重写整段责任条文 |
| 争议解决方式及机构 | 法务／公司模板默认，合同确认 | 诉讼和仲裁按模板要求二选一，相关机构填写完整，不能以通用备注替代 |
| 购物、自费项目 | 产品方案已有清单；团期落实日期／时长 | 合同列本次安排及需签署的补充约定，明确无安排也可；不能只有上传附件名 |
| 其他约定 | 模板标准选用条款＋产品专项说明＋本单补充 | 显示来源及本次修改；有矛盾先审核，不能让自由文字覆盖固定条款和订单事实 |
| 签署方式、签署人、代表关系、同意结果 | 合同办理，销售／合同经办人 | 每份文书独立确认，不能配置在线路后直接当客户已同意 |

**采用规则不是“后填的永远覆盖前面的”。** 公司资格和模板固定条款是限制；产品给默认，团期给本团事实，订单给成交及人员事实，合同补本次客户选择。内容冲突应显示待核对及责任岗位，不能静默取最后一个值。

## 五、按菜单、按页面的增改清单

### C01 系统设置→合同模板：补成可实际准备合同的模板

页面：[合同模板列表](../merchant/sales/contract-templates.html)、[合同模板编辑](../merchant/sales/contract-template-edit.html)。使用人：法务／合同运营。

- 保留既有版本、审批、启停；补真实模板分类，区分全国／地区、境内／出境／赴台、一日游、邮轮、研学、代订代办。平台目录编号可记录，不能直接标成已获接口授权。
- 编辑页按“适用条件、合同内容、填写要求、版本发布”组织。每种模板配置自己的内容组、必填条件、默认值、可否逐单修改、需要谁确认、所需附件。
- 固定正文与逐单填写项分开。将保险、成团与不成团、解除必要费用、不可抗力、双方违约、争议、其他约定等按实际模板纳入；不再全部压进“业务补充约定”。
- 原四行平台字段对应保留为技术配置区，但增加业务内容来源核对表；原型不要求填写未知接口参数才能演示业务。
- 切换模板显示新增必填及不适用内容，保留已填草稿；不默默把不兼容的选项挪到另一模板。

验收：境内、邮轮、研学、代订代办的填写内容和必填明显不同；不能把境内争议选项序号直接用于邮轮；停用模板不改变历史已签文件。

### C02 集团配置→组织架构／接口配置；业务端→基础参数和门店销售设置

页面：[集团组织](../admin/org.html)、[接口配置](../admin/interface.html)、[基础参数](../merchant/system/business-params.html)、[门店详情](../merchant/sales/store/detail.html)。使用人：组织管理员、平台配置管理员、公司业务管理员。

- 公司签约资料补经营范围及对应资格、分社／服务网点关系，投诉联系资料按模板需要拆清楚；仍复用原公司资料，不在产品重建公司。
- 接口配置保留公司授权／用章，增加“当前采用的办理方式”：平台签署并监管处理、其他获准签署渠道完成后上传监管、待确认。账号能登录与接口已开通分别展示。
- 基础参数合同规则补旅游范围、模板类别／适用地区、客户类型，支持研学等既有业务；明确哪些合同方式已获准，哪些仅为原型场景。
- 门店选用公司允许的模板范围，不用一个门店默认模板覆盖所有产品。产品推荐与门店权限取共同可用范围，多条冲突须处理。

验收：没有出境经营资格的公司不能因为选中了“出境模板”而变可用；一店经营境内、邮轮时不被强制用同一模板；“仅监管上传”不出现12301发起游客签署的假结果。

### C03 产品中心→自营产品→产品编辑／方案：增加合同资料和模板关系

页面：[参团及自由行编辑](../merchant/product/product-self-edit.html)、[邮轮编辑](../merchant/product/product-cruise-edit.html)、[专列编辑](../merchant/product/product-train-edit.html)、[研学编辑](../merchant/product/product-study-edit.html)。使用人：产品负责人。

- 在现有费用规则／预订说明区域增加“合同约定”分区：允许选用模板、默认推荐模板、采用的约定版本、保险计划、成团说明及本产品专项约定。
- 对存在不同方案的产品，允许方案使用不同的服务和退改约定；产品给通用默认，方案的差异明确显示。
- 沿用现有退改阶梯、费用、购物、自费与每日行程；补缺失的合同需要值，例如购物／自费明确时长及本团日期换算、研学课程课时、邮轮岸上标准。不是复制一套相同表格。
- 产品选模板按业务内容及旅游范围判断，**专列不自动等于独立平台“专列模板”，自由行也不自动等于代订代办**；先判断销售的是包价旅游还是受托代办。
- 产品阶段只校验应由产品提供的资料，不要求提前填写游客、实际签署人、订单金额和投保结果。

验收：同一线路不同方案可有不同获准约定；产品准备好后，新合同能说明推荐模板和资料来源；修改产品规则不覆盖已签合同。

### C04 产品中心→外采产品／单项服务：补同样的对客承接

页面：[代理产品包装](../merchant/product/product-outsource-package.html)、[产品管理中的服务项目抽屉](../merchant/product/products.html)、[自由行出行日期](../merchant/product/product-free-travel-list.html)。使用人：外采产品负责人、服务产品负责人。

- 外采包装补我方对客合同的可用模板和推荐模板，引用供应商确认行程和规则，同时区分实际组团／地接旅行社与我方签约公司。
- 供应商扣损与我方对客扣费分开；现有“对客不得宽于供应商”提示不能代替对客合同适用性审查。差异可作为风险和审批内容，不能机械覆盖已签约定。
- 单项服务抽屉按机票／酒店／用车／导游／签证／其他服务维护可复用规格、办理条件、费用说明和可用模板；具体日期数量价格仍在本单。
- 自由行日期页仅提供本次套餐、服务组成及确认结果，不另放全套法务条款；保险加购选项不等于投保同意和实际出单。

验收：酒店代订只显示相关服务约定；签证能承接资料期限；外采合同里的旅行社角色明确，采购成本不进入游客合同价。

### C05 履约中心→团期管控→新建／团期详情：确认本团合同资料

页面：[新建团期](../merchant/tour/team-create.html)、[团期详情](../merchant/tour/schedules-detail.html)。使用人：计调／团控。

- 新建及详情复用现有最低成团人数；补适用模板需要的“不受人数限制”选项、通知安排及本团不成团可提供方案。研学产品已有值作为默认，不把它与团期实际值混为同一个字段。
- 在现有“行程／服务标准”区维护本团日期时间地点、实际组织／接待旅行社、邮轮舱等／岸上标准、研学课程等共同资料，显示合同采用版本。
- 保险执行仍留名单／资源办理；客户购买意愿来自合同或订单服务资料。投保待办、实际保单与合同委托分开。
- 本团行程、成团约定或服务标准修改后，显示受影响的已签订单和需合同变更的内容；原型只表达处理入口，不要求自动回写合同。
- 不成团实际发生时由计调确认可提供方案，销售逐单确认客户决定，再进入订单售后和合同变更／解除；不能因线路上写了“同意转团”就自动全团转走。

验收：名额30、最低成团16、已报12能各自表达；已签后修改行程显示差异，旧合同不变；合同委托买保险但尚未出单时仍显示待投保。

### C06 销售中心→订单管理→订单详情：补来源核对，不另建签约表单

页面：[新建订单](../merchant/sales/booking.html)、[订单详情](../merchant/sales/orders-detail.html)。使用人：销售顾问。

- 新建订单只采集成交所需联系人、游客、费用及选购服务；可后补的合同专属约定放合同准备，避免下单时填整份长合同。
- 订单详情“合同”区增加采用的模板／推荐来源、服务及退改版本、合同资料缺项；显示哪类内容交产品、计调或销售处理。
- 游客资料补模板确需的代表是否参团、单位委托资料、紧急联系人、健康／分房等；已有字段引用，签署人及授权继续在合同草稿主入口维护。
- 本单费用按已确认明细提供总额、成人儿童、导游费及必要服务分项；支付约定与实收分开。保险选择如涉及新增费用，先走本单服务／金额确认。
- 合同结果分别显示覆盖游客人数、必要签署方完成数、合同份数、我方签章及监管结果；不因所有游客资料齐全就显示全部签完。

验收：3人被合同覆盖、仅2名获准必要签署人时，能显示“覆盖3人、签署1/2”；未参团联系人不会增加游客人数或合同金额。

### C07 销售中心→合同管理：补“合同准备”二级办理页

入口：[现有合同管理](../merchant/sales/contracts.html)。**建议新增一个无独立菜单的二级页** `merchant/sales/contract-prepare.html`，承接现有长编辑抽屉；本轮仅提出，尚未创建。使用人：销售／合同经办人。

由原“准备合同／编辑”进入这个唯一办理入口，列表继续负责识别状态及处理当前合同，签署查询等轻量动作保留原抽屉。二级页分四步：

1. **合同与服务**：本单公司、模板、代表；行程及服务、组织接待旅行社、费用与付款，显示来源和缺项。
2. **游客与签署**：覆盖名单、必要签署人、代表／监护／代理关系及材料。
3. **本次约定**：按模板显示保险、成团与不成团、拼团、解除费用、不可抗力、违约、争议、其他约定；购物及自费按模板承接。
4. **预览与提交**：完整正文、名单、费用、行程及适用补充材料；缺项可返回对应分区，提交原审批流程。

通用固定条款只读，模板允许的参数可填，改变订单金额／游客／日期须回来源确认。客户选择必须有明确结果，尚未确认不能自动用“同意”默认通过。

内容、附件要求随模板变化；通用附件、系统生成的行程／费用材料、代签授权分别归类。支持格式和数量按办理渠道配置，不能把ERP现有PDF／图片／TXT、20MB规则当成12301已核实限制，也不简单把全部文件压为3份。

验收：不依靠“见附件／以正式模板为准”一句话掩盖缺失字段；邮轮能完整核对必要费用、不可抗力、违约、争议，代订代办不会出现不适用的成团必填项。

### C08 合同管理→签署进度／撤销解除：补真正的多人办理

页面：仍在[合同管理](../merchant/sales/contracts.html)现有签署与结束办理抽屉内，不新增菜单。

- 覆盖游客与必要签署人分别选择；必要签署清单列出实际签署人、代表哪些游客、关系及材料、核验结果、签署结果和时间。
- 合同代表签署、多名必要签署人签同一份、按人生成多份分别表达。按人分签沿用已确认分配金额，不能平均拆价；代表多人不重复计算合同金额。
- 只有本份全部必要签署及我方签章完成才标记已签署。未选为签署人的游客仍可属于合同覆盖范围，不能据此判漏签。
- 补正常部分完成、身份失败、拒签／过期／入口失效场景；它们是否为平台原生状态待接口核实，原型先清楚表达待处理原因。链接失效不删除已有签名。
- 撤销／解除办理增加逐方确认表，显示待确认、同意、不同意及时间；内部通过后仍待这些结果。部分同意、不同意或超时不直接改成已解除。
- 平台“作废”与本地撤销／业务解除分别对应，保留实际平台结果。部分游客退订，先判断整份多人合同需要变更还是解除重签，不能只把这个人的名字和签名删除。

验收：3游客由2名必要签署人完成一份合同；一位监护人代表2名儿童有明确覆盖和授权；多人签署完成后作废只有1人确认，原合同仍保留；按人分签缺口补签不影响其他已签合同。

### C09 审批中心→合同审批；合同管理→预览与变更；销售→售后

页面：[审批中心](../merchant/approval/approvals.html)、[合同管理](../merchant/sales/contracts.html)、[订单售后](../merchant/sales/orders-after-sales.html)。使用人：审批人、合同经办人、售后经办人。

- 预览、审批、签后文件要表达同一份内容，包含真实选用的条款、名单和附件；更换模板、修改保险／成团／违约／争议等约定后重新预览，需审批的重新送审。
- 变更对比从金额和一句服务描述扩展到本次改变的具体约定：行程、人员、保险、成团、费用、争议等；同时保留原模板和原文件版本。
- 售后核对已签主合同及有效补充协议中的退改条款，不能改用当前产品的新退改版本；供应商扣损是费用依据之一，不自动等于可向游客收取金额。
- 只调整客户选择而未改金额也可能需要补充协议；合同解除、客户退款、资源释放分别办理并在详情关联。

验收：原合同按A退改规则签署后产品改B，售后仍能查A；30,000元合同变更某项无金额约定，不重复新增30,000元成交；审批看到的内容与本次提交预览一致。

### C10 接口配置→对接记录；合同详情→签署与监管：补办理路径和状态解释

页面：[接口配置](../admin/interface.html)、[合同管理](../merchant/sales/contracts.html)。使用人：平台配置管理员、合同经办人。

- 保留ERP内部状态；同时保留实际平台来源、原状态和核对时间。平台草稿／待审核／签署中／已签署／已作废不能用一个“成功”统推已完成。
- 平台签署路径：准备、内部审批、向签署渠道发起、各方签署、监管及文件分别核对。监管上传路径：先有获准渠道的真实签署证明，再上传监管；不制造12301签署短信或签署入口。
- 已有对接合同应支持按实际签约公司、外部编号和订单关联核对；匹配不唯一时待确认，不能仅按姓名或手机号自动合并。历史导入可先只读，不要求本轮建设迁移服务。
- 超时先核对原申请，明确未受理再修正重提；已签但监管失败、文件缺失分别处理，保留已有签署事实。

验收：监管上传失败不倒退已签状态；同一外部记录重复核对不多出一份合同；办理方式未确认时可以准备原型资料，但不宣称真实授权已开通。

## 六、暂不作为本次签约主流程必改的部分

1. **不新增独立保险管理菜单。** 先补产品保险计划、合同选择和现有订单／团期投保承接。真实保险接口、理赔系统不在本次范围。
2. **不照搬12301产品库和出团通知模块。** ERP已有产品与团期出团资料；合同依据及版本关联补清楚即可。真实平台通知后半段因无已签合同未验，列为后续平台核实。
3. **不把同业4种合同塞进销售游客合同。** 已有[集团供应商详情](../admin/supplier-detail.html)、[集团协议模板](../admin/supplier-contract-templates.html)、[业务端供应商详情](../merchant/resource/supplier-detail.html)可复用；是否把具体同业采购／接待合同纳入12301签署，另定业务范围，不阻塞对客合同原型。
4. **评价、概览统计与更新日志不另建ERP页面。** 本次未发现它们是完成合同准备、签署和后续变更的必要条件。
5. **不要求本次做真实接口、短信、实名认证、电子印章、自动备案或跨页数据回写。** 原型使用明确的正常／异常场景，证明角色能完成各步骤即可。

## 八、仍需核实的少量平台事实

- 对客出境、赴台模板的实际字段：当前账号触发资质提示，未绕过；取得对应可查看条件后补核，原型可先保留明确待核实的模板样例。
- 本公司正式采用哪种接入方式、哪些公司和模板已开通；网页登录权限不能代替接口能力证明。
- 同一代表覆盖多人、未成年人／企业签署及作废确认的实际任务规则、签署顺序、拒签和到期结果；当前依据是后台提示，不是实签验收。
- 平台“待审核”的实际审批方、对接合同状态与普通合同的对应、作废与业务解除的办理方式。
- 文件格式／数量／大小、Word转换、系统生成附件及授权专用材料的具体接口要求。
