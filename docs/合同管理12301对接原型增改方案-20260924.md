# 合同管理12301对接原型增改方案

日期：2026-09-24。状态：本文件为实施前缺口证据；菜单细化方案的三步原型现已完成，见[第3步实施收尾](合同12301审批变更归档原型第三步实施验收-20260924.md)。

> 同日补充：用户要求明确接入、配置、使用和菜单页面归属，已形成[菜单页面细化方案](合同管理12301接入配置与菜单页面方案-20260924.md)。本文件保留11项源码缺口证据；页面范围、配置责任和实施顺序以细化方案为准，第八节原先“先改合同页”的顺序已被细化方案的“先配置、再办理”替代。

用户已确定接入12301。本轮核对现有原型并提出增改方案，不再做供应商选型，不调用真实签署服务、不发送客户通知、不修改业务页面。正式接口能力须以12301提供的现行资料及测试环境为准。

## 一、页面定位与范围

合同管理是销售顾问办理订单签约的工作页。上游是已确认的订单、游客、行程、成交金额、签约公司和适用模板；销售的高频任务是核对内容、提交审核、发起签署、查看未完成的签署及处理异常。审批人处理合同审核和变更审核，法务／运营维护模板，配置管理员维护公司授权。下游向订单提供合同覆盖情况和正式文件，向12301承接签署及备案结果。

合同签署、备案或解除均不能直接代替收款、退款、收入确认或财务核销。签约付款条件沿用已配置规则，未确认政策仍标待确认，不统一改成全款后签约。

保留销售中心“合同管理”及设置中的游客合同模板入口。主改合同列表与现有抽屉，必要时修正订单合同区、模板配置和合同审批的直接承接内容，不新增一级菜单，不改供应商协议模块，不做跨页面生产数据联调。

## 二、已具备的能力

- 从订单进入合同管理、带入订单资料、合同生成和送审的基本入口。
- 多人一份及按游客拆分合同、游客金额分配、监护代签及条件附件的演示。
- 逐人签署记录、签署二维码失效及重新发起的演示。
- 补充协议和新版本入口、企业合同线下盖章审核归档及版本记录。
- 游客合同模板已包含适用公司、12301模板编码、合同类型及字段对应关系。

以上为现有原型能力，不能记成全新功能，也不能据此视为真实12301已经接通。历史依据为《88-17个人合同多人签署企业合同实施与验收-20260919》；本次发现的问题以当前代码为准。

## 四、页面操作建议

### 1. 列表

建议保留合同／订单、客户及人数、产品／出行、合同类别、金额、合同状态、签署进度、负责人和操作这些核心信息。模板版本、完整12301编号、所有签署人、具体失败原因和文件记录放详情，避免增加一串状态标签。

主状态建议收敛为草稿、待审核、待签署、签署中、已签署、已撤销、已解除；审核退回显示原因并提供修改入口。旧“已生效”只有在合同约定的生效条件及判定方式明确后才使用，不与已签署或已备案自动等同。最终状态名称及映射在实施时结合已有订单表达核定。

| 主流程阶段 | 销售侧主操作 | 详情承接 |
|---|---|---|
| 草稿／审核退回 | 编辑、提交审核、详情 | 缺项、退回原因、内容预览 |
| 待审核 | 详情；允许时撤回 | 审核记录、审批来源 |
| 待签署 | 发起签署、详情 | 公司授权、签署人及合同内容检查 |
| 签署中 | 查看签署、详情 | 各方进度、查询结果、失效入口处理及允许的撤销 |
| 已签署 | 详情；变更作为低频处理 | 正式文件、备案结果、变更／解除、历史版本 |
| 已撤销／已解除 | 详情 | 原文件、处理依据、后续合同 |

发起签署是业务状态动作，可以保留在列表；催签、通知、联系游客等过程动作不占列表操作列。备案失败只作异常提示，进入详情处理，不因每行错误不同生成不同按钮。补充协议／新版本统一到一个变更处理入口，避免列表与详情各有一套并列主操作。

### 2. 生成、签署及详情抽屉

生成抽屉：订单及签约公司 → 合同方式与游客分配 → 正文与附件预览 → 缺项检查 → 保存／提交审核。销售只确认上游已确认资料，不在合同页另造订单价格。

签署抽屉：本次文件版本 → 必要签署方 → 身份及签章状态 → 平台提供的签署入口 → 本次结果。短信、微信、邮件和二维码有效期只按已确认的平台能力表达，不假定所有渠道都可用。

详情抽屉：合同概要、正文与附件、签署记录、备案结果、变更／解除及历史版本。已确认成功、失败和结果未知分别表达，保留上次核对时间。原型采用明确场景样例，不为演示接入构造跨页面自动回写。

## 六、12301资料待补充事项

接入对象已确定，不再把选型作为下一步。仍需12301接口文档、现有企业账号及授权说明、测试环境和典型返回样例，用于核实以下能力：

1. 现有签约公司、分公司或门店如何使用账号和印章；哪些公司具备有效授权。
2. 平台支持的合同模板、版本、业务类型、多人共同签署、按人分签及代理签署方式。
3. 内部合同号、平台合同号与监管统一编号如何对应；签署入口与监管查验码分别来自哪里。
4. 创建、签署、签章、备案结果能否主动查询或接收通知；超时、重复提交及部分完成如何处理。
5. 已发起合同如何撤销，已签合同如何变更、解除、重新签署；各阶段文件和原合同的状态处理。
6. 正式文件、附件及查验信息如何取得；实际支持的通知渠道、有效期和下载期限。

内部还需确认合同审批人及退回规则、签约付款条件、合同生效条件、企业合同电子化适用范围。以上未定内容进入配置或待确认清单，不能从行业规范推断某个接口已经支持。

## 七、行业依据及判断边界

文旅部《旅游电子合同管理与服务规范》解读说明了监管统一编号、签署变更解除规范及实时上传备案要求。本方案据此区分签署与备案，不把备案成功代替合同本身的生效条件。来源：[文旅部官方解读](https://zwgk.mct.gov.cn/zfxxgkml/zcfg/zcjd/202310/t20231011_949067.html)。

LB/T 086—2023第5.1.4节分别说明签署前取得监管统一编码及二维码、签署操作和签后上传；第5.2、5.3节涉及变更与解除。本方案据此提出两类二维码及变更记录应分开表达。来源：[标准原文](https://zwgk.mct.gov.cn/zfxxgkml/hybz/202309/W020230918349653116349.pdf)。这是业务规范依据，不是12301现行接口说明书。

## 八、实施顺序与验收边界

1. 第一轮只实施合同管理页及直接共享脚本：完成C01—C06、C08与列表的C10，具备正常签署、部分签署、失败、结果待确认、备案失败、变更与解除样例。
2. 第二轮完成订单合同覆盖C07、模板及公司条件C09、企业分工C11和必要审批说明修正，核对直接入口。不重做订单、项目和审批模块。
3. 接到12301资料后再将已确认能力填入原型及开发接口说明；真实接入另行联调和验收，不将页面演示标记成已接通。

关键算例：3人1份、3人3份、监护代签、2／3签署、公司未盖章、签署入口失效、创建超时、签署成功备案失败、主合同1万元增补1千元、旧版本保留、撤销与解除分开、企业替换版未通过、公司／模板不匹配、缺附件、未知付款条件、日期筛选及实际文件下载。金额与状态按明确样例核对，不通过改行文字制造通过结果。

本轮完成代码和文档核对、公开行业依据核查及方案记录。浏览器启动超时，未完成本轮点击与视觉验收；历史88-17验收不能替代后续改版验收。没有修改HTML／JS／CSS，没有进行真实签署或平台联调。

本节原实施顺序已被菜单页面细化方案替代。当前三步原型已完成；下一动作按实施记录试用页面，不将真实接口实施当作下一步。
