# 财务流程03：结算对账、发票与 NC 流程

业务确认稿 v1.0  
编写日期：2026年8月1日  
面向角色：结算会计、成本会计、应收应付会计、门店/渠道财务、税务会计、总账/NC接口负责人、业务负责人、财务主管

**核心目标：** 让一个团期、项目、供应商、渠道或门店从业务完成到财务结算、对账、开票/收票、凭证生成、NC 推送和期间关账的过程清楚可追溯。结算不是重新录一遍收入成本，而是把前面已经确认的收款、退款、转款、成本、应付、付款、预收、预付等财务事件汇总成可核对、可关账、可报表的数据。

## 本文件怎么读

- 结算会计重点看第一至第六部分、第九至第十部分，确认团期/项目结算、供应商对账、渠道和门店对账、差异调整和报表。
- 发票岗和税务会计重点看第七至第八部分，确认客户发票、供应商发票、验真、税务标签和 NC 标签来源。
- NC/总账负责人重点看第八至第九部分，确认凭证事件、NC 推送、失败处理、关账和调整冲销。
- 业务负责人重点看第三至第六部分、第十一至第十二部分，确认结算节点、差异退回、门店分润和待拍板事项。

## 第一部分：整体业务流程概览

旅游业务完成后，财务需要回答的不只是“收了多少钱、付了多少钱”，还包括：

- 这个团期或项目最终收入是多少。
- 已确认收款、退款、转款后，客户侧余额是否准确。
- 供应商成本是否完整，应付和预付是否已处理。
- 供应商、渠道、门店是否对清账。
- 发票是否收到或开出。
- 免税、差额税、主体、内部/关联方等标签是否能传给 NC。
- 期间关账后如果发现差异，应该怎么调整。

结算对账主链路如下：

> 团期/项目达到结算节点 → 系统汇总订单收入、收款、退款、转款、成本、应付、付款 → 业务确认成本和异常 → 财务确认结算 → 供应商/渠道/门店对账 → 差异调整 → 发票处理 → 凭证生成 → NC 推送 → 期间关账 → 报表

这条链路的关键原则是：结算只能使用已经确认的业务和财务事件。未确认认款、未执行退款、未确认成本、未处理账单差异，都不能被当成最终结算结果。

## 第二部分：结算数据从哪里来

### 客户侧数据

客户侧数据来自收款应收流程，包括：

- 订单应收。
- 项目阶段应收。
- 已确认认款。
- 预收转入。
- 预存扣款。
- 客户退款。
- 退款转预存。
- 订单转款转入或转出。
- 应收调整或坏账关闭。

这些数据决定团期、项目、渠道或门店的收入和客户侧余额。

### 供应商侧数据

供应商侧数据来自成本应付流程，包括：

- 成本项。
- 供应商账单。
- 账单差异。
- 已确认应付。
- 已付款。
- 预付分摊。
- 预付冲抵。
- 付款退回。
- 供应商追款。
- 发票状态。

这些数据决定成本、应付、已付、预付余额和供应商对账结果。

### 业务标签数据

结算和 NC 还需要业务标签：

- 主体。
- 部门。
- 产品类型。
- 团队类型。
- 境内/境外。
- 出境游免税。
- 境内旅游服务差额税。
- 渠道。
- 门店。
- 供应商类型。
- 内部、外部、关联方标签。

这些标签不能等到推 NC 时由财务临时补，应在产品、团期、订单、供应商档案中形成。

## 第三部分：团期和项目结算

### 什么时候进入结算

团期、航次、班期或项目达到业务结算节点后进入结算。不同业务的节点可能不同：

- 普通团期：回团后进入结算。
- 邮轮航次：航次结束、舱房和名单确认后进入结算。
- 专列班期：班期结束、铺位和损耗确认后进入结算。
- MICE/单团项目：项目完成或合同阶段完成后进入结算。
- OTA 或渠道业务：平台账单确认后进入渠道结算。

具体节点可按业务类型配置，但结算时必须能看到收款、退款、成本、应付和异常是否完整。

### 团期结算怎样跑

一个团期结算的正常过程如下：

1. 系统汇总该团期所有订单和客户。
2. 系统汇总订单应收、已确认收款、退款、转款和预收预存。
3. 系统汇总成本项、供应商账单、应付、预付冲抵和已付款。
4. 计调确认成本是否完整，票损、舱损、铺损等是否确认。
5. 财务查看是否有未认流水、未执行退款、未处理转款、未确认账单、发票异常。
6. 系统计算收入、成本、毛利和毛利率。
7. 如果有差异，退回对应环节处理，而不是在结算页直接改数。
8. 差异处理完成后，财务确认结算。
9. 结算结果进入凭证、NC 和报表。

### 为什么要保留最细颗粒

旅游业务不能只按团期总额结算。一个团期里可能有散客、单位客户、门店订单、渠道订单、多人合同、一人代多人付款。成本也可能按人、按房、按舱、按铺、按批次分摊。

因此系统需要保留：

- 团期总额。
- 订单明细。
- 订单内客人明细。
- 客户付款明细。
- 成本费用项目明细。
- 供应商明细。

这样后续才能做部门毛利、产品线毛利、客户收入、供应商成本、散客和团队拆分，以及 NC 需要的辅助核算。

## 第四部分：供应商结算和对账

### 供应商对账的业务场景

供应商对账用于确认我方系统成本和供应商账单是否一致。供应商可能是地接、酒店、车队、票代、航司、船司、专列运营商、签证保险服务商，也可能是集团内部主体或关联方。

供应商结算并不等同于付款。供应商账单确认后可能形成应付，也可能先冲抵预付，还可能因为差异暂不付款。

### 供应商对账流程

1. 系统根据团期、项目或资源批次生成待对账范围。
2. 供应商提交账单，或我方上传/导入账单。
3. 系统识别供应商、账单号、金额、币种、费用项目。
4. 系统匹配对应成本项、团期、项目或资源批次。
5. 财务核对供应商账单金额与系统成本。
6. 一致时确认账单并生成应付或冲抵预付。
7. 不一致时标记差异原因。
8. 业务和财务确认差异由谁承担。
9. 确认后的金额进入应付、付款、发票和结算。

### 差异如何处理

供应商账单差异常见有：

- 供应商多收。
- 系统漏成本。
- 供应商优惠或减免未体现。
- 汇率口径不一致。
- 重复账单。
- 票损、舱损、铺损未确认。
- 成本项挂错团期或批次。

差异不能线下改表。系统应记录差异原因、责任方、确认金额和处理结果。处理结果可能是供应商承担、我方认可补差、按系统成本确认、部分认可、退回业务补成本或关闭账单。

### 内部、外部和关联方

供应商档案需要标记供应商是外部供应商、内部主体还是关联方。这个标签会影响往来分析、关联交易披露、内部交易归类和 NC 辅助核算。

标签应在供应商档案中维护，关系变化时可以调整，不能等财务结算时临时判断。

## 第五部分：渠道和 OTA 结算

### 渠道结算为什么单独处理

渠道和 OTA 往往不是一张订单一笔收款，而是平台按周期出账单、统一结算。平台可能扣佣金、服务费、退款、活动补贴，最后一笔打款对应多个订单、多个部门甚至多个产品线。

因此渠道结算要把三类数据对起来：

- 系统订单应收。
- 平台账单明细。
- 平台实际到账或扣款。

### OTA 月结流程

1. OTA 订单进入系统，形成渠道订单和应收。
2. 平台出月结账单。
3. 渠道运营或财务上传平台账单。
4. 系统按平台订单号匹配系统订单。
5. 系统识别平台扣费、佣金、退款、活动差额。
6. 一笔平台款拆分到对应订单、部门和主体。
7. 财务确认平台实结金额和系统应收差异。
8. 确认后核销渠道应收。
9. 平台扣费或佣金进入费用、应付或结算调整。
10. 差异留在渠道结算单中继续处理。

### 平台退款

平台退款有时由客户直接在平台申请并自动退回，财务只在平台账单里看到一进一出。系统需要在渠道结算中识别平台退款抵扣，并与系统订单售后退款对上。如果平台退款流程无法自动回传，至少要在平台账单导入时标记该订单已由平台退款。

## 第六部分：门店对账和分润

### 门店对账看什么

门店对账不是只看销售额。对门店来说，最关心的是本期充值了多少、下单扣了多少、退款回了多少、管理费扣了多少、还有多少余额。

门店对账单应包括：

- 期初余额。
- 本期充值。
- 订单扣款。
- 退款转预存。
- 管理费。
- 冻结和解冻。
- 差异调整。
- 期末余额。

### 门店对账流程

1. 系统按月或约定周期生成门店对账单。
2. 门店查看本期充值、扣款、退款转预存、管理费和余额。
3. 门店确认无误，或提出异议。
4. 财务复核异议，必要时关联订单、认款、退款或预存流水。
5. 财务确认后，对账单生效。
6. 生效结果进入门店余额、分润计算和财务报表。

### 分润先展示，发放另走规则

门店可以看到销售额、订单数、预存余额和可见利润，但“可见利润”不等于门店可以自行分润。分润发放需要公司规则、财务复核和可能的审批。

出行后如果订单发现错误，不能让门店或销售随意改订单，因为会影响分润、收款和结算。应进入财务反结算或结算调整流程。

## 第七部分：发票如何承接结算

### 发票分两条线

发票至少有两条线：

- 供应商给我方开的发票，服务于成本、应付和付款。
- 我方向客户、渠道或门店开的发票，服务于收入、合同和税务。

供应商发票通常从供应商账单、应付或付款流程承接；客户发票则从订单、收款和客户开票申请承接。

### 供应商发票

供应商发票要能和供应商、账单、应付、付款关联。系统应记录：

- 发票号。
- 开票日期。
- 开票公司。
- 购方公司。
- 发票金额。
- 税额。
- 税率。
- 发票项目。
- 关联供应商。
- 关联账单、应付单、付款单或结算单。
- 验真状态。
- NC 状态。

### 发票进度表

财务需要知道某个供应商付款后是否收票、收票金额是否足够、发票是否验真。

发票进度表应能展示：

- 供应商。
- 付款主体。
- 已付款金额。
- 已开票金额。
- 未开票金额。
- 发票异常。
- 验真状态。
- 先款后票说明。

这样财务可以追踪供应商全年付款和开票情况。

## 第八部分：税务标签和 NC

### 业务系统不做复杂拆税

旅游业务的免税、差额税、不差额等拆税逻辑最终由 NC 或财务核算规则处理。业务系统不应在前端页面做复杂会计拆分，但必须把 NC 需要的业务标签准备好。

### 需要传给 NC 的标签

系统至少要提供：

- 主体。
- 部门。
- 产品类型。
- 团队类型。
- 境内/境外。
- 出境游免税。
- 境内旅游服务差额税。
- 不差额。
- 渠道。
- 门店。
- 供应商类型。
- 内部、外部、关联方。

这些标签应来自产品、团期、订单、供应商档案和组织主体，不应在 NC 推送时由财务临时补。

### NC 推送流程

财务事件确认后，系统形成凭证数据。可推送 NC 的事件包括：

- 收款确认。
- 退款执行。
- 转款确认。
- 应付确认。
- 付款执行。
- 预付冲抵。
- 付款退回。
- 供应商结算。
- 渠道结算。
- 门店对账。
- 发票确认。

推送成功后，系统记录 NC 凭证号、推送时间、推送人和返回结果。推送失败时，系统保留失败原因，财务修正基础信息后重推。

已推送或已关账的数据，不应直接改原单。后续通过冲销、调整或反结算处理。

## 第九部分：期间关账和反结算

### 关账前检查

期间关账前，系统应帮助财务检查：

- 是否有未确认认款。
- 是否有未认流水余额。
- 是否有未执行退款。
- 是否有未完成转款。
- 是否有未确认成本。
- 是否有供应商账单差异。
- 是否有应付未处理。
- 是否有付款退回未核销。
- 是否有发票异常。
- 是否有 NC 推送失败。

这些异常不一定全部阻止关账，但必须有状态、责任人和处理路径。

### 关账后的调整

关账后发现错单、漏成本、漏收款、退款差异、供应商账单差异，不能直接修改原单。

应通过以下方式处理：

- 应收调整。
- 应付调整。
- 结算调整。
- 退款冲销。
- 付款退回。
- 预付冲抵调整。
- NC 冲销或调整凭证。

这样才能保证历史期间数据稳定，后续审计和追溯有依据。

## 第十部分：报表体系

### 资金报表

资金报表从收款、付款、退款、转款和资金计划中生成，主要服务出纳和资金管理。

应包括：

- 资金日报。
- 资金周报。
- 头寸表。
- 资金计划表。
- 收款流水明细。
- 付款执行明细。
- 退款执行明细。
- 转款报表。

### 应收应付报表

应收应付报表服务财务日常对账和催收催付。

应包括：

- 应收账龄。
- 未认流水。
- 预收余额。
- 预存余额。
- 应付余额。
- 预付余额。
- 付款与发票进度表。

### 业务结算报表

业务结算报表服务管理层和业务部门看经营结果。

应包括：

- 团期收入、成本、毛利、毛利率。
- 项目收入、成本、毛利。
- 部门收入成本毛利。
- 产品线收入成本毛利。
- 订单收入明细。
- 成本费用项目明细。
- 客户或散客颗粒度明细。
- 供应商结算明细。
- 渠道结算明细。
- 门店对账明细。

管理层需要每天看到收入、付款、利润、各部门各团盈亏，系统必须依赖结构化业务事件自动生成，而不是再靠人工汇总 Excel。

## 第十一部分：财务结算端常见端到端场景

本章只讲结算会牵动业务、财务、发票、NC 和报表继续处理的场景。结算不是重新录收入成本，而是把前面已经确认的订单、收款、退款、转款、成本、应付、付款、预付和发票汇总起来审核。财务阅读时重点确认：业务提交结算后我审核什么，哪些情况打回，最终形成什么结果。

### 场景一：团期、航次、班期或项目结算

团期回团、航次结束、班期完成或项目交付后，计调或专项团队提交结算。系统会把订单、收款、退款、转款、成本、供应商账单、应付、预付冲抵、已付款和发票状态汇总到结算中。

财务审核时，重点看客户收款是否完整，退款或转款是否已处理，成本是否由业务确认，供应商账单是否存在差异，预付款是否正确冲抵，发票和 NC 是否存在异常。发现未认款、未退款、成本未确认、账单差异、发票缺失等问题时，财务打回给对应来源岗位补齐。

业务最终要拿到的是结算通过结果。结算通过后，该团期、航次、班期或项目的收入、成本和毛利才能进入稳定报表；结算后再发生差异，应走二次结算或调整。

### 场景二：供应商对账结算

供应商完成接待、出票、分房、地接或其他服务后，供应商或我方业务提交对账单。系统会把供应商账单、系统成本、差异原因、确认金额、应付、预付冲抵和发票情况放在一起。

对账先由业务确认事实，例如接待人数是否正确、票号是否真实、房型舱型是否一致、名单和扣损是否确认。财务再确认应付金额、付款对象、预付冲抵、发票和付款条件。差异没有业务确认前，财务不能直接按供应商账单付款。

供应商最终要拿到的是应付确认金额和付款进度。对账不等于付款，付款还要经过应付、审批、出纳和回单流程。

### 场景三：OTA 或渠道月结

OTA 或渠道月结时，渠道运营或财务上传平台账单，系统把平台订单、系统订单、渠道应收、平台扣费、平台退款、到账流水和实结差异汇总起来。

渠道运营负责解释平台扣费、活动差额、退款和特殊差异。财务负责核对平台账单、系统订单和实际到账三方是否一致。三方不一致时，不能只按到账总额结算，也不能把未解释差异直接冲掉。

渠道最终要拿到的是应收核销和月结完成结果。平台订单号不准、退款未对齐、扣费规则不清，会导致月结无法关闭。

### 场景四：门店账期对账和分润

门店账期结束后，系统根据门店预存、订单扣款、退款转预存、冻结解冻、管理费和分润规则生成对账单。门店先确认账单，或对具体订单、扣款、退款、分润提出异议。

财务复核门店确认结果，异议处理完后对账单生效。分润金额生效后，才进入付款流程和 NC；如果退款未对齐、订单扣款未确认、异议未处理，分润不能直接付款。

门店最终要拿到确认后的余额、对账结果和分润结果。需要业务确认的是分润何时可确认、异议期多长、退款或退团跨账期时如何影响分润。

### 场景五：发票、NC、关账和后续调整

结算过程中，发票岗处理客户开票和供应商收票，NC 负责人根据确认后的收款、应付、付款、结算和税务标签推送凭证。系统会记录发票状态、税务标签、凭证事件、NC 凭证号、失败原因和关账状态。

关账前，财务需要检查当期是否还有未处理收款、退款、转款、应付、付款、发票和 NC 失败。关账后再发现差异，不能直接覆盖原单，而应走调整、冲销、反结算或二次结算。

财务最终要拿到的是可关账、可追溯的结果。每一笔调整都要能说明来自哪个业务场景、影响哪张订单或账单、是否已经重新推送 NC。

## 第十二部分：需要业务和财务确认的事项

1. 各业务类型进入结算的节点：回团、项目完成、平台账单确认、供应商账单确认等。
2. 供应商结算由供应商主动发起，还是我方生成后供应商确认。
3. 供应商结算单是否必须盖章，线上确认能否替代纸质盖章。
4. OTA 月结账单字段、扣费、退款抵扣和差异处理规则。
5. 门店分润是否进入本期，若进入，分润节点和复核规则。
6. 发票是否作为付款强控条件，哪些允许先款后票。
7. 发票 OCR 识别字段和验真方式。
8. 免税、差额税、不差额标签由哪些页面维护。
9. NC 推送采用单据级推送还是总账层汇总推送。
10. NC 推送失败后，谁处理，是否允许业务侧修改源单。
11. 期间关账前哪些异常必须清理，哪些可以带状态关账。
12. 管理层日报、部门毛利、团期盈亏、供应商发票进度等报表字段模板。
