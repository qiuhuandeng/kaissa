# 业财报表系统全貌盘点

## 一、本次盘点结论

当前项目是一个覆盖集团管理、旅游业务、供应商协同、客户端和运营平台的静态业务原型。代码能够证明页面、入口、字段、按钮、查询参数和少量跨页面演示记录是否存在，但项目没有后端接口、数据库、正式报表计算服务或统一财务明细，因此不能仅凭页面上展示了某个数字，就认定系统已经能够自动形成财务报表。

现有原型已经搭出了较完整的业务链路：

```text
集团组织和基础配置
→ 资源、供应商和产品
→ 团期/航次/班期/出行日期
→ 产品预订、订单、合同和售后
→ 到账、认款、应收、退款和转款
→ 履约、回团、成本和供应商账单
→ 应付、付款、预付、结算、发票和NC
→ 经营分析和财务报表
```

问题不在于“完全没有业财页面”，而在于现有页面是否使用同一统计对象、同一时间口径、同一金额口径和同一历史归属规则。目前代码层面尚不能证明这一点。

## 五、各端业务链路

### 1. 客户端

客户端已表达以下连续路径：

```text
首页/产品列表 → 产品详情 → 选择出行人 → 附加服务
→ 确认订单 → 支付 → 支付成功 → 订单详情/旅程详情
→ 合同、材料、发票、退款、评价和客服
```

客户端页面均为静态示例，没有把客户操作真实写入主业务端订单、收款、退款或发票数据。

### 2. 供应商端

供应商端导航包含产品管理、团期管理、订单确认和对账结算。它表达了第三方供应商维护产品与供给、确认订单、提交或查看结算的路径，是外采成本和供应商账单的重要来源。

供应商团期详情仍保留指向不存在的 `fulfillment-outbound.html` 和 `fulfillment-return.html` 的履约链接；这说明部分供应商履约入口与主业务端已经调整后的“团期管控”结构没有同步。

### 3. 集团端

集团端主要管理公司、组织、岗位、人员、权限、接口、参数和操作审计。它对财务报表的关键作用是提供法人公司、分公司、中心、部门、门市部、门店和人员任职关系。后续必须检查这些归属是否带生效时间，以及订单发生后是否保留当时的组织和人员归属。

### 4. 运营平台

运营平台面向旅游软件的商户、套餐、模板、组件和平台运维。其“经营总览、销售分析、财务分析、报表下钻”分析的是租户使用量、租户业务总额、软件订阅和续费账单，不是财务5份材料要求的凯撒旅游经营报表，不能混入本项目的财务报表范围。

## 六、当前原型的数据和交互方式

### 1. 没有正式业务数据服务

项目中没有应用构建配置、业务接口调用、数据库定义或服务端代码。共享导航中的网络读取只用于把静态页面局部加载进同一个后台外壳，不是读取订单、收款、成本或报表数据。

### 2. 大部分页面使用固定示例数据

列表、金额、人员、产品和状态通常直接写在页面中。搜索、筛选、抽屉、弹窗、按钮和导出主要用于演示操作过程；“任务已创建”“数据已刷新”等提示不代表真实生成文件或完成后台计算。

### 3. 少量跨页面演示依赖浏览器本地记录

现有原型通过多个相互独立的浏览器本地记录演示订单、审批和财务结果，包括：

- 订单及其财务结果。
- 应收、收款和退款结果。
- 付款、回单和NC推送结果。
- 发票任务。
- 外采产品、单团项目和单项服务结果。
- 团期财务承接记录。
- 汇率、自由行出行日期、团期创建和资源模板草稿。

财务报表页会从上述多个本地记录中拼装部分结算、应收、应付和收付款明细。这能演示“报表引用业务结果”的方向，但还不是统一的财务业绩明细，也不能保证刷新浏览器、换设备或多人协同时口径一致。

## 七、现有分析和报表入口

### 1. 主业务端财务报表

`finance/finance-reports.html` 当前有六个分析页签：

- 经营损益：结算收入、确认成本、毛利和毛利率。
- 收款分析：收款单、来源流水、订单或应收、客户或渠道、产品和收款金额。
- 付款分析：应付、付款、供应商、产品、应付金额和已付金额。
- 往来分析：应收和应付汇总及明细。
- 预付分析：供应商预付款余额、新增和冲抵。
- 资金余额：账户、收款、付款、退款和可用余额。

该页面已有筛选、导出和从损益汇总查看收入、成本明细的交互，也会读取部分浏览器本地财务结果。但它目前没有明确表达财务材料要求的“订单口径”和“回团口径”，也没有预算版本、年度任务、同比环比、预算区域、来源系统和历史归属等完整分析能力。

### 2. 产品分析

`data/product-analysis.html` 当前展示销售额、收客人数、订单数、预估毛利率、退款率和客户满意度，并可按产品类型、目的地、负责人、渠道和产品状态筛选。

它适合产品经营人员判断加量、成本复核和产品优化，但当前金额和分类是页面固定数据，“预估毛利率”也不能代替财务确认的团期收入、成本和毛利。

### 3. 电销业绩

`sales/call-center/performance.html` 当前按顾问、分组、来源和产品类型展示咨询、意向、订单、成交金额和转化率。它覆盖财务周报中的部分呼叫中心分析维度，但没有订单口径、回团口径、预算完成和历史同期规则。

### 4. 工作台

主体负责人和门店店长工作台展示业务总额、销售额、毛利、收款、订单和顾问表现等摘要。它们是角色工作入口，不应作为财务数据计算来源；最终应引用已经统一的财务分析结果。

## 八、阶段1发现的结构问题

以下结论只涉及代码结构和入口，不代表已经完成业务口径判断。

1. **不存在统一财务业绩明细。** 当前财务报表从多个浏览器本地记录和页面固定数据拼装，尚未发现一套同时承接订单、团期、组织、渠道、收退款、成本和结算的共同明细。
2. **财务五类结果没有统一入口。** 财务报表、产品分析、电销业绩和各角色工作台分别表达部分指标，但缺少共同下钻关系。
3. **订单口径和回团口径尚未在页面中命名和区分。** 全项目页面代码没有出现“订单口径”“回团口径”；存在下单、出团、回团和结算日期，但尚未形成报表期间选择规则。
4. **部分财务要求在页面中没有直接表达。** 当前页面没有“财务确认收入”“不含税收入/成本/毛利”“预算区域”和“来源系统”等明确字段或筛选项。
5. **预算没有形成统一经营任务模块。** 页面中的预算主要服务单团项目或局部业务控制，尚未发现个人、团队、门店和渠道年度任务及版本管理入口。
6. **销售订单和团期订单存在成套复制。** `merchant/sales` 与 `merchant/tour` 下有订单列表、详情、新建、售后及退转页面的近似副本。两个入口服务销售和团控的不同工作场景是合理的，但复制代码可能导致字段和规则逐步分叉，需要在订单模块成对核对时确认主数据来源和页面职责。
7. **存在无菜单或无静态入口的页面。** 包括渠道来源、付款管理汇总、预收预存汇总、退款转款汇总、产品渠道授权和旧的主体选择页。其中部分可能是已拆分后的旧聚合页，部分可能是应保留的二级页面，不能仅凭无入口直接删除。
8. **存在兼容跳转页面。** 分销代理、平台订单、平台退款、同步日志、旧单团项目和部分财务/履约页面仅负责跳到新入口。这些页面应在后续文档整理时统一列为兼容入口，而不是当作独立功能重复统计。
9. **供应商履约链接没有同步。** 供应商团期详情引用了当前不存在的履约页面，是已确认的页面链接缺口。
10. **现有自动检查范围不完整。** 项目检查脚本只检查主业务端、客户端和运营平台，没有覆盖集团端和供应商端，因此它报告“无断链”不能代表整个项目无断链。
11. **存在两份主体选择页面。** 登录实际进入 `workspace.html`，`select-workspace.html` 没有入口，两者内容相近，属于后续合并或归档候选。
12. **运营平台报表与旅游业务报表名称容易混淆。** 运营平台的财务分析属于软件订阅财务；后续文档和页面说明需明确排除，避免被误认为集团旅游财务报表。

## 十、下一阶段阅读边界

下一步从“产品与团期”开始进行代码和文档成对核对，原因是它们决定财务报表中的产品类型、业务类型、产品负责人、目的地、出团回团日期、团号和成本归集对象。

本轮应同时核对：

- 资源、供应商和目的地资料如何进入产品。
- 自营、外采、邮轮、专列、自由行、研学和单团项目如何分类。
- 产品负责人、产品经营公司和供应商分别在哪里维护。
- 产品如何开排团期/航次/班期/出行日期。
- 团期如何形成出团、回团、人数、资源消耗和成本归集依据。
- 代码页面与产品、团期、外采及专项业务文档是否一致。
