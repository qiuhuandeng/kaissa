## 二、页面修改

### 1. 履约中心 → 团期管控 → 团期详情

页面：[schedules-detail.html](../merchant/tour/schedules-detail.html)，直接脚本：[schedule-change-handoff.js](../shared/schedule-change-handoff.js)。

- “团期订单”页签增加“整团转移”，按“选择订单—逐单记录决定—核对目标资源—查看结果”四步处理。
- 逐单结果分别显示成功、待处理或失败及原因；成功记录锁定，待处理和失败记录可继续处理，部分失败不会把全团统一标成成功。
- “交通资源”页签增加“航班时刻变更”，独立记录原航班、新时刻、成本影响、资源影响和申请依据；提交后形成待审批记录，原团期航班不被直接覆盖，重复提交不会重复生成同一申请。
- 原团有订单或成本时，拦截直接取消或删除，并提示先完成订单、合同、退款和成本责任处理。
- “出团准备”页签增加“特殊服务确认”，计调可按旅客和服务选择可供、不可供或需补差并填写确认依据；需补差时校验金额，并标为“待销售确认”。
- “出团准备”页签增加“出团资料缺口”，定位到具体旅客或服务；自办游客只提示出行证件核对，不计入代办送签缺口。

**2026-09-19 后续调整：** 按用户对团期详情截图的明确要求，已移除“出团准备”页签的整块“出团资料缺口”及六项演示数据；上条保留为当次实施历史，不代表当前页面仍显示该区块。“特殊服务确认”、原出团准备清单及出团通知页的缺项预览不受本次删除影响。本次仅完成源码与语法核对，浏览器实际显示待验。

本页没有修改核心资料编辑保存方法，也没有增加用户排除的“变更影响范围及目标团期”处理区。

### 2. 销售中心 → 合同管理

页面：[contracts.html](../merchant/sales/contracts.html)，直接脚本：[contract-version-change.js](../shared/contract-version-change.js)。

- 已签合同的“补协议”由简单提示改为可操作抽屉。
- 抽屉只读显示原合同、原团期、原金额和签署状态，可选择补充协议或新版本并填写新团期、新金额和变更原因。
- 提交后新增一条待审核变更文件，显示与原合同的关联；原已签合同和原文件保持只读，不被覆盖。

### 3. 履约中心 → 游客名单

页面：[fulfillment-roster.html](../merchant/tour/fulfillment-roster.html)，直接脚本：[fulfillment-roster-verify.js](../shared/fulfillment-roster-verify.js)。

- 游客编辑抽屉改为证件原图和识别字段并列核对，包含中文名、英文名、证件号、有效期、识别置信度和人工确认。
- 识别不清或缺失字段显示“待补”，未人工确认不能当成已核对结果保存。
- 批量导入确认区区分新增、重复、格式错误和超过订单人数四类，异常行可逐行修改或跳过；未处理异常时禁止确认导入，再次导入不会覆盖原旅客。
- 每名旅客可查看关联订单、签证方式、交通票号或舱铺、房型、特殊服务结果和具体资料缺口。
- “导出当前名单”按当前筛选结果导出，证件号和手机号使用页面已脱敏值。

### 4. 履约中心 → 出团通知

页面：[fulfillment-notice.html](../merchant/tour/fulfillment-notice.html)，直接脚本：[fulfillment-notice-preview.js](../shared/fulfillment-notice-preview.js)。

- “预览／详情／回执”进入统一通知预览抽屉。
- 预览显示团号、通知版本、行程版本、更新时间和当前通知内容。
- 汇总名单、代办签证、交通资源、领队和集合事项，缺项定位到具体旅客或事项。
- 自办游客单独列为出行证件核对，不计入代办送签缺口。

### 5. 销售中心 → 订单管理 → 订单详情

页面：[orders-detail.html](../merchant/sales/orders-detail.html)，直接脚本：[order-change-service.js](../shared/order-change-service.js)和[order-visa-detail.js](../shared/order-visa-detail.js)。

- “游客信息”增加独立服务项目区，房型、联运、升舱和加床分别记录旅客、申请内容、价格、资源确认、结果和确认依据，不再只放在备注中。
- “应收收款”增加“结算后追加调整”。原结算结果只读，新增调整必须填写方向、金额和原因，提交后形成待审批记录，不恢复无痕编辑。
- 每名旅客分别显示未选择、游客自办、随团代办或无需签证；可选项受当前产品允许方式限制，未选择不会自动当成代办。
- 变更签证方式必须填写原因；已进入代办流程的旅客转出代办时，必须选择终止未开始任务、申请撤回并保留送签记录或保持任务待处理。
- 签证方式变化不直接改订单价。涉及退补时单独记录原费用、申请金额和待审批结果。
- 变更历史保留原方式、新方式、原因、任务处理和费用影响。

本页没有增加用户排除的改期接受、拒绝取消或资源不足替代方案处理区。

### 6. 履约中心 → 签证办理

页面：[visa-processing.html](../merchant/tour/visa-processing.html)，直接脚本：[visa-processing-agency.js](../shared/visa-processing-agency.js)。

- 页面顶部增加任务范围汇总，明确仅委托随团代办的游客进入材料、送签、补件、出签或拒签和交付任务。
- 任务表增加办理方式和委托来源，任务行均明确为“随团代办”；自办游客仅保留出行证件核对说明，不进入任务数和材料缺项。
- 增加“补件中”和“结果待交付”状态，原材料、送签、审批和结果处理入口继续使用。
- 同一订单3人样例按1人自办、2人代办统计，只显示2条代办任务。

## 三、实际验收结果

使用本地HTTP页面和Chrome执行交互验收，页面控制台错误均为0。

| 场景 | 实际结果 |
|---|---|
| 整团转移未确认目标资源 | 阻止提交并提示“请先核对目标名额及供应条件” |
| 整团转移部分失败 | 三笔结果分别为成功、待处理、成功并显示原因；未统一改为全部成功 |
| 航班时刻变更缺申请依据 | 阻止提交；补齐后生成待审批申请，原团状态未变 |
| 特殊服务补差为0 | 阻止保存；填写500元及依据后显示“待销售确认、补差¥500” |
| 原团仍有订单或成本时取消 | 直接取消被拦截，销售状态仍为“开放报名” |
| 名单证件识别 | 初始显示待人工确认；勾选确认后保存为已核对 |
| 名单导入存在异常行 | 未处理时阻止导入；逐行跳过后关闭导入框，只带入可导入行 |
| 名单分类 | 新增、重复、格式错误和超过订单人数四类均显示 |
| 订单签证方式 | 初始明确1人自办、1人代办；方式变化记录历史 |
| 已送签旅客转出代办 | 未选择任务处理方式时阻止保存 |
| 一单3人混合签证 | 汇总为1人自办、2人代办，签证工作台仅显示2条代办任务 |
| 结算后追加调整 | 0元被阻止；有效金额生成1条待审批记录，原结果保留 |
| 合同变更 | 生成待审核补充文件并关联原合同，已签原合同保持不变 |
| 出团通知预览 | 显示通知版本、行程版本、更新时间及3项具体缺口，自办游客不计入送签缺口 |
| 抽屉可见性和标题 | 出团通知、合同变更及整团转移抽屉均实际可见，标题分别保持业务名称 |
| 390px窄屏 | “整团转移”“航班时刻变更”按钮文字完整可见，整团转移抽屉可滚动操作 |

语法检查覆盖本次新增或修改的共享脚本及六个页面内联脚本；`git diff --check`通过。财务执行清单检查继续保持原8批、36项、6场景完成状态。本次没有真实跨页数据同步、自动退款或生产权限，也没有把演示申请当成审批通过。
