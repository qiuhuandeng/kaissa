# 业财底座01：多主体交易关系与核算责任基线

版本：v1.0（开发前设计基线）  
编写日期：2026年8月23日  
适用范围：凯撒旅游集团多主体、多分公司、多门店、多渠道、自营与外采、专项产品、内部互采及体系外供应商业务

## 一、文档定位

本文不是对现有财务原型页面的复述，也不以现有 HTML 字段、按钮和模拟数据作为开发模型。

现有原型用于证明业务人员需要完成哪些操作、业务对象之间如何流转；本文负责重新设计正式开发所需的公司级业财底层逻辑，先回答以下问题：

1. 一笔业务中有哪些主体，各主体分别承担什么法律、业务、资金和核算责任。
2. 客户订单、团期/项目、供应商采购、门店、渠道和集团内部单位之间会形成几段交易关系。
3. 每一段交易关系应形成什么应收、应付、收款、付款、内部往来、发票和结算数据。
4. 业务结果如何形成不可覆盖的财务事项，并进一步生成会计事项和 NC 凭证。
5. 多主体代收、代付、内部互采、外采转售、加盟门店、OTA、航服内部供票等复杂场景如何对清。

本文是后续以下工作的上游基线：

- 业财场景矩阵；
- 财务主数据模型；
- 订单与团期结算模型；
- 应收、应付、资金和核销模型；
- 内部交易和合并对账模型；
- 会计事项、凭证规则和 NC 接口模型；
- 数据库、服务边界和接口设计。

### 文档用词原则

本文优先使用业务和财务日常用语。法人主体、核算主体、应收、应付、预收、预付、核销、收入确认、内部往来等属于业务或财务术语；技术字段和程序实现名称不在正文中定义业务。正文中的“财务事项”表示某个业务结果已经对金额、债权债务、资金或损益产生影响，例如收款确认、应付确认或退款执行。

## 二、当前系统现状与本次重构原则

当前项目已经覆盖资源、产品、履约、销售、门店、渠道、供应商、财务、审批、客户端和平台端的主要使用流程，但仍属于静态业务原型。现有财务页面已经表达到账、认款、应收、预收、预存、退款、转款、账单、应付、付款、预付、回单、结算、发票、资金、关账和 NC 等功能方向，但尚未形成可直接开发的统一数据底座。

正式开发必须遵守以下原则：

1. 不按页面建表。页面是角色工作入口，不是领域模型边界。
2. 不用一个“所属公司”字段承接所有主体责任。
3. 不用订单总状态代替收款、合同、履约、结算和 NC 等独立状态。
4. 不把收款等同收入，不把付款等同成本，不把预估成本等同应付。
5. 不直接修改已经生效、已结算、已推 NC 或已关账的数据。
6. 不以自营、外采、内部产品等简单标签直接决定收入确认方式。
7. 不将增值税差额计税口径直接等同于会计收入净额确认口径。
8. 每一笔财务数据必须能够反查业务来源、责任主体、结算对象、核销关系和会计结果。
9. 业务系统保留最细业务与业财明细，NC 可以按凭证模板汇总推送，但不能丢失明细追溯关系。
10. 多主体交易先形成双方对应的内部应收和内部应付，再进入各自账套；不能只在一方做一张内部成本记录。

## 三、集团组织必须拆成六类对象

原型中已经出现“旅游板块—主体公司—分公司/中心—部门/门市部—门店”的组织树，并配置独立核算状态和 NC 科目空间。这只能作为组织展示线索，不能直接成为正式核算模型。

### 1. 集团和板块

用于管理汇总和权限导航，例如旅游板块、航服板块等。

集团和板块本身通常不是交易和记账主体，不应直接出现在应收、应付或银行账户上。若某集团总部本身也是法人公司，应另建法人主体记录。

### 2. 法人主体

依法承担合同、资产、负债、税务和对外责任的公司。

法人主体至少维护：

- 法定名称、统一社会信用代码；
- 法人类型和启停状态；
- 默认本位币；
- 税务登记和纳税人属性；
- 可用合同章和发票资质；
- 可用银行账户和支付商户；
- NC 账套、公司编码和核算组织映射；
- 是否允许内部交易；
- 生效起止日期。

原则上，客户合同、供应商合同、应收、应付、收付款、发票和凭证都必须归属明确法人主体。

### 3. 核算主体/账簿映射

核算主体表示业务系统中需要独立形成会计结果并推送到 NC 的核算单元。

正常情况下法人主体与主核算主体一一对应，但系统不能把两者写死为同一个对象，因为可能存在：

- 一个法人对应多个账簿或会计准则；
- 一个 NC 账套承接多个业务组织；
- 分公司独立考核但不独立承担法律责任；
- 历史主体合并、迁移或账套切换；
- 境外主体存在不同本位币和会计期间。

核算主体至少维护 NC 账套、公司编码、科目表、会计日历、本位币、凭证模板集和接口版本。

### 4. 经营单元

经营单元用于经营责任和利润归属，例如产品中心、邮轮事业部、航服业务单元、区域公司、长线中心、短线中心。

经营单元不是天然法人，可以归属于某一法人，也可以在授权范围内代其他法人处理业务。它决定：

- 产品和业务归属；
- 收入、成本和毛利责任；
- 预算和业绩统计；
- 默认部门、利润中心和 NC 辅助核算；
- 可经营产品范围；
- 可使用的结算政策。

### 5. 组织部门

部门用于人员任职、数据权限、成本中心和管理报表，例如销售部、产品部、财务部、计调部。

部门不能承担合同、收付款和发票责任。部门可以作为收入部门、成本部门、业绩部门或费用部门进入辅助核算。

### 6. 门店经营单元

门店必须先分类，不能仅按组织树层级判断：

| 门店类型 | 法律关系 | 典型资金关系 | 典型结算关系 |
|---|---|---|---|
| 直营门店 | 法人内部组织 | 客户款进入所属法人账户 | 不产生法人间往来，按部门/利润中心核算 |
| 内部承包或非独立门市 | 法人内部经营单元 | 可使用预存额度或内部资金池 | 管理核算、提成或内部利润分配，不生成外部应付 |
| 加盟门店（非系统内法人） | 外部合作方 | 预存、代收或总部直收 | 门店对账、佣金/分润、管理费、应收应付 |
| 集团内独立法人门店 | 集团内部法人 | 自有账户或集团代收 | 内部交易、内部应收应付、内部开票和合并抵销 |
| 外部分销门店 | 外部渠道 | 账期、押金、预存或平台结算 | 渠道应收/应付及佣金结算 |

门店类型一经用于交易，不允许直接修改；关系变化应新建生效版本。

## 四、交易参与方不能再用一个主体字段表示

每一笔订单、采购、结算或财务事项都需要保存“本单各方主体信息”。以下责任可能由同一主体承担，也可能由不同主体承担：

| 角色 | 业务含义 | 主要决定内容 |
|---|---|---|
| 签约销售主体 | 与客户建立合同关系的法人 | 客户应收、合同责任、可开票主体 |
| 销售经营单元 | 实际获客、报价和维护客户的组织 | 销售业绩、部门归属、门店归属 |
| 产品归属主体 | 拥有产品经营权和定价责任的主体 | 产品归属和内部采购判断 |
| 供给/库存主体 | 持有团期、舱房、铺位、机位或采购配额的主体 | 库存占用和供给责任 |
| 履约责任主体 | 对交付旅游服务承担主要业务责任的主体 | 履约结果、质量责任、结算节点 |
| 收款主体 | 实际拥有收款账户或支付商户的法人 | 资金流水和代收关系 |
| 收入确认主体 | 会计上确认客户收入的核算主体 | 收入凭证和利润归属 |
| 销项开票主体 | 向客户开票的法人 | 销项发票和税务申报 |
| 成本承担主体 | 承担采购成本或履约成本的核算主体 | 成本和毛利归属 |
| 付款主体 | 实际从银行或平台付款的法人 | 付款流水和代付关系 |
| 采购签约主体 | 与供应商签合同并承担债务的法人 | 应付和可收票主体 |
| 进项收票主体 | 取得供应商发票的法人 | 进项票台账和税务处理 |
| 内部交易伙伴 | 集团内交易的对方法人 | 内部往来、对账和合并抵销 |

### 本单各方主体如何确定

本单各方主体不应要求销售逐个填写。系统应根据以下业务规则自动判断，并在订单确认前保存本次确认结果：

```text
当前工作主体
+ 产品归属及供给关系
+ 门店/渠道合作关系
+ 合同模板与签约政策
+ 收付款及开票政策
+ 内部交易政策
+ 主责方/代理方核算政策
= 本单各方主体确认结果
```

系统自动判断的主体发生冲突时，订单不能直接确认，应进入主体冲突处理。例如合同主体为 A、收款账户为 B，但 A-B 之间没有有效代收协议和内部结算规则时，必须阻断。

## 五、统一交易关系模型

一张客户订单不等于一条财务关系。系统需要按实际交易对象拆成一条或多条“结算关系”。

### 1. 结算关系

每条结算关系至少包含：

- 关系类型；
- 提供方和接收方；
- 应收主体和应付主体；
- 来源订单、团期、项目、采购批次或服务单；
- 结算价格及币种；
- 计价方式；
- 税务处理；
- 发票方向；
- 结算节点；
- 内部交易伙伴；
- 规则版本。

关系类型至少包括：

- 客户销售；
- 外部供应商采购；
- 集团内部产品互采；
- 集团内部专业服务；
- 门店结算；
- 渠道/OTA 结算；
- 代收资金清算；
- 代付资金清算；
- 分润/佣金；
- 客户预存和门店预存；
- 供应商预付；
- 供应商追款或退款。

### 2. 一笔业务可形成多条结算关系

例如 A 公司销售 B 公司从外部供应商采购并包装的邮轮产品：

```text
客户 -> A：客户销售关系
A -> B：集团内部产品采购关系
B -> 外部船司/供应商：外部采购关系
```

三条结算关系分别生成自己的应收、应付、结算、发票和 NC 结果，同时保存同一个业务关联号，可以反查到同一客户订单、航次和舱房消耗。

## 六、合同流、业务流、资金流、票据流和会计流

系统必须同时保存五条流，不能假定它们天然一致。

| 流 | 核心问题 | 主要对象 |
|---|---|---|
| 合同流 | 谁向谁承诺什么、谁承担法律责任 | 客户合同、供应商合同、内部协议、渠道协议 |
| 业务流 | 谁提供产品、谁占用资源、谁实际履约 | 产品、团期、航次、班期、订单、服务单、采购批次 |
| 资金流 | 钱从哪里来、进入谁的账户、最终归谁 | 到账流水、认款、付款、退款、预收预付、资金清算 |
| 票据流 | 谁向谁开票、开什么内容、金额和税务口径是什么 | 销项发票、进项发票、红票、行程单、扣除凭证 |
| 会计流 | 哪个核算主体在什么期间确认什么资产负债和损益 | 会计事项、分录、凭证、NC 返回、关账 |

五条流允许不同，但差异必须有合法配置关系。例如客户合同由 A 签、客户款由集团资金主体 B 代收时，系统需要同时生成：

- A 对客户的应收；
- B 的实际到账；
- B 代收 A 的内部应付或资金清算义务；
- A 对 B 的内部应收；
- 后续资金划拨或内部清算记录。

不能因为客户款已经进入集团某个账户，就直接把 A 的客户应收核销而不形成代收清算关系。

## 七、核心业务场景的标准核算关系

### 场景一：同一主体自营、销售、履约和收付

适用于同一法人自营标准团、邮轮、专列、研学、项目或自由行业务。

```text
客户销售应收 -> 客户收款核销
外部采购成本 -> 供应商应付 -> 付款
订单收入 + 团期/项目/订单成本 -> 业务结算 -> NC
```

不产生内部往来。部门、产品线、门店和团期通过辅助核算区分。

### 场景二：同一法人内跨部门或跨经营单元协作

例如航服部门向同一法人内的旅游产品部门供票。

此场景不生成法人间应收应付，但要形成内部管理结算：

- 航服经营单元内部收入或内部贡献；
- 产品经营单元大交通成本；
- 同一法人总账层面按公司财务政策决定是否仅做管理会计分摊，避免重复确认对外收入成本；
- 经营报表保留提供方和接收方；
- NC 若只承接法定账，内部管理收入成本可不进入法定损益，或通过专用内部结转科目并在公司层抵销。

因此“航服收入强推团期成本”必须先判断双方是否同一法人，不能对所有内部供票使用相同会计分录。

### 场景三：不同法人之间内部互采

例如 A 公司销售 B 公司拥有并履约的产品。

```text
客户 -> A：A 确认客户应收、收款和待财务确认收入
B -> A：B 形成内部应收，A 形成对应的内部应付
B -> 外部供应商：B 形成外部成本和应付
```

系统要求：

- A-B 内部交易使用统一关系编号；
- 提供方内部应收与接收方内部应付成对生成；
- 双方金额、币种、税额、结算期和交易伙伴一致；
- 内部结算价与客户售价分开；
- 双方分别推 NC；
- 集团合并层可以按交易伙伴和关系编号匹配并抵销；
- 时点、汇率或开票差异进入内部对账，不允许一方单独关闭。

### 场景四：A 销售 B 包装的外部供应商产品

必须保留两段供应链：

```text
A <-> B：内部产品结算
B <-> 外部供应商：外部供应商结算
```

A 不应直接向 B 的外部供应商形成应付，除非存在明确委托付款或债务转移协议。即使 A 代 B 付款，也应形成代付清算关系，而不是改变原应付责任主体。

### 场景五：体系外供应商直采

采购签约主体按供应商合同和订单确认形成成本及应付。供应商是谁、资源由谁提供、钱付给谁需要分开：

- 航空公司可能由 BSP、B2B 平台或票代结算；
- 邮轮船公司可能通过境内代理收款；
- 酒店品牌、实际酒店和结算公司可能不同；
- 供应商集团和具体收款主体可能不同。

系统应建立“业务资源方—供应商主档—收款账户—发票开具方”关系，不允许仅靠一个供应商名称处理。

### 场景六：直营门店销售

直营门店作为法人内部经营单元：

- 客户应收和收款归所属法人；
- 门店作为销售部门、利润中心和业绩归属；
- 店员提成是人员激励，不与客户收款混账；
- 门店内部预存若只是授信或资金控制额度，不应伪造为外部负债；
- 门店经营利润是管理结果，不是可直接提现的资金余额。

### 场景七：加盟门店或外部分销门店

加盟门店是外部合作方时，需要根据合同选择一种或组合使用的模式：

1. 总部直收客户款，门店按佣金或分润结算；
2. 门店代收客户款，形成门店应缴和资金清算；
3. 门店预存后下单，订单从门店预存账户扣款；
4. 门店账期采购，形成渠道应收；
5. 门店以独立法人身份采购产品，再自行对终端客户签约。

五种模式的应收对象、合同主体、发票对象和收入确认完全不同，不能只用一个“门店订单”类型承接。

### 场景八：集团资金主体代收或代付

集中资金管理不改变原交易债权债务。

代收：

```text
业务主体对客户应收
资金主体实际到账
资金主体对业务主体形成代收应付
业务主体对资金主体形成内部应收
内部清算后结清
```

代付：

```text
业务主体对供应商应付
资金主体替业务主体付款
资金主体对业务主体形成内部应收
业务主体对资金主体形成内部应付
内部清算后结清
```

代收代付必须保存原客户/供应商、原业务单据和银行流水，不能只生成一张主体间资金调拨单。

### 场景九：OTA 和平台月结

必须同时保存：

- 终端客户订单金额；
- 平台客户或渠道应收；
- 平台账单明细；
- 平台佣金、服务费、补贴和退款；
- 实际到账；
- 平台开票和我方开票关系；
- 平台结算差异。

平台从客户收款不代表我方已经收到资金。是否把终端客户或 OTA 作为应收对象，由合同、平台模式和开票关系决定。

### 场景十：邮轮、专列、包机和切位预付

采购付款节点早于履约和实际成本确认时，应先形成供应商预付，不得直接形成最终成本或应付结清。

预付必须依次经历：

```text
采购计划/协议付款节点
-> 预付款申请与执行
-> 供应商预付余额
-> 分摊至资源批次/航次/班期/团期
-> 实际账单及成本确认
-> 冲抵应付
-> 剩余余额转用、退回或损失确认
```

### 场景十一：航服对内供票

航服必须保存票号、PNR、航司订单号、团号、出票记录、退改记录和成本来源。

处理规则分两类：

- 同法人内部供票：形成内部管理结算和团期成本承接，不当然形成法人级内部应收应付；
- 跨法人内部供票：形成航服主体内部应收和产品主体内部应付，双方按交易伙伴推送 NC。

退票、改签和票损必须同时调整航服经营单元和产品团期，已结算对象走补充结算。

### 场景十二：客户退款与供应商追款

客户退款依据客户合同；供应商追款依据采购合同。系统形成两条相互关联但独立处理的结算关系：

```text
客户侧：应收冲减/退款执行/客户预存
供应商侧：应付冲减/供应商退款/预付退回/扣损承担
```

客户是否等待供应商退款，应由产品和合同政策决定，不能从数据库关系上强制绑定为同一状态。

### 场景总览矩阵

下表用于开发前快速判断一笔业务会形成哪些主要财务关系。它只确定关系结构，不代替后续逐项金额和分录设计。

| 业务场景 | 客户侧债权 | 供应侧债务 | 内部/渠道关系 | 主要结算对象 | 特殊控制 |
|---|---|---|---|---|---|
| 同主体自营跟团 | 签约主体对客户应收 | 同主体对外部供应商应付 | 无法人间往来 | 团期 | 收款、履约、收入确认分离 |
| 同主体自营邮轮 | 签约主体对客户应收 | 船司/代理应付及预付 | 无法人间往来 | 航次 + 舱型 | 包舱预付、舱损、固定成本分摊 |
| 同主体自营专列 | 签约主体对客户应收 | 运营商应付及预付 | 无法人间往来 | 班期 + 铺位 | 包列预付、铺损、空置损失 |
| 研学/学校订单 | 合同主体按阶段对学校或个人应收 | 基地、交通、住宿等应付 | 学校和个人多付款方 | 营期/项目 | 阶段收款、多付款方、学生颗粒度 |
| MICE/单团项目 | 合同主体按节点应收 | 项目供应商应付 | 可能含跨主体协作 | 项目 + 阶段 | 客户确认额、变更单、验收节点 |
| 自由行 | 签约主体对客户应收 | 按采购批次形成应付 | 视供给来源产生内部结算关系 | 订单 + 采购批次 | 批次成本分摊至订单 |
| 单项服务 | 服务主体对客户应收 | 服务商应付或代垫核销 | 可含内部服务 | 服务单 | 服务费收入与代收代付分离 |
| 体系外外采转售 | 签约主体对客户应收 | 采购主体对外部供应商应付 | 视主体是否一致判断 | 跟随原产品类型 | 主责/代理判断，不由外采标签决定 |
| 跨法人内部互采 | 销售主体对客户应收 | 接收方内部应付 + 提供方外部应付 | 双方对应的内部应收应付 | 原产品结算对象 + 内部业务结算单 | 内部往来单位、内部价、双方期间匹配 |
| 航服同法人供票 | 对外订单或产品订单应收 | 航司/BSP/票代应付 | 法人内管理结算 | 票/团号/航服准单 | 不重复确认法人层收入成本 |
| 航服跨法人供票 | 销售主体或产品主体客户应收 | 航服主体外部应付 + 产品主体内部应付 | 航服内部应收 | 票/团号/双方内部结算 | PNR、票号、团号、双方对应调整 |
| 直营门店 | 所属法人对客户应收 | 所属法人应付 | 部门/利润中心归属 | 订单 + 团期/项目 | 提成与客户资金分离 |
| 加盟门店总部直收 | 总部对客户或门店应收 | 总部供应商应付 | 对门店佣金/分润应付 | 订单 + 门店账期 | 分润不等于可提资金余额 |
| 加盟门店代收 | 合同主体对客户应收 | 合同主体供应商应付 | 门店代收应缴/清算 | 订单 + 门店对账单 | 客户款与门店自有资金隔离 |
| 门店预存采购 | 对门店预存负债或渠道应收 | 业务主体供应商应付 | 预存扣款和门店结算 | 订单 + 预存账户 | 充值、冻结、扣款、退款全量流水 |
| OTA/平台月结 | 按合同确定对平台或终端客户应收 | 业务主体供应商应付 | 平台佣金、扣费、补贴、退款 | 平台账期 + 订单 | 订单、账单、到账三方对账 |
| 集团资金代收 | 业务主体保留客户应收 | 不变 | 资金主体代收应付/业务主体内部应收 | 原订单 + 内部资金清算单 | 到账不改变收入和债权归属 |
| 集团资金代付 | 不变 | 业务主体保留供应商应付 | 资金主体内部应收/业务主体代付应付 | 原应付 + 内部资金清算单 | 付款主体不替代采购债务主体 |
| 客户退款及供应商追款 | 客户侧退款或预存 | 应付冲减/供应商退款/预付退回 | 客户与供应商两条链关联但不共用状态 | 售后单 + 原结算对象 | 必须反查原收款、原付款和扣损 |

## 八、主责方、代理方、全额和净额确认

### 1. 不能按“自营/外采”直接决定

收入全额或净额确认要在交易政策中判断公司在客户合同中是主责方还是代理方。关键依据包括：

- 公司向客户承诺的具体商品或服务是什么；
- 在服务转移给客户前，公司是否控制该服务或服务权利；
- 公司是否承担库存、资源、履约、退款或信用风险；
- 公司是否有定价和供应商选择权；
- 公司是否对服务组合、变更和客户投诉承担主要责任；
- 合同、发票和实际业务安排是否一致。

因此可能出现：

- 自营产品按全额确认；
- 外采但由凯撒重新组合、定价并承担履约责任的产品，仍可能按全额确认；
- 名义自营但实质只撮合并收取服务费的业务，可能按净额确认；
- 单项服务中的服务费按收入、代垫按往来处理。

系统应在“交易核算政策”中形成版本化判断结果，而不是让销售在订单上选择全额或净额。

### 2. 差额计税不等于净额确认收入

旅游服务增值税差额计税是税务销售额计算规则；会计全额或净额确认是收入确认问题，两者不能共用一个“差额收入”字段。

系统应分别保存：

- 客户合同总价；
- 会计收入确认口径及金额；
- 可扣除旅游成本及合法凭证；
- 增值税计税销售额；
- 销项发票可开范围；
- NC 收入和税务分录。

外采产品只能表示供给来源，不能自动决定上述任何一个金额。

## 九、订单与履约对象的双重归集

旅游业财需要同时按客户交易和实际履约两个方向归集。

### 1. 客户交易归集对象

客户交易归集对象回答“向谁卖了什么、应收和收款是多少”：

- 客户订单；
- 订单费用行；
- 合同和变更单；
- 付款计划；
- 订单成员或游客；
- 门店/渠道归属。

### 2. 履约成本归集对象

履约成本归集对象回答“谁在何时交付、成本归到哪里”：

- 团期；
- 邮轮航次；
- 专列班期；
- 研学营期；
- 项目或项目阶段；
- 服务单；
- 自由行采购批次；
- 航服出票或资源批次。

### 3. 两者通过分配关系连接

一个订单可以消费多个履约对象，一个履约对象可以承接多个订单。系统需要独立的订单履约分配记录，不得只在订单上保存一个团期编号。

成本也不能只挂团期总额，至少保留：

- 成本费用项目；
- 供应商；
- 资源批次；
- 受益履约对象；
- 分摊到订单或游客的规则和结果；
- 原币、本币、汇率；
- 预估、确认、应付、已付的不同金额。

## 十、正式系统需要保存的七类业务和财务记录

正式系统至少需要保存以下七类记录。这里先说明业务含义，具体数据库表和字段在后续技术设计中定义。

### 第一类：业务来源记录

订单、订单费用行、团期、项目、服务单、出票、舱房、铺位、资源消耗、供应商确认、客户变更等。

### 第二类：业务触发的财务事项

业务结果达到财务确认条件后形成财务事项，例如：

- 业务应收成立；
- 客户收款确认；
- 退款执行；
- 实际成本确认；
- 供应商账单确认；
- 应付成立；
- 付款执行；
- 预付冲抵；
- 结算确认；
- 收入确认；
- 成本结转；
- 内部交易确认；
- 发票确认；
- 调整或冲销。

已生效的财务事项不得删除；重复操作应识别为同一笔事项并返回原处理结果。

### 第三类：财务单据

应收单、收款单、预收单、预存账户变动明细、客户退款单、应付单、供应商预付单、付款单、内部业务结算单、内部资金清算单、渠道结算单、门店结算单和业务结算单。

一张财务单据只能归属一个法人和一个核算主体。跨主体场景必须拆成各主体自己的单据并保持相互关联。

### 第四类：核销与分摊记录

核销和分摊必须单独保存明细，支持：

- 一笔到账拆认多张应收；
- 一张应收多次收款；
- 一笔收款转多个订单；
- 一笔付款核销多张应付；
- 一张供应商账单匹配多个成本项；
- 一笔预付分摊多个团期或资源批次；
- 一个固定资源成本分摊多个订单；
- 一张发票匹配多张应收、应付或付款。

不允许为方便核销而复制银行流水或伪造多张原始账单。

### 第五类：结算确认记录

结算单不是重新录数，而是保存结算确认时纳入的收入、成本、收付、预收预付、发票和差异结果。

结算后新增的业务或财务结果通过补充结算或调整单承接，不覆盖原结算确认记录。

### 第六类：会计事项和分录

财务单据生效且达到会计确认条件后，按核算主体、财务事项类型、会计政策版本和会计期间形成会计事项。尚未达到会计确认条件的业务应收、业务应付、账单或结算资料只进入财务管理，不直接生成分录。系统按照会计规则生成分录草稿。

每条分录保留：

- 来源财务事项；
- 来源财务单据和明细行；
- 核算主体和账簿；
- 会计日期和期间；
- 借贷方向及金额；
- 本币、原币和汇率；
- 科目和辅助核算；
- 交易伙伴；
- 规则版本；
- 冲销来源。

### 第七类：NC 凭证与来源追溯

系统保留每笔会计事项明细，按 NC 凭证模板汇总生成凭证。汇总后仍要保存“财务事项明细—会计分录—NC 凭证明细”的对应关系。

NC 推送失败只改变推送状态，不回滚业务单据和会计事项。

## 十一、NC 辅助核算和凭证承接

NC 映射至少需要以下维度：

| 维度 | 来源 |
|---|---|
| 核算主体/公司 | 法人及账簿映射 |
| 部门/成本中心 | 业务组织和责任部门 |
| 利润中心/经营单元 | 产品归属和经营责任 |
| 客户 | 客户或渠道结算对象 |
| 供应商 | 采购付款对象 |
| 内部往来单位 | 集团内部交易的对方公司 |
| 产品类型 | 跟团、邮轮、专列、自由行、研学、MICE、单项服务、航服等 |
| 业务线/团队类型 | 境内、出境、专项等 |
| 订单 | 客户交易归集对象 |
| 团期/项目/服务单 | 履约和结算归集对象 |
| 门店/渠道 | 销售来源和分润对象 |
| 税务政策 | 一般、免税、旅游差额、代理票务等 |
| 币种和汇率类型 | 交易及会计折算来源 |

具体哪些维度作为 NC 辅助核算、哪些只保留在业务系统，需要根据凯撒现有 NC 科目表、辅助核算档案和接口能力确认。业务系统应保留全量，不应受 NC 当前字段数量反向限制。

## 十二、内部交易必须成对、匹配和可抵销

内部交易至少需要以下对象：

- 内部交易关系；
- 提供方组织和接收方组织；
- 提供方法人和接收方法人；
- 内部产品或服务类型；
- 内部定价规则；
- 发票规则；
- 结算周期；
- 提供方内部应收；
- 接收方内部应付；
- 双方会计事项；
- 对账差异；
- 合并抵销标识。

双方单据使用同一个内部往来关联号，但各自拥有独立单据号、状态、会计日期和 NC 凭证号。

内部对账至少匹配：

- 双方法人；
- 交易伙伴；
- 内部关系编号；
- 来源订单/团期/批次；
- 原币和本币金额；
- 税额；
- 会计期间；
- 发票；
- 双方凭证状态。

差异可能来自时间、汇率、税额、单据遗漏和双方调整。系统必须支持一方已入账、另一方待处理的在途状态，不能为了“自动对平”覆盖事实。

## 十三、收入、成本和结算时点必须分开

### 1. 收款确认

确认钱已经真实到账并归属某张应收，只影响资金、应收、预收或预存，不自动代表服务已经履约。

### 2. 收入确认依据

系统根据产品和履约类型形成待财务确认的收入记录：

- 标准跟团、邮轮、专列、研学：通常基于出行/履约进度或完成节点；
- MICE 和项目：按合同履约义务或验收阶段；
- 单项服务：按服务完成或阶段履约；
- 航服票务：按出票、代理服务完成和退改结果；
- 平台和代理业务：按主责方/代理方政策确认全额或净额。

最终会计时点和金额由财务政策确认，不应在前端页面固定写死。

### 3. 成本确认

成本依据资源实际消耗、履约事实、供应商确认、票号/房号/人数和扣损等形成。供应商尚未开票或付款，不代表成本没有发生。

### 4. 应付确认

应付表示对特定付款对象的现时债务已经成立。可能来源于账单确认、合同付款节点、资源交付或暂估规则。

### 5. 业务结算

业务结算用于确认某一结算对象在当时的收入、成本和毛利结果，不替代收款、付款和收入确认事项。

## 十四、五组必须持续对账的账面

### 1. 订单侧对账

```text
有效客户交易金额
= 有效业务应收 + 尚未到应收节点的有效付款计划

有效业务应收
= 已确认收款核销 + 预收核销 + 预存扣款核销 + 待收余额
```

已经批准并生效的减价、退差和取消直接进入有效客户交易金额及有效业务应收，不在公式外再次加回。

### 2. 资金侧对账

```text
资金流入原始记录
= 已确认收款分配 + 待认领金额 + 其他已确认资金转入

资金流出原始记录
= 已确认付款 + 已确认退款 + 其他已确认资金转出
```

银行、平台和现金按流入、流出分别核对；退款、付款退回和资金清算不能与客户入款混在一个无方向的等式中。

### 3. 供应商侧对账

```text
有效实际成本
= 实际成本原额 + 已确认损耗 + 成本增加调整 - 成本减少调整

有效应付
= 付款核销 + 预付冲抵 + 待付余额 + 供应商应退款抵减

供应商确认结算金额
= 已形成正式应付 + 待形成应付或待调整金额
```

实际成本、供应商账单和应付分别核对，不要求三者在每个时点数值相等；差额必须能够解释为暂估、账单未到、业务待确认、预付或调整。

### 4. 结算对象对账

```text
业务结算收入 - 结算成本 = 业务毛利

业务毛利
- 另列的渠道/门店费用
- 未在收入中冲减的公司承担优惠
= 结算贡献
```

已经冲减客户交易价格或收入的优惠不得在结算贡献中再次扣减。

### 5. 业务系统与 NC 对账

```text
已生效会计事项
= 已生成凭证 + 经批准暂缓入账事项

应推送凭证
= 待推送 + 推送中 + NC已接收 + NC拒绝 + 结果待确认
```

任何报表都应从上述同源数据生成，不能再维护独立的财务 Excel 结果表。

## 十五、关键底层约束

1. 金额字段至少保存原币金额、本币金额、币种、汇率、汇率类型和汇率日期。
2. 金额使用定点小数或最小货币单位，不使用浮点数。
3. 财务单据必须有业务日期、会计日期和创建日期，三者不能混用。
4. 主体、客户、供应商、账户、税务和会计映射全部使用生效日期版本。
5. 订单确认时保存当时的主体和政策确认记录，后续主数据变化不反向篡改历史订单。
6. 同一笔业务事项只能生成一次有效财务结果，重复提交不能重复记账。
7. 已生效财务事项不删除，只能冲销或生成调整事项。
8. 所有跨主体单据必须保存内部往来单位和双方对应单据关系。
9. 所有收付款必须能追溯到真实的银行流水、支付平台流水、POS 流水、现金收付记录或预存账户变动明细。
10. 所有结算差异必须有来源、责任方、确认结果和处理单据。
11. 所有 NC 凭证必须可反查到会计事项、财务单据、业务来源和原始流水/账单。
12. 业务和财务状态分离，NC 失败不回滚业务状态。

## 十九、外部成熟实践参考

本文吸收的不是其他系统的页面形态，而是以下成熟设计原则：

- Oracle 将法人、业务单元、账簿和内部交易组织分开；内部交易由提供方和接收方形成应收应付，并通过交易伙伴和内部平衡规则承接。
- Oracle 子账会计按照会计事项、事项类型、来源数据、分录规则和辅助核算生成子账分录，并保持总账到子账的审计追溯。
- SAP Universal Journal 强调财务会计与管理会计共享同一事实来源，减少重复数据和账间对账；内部交易匹配按公司与交易伙伴持续识别差异。
- IFRS 15 主责方/代理方判断以向客户承诺的特定服务及转移前是否控制该服务为核心，而不是只看产品由谁最终履约。

## 二十、订单金额归属和多主体结算补充基线

依据 A 主体销售 B 主体外采产品的业务讨论，跨主体业务除确定销售、产品、采购、收付款和开票主体外，还必须把订单上的每个金额归到明确关系：

```text
金额来源 → 应付方 → 取得方 → 规则依据 → 所属法人 → 管理归属 → 结算与NC去向
```

1. A—客户、A—B、B—外部供应商是三段独立交易，使用业务关联号连接，但不得共用客户、应收应付、收付款和发票。
2. 同名“结算价”必须带交易双方。A 应付 B 的内部结算金额与 B 应付供应商的采购结算金额不是一个金额字段。
3. 对外展示价、合同金额、客户应付、现金实付、优惠抵扣、销售差额、内部结算、采购返还和供应商最终应付分别保存。
4. 公司法定收入成本和部门管理贡献分开。同法人部门差额不形成法人间往来；跨法人必须成对形成内部应收应付并分别进入 NC。
5. 全额上缴后返还与扣除后净额上缴分别保存真实资金。净额上缴不得伪造全额银行流水，全额上缴不得只保留净额。
6. 多张销售订单可以归集到同一出发日期和履约团期；不同出发日期不得合并为一个新团期。付款可以批量，但核销必须回到原应付和团期。
7. 团期业务结算、双方对账、应付成立、付款申请和银行付款是不同环节，不能用一个“结算完成”状态替代。

详细数字案例见[业财场景确认手册02：订单收款与多主体结算深化案例](业财场景确认手册02-订单收款与多主体结算深化案例.md)。
