# 合同模板编辑页重审设计

日期：2026-09-29｜状态：设计已落实到实际原型页面

> 用户刷新复核后，本设计已实施到模板新增／编辑页。实际变化、验证及限制见[工作区实施验收](合同模板编辑工作区实施验收-20260929.md)。以下“本轮仅设计／尚未实施”保留设计阶段记录，现行状态以实施验收和进度第三、四节为准。

## 一、设计结论和角色

本轮回应用户对 `admin/contract-template-edit.html` 的复核：填写内容、资料来源、平台对应、明细表和正文插入交叉重复，管理员无法判断先做什么。

建议保持一个模板编辑页，改成“模板信息＋文书工作区”，以文书生成方式决定工作区。平台模板显示该模板要求的资料，公司文书显示正文及其填写位置。资料来源跟随选中的内容出现；接口参数归技术维护；签署安排单独处理；预览和审核覆盖整份模板。不恢复四个配置Tab，也不再并排放两张字段长表。

主要使用人是集团合同管理员／法务，任务是维护一份可以发布给业务使用的模板版本；技术管理员负责接口接入和逐模板技术核对。上游是已审定文本、可用平台模板、公司授权和ERP现有业务资料；下游是合同规则／产品选用和销售合同准备。销售在订单里核对客户与本次约定，不配置模板来源或接口参数。

本轮交付现状审查、页面结构、可操作设计示意和实施验收要求；没有改动业务HTML、JS、CSS。此前多平台三步已交付的原型仍保留，新反馈尚未实施，不能用之前的测试数量代替本次设计验收。

## 二、已知的平台能力与待核实边界

- 12301官方《电子合同和权限系统操作指南》（2024.01）展示先选合同模板，再填写产品费用、游客／代表、其他约定，最后预览创建的使用流程。此前真实后台核查还记录了境内、邮轮、研学、代订等模板的资料差异。它们能证明网页功能，不能证明本公司接口的模板编号、表格参数、自由编辑正文或文件上传签署能力。
- 法大大官方SaaS API产品页公开介绍本地文件和合同模板两种签署来源，以及文档模板和签署模板可分别制作、组合使用。因此页面应区分“平台生成文书”和“ERP生成文件后交平台签署”。本公司开通的接口版本、授权范围、重复表格、签章定位方式及文件限制仍待核实。
- “境内走12301、公司邮轮走法大大”是本公司的模板选用场景，不是写死的平台分类。12301也有邮轮目录；法大大也有平台模板。示范文本名称不能自动当作接口可识别的模板编号。

来源：[12301官方操作指南](https://static.12301.cn/econtract/doc/%E6%97%85%E8%A1%8C%E7%A4%BE%E7%94%B5%E5%AD%90%E5%90%88%E5%90%8C%E5%92%8C%E6%9D%83%E9%99%90%E7%B3%BB%E7%BB%9F%E6%93%8D%E4%BD%9C%E6%8C%87%E5%8D%97.pdf)、[法大大官方SaaS API产品页](https://www.fadada.com/product/saasapi)、[本项目12301后台核查](12301真实后台逐页核查与ERP原型增改方案-20260928.md)。公开资料核查日期为2026-09-29；本轮未进入真实平台办理合同。

## 三、当前页面为什么乱

代码依据为编辑页实际加载的 `shared/contract-settings-ui.js`、`shared/contract-platform-ui.js`、`shared/contract-template-fields.js` 和 `shared/contract-platform-tables.js`。

| 当前入口 | 问题 | 建议处理 |
|---|---|---|
| 合同文本、业务结构、签署平台、文书生成方式分别选择 | 管理员自行组合，容易把示范正文、平台模板和公司自有文本混为一谈 | 新建时先确定可用的文书来源，再绑定平台；已有版本顶部显示确定的办理方式 |
| 填写内容与资料来源长表 | 先维护项目，再回正文放置；未使用项与实际出现项混在一起 | 平台模板按所需资料分组；公司文书只列本份文书已使用的填写项，点击位置直接配置 |
| 明细表配置与平台表格对应 | 同一整组资料来源重复选择，正文列和接口列又混在一起 | 业务管理员选择预设表格并决定展示列；技术人员维护平台接收列，复用同一份合同资料 |
| 合同正文插入填写项／明细表 | 平台标准模板也暴露正文插入，文本标记要求用户理解制作机制 | 只有ERP制作公司文书时显示“插入内容”；平台正文按取得的版本展示，只配置允许填写的区域 |
| 平台对应 | 参数名、格式、枚举与业务取值同层 | 移入技术人员专属“对接检查”，业务管理员只看到未完成事项和责任归属 |
| 签署设置、正文签署项、页末附件 | 角色、位置、文件范围分散，容易把签名当普通姓名字段 | 一个签署设置入口；文件清单统一管理正文、需签附件和证明材料 |

## 四、页面具体长相

### 4.1 页面外层：一页、一个主要工作区

顶部：合同模板 / 模板名称；版本与草稿／待审核等主状态；右侧“签署设置、预览、保存草稿、提交审核”。已提交版本只读，修订建立新版本；已有合同继续采用原版本。

顶部下方是紧凑的模板信息：模板名称、适用公司、适用业务／地区、生效范围，展示平台和文书来源。低频信息可以展开编辑，版本自动生成。适用范围只约束能否使用；哪类订单默认采用哪份模板仍由合同规则管理，不在这里重复配置。

正文区按以下三种情况呈现。新建时只提供该平台和公司已确认可用的方式；未核实的方式可保存草案，但不能伪装成正式可用。已发布模板更换平台或生成方式须建立新版本并重新核对。

### 4.2 12301境内：平台模板资料配置

```text
全国版境内旅游合同   V2 草稿                签署设置  预览  保存草稿  提交审核
12301 · 平台生成文书 · 适用公司/业务                     编辑模板信息

平台模板：全国版境内旅游合同      对接情况：待核对       技术人员：对接检查
┌───────────────────────────────┬──────────────────────┐
│ 旅行社与游客                  │ 当前选中：合同总额   │
│ 签约旅行社    实际签约公司     │ 来源：本份合同分配金额│
│ 游客名单      本份覆盖游客     │ 必填：是（模板要求） │
│ 行程与费用                    │ 销售修改：不允许     │
│ 出发日期      订单采用出行日期 │ 空缺时：返回合同准备 │
│ 合同总额      本份合同分配金额 │ 示例：12,600.00元    │
│ 其他约定 / 购物 / 自费 / 附件  │                      │
└───────────────────────────────┴──────────────────────┘
```

- 先选已登记的平台模板，带出它要求的资料组和默认来源。逐项展示“合同内容、来源、必填／条件”，点击行在右侧查看或调整允许修改的属性。只对异常和需要人工补充的项目突出提示。
- 正文通过“查看范本／预览”查看；取得正式范本后展示原文。没有正式范本时清楚区分填写结构示意与平台真实预览，不用ERP模拟正文冒充。
- 没有通用的“插入填写项”“插入明细表”按钮。新增资料必须有平台模板对应能力；其他约定、补充文件等也只能使用该模板明确支持的位置。
- 12301所需技术传递资料可能不出现在正文，如联系人或平台办理信息。这些在对接检查中单独核对，不能为了传参数强行插入正文。

### 4.3 法大大邮轮：公司制作文书后签署

```text
邮轮旅游合同   V3 草稿                     签署设置  预览  保存草稿  提交审核
法大大 · ERP生成合同文件 · 邮轮                         编辑模板信息
┌────────────┬─────────────────────────┬──────────────────┐
│ 合同文件   │ 正文                     │ 当前选中         │
│ 合同正文   │ 插入内容 ▾               │ 游客名单         │
│ 行程附件   │ 游客代表 [游客代表姓名]  │ 来源：本份覆盖游客│
│ 舱房约定   │ 合同总额 [合同总额]      │ 展示列           │
│            │ [游客名单：实际表格]     │ 姓名 / 证件 / 舱型│
│ 所用填写项 │ [航程安排：实际表格]     │ 空缺时：不能生成 │
│ 游客代表   │ 固定条款及补充约定       │ 多行自动增加     │
│ 合同总额   │                          │                  │
└────────────┴─────────────────────────┴──────────────────┘
```

- 左侧列出正文及附件；其下是当前文件已经使用的填写项，可定位。中间是文书内容；右侧只配置当前选中的一个项目／一张表。三者是同一套内容的不同视角，不能分别创建三份配置。
- 固定条款由法务维护。常规文书采用受控段落、填写位置和表格编辑；原型不承诺任意Word文件无损转换为在线编辑器。复杂正式版式可沿用经审核的模板源文件和专门文书制作工具，ERP登记版本与填写位置；正式生成工具另行核实。
- “插入内容”只有一个入口，分类为现有业务资料、预设明细表、自定义补充填写。选定后在当前位置生成填写位置并立即打开属性，不先去另一张表新增再回来插入。普通管理员不输入程序标记。
- 已有资料自动带默认来源；核心公司、金额和本份游客范围禁止随意改取值。自定义项填名称、格式、是否必填、销售在哪一组补充；本次客户意愿不得设为自动同意。
- 同一资料多次出现在正文中共用一个业务值，但保留各自位置。移除最后一个正文位置，仍需检查它是否被附件、签署或平台办理使用，不能直接删除资料定义。
- 生成完成的文件交法大大签署时，正文中的每个填写项不再逐个对应法大大正文参数；平台仍需文件、签署人、企业用章及签署位置等办理信息。

### 4.4 法大大已有平台模板

采用与4.2相同的“平台模板资料配置”布局；选择文档模板及适用签署模板，ERP为平台控件提供资料。正文与控件在其规定的编辑位置维护，不在ERP复制出第二份自由正文。重复表格和签署模板能否引用，按所开通版本核实。不能因为平台是法大大，就固定显示公司文书编辑器。

接口未覆盖时使用已经存在的平台办理流程，模板页记录需准备的资料和附件；不呈现虚假的自动生成或自动传递已成功。

## 五、资料来源和明细表如何收敛

### 5.1 普通填写项只出现一次业务配置

| 例子 | 建议默认来源 | 管理员能配置什么 | 签约时怎么处理 |
|---|---|---|---|
| 旅行社名称 | 本单实际签约公司 | 展示名称／格式；来源受控 | 随签约公司带入，章与公司一致 |
| 合同总额 | 本份合同确认分配金额 | 展示格式；来源受控 | 分签不重复采用整单金额 |
| 出发日期 | 本单采用的出行日期 | 文书日期格式 | 缺少日期回合同准备／来源核对 |
| 其他约定 | 销售本次补充 | 是否必填、填写分组、可调整范围 | 销售在本单补充，变化重审 |
| 客户是否同意拼团 | 本次客户确认 | 条件必填及证明要求 | 不用产品建议代替客户确认 |

选择来源仅允许同含义、同层级的业务资料。来源、固定文字、销售填写三种方式只在适用项目出现，不能把所有项目都开放成自由选择。

### 5.2 明细表是完整业务内容，不是高级字段映射

例如选“游客名单”，默认采用本份合同覆盖游客，并提供已知列；选“每日行程”，采用本单确认的行程版本。管理员选择可选展示列、业务列名及顺序；必需列不可删除。无需重新选择“姓名从哪个字段来”。

右侧表属性只保留：表名、整组来源（核心范围只读）、展示列、空资料处理。排序沿用业务顺序；只对确有业务必要的表提供可选排序，不默认放“正序／倒序”设置。

表格提供0行、1行、多行样例。已有安排但资料缺失必须提示缺项；已确认无购物／自费可显示“无安排”，两者不能混为一个空数组。长表分页重复表头，整行及签署区不得被截断。表格是正文／附件真实表格，不生成一长段逗号拼接文本。

平台模板的列和重复区域由平台定义。业务管理员核对资料；技术人员负责目标表格、逐列含义和格式转换。两边复用同一来源定义，但正文未引用的资料也可能被平台要求，不能把正文清单当作全部接口资料。

## 六、平台对应放在哪里

分两层维护，不把所有模板差异塞进全局接口配置：

1. `admin/interface.html`：连接、公司授权、平台共用参数、结果查询及通知校验，由技术管理员维护。
2. 当前模板的“对接检查”：仅技术角色可编辑，保留与该模板版本绑定的具体平台模板、控件／表格对应及格式规则。复用已登记的业务资料，禁止重复定义业务来源。普通管理员只见“可以使用／有N项待核对”及具体业务影响。

使用文件签署时，只检查文件和签署办理信息，不显示整页正文参数。使用平台模板时，检查平台要求的全部资料，包括不入正文的办理资料。技术配置保存不等于接口验证成功；在原型里可以用明确标记的正常／异常样例演示，真实发布条件以接口核对结果为准。

## 七、签署设置、预览及发布

“签署设置”是当前模板的唯一配置入口：明确哪些角色要签、签哪些文件、签署顺序及位置。正文中的游客姓名只是文本，不是签名位置；游客名单也不等于所有人都必须签。

模板设置角色及规则，具体人员由销售按本份合同确定；我方公司及可用章来自公司授权。签署文件与仅供审核的授权证明分开，避免把证明材料自动发给全部游客签署。平台模板使用其已配置的签署位置／角色；文件方式在最终生成文书上核对位置，动态表格变长后重新检查。具体坐标、关键字或控件方式随平台能力确定。

“预览”打开整份样例文书及附件，可选择正常、缺项、多游客／长行程样例；同时看销售需要补哪些内容和哪些角色在哪些文件签署。平台真实生成结果与ERP参考预览须显著区分。改正文、来源、表格列、签署或附件后，之前的预览确认失效。

“提交审核”沿用现有模板内部审批，只提交完成配置的版本；真实平台核对和法务文本审核分别记录。已启用版本保留；新版本通过前不替换产品引用和在途合同。审核通过不等于平台创建签署，测试也不得向真实客户发通知。

## 八、从配置到业务使用的两条例子

- 境内游：管理员选12301境内平台模板 → 核对它所需资料及补充约定 → 确认签署规则与公司适用 → 样例预览、审核发布 → 合同规则设为相关业务默认／产品指定 → 销售带入订单资料、确认代表及客户选择 → 原审批和12301办理流程。
- 邮轮：法务维护公司邮轮文书 → 插入本份游客、航程、费用和舱房约定 → 配置法大大签署角色及文件 → 长表样例预览、审核发布 → 邮轮产品沿用／指定 → 销售补齐本次约定并预览完整文件 → 原审批和法大大办理流程。

两条路径都在销售合同准备中汇合。资料缺项回当前准备页处理；授权／模板失效提示具体集团配置责任；接口未覆盖按已设置的平台办理，不悄悄改平台。签署结果、正式文件、监管和后续变更继续使用现有多平台原型，不重做一套。

## 九、拟修改范围与验收

| 业务要求／财务边界 | 当前功能及缺口 | 拟修改页面／流程 | 验收方式 |
|---|---|---|---|
| 管理员理解不同生成方式 | 已有方式字段，但工作区相同 | 编辑页与直接共享UI，新增时引导选择，已有时按方式展示 | 12301平台、法大大文件、法大大平台三种界面互不混用 |
| 单一资料配置入口 | 来源表、正文插入、平台表格重复 | 文书工作区、右侧属性和技术对接检查 | 插入、改名、多位置复用、移除、取消、保存后配置一致 |
| 明细表完整且范围正确 | 已有整组来源和列配置，操作过重 | 预设表格与受控展示列 | 0／1／多行、本份名单、分签金额、线路版本隔离、缺项均正确 |
