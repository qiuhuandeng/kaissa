# 电子合同多平台协同与定制模板完善方案

日期：2026-09-28。状态：第1步集团配置、第2步销售准备与发起、第3步结果与后续的业务原型均已完成，详见[集团配置验收](电子合同多平台集团配置第一步实施验收-20260928.md)、[销售与后续验收](电子合同多平台销售与后续实施验收-20260928.md)和[页面复核清单](电子合同多平台页面变更复核清单-20260928.md)。用户已明确要求连续执行；第三节保留实施前核查依据，不能用于覆盖当前进度。真实平台及PDF签章、正式监管接入仍未验收。

## 一、需求与本次边界

用户此前说明：现有12301模板接口覆盖不全，固定模板无法满足所有业务。本轮进一步明确公司接下来同时支持法大大，境内游采用12301模板、邮轮有法大大模板，并要求梳理admin端接入、模板配置和业务端应用。方案据此将法大大作为本次明确要支持的平台；采购版本、实际开通权限及正式账号尚未核实，不把“支持法大大”的需求理解为已经采购或完成生产接入。研学等其他定制场景保留此前方案范围。

目标仍是完善可操作原型，真实账号、正式接口和生产联调不是本轮交付条件。最初按方案交付；用户随后授权执行并要求连续完成，现已复用原字段、表格、合同准备、审批及多人签署完成三步原型，当前状态以文首验收为准。

主要使用人及上下游：集团法务和合同管理员准备、发布可复用模板；技术管理员维护平台连接和公司授权；产品人员选用模板；销售从已确认订单准备本份合同并发起签署；审批人审核具体文书；签署结果和文件回到同一合同记录，后续变更、解除及售后引用该记录。收付、退款和结算仍由原有业务与财务模块办理。

## 二、总体结论

**保留一套ERP合同管理，按模板确定签署平台；合同文本、文件生成、电子签署和监管报送分别管理。** 不按供应商拆两套销售菜单，也不让产品或销售重复选择平台。

| 业务示例 | 采用文本 | 文件如何形成 | 签署办理 | 监管处理 |
|---|---|---|---|---|
| 境内参团游 | 适用的12301标准模板 | 按可用接口填写平台模板；接口不覆盖则到平台办理 | 12301 | 按该渠道实际受理、签署、监管结果分别记录 |
| 出境参团游 | 适用的12301标准模板 | 同上 | 12301 | 同上，不能以取到编号代替签署或报送完成 |
| 定制研学 | 公司批准的研学合同及附件 | 建议ERP生成完整文件；也可采用已验证的第三方模板填充方式 | 法大大等获选平台 | 根据适用要求确定，不能默认豁免或默认可上传12301 |
| 定制邮轮 | 公司批准的邮轮合同、舱房及岸上安排等 | 同上 | 法大大等获选平台 | 同上 |
| 省级示范、企业服务及其他定制场景 | 具体适用文本及版本 | 由该模板配置确定 | 由该模板配置确定 | 由适用的报送要求确定 |

这是业务默认方向，不把“研学／邮轮”永久等同于第三方。原12301研学、邮轮和省级示范模板仍可保留为适用时的候选，企业自有定制版单独管理。产品类型、文本来源和签署平台不能用一个字段代替。

为控制第一版复杂度，一个已发布模板版本确定一种签署平台及一种文件生成方式。需要另一平台同时办理时采用另一个明确发布的模板版本或方案，不在销售送签时临时更换。技术凭据更新不等于文本修订，但在途合同必须保留原平台和原申请关系。

## 四、模板及“平台对应”如何改

### 4.1 页面使用角色与结构

集团“合同管理 → 合同模板 → 新增／编辑”仍是模板准备页。保持适用信息、合同填写项和正文的业务主线，增加必要的签署设置；技术对应放受控抽屉，不让法务填写接口参数。

| 内容 | 配置方式与作用 |
|---|---|
| 适用信息 | 实际签约公司、产品类型、旅游范围、签约对象及必要的省级条件继续保留 |
| 合同文本 | 区分平台标准文本与公司自有文本，分别留存正文、来源、版本和附件。标准正文不可因改用第三方就随意变更 |
| 签署平台 | 选择已登记的12301或第三方；下游自动带出，平台选择不替代模板适用性 |
| 文件生成方式 | 由实施人员按能力配置“填写平台模板”或“ERP生成文件”；平台模板接口未覆盖时明确“需到平台办理” |
| 合同填写项 | 继续维护ERP对应资料、固定条款、签约时填写项和必要条件；所有平台共用同一套本份合同事实 |
| 明细表 | 复用游客、行程、购物、自费、费用等现有整组来源及列对应；保留当前线路、方案及版本范围，不另建重复业务台账 |
| 签署设置 | 必要签署角色、企业／个人、监护或代理关系、同时或按顺序签署、需盖章的文件及位置。只开放平台已确认支持的选项；具体名单在合同准备中确认 |
| 发布校验 | 内容和来源可用、必要签署安排可表达、公司具备该平台办理条件、样例文件与签署位置正确。原型用明确样例，不把“待核实”伪装成正式可用 |

模板正文审批与平台技术检查分工：法务审批文本和适用条件，实施人员验证生成及传递配置；公司授权和印章仍引用接口页。发布一个可办理版本应有两类依据，不能由销售勾一个“已核对”越过缺项。

### 4.2 两种数据传递方式

**填写平台模板：** ERP已确认资料 → 合同填写项／明细表 → 该平台模板的控件或表格 → 平台生成待签文件。保留现有普通项、整组来源和逐列对应，但配置必须属于指定平台和模板版本。第三方动态表格、增行、附件及签署控件能力需要实际接口确认，不能因后台界面有表格就推断接口支持。

**ERP生成文件（定制合同建议优先采用）：** ERP已确认资料 → 获准合同版式 → 完整待签文件 → 第三方签署。名单、购物、自费等多行内容在ERP生成文件时排版；第三方接收完整文件及签署安排，不需要再次把每一列对应为第三方模板字段。

文件方式下，“平台对应”只维护文件提交、签署角色和位置等实际需要的技术关系；ERP资料与正文位置、明细列的对应仍在合同填写项中。已有ERP表格来源配置继续复用，不要求产品再填一套表格，也不为传递配置强行新增正文内容。

平台和ERP不能各自维护一份同时生效、互相漂移的正文。一份发布版本明确以哪边的批准文书为准，另一边保存引用及审阅文件。签署平台生成文件时，应取得并核对实际待签文件；取不到预览的具体能力问题要单独登记，不把ERP示意预览称为最终待签文书。

### 4.3 定制文件必须补齐的主流程能力

- 合同正文、行程及需要共同签署的附件组成明确的文件清单；区分“共同签署文件”和“仅供核对材料”，不能只把材料上传成功算作已签附件。
- 0行、1行、多行及跨页的表格有确定处理方式；未取得资料与确实无安排区分，必需表格不能静默漏行。
- 多行导致页码变化时，签字盖章位置仍正确。可以由生成器计算位置或使用平台支持的定位方式，不能写死最后一页页码；具体接口方式待核实。
- 多人签署明确每个必要签署人应签哪些文件、覆盖哪些游客或哪一企业。成人、监护代签、企业代表按身份和授权关系处理，不能只按手机号去重。
- 送审、发起和客户实际签署使用同一份确定文件。正文、名单、金额、附件或关键签署安排改变后重新生成、预览并按审批规则重审；不能审批一份文件、发送另一份。
- 正式文件转换、分页和签署定位由开发实现；原型展示样例生成、完整预览及异常，不以生产文档引擎作为原型完成条件。

## 六、完整办理流程与状态

### 6.1 正常流程

1. 公司资料与各平台授权准备好；法务、实施人员完成模板内容、取值、签署安排及发布。
2. 合同规则确定业务默认模板；产品可以指定一份适用模板。产品明确指定时不再强制先有默认选模规则，但仍检查适用性、审批及付款要求。
3. 销售从订单进入合同准备，确认覆盖名单、签署身份、金额和约定。系统读取本份合同使用的线路／方案／服务版本及对应资料。
4. 生成并核对本次待签文件，检查必要签署人的文件范围与位置。适用内部审批时，审批的是这次确定版本。
5. 发起签署前重新检查授权、订单和付款条件；按模板确定的平台创建一次签署申请，保存真实返回的办理号，或明确结果待核对。
6. 各方按约定顺序签署并完成必要盖章。ERP查询或接收可信平台结果，记录每方实际进度；客户页面返回成功不是完成依据。
7. 必要签署全部完成，确认已签署；取得完整已签文件及可取得的签署证明，保存归档。文件暂未取得继续补取，不倒退签署事实。
8. 根据已确认适用要求办理监管报送；与签署、归档分开记录。有的渠道在发起时取号，有的在签后提交，按实际接口安排，不统一硬编码成“签后必报12301”。

签署完成、文件齐全和应办报送办结是三个不同结果，不能用一个“成功”混在一起。订单签约覆盖仍以已确认的必要签署和原版本规则判断；监管或归档缺口是否限制后续出行，由既有或另行确认的业务政策决定，不在本次擅自设定。

### 6.2 12301接口未覆盖的模板

模板登记为“需到平台办理”。ERP完成资料准备与内部审核后，提供本次填写资料及到12301办理入口；经办人按权限登记平台办理号、补充平台实际文件，核对人员、金额、正文和审批版本。已有查询／文件接口的部分只使用已确认能力。

若平台实际待签文件与送审稿有差异，签署前回到核对／审批环节；已签后才发现差异则进入合同异常和变更处理，不倒填审批通过。没有查询能力时明确人工核对来源、时间及证据，不能模拟成自动同步。平台外办理入口必须先核对是否已有申请，避免重复创建。

### 6.3 主状态和辅助结果

沿用草稿、待审核、审核退回、待签署、签署中、已签署、已撤销、已解除等主状态。原企业线下合同待归档／已归档分支保留，第三方线上签署不能一概伪装成线下归档。

| 情况 | 业务判断与后续处理 |
|---|---|
| 创建请求超时，是否受理未知 | 保留原申请并核对结果，不重复发起、不切另一平台重建 |
| 明确未受理且尚无签署任务 | 修复授权或资料后重试；需要更换模板／平台时显式重新准备，按变化重审 |
| 已受理或部分签署 | 固定原平台、文件及签署范围；不能用另一平台替换未完成的几个人 |
| 签署链接到期 | 在原任务仍有效且平台支持时取得新入口；不能把链接到期当成合同失效 |
| 拒签、合同任务到期或平台退回 | 保留具体结果；根据平台实际终态与业务选择办理修订、撤销或新申请，不自行改为已解除 |
| 全部签完但文件获取失败 | 主状态仍已签署，文件待获取；补取原任务文件，不能创建新合同 |
| 已签署但报送失败／结果未知 | 保留签署事实及文件，单独核对原报送申请，不让客户重复签署 |
| 我方印章授权到期 | 区分新申请阻断与在途查询／文件服务；存量任务如何继续由实际权限判断，不借其他公司章完成 |
| 平台不提供解除接口 | 仍可按公司流程准备解除协议并取得必要方同意；区分原平台任务处理与业务解除依据，不能把撤销任务当成解除已签合同 |

必要签署人、代表关系和我方章全部满足本模板要求后才能标记已签署；平台原始结果要留存，未知状态不能默认成功。列表只显示一个主状态，平台、文件及监管的辅助结果放详情或必要筛选中。

### 6.4 变更、补充协议与平台切换

已签正文不覆盖。补充协议关联原合同，新版本保留旧文件、审批和签署记录；新合同未完成时不提前替代原合同覆盖。模板或默认规则改变只影响新办理，已有版本不自动换平台。

默认在原平台处理已有合同的后续签署。确需跨平台重签或另签补充协议，应作为明确的新办理，记录原合同、变更原因、必要同意及原申请处理结果；平台不能操作原平台任务时，不宣称已自动撤销或解除。具体法律文本及生效约定由法务确定。

## 七、监管配置边界

公司同时拥有两平台签署授权，不代表所有第三方合同都能报12301，也不代表第三方签署后无需监管处理。需分别确认适用业务、公司及地区要求、接收渠道、报送时点、内容、附件和变更／解除后的处理。

建议由获授权管理员从合同规则页的“监管要求”独立配置入口维护公司、业务及地区适用要求，不塞进每条默认选模抽屉，也不把它作为默认选模的匹配条件。同一条件存在冲突时阻止启用；产品指定模板即使没有默认选模规则，仍按实际公司和业务核对监管要求。界面先使用待确认、需要报送、经确认不适用，正式“不适用”须有确认依据。接口页只维护接收能力及技术记录，合同详情显示该份适用结论和办理结果。

原型可以用明确的已确认样例演示需报送与不适用两类，以及待确认异常；公司真实政策继续待确认。自动报送接口未开放但存在获准人工路径时保留人工登记及证明；路径本身未确认时显示待处理，不能以勾选“已备案”制造结果。

## 八、面向开发的承接建议

先保持业务对象统一：订单合同、模板版本、必要签署方、已签文件、报送记录分别可追溯。现有合同模块不要按供应商复制两份。

1. 平台连接与公司授权：现有草案已开始采用平台连接集合和“公司＋平台”授权关系，保留单12301引用供旧界面使用；继续核对所有页面读取和保存是否采用对应关系。公司经营资料独立复用；凭据不进入合同文书或前端演示数据。
2. 模板版本：保留正文版本、资料来源及表格列配置版本、文件生成方式、签署平台及对应版本。合同创建时记录本次采用值，不能送签时读取最新映射覆盖审批依据。
3. 合同业务资料：复用稳定资料标识和多行集合，显示名称仅供识别。每份合同先形成确定的资料及文件，再由12301或第三方对应程序生成请求；文件模式无需重复传递每个正文单元格。
4. 平台申请：ERP合同号、签署平台办理号、监管编号分别保存。外部编号在平台及公司关系内识别；避免两个平台同号混淆。多次合法办理有独立历史，未知受理结果不能创建第二次申请。
5. 状态接收：验真、查明所属公司和申请，再映射为共同业务状态；保留原始返回及时间，重复通知不能重复办理，晚到结果不能覆盖已核实终态，矛盾结果进入核对。
6. 文件：保存实际送审稿、实际送签稿、已签文件、附件清单及必要证明之间的版本关系。内容校验值用于检查审批、提交和文件是否对应；不只保存会过期的下载地址，不用当前模板重新生成历史已签文件。
7. 平台差异：创建、查询、文件、撤销、解除等按实际能力开放；不支持不是失败重试，也不因接口页一个总开关就显示全部可用。

这些是正式开发承接点。本轮原型后续只需用样例表达角色、步骤及正常／异常结果，不扩展为真实账号管理、后台调度或跨模块自动回写。

**模板B：邮轮旅游合同，采用法大大。**

- 由法务提供获准邮轮合同正文及附件版式，登记适用公司、邮轮、相应境内或出境范围、个人／企业客户及有效期，签署平台选择法大大。
- 建议第一版选择“ERP生成文件”：用现有资料来源配置生成完整待签文件，法大大承担身份核验和电子签署。合同模板仍由ERP统一选用，销售不去法大大再选一次。
- 配置本份游客、确认航次、出发返回日期、舱房及服务标准、成交金额、船票／退改约定；可重复的名单、行程和费用用明细表承接。尚未确认的舱房或服务资料显示缺项，不由生成文件过程补造。
- 签署设置明确必要游客／代表、监护或代理授权、我方公司、先后顺序，以及每一方需要签的正文或附件位置。企业授权书属于依据材料，不因上传就成为共同签署附件。
- 使用不同人数、长行程与跨页样例检查最终文件。某份文件仅需查阅、某份须共同签署要明确区分；文档增长不能导致盖章落错页或盖住正文。

两种文件生成方式均可保留，但每个发布版本只能确定一种：

| 采用方式 | 正文和可填写位置在哪里维护 | ERP负责什么 | 平台对应维护什么 |
|---|---|---|---|
| 填写平台模板 | 采用平台上获准的模板；ERP保留所采用版本与审阅文件 | 提供本份合同资料、补缺项、预览及内部审批 | 平台模板版本、字段／表格、签署角色及位置 |
| ERP生成文件 | 采用ERP内经批准的正文和版式 | 将正文、名单、行程、费用排成确定的待签文件，供审批和送签 | 文件及签署安排；不重复填写每个正文格子的接口参数 |

法大大官方公开介绍同时支持本地文件和模板签署、文档模板与签署模板组合使用。上表为基于该能力的产品设计建议，具体上传格式、控件、附件与授权方式仍按开通版本核实。[官方产品说明](https://www.fadada.com/product/saasapi)

模板发布继续按已有草稿、审核和启用流程办理。正文、资料取值、平台或生成方式等影响实际文书的变化形成新的待审版本；旧启用版保留，新版通过前不能覆盖历史合同。公司授权临时失效时暂停该公司的新发起，其他已获准公司和历史合同按各自实际条件处理，避免一家公司失效把全部模板一并停用。

### 11.4 admin第三步：配置哪些业务默认用哪份模板

`admin/contract-rules.html`每条规则仅解决选模，示例如下：

| 签约公司 | 产品类型 | 旅游范围 | 签约对象 | 默认模板 | 自动带出的平台 |
|---|---|---|---|---|---|
| 福建凯撒 | 参团游 | 境内 | 个人 | 团队境内旅游合同 | 12301 |
| 福建凯撒 | 邮轮 | 出境 | 个人 | 邮轮旅游定制合同 | 法大大 |

地区、一日游等确有依据的差异作为附加条件。重叠范围无法唯一确定时不允许启用；无匹配、模板失效或公司不适用时明确阻断，不悄悄换成另一平台。审批仍由审批配置承接，付款限制由销售签约条件承接，移动配置入口不能导致默认免审或付款条件丢失。

### 11.5 产品端：仍然只有“沿用／指定”

产品经理编辑线路或邮轮产品时，继续保留“沿用系统设置”和“指定合同模板”两个选择。

- 普通境内线路沿用系统设置，由实际签约公司及本单条件匹配12301境内模板。
- 邮轮产品可沿用邮轮默认规则，也可指定“邮轮旅游定制合同”。选中模板可查看其正文、适用范围和平台，产品人员不另配公司章或平台参数。
- 同一邮轮业务确有两种获准文本时，可分别发布12301模板和法大大模板；具体产品指定哪一份即可，不能仅凭“邮轮”标签强制一种平台。
- 集团产品跨公司销售时，订单准备阶段按实际签约公司重新校验。产品指定模板若不适用于这家公司，明确指出问题，不静默替换；维护人应提供适用模板或改回沿用规则。

已撤回的团期“本团合同资料”和门店多模板配置不恢复。合同引用原有产品、团期和订单资料；不为接入法大大让业务人员重复填同一份行程。

### 11.6 销售端：两平台沿用同一条办理路径

销售从订单合同入口进入`merchant/sales/contract-prepare.html`，随后由原合同管理和审批页面承接。

1. **确定本单合同。** 系统带出实际签约公司、模板名称／版本、签署平台、覆盖游客和本份金额；销售无需先判断进哪个平台菜单。
2. **补齐本次约定。** 沿用已有多人合签、按人分签、必要签署人、监护／代理材料和条件项。来源错误回所属业务入口处理；客户本次选择在合同准备内完成。
3. **预览并提交审批。** 境内合同核对12301生成或实际采用的文件；邮轮文件模式核对ERP生成的完整待签文件。审批查看同一正文、附件和签署安排，资料改变后重新生成并按规则重审。
4. **发起签署。** 内部审批及付款条件满足后，系统按模板平台提交。前台保留统一“发起签署”动作，在本份详情明确12301或法大大；所需身份核验由对应平台按实际能力承接。
5. **查看逐方结果。** 保留未签、已签、拒签等逐方进度和我方盖章结果。所有必要方完成后才显示已签署，客户关闭页面或返回成功不能代替平台结果。
6. **归档和后续办理。** 取得已签文件及签署证明，保留原文书和版本；订单合同区域、补充协议、解除及售后都反查同一记录。需监管处理的另看其办理结果。

以示例订单说明：境内3人订单确认金额18,000元，采用12301模板；邮轮2人订单确认金额26,000元，采用法大大模板。合签时本份覆盖全部游客和整单确认金额；若按人分签，沿用订单确认的逐人金额分配，不能默认平均或每份重复整单金额。改变签署平台不改变订单价格、收款公司或财务金额。

### 11.7 必须在原流程内处理的异常

| 情况 | 员工在哪里处理 | 应有结果 |
|---|---|---|
| 公司缺法大大授权或用章过期 | 合同准备提示缺项及负责管理员；管理员回接口配置 | 保留资料草稿，新发起被阻断；不能借其他公司章 |
| 产品指定模板停用／不适用 | 产品选用或合同准备 | 显示具体原因，由获授权人员明确调整模板，重新预览／审批 |
| 送签超时，是否创建成功未知 | 合同详情的原申请记录 | 先查询原任务，不重复创建，也不自动改投12301 |
| 部分游客已签或我方尚未盖章 | 同一合同逐方进度 | 保留签署中和未完成方，不更换平台拆开剩余人员 |
| 全部签完但文件暂未取得 | 合同详情的文件区域 | 主状态保留已签署，补取原任务文件 |
| 签后订单发生变更 | 原售后及合同变更入口 | 保留原合同；按批准变更签补充协议或新版本，不能覆盖原文件 |
| 法大大签完、监管尚未办结 | 合同详情的监管区域 | 签署与监管分别记录，不假定自动报12301或无需报送 |

### 11.8 开发承接和本轮完成条件

以下为面向开发的补充。ERP是一套合同主流程，12301和法大大分别有请求与返回转换程序。销售发起时提交确定的合同版本、文件和签署人；后台选择其绑定平台，不由浏览器自由拼接平台参数。

- 合同业务编号、签署平台任务编号、监管编号分别保存；平台编号必须连同公司和接入关系识别。
- 发布模板、正文／文件、填写对应和签署设置保留版本；内部审阅文件与实际提交文件须可核对，不能发起时取“最新模板”替换批准内容。
- 接口凭据保存在服务端；签署结果通知先验签和确认归属，再更新本份进度。重复及乱序通知不能重复推进或覆盖可靠结果，未知状态进入核对。
- 本次发起申请保留防重复标识；超时先核对原申请。已签文件持久保存，不能只记录会过期的下载链接。
- 历史已明确来自12301的合同继续保留其平台及编号；来源不明确的先核实，不能给所有旧记录统一补法大大或按当前默认模板重算。
