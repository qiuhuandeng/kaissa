# 邮轮需求与现有系统对照及调整建议

日期：2026年10月23日。阶段：需求理解与现状核对，尚未实施。

依据：用户本次《邮轮业务ERP标准功能需求梳理》、当前页面与共享脚本、项目邮轮业务确认稿和产品字段分层标准。本文将用户材料中的会议结论作为本次输入，不将其中引用的“行业标准”“合规要求”直接视为凯撒已批准的制度。

本次只分析并记录建议，未修改业务页面、导航或共享业务代码。代码证据可以证明已有入口和处理逻辑，不能代替浏览器交互验收。财务原8批、36项、6场景状态保持，不把本次邮轮分析算作已完成的新增原型。

## 一、结论

现有系统已有邮轮主干：船公司、船只、邮轮模板、自营邮轮产品、外采邮轮定价、航次舱型价格库存、邮轮包舱采购、邮轮下单、名单、转团、预付冲抵和团期结算。问题不是完全没有库存，也不是要重新建设六个一级中心。

最需要补齐的是以下五件事：

1. **同一船方航次下的共享舱房**：多个出发城市、销售方案、团号共同使用一套有来源的舱房；目前采购分配与航次库存有基础，尚未完整表达共同销售占用。
2. **按每间舱房组织乘客和报价**：舱房数、乘客数、同舱人数、成人儿童身份、第几位乘客分别表达，解决重复计人和人数与房量混用。
3. **可操作的分房和船方名单**：从游客有“舱型／舱号”字段，补成房号导入、同舱匹配、异常修正、调整记录和船公司格式导出。
4. **岸上方案与附加服务分开**：影响整套行程和合同的A/B/C/D作为销售方案；独立加购项才作为附加服务，二者可共用同一航次库存。
5. **客户款、船方预付、航次成本分别承接**：复用现有财务入口，补跨航次去向和差异依据，不另建邮轮财务账。

## 二、先把业务关系和入口放对

### 1. 六类能力不等于六个新菜单

所有原型使用超级管理员演示。岗位说明用于解释实际责任，不能据此隐藏金额、页面或按钮；单据阶段及已经办理的结果仍应约束动作。

### 2. 必须区分的几类对象

- **船公司与供应商**：船公司是品牌和运营方；采购合同的交易对手可能是船公司，也可能是代理商。同一船只不能唯一决定付款供应商。
- **基础舱型**：属于船只，保存船方代码、类别、标准和最大入住、面积、床型、景观、设施等。业务显示可为“阳台双人房 BA”，但不能仅凭显示名称识别库存。
- **航线模板**：保存可复用逐港行程，可以适用于多条产品方案；不是带库存的具体航次，不把“航次／模板编号”继续混成一个字段。
- **船方航次**：同一船只一次具体航行，保留船方航次号、登离船时间与港口。它与公司内部用于销售、交通及执行分组的团号不是必然一对一。
- **采购舱房**：明确采购公司、供应商、协议、船方航次、船方舱型代码、数量及来源批次。不同供应商、公司和合同的责任不能因为船只日期相同就混在一起。
- **销售安排**：选用产品方案、出发城市、交通和报价，关联某一船方航次可供本公司销售的舱房。原“线路→方案→团期”销售链路保留，在邮轮侧补齐团期与共同船方航次的关系。
- **订单内舱房与游客**：一笔订单可以有多间舱，每间舱有自己的入住人、价格明细、偏好及房号确认结果。同行跨订单同舱要有明确关联，不能只按相同房号文字拼接。

例：北京出发A方案、上海出发A方案、上海出发B方案都搭乘同一船方航次，可以共用阳台BA的20间舱房。北京交通有独立机位上限，B方案岸上服务有独立人数上限；这些上限不能复制出新的20间舱房。

| 邮核24 | 分销、消息、实时接口和移动操作 | 已有渠道中心、定价政策、通知配置与领队移动端范围 | 分销共用航次余量／渠道配额；业务截止与提醒配置分开。邮轮公司实时接口、移动分房是增强项，领队端不默认改为计调端 | 渠道专属额度与公共余量不重计；消息记录不等于处理完成；未接接口不宣称实时保舱 |

## 四、库存应该怎样补

### 1. 两层库存、一个真实使用关系

采购层回答“向谁买了多少、船方确认多少、退回多少、还承担多少采购责任”。销售层回答“本公司这个航次目前还可接多少间、被哪些订单占用、哪些销售安排共用”。分房回答“这些已订舱房住了谁、船方确认了哪个房号”。三者关联，但不能互相代替。

同一公司可用的库存建议按船方航次、船方舱型代码及采购来源追踪；展示时可以汇总，采购责任和成本仍分来源。渠道或部门如有专属额度，明确从公共余量拨出还是只设销售上限；不能把额度及其已售量再次从总量重复扣减。

### 2. 不采用六个互斥库存状态

用户材料中的“可售、锁定、已售、已分房、释放、取消”分属不同事实：

| 业务事实 | 应如何表达 |
|---|---|
| 有效销售供给 | 船方已确认可供本公司销售的舱房；已退船方及不可用部分另有记录 |
| 当前占用 | 临时锁舱、正式订单占用、内部专属保留等互斥数量；正式占用中的付款进度另查 |
| 房号安排 | 待分房、已建议、船方待确认、已确认；是订单占用上的安排结果，不再扣一次库存 |
| 释放／取消 | 是有时间、原因和来源的处理记录；取消订单、取消采购及释放内部额度分别处理 |
| 风险提醒 | 低于阈值、临近退舱日、待船方确认，作为提醒，不决定列表主流程按钮 |

无专属额度的简单算例：20间有效可售供给，临时锁3间、正式占用5间、内部保留2间，公共可售10间。正式占用中已分房4间，可售仍是10间。释放临时锁舱1间后可售11间；改成正式订单占用只在占用分类间转换，可售不再减少。

退舱申请提交不等于船方接受退舱。先记录申请，取得确认后再减少有效采购数量；损耗金额依据具体协议或船方账单确认，不能使用当前代码的固定50%作为制度。

### 3. 临时锁舱与长期占用分开

临时锁舱用于完成报价或下单，保留到期时点、数量和来源；订金订单的保舱按采购／销售约定，不能到15分钟就同样释放。供应商只有询位、没有保舱承诺时，页面显示待确认。

15—30分钟可以作为演示参数候选，不能先定为全船司制度。到期、续留、主动释放、已确认后重复释放等分支须有原型结果。正式系统的并发防超售属于后续开发；原型用同页示例演示数量变化，不以跨页自动同步为交付条件。

### 4. 舱房数量和乘客容量双重核对

“不另占房间”“不占床位”“是否计入船方允许乘客数”是三件不同的事。不得沿用儿童不占位就不受同舱人数限制的含义。船方最大入住、婴幼儿限制及是否允许第3／4人须按实际舱型核对。

当前开排脚本将邮轮计划量显示为“人”，又把同一计划量填入“占用舱房”，属于需优先修正的单位混用。建议分别维护可售舱房数、允许入住规则和预计乘客数，预计乘客数不自动等于采购舱房数。

## 五、产品、价格与附加服务怎样组织

1. 产品层维护船舶引用、销售方案、行程和包含服务；航次层维护当期舱型、价格、库存和截止节点；订单保存成交时的选择和金额。
2. 舱型档案保留标准入住与最大入住，销售名称可以用“类型＋人数＋代码”，但名称不代替房间规则。第2／3／4人是同舱价格位置，成人／儿童是旅客属性，不能都当互不相关人数加总。
3. 每名乘客只命中一份基础船票计价；按登船日计算年龄只是建议，实际年龄口径待船方条款确认。单人附加费、港务税、服务费和独立加购另列。
4. 港务税已经有单列基础；应统一“已含／另收／船上支付”、计费人数、币种及退款依据，港口档案中的参考税费不能直接成为航次最终成交税费。
5. 旺淡季是按开航日期选择航次批量改价的工具；早鸟按预订日期、尾单按销售范围和活动条件处理。已售订单保留原价，调价不自动改历史合同。
6. A/B/C/D若改变整体岸上行程、包含标准及合同附件，就做产品下的“销售方案”；如果只是某个港口一天的可选游览，则做按游客选择的岸上服务。两种情况不能全部强制成四个独立产品。
7. 附加服务使用“可复用模板＋本航次配置＋订单按人／按舱选择”三层。模板便于复用，具体供应商、服务日期、容量和当期价格仍在航次明确。已有单项服务可独立售卖时复用其档案；纯船上升级不必先制造独立单项产品。
8. 必选与互斥规则应能解释业务结果，例如A/B岸上项目同一时段不可同时选；已含保险不重复收费；免费儿童仍占服务人数。可售组合同时受舱房、交通、岸上服务等各自约束。

## 六、订单、名单和变更怎样补

### 1. 下单建议顺序

选航次和出发安排 → 选销售方案 → 增加每间舱房并填入住人 → 选择按人／按舱附加服务 → 核对船票、税费、服务和订金尾款 → 临时锁舱或提交待船方确认 → 按确认条件推进订单与合同。

资料不齐可先以默认演示乘客走原型；资料后补、资料截止后更正与确认后改价是不同动作。遵守项目无阻断表单演示规则，同时保留库存不匹配、船方待确认等业务差异状态，不能显示未获确认的业务已成功。

当前预订页的组合舱房分支没有得到普通“余X位”的解析结果，却又统一进入“所选资源余量尚未确认”的判断；因此源码显示邮轮确认路径存在确定的逻辑缺口。该判断须改用所选航次各舱型的数量依据。本轮未运行浏览器，不写为已复现或已修复。

订单主状态继续表达草稿、待确认、已确认、履约中、已完成、已取消等业务阶段；订金／尾款是付款计划和进度，退款是独立售后责任，分房和船方确认是履约结果，不把它们全部串成一个主状态。

### 2. 分房以工作区承接

航次详情设置“名单与分房”主办理区域：上方筛选舱型、出发地、销售团、房号确认情况；工作区展示待安排游客、每间舱房入住人、房号及特殊需求。第一阶段先做可操作表格、选择分配和调整抽屉，自动建议可后补，拖拽不作为第一阶段必备。

船方返单导入全部在右侧抽屉完成：默认演示资料 → 匹配预览 → 逐行修正或保留待匹配 → 批次结果；返回保留批次与筛选。不恢复“载入样例”按钮，不要求真实文件上传才能走演示；没有解析真实文件时也不提示真实读取成功。

房号在同一航次可对应多名同舱游客，重复检查应判断是否冲突占用同一间房，不能简单拒绝同房号第二名游客。保证舱只确认舱型未回房号的情况须能独立表示；分房建议不等于船方已确认。

### 3. 船方变更的处理

按用户本次输入，对“四岛变三岛”等重大售卖内容变化，设计以新建销售版本／产品及批量转团作为主要处理路径，原订单和原合同保留。实际是否必须解除重签、允许补充协议，以及取消损失，由公司业务和法务确认；不把“轻／中／重”三个标签直接等同法律结论。

批量处理逐单记录客户选择，核对新航次舱型和入住人，客户补退款、原收款转用、船方预付转用、成本差额分别表达。整批中待决定或目标舱不足的订单保持原状态，不因其他订单完成而一并转成功。

## 七、财务与报表复用边界

- **预付**是已经付给供应商、尚待按实际业务使用或冲抵的款。分配给航次只说明用途，不等于确认成本，也不等于已冲抵。
- **应付**是经业务与财务确认需要承担的供应商款项。预付冲抵应付减少待付款责任，不再作为成本减项计一次。
- 客户实收转单使用现有转款核销；供应商预付转用使用现有预付管理。先核对同一公司、供应商、币种和协议是否允许；跨公司、跨供应商或跨币种不能视为普通改航次直接平移。
- 已确认成本的归属调整必须保留原成本及调整依据；不能将“已付成本转航次”统一当成“预付转预付”。原款去向、成本责任和未付应付分别核对。
- 同一航次包舱费在多个出发地／销售方案间有明确分配，不能每个团号重复计整船费用。未售舱损、服务费、港税、岸上服务、交通、返点分别有依据；不因预付或开票而自动确认成本。
- 原结算不删除、不覆盖；追加收入或成本差额进入现有结算调整，保留原结算、差异单及本次期间。既有数据中心业务毛利补航次、销售方案和采购来源查询，不另建独立邮轮损益系统。
- 预估、已确认、结算后调整三类数分开；缺少确认依据时展示待确认，不用预估冒充实际。正式税务、收入确认、成本分配和内部结算规则保留财务待确认。

## 九、建议实施顺序与待确认事项

以下为建议顺序，用户本次只要求先分析，尚未执行页面改造。

1. **先定航次、库存和销售方案关系**：用“同航次＋北京上海出发＋A/B岸上方案”样例，明确采购来源、共用数量、逐舱入住、占用／分房／释放。修正船方舱型代码、单位、供应商和退舱损失口径。
2. **再补产品开排和销售下单**：主数据引用、逐港行程、航次价格和服务菜单、逐舱计价及临时锁舱；同时覆盖自营配额和外采待确认。
3. **补履约与售后**：名单与分房、房号导入、船方名单输出、登船资料、部分客户转团／退款与合同处理。
4. **补财务承接与分析**：在原页完善多航次预付、资金转用、共同成本分配、预估实际差异及结算后调整；按对应原型场景验收，不扩成生产对接。
5. **增强项单独排期**：实时船司接口、自动分房优化、移动计调操作、船方高级安排。接口协议、模板和真实政策另行交接。

优先需要业务明确的不是一长串字段，而是以下决策：

| 编号 | 待确认问题 | 影响 |
|---|---|---|
| 邮待01 | 当前最常见是整船、切舱硬配额、代理配额还是逐单询位；是否同航次存在多个采购供应商／公司 | 供给来源和库存责任 |
| 邮待02 | 多出发地、多个销售团是否完全共用；哪些部门／渠道有独占额度 | 共用可售与专属额度公式 |
| 邮待03 | A/B/C/D是整套销售方案还是逐港可选服务；同一间舱的客人能否选不同方案 | 产品方案、订单选择及岸上服务容量 |
| 邮待04 | 实际保舱期限、订金后的保舱条件、尾款截止；报名／资料／船方付款截止分别是什么 | 临时占用、正式占用与截止行为 |
| 邮待05 | 船方是否给完整房号；由谁最终确认；保证舱、儿童／婴儿及第三四人规则 | 分房范围和同舱人数核对 |
