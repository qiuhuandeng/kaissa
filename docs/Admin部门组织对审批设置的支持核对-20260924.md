## 判断与前序交付边界

当前部分支持，尚不能由管理员从组织和员工维护开始，完整配置出可用的审批关系。上一轮“功能完成”指四种组织取人方式、共用组织负责人示例和试跑演示；不等于admin部门组织模块的创建、任职、账号、变更审批及生效全流程已完成。前序163组检查仅证明其所覆盖功能，不能替代本次发现的管理流程缺口。

这不只是未接后台：新增组织仍可能只提示保存，直属上级没有admin主维护入口，组织变更申请也缺后续受理动作。这些是业务原型应能表达和操作的功能。

## 页面角色与上下游

- 集团组织管理员：维护公司内上级组织、成员任职和部门负责人，核对变更影响。
- 账号管理员：维护员工身份、开通和停用；账号不能另造一套任职关系。
- 公司组织管理员：查看本公司组织、提交任职和负责人调整申请。
- 审批管理员：在审批中心配置模板范围、公司审批职责、取人方式及异常处理。
- 上游为组织、人员及任职资料；下游为业务申请的审批人确定和审批异常处理。岗位只描述职务，不能推导员工直属上级；业务角色管权限，也不等于某节点的审批人。

## 页面职责与最小增改建议

保持现有“部门组织”四个菜单，不再新增一套审批专用组织菜单。

1. **组织架构**：围绕当前组织提供组织信息、下级组织、成员任职、负责人、变更记录，按节点类型显示适用Tab。将旧的单人负责人表和仅提示保存的入口收敛为可操作的共用维护流程；主体的合同／财务资料保持原业务归属。
2. **员工账号**：维护身份、账号状态和可用公司；展示任职与直属上级，复杂任职维护使用组织模块的唯一主入口，避免账号页和组织页各改一套。
3. **岗位管理**：维护岗位名称和适用组织类型即可；不做“岗位等级自动决定谁审批”。
4. **业务角色**：维护谁能看、配置、发布和办理审批，以及授权公司范围；不拿角色名替代实际审批人安排。
5. **审批中心**：继续承载模板、公司审批职责、代办、异常交接和审批动作。组织侧提供资料和变更申请，不复制第二套审批模板设置。

## 下一步与未确定规则

优先补齐admin组织内成员任职／直属上级维护，并统一员工账号、组织成员和审批候选资料；随后完善组织新增／停用和变更受理、生效、历史核对。新增部门、新开员工、负责人更换、兼任、离职停用和两公司分别试跑应形成六组业务验收。

是否允许跨主体审批、组织变更是否影响未完成节点、紧急交接的授权边界仍需业务政策确认。原型可以默认公司内处理，变更不自动改在途人员，异常交管理员处置；不把默认方案当正式政策。本轮为核对，以上补充尚未实施，浏览器视觉验收断点继续保留。
