# 履约付款申请：预付与应付类型实施验收

2026年9月29日。用户在恢复 Git 原付款申请页面后，明确要求批量申请逐张体现预付或应付，并授权执行。本次仅在原待申请付款、申请记录及抽屉内增加类型与拆单处理，不恢复此前撤回的独立成本付款页面和业务减费退回入口。

## 页面变化

| 财务／业务要求 | 修改前现状与缺口 | 本次修改 | 验收 |
|---|---|---|---|
| 批量时知道每张申请是什么款 | 只有付款节点；批量按钮实际打开普通申请抽屉，原拆单预览未作为入口 | 接回批量拆单抽屉，逐张显示申请类型及来源依据，保留付款对象、节点、关联业务、成本项和可填写金额 | 同供应商、账户、公司、币种及“本期付款”节点，3万元预付与2万元应付分别展示 |
| 不把预付和应付合成一张 | 原拆单条件没有申请类型 | 申请类型加入拆单条件；跨公司、账户、币种、节点及项目仍分开 | 两类分别提交1.2万元和8千元，生成两张申请 |
| 申请类型有据可查 | 只看“预付款／尾款”文字容易误判 | 由费用来源的明确付款依据带入，不按节点名称猜测，业务不能随意改类型；缺确认依据显示待确认并阻断提交 | 首款／尾款改名不改变类型；类型不明混入整批不生成申请 |
| 提交之后仍能辨认类型 | 记录和详情无类型 | 申请记录增加申请类型列，普通申请抽屉、申请详情及既有审批摘要保留类型；单一类型的草稿复开仍带原类型和金额 | 预付、应付记录及详情、草稿复开已检查 |
| 防止其他入口绕过拆单 | 按团期／科目汇总可能包含多个付款对象和类型 | 普通汇总行若跨拆单条件，同样进入拆单预览 | 科目汇总入口保留预付、应付及待确认各行 |

批量每条成本可填写本次金额，零元表示本批不申请该明细。负数、超过两位小数、超额及全部零元不提交；提交前整批检查，避免先生成一部分再发现错误。成功后锁定本抽屉金额与提交按钮，避免重复点击。

原单笔付款表单、公司协议和账期展示继续沿用；财务仍需复核申请类型。本次不修改正式审批政策、会计确认条件或财务实际付款，不把本地样例标为真实已确认账务。

## 验收及范围

新类型规则6项、浏览器14项、既有供应商付款账期20组通过。浏览器覆盖原入口、混合拆单、依据及只读类型、超额、实际提交金额、记录和详情、待确认阻断、草稿复开、汇总行及390像素抽屉，页面脚本异常为零。

已检查桌面批量抽屉、申请记录及390像素截图；窄屏抽屉已修正为视口宽度，提交按钮实际边界在屏幕内。语法、资源引用与差异格式检查通过，财务清单检查无错误，原8批／36项／6场景保持。申请记录固定操作列110像素，申请单号、金额、类型和主状态完整显示；批量抽屉的类型与依据合并在同一列，窄屏表格内部横向滚动。

下一步：用户在原“付款申请”中勾选预付与应付费用，打开批量申请复核类型和拆单结果；具体问题按本页修正，不扩展已撤回独立页面。正式来源取数、公司政策和后台权限继续由正式实施确认。
