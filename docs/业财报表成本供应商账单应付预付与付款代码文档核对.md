# 业财报表：成本、供应商账单、应付、预付与付款代码—文档核对

版本：v0.1

核对日期：2026年9月6日

## 一、本轮目的

本轮从财务五类目标结果倒查供应商侧链路，判断系统能否把“实际花了多少钱、已经欠供应商多少钱、已经付了多少钱、还有多少预付款或待付款”落到同一团期、订单、供应商和原始依据上。

本轮只做代码与文档审计，不修改业务页面。结论用于确定后续功能、数据和页面改造顺序。

## 二、结论先行

现有原型已经覆盖团期成本、资源采购付款节点、供应商账单、应付、付款申请、审批、付款执行、回单核销、预付冲抵和付款退回等页面，业务名词和页面分工也大体具备。

但当前仍不能自动生成可信的团队成本、供应商结算价、应付、已付、待付、预付余额和毛利报表。根本原因不是少一个报表页面，而是这些页面使用互相独立的固定示例和页面内数据；相同编号在不同页面对应不同业务或金额，页面操作也只改当前行，不生成共同单据、余额变化和历史记录。

更严重的是，团期结算页为了把原型展示完整，会按比例虚构订单收入明细、按文字猜币种和汇率、按成本占比分摊已付金额，并把手工维护的“实际成本总额”直接作为总成本。这些只能作为界面演示，必须明确禁止进入财务报表。

因此本轮判断为：

1. 文档中的业务边界和金额公式总体可作为正式开发方向。
2. 页面原型可保留主要入口和交互框架，但数据层与关键动作需要重做。
3. 先建立共同的成本、账单核对、应付、付款、预付和调整记录，再建设报表；不能先把现有页面数字拼成报表。

## 四、财务需要的正确业务链

### 4.1 正常成本和付款

```text
采购合同或资源占用
-> 预估成本和付款节点
-> 实际资源使用、服务完成、出票或回团事实
-> 实际成本明细
-> 成本确认
-> 供应商账单及逐项核对
-> 应付确认
-> 付款申请占用可申请金额
-> 审批
-> 付款执行
-> 回单或银行流水核对
-> 应付核销
-> 业务结算和会计承接
```

实际成本回答“本团真正消耗了什么”；供应商账单回答“供应商向我方主张多少”；应付回答“我方已经确认欠多少”；付款回答“资金实际付出多少”。四者允许时间和金额不同，不能互相覆盖。

### 4.2 先付款后确认成本

```text
合同付款节点
-> 预付款申请与审批
-> 付款执行
-> 供应商预付余额
-> 分摊到资源批次、航次、班期、团期或项目
-> 实际成本和应付成立
-> 预付冲抵应付
-> 剩余余额继续使用、退回、转用或确认损失
```

供应商预付是已经付出但尚未由最终应付核销的资产，不等于实际成本，也不等于已结清应付。

### 4.3 供应商退款和付款退回

供应商退款是采购取消、折让或多付后供应商应返还；付款退回是银行把原付款退回。两者都必须关联原付款、原应付或原预付，但不能删除原付款。资金到账后通过新记录恢复应付余额、恢复或减少预付余额，必要时形成成本和结算调整。

## 五、必须固定的金额口径

```text
有效实际成本
= 实际成本原额
+ 已确认损耗
+ 成本增加调整
- 成本减少调整

账单确认金额
= 供应商账单原金额
- 不认可金额
+ 已认可补差
- 账单冲减或供应商折让

有效应付
= 首次确认应付
+ 应付增加调整
- 应付减少调整
- 已关闭金额

应付未付余额
= 有效应付
- 付款核销
- 预付冲抵
- 供应商应退款抵减
- 已批准往来抵销

可申请金额
= 应付未付余额
- 审批中付款申请占用
- 已审批待付款占用
- 争议冻结金额

供应商预付余额
= 已执行预付款
- 已冲抵应付
- 已退回
- 已批准转用
- 已确认损失
- 调整冲销
```

团队毛利只能使用纳入结算范围的有效实际成本。预估成本、供应商账单主张额、应付额、已付款和预付余额可以并列展示，但不能任选一个冒充团队成本。

## 六、逐页面核对结论

### 6.1 团期结算和业务侧付款申请

`fulfillment-cost.html` 把团控的成本维护、团期经营结果和业务侧付款申请放在同一页面，通过两个兼容入口进入不同视图。入口归属基本合理：团控确认成本，业务发起付款申请，财务执行付款。

已具备的原型表达：

- 团期、项目团、供应商和费用项目；
- 预估成本、实际成本、预付、应付、已付和待付；
- 单笔和批量付款申请，可按付款对象、收款账户、币种、结算主体及付款节点拆单；
- 成本未完整时的阻断提示和审批任务入口。

确定问题：

1. `costTotal()` 直接取页面维护的 `actual` 总额，不按有效成本明细汇总。示例 `EU20260818001` 的实际成本显示为 290,600 元，但其四条成本明细合计为 214,540 元；`CZ20260912001` 显示 448,000 元，明细合计为 489,600 元。
2. `settlementIncomeRows()` 把团期总收入按 62% 和 38%拆成两张并不存在的订单，并生成虚构订单号，不能作为订单收入明细。
3. `costCurrencyMeta()` 根据线路、供应商和费用文字猜测币种与固定汇率，不是合同、账单或财务确认的汇率事实。
4. `paymentPaidForCost()` 找不到对应付款明细时，会按成本占比把总已付分摊到各费用项目，制造并不存在的付款核销关系。
5. 非项目团的已付金额取预付汇总，导致“预付”和“已经支付并核销该成本”混用。
6. 收入和费用项目仍使用笼统的“团费”，与业务确认稿要求使用真实费用项目冲突。
7. 成本修改直接覆盖当前金额和状态，没有成本确认记录、调整原因、原金额、审批和生效日期。
8. 付款申请只保存在页面数组；申请金额通过 `Math.max` 回写成本项累计已申请，不能还原多次申请、释放占用和驳回后的余额。
9. 页面只把审批任务写入浏览器本地记录。审批中心通过或拒绝后只写审批结果，不回写付款申请，也不生成财务付款任务。

结论：本页可保留为业务原型入口，但所有由比例、文字和默认值补齐的金额必须标明“演示推算，禁止财务取数”，正式改造时改为读取共同订单、成本确认、应付和付款核销记录。

### 6.2 动态资源采购付款节点

`resource-procurement-inventory.html` 已能表达包机、锁位、包舱和包列的分期付款、预付分摊、损耗和数量变更，符合此类动态资源由团控或资源调度日常处理的角色习惯。

但点击发起付款申请时，页面同时自行生成付款申请号、应付号和付款号，并立即把付款状态改成待付款。预付款在实际成本和债务尚未成立时不应强制造正式应付；审批通过也不等于已生成真实付款结果。所有结果仍只存在当前页面数组，与财务应付、付款执行和预付管理没有共同记录。

建议保留合同付款计划和资源分摊入口；普通应付付款引用已确认应付，预付款申请引用合同付款节点。两类申请通过同一付款申请流程，但分别生成“应付占用”或“待形成预付”的结果。

### 6.3 供应商端对账

`supplier/settlements.html` 可展示供应商按期间查看应结金额、订单明细、确认账单、提出差异和提交发票的场景，但页面只有三行固定数据，所有按钮打开同一个固定抽屉，确认后不产生账单或差异记录。

页面把供应商期间对账、单张账单确认和发票提交放在同一个“结算单”里，容易与财务业务结算混淆。正式设计应把它定位为供应商协同入口：查看我方提供的对账范围、提交或确认供应商账单、提出逐项差异、上传进项发票；正式应付仍由我方财务确认。

### 6.4 供应商账单

`finance-supplier-bills.html` 已表达邮件、上传、接口和供应商回传等来源，支持识别、挂接、核对、差异处理和应付承接，页面方向较完整。

确定问题：

1. 新建或上传账单时只提示成功，不新增账单记录。
2. 一张账单只能填写一个业务编号和一个费用项目，无法承接“一张账单覆盖多个团期”或“多张账单覆盖一个成本范围”。
3. “确认挂接”会直接把系统成本复制为账单金额，并把差异改为零。这等于用供应商主张覆盖我方业务事实，失去对账意义。
4. 确认账单只把当前行标成“应付待生成”并拼出应付号，不会在应付管理生成同一记录。
5. 供应商、对方账单号、日期和金额可直接覆盖，没有原始账单版本、识别结果和人工更正记录。
6. 页面虽有一条重复账单示例，但没有按供应商、对方账单号、币种、金额和来源文件执行防重复校验。

供应商账单必须保留原始文件和原始识别结果；账单分配明细独立记录每一行认可金额对应哪些实际成本；未分配、重复和差异未处理的金额不能生成有效应付。

### 6.5 应付管理

`finance-payable.html` 已把应付来源、付款对象、费用、原币、本币、已付、待付、预付、发票和退回信息放在同一详情中，页面职责基本正确。

确定问题：

1. `availableAmount()` 直接返回页面里的待付金额，没有扣减审批中申请、已审批待付款占用和争议冻结。
2. 应付确认会直接用输入值覆盖调整后应付和待付余额，没有生成应付确认或应付调整记录。
3. 已付款、预付冲抵、退回和关闭后无法由明细重新计算有效应付和未付余额。
4. 一张应付只挂一个账单号，缺少一对多、多对多的账单及成本分配关系。
5. 页面内更新不会同步付款申请、预付、结算或供应商账单。

正式改造时，一级列表展示“应付金额、已核销、可申请金额”；付款抽屉才展示“本次可申请”和“本次申请金额”。应付确认后的变化必须通过应付调整、付款核销、预付冲抵和退款抵减明细计算，不能覆盖余额。

### 6.6 付款申请与审批

`finance-payment-apply.html` 已区分付款依据、可申请金额、本次申请、原币、本币、预付处理、审批和付款承接，页面字段方向正确。

但财务复核时填写或展示的金额、汇率和本币金额并没有参与提交结果；确认操作只改变当前行状态和审批号。业务侧发起的付款申请也不会进入该页面。审批中心完成后只改变浏览器里的审批结果，不会释放或转移应付占用，也不会生成付款执行任务。

正式流程必须保存付款申请选择了哪些应付或合同付款节点、每项占用多少；驳回、撤销和关闭释放原占用；审批通过形成待执行付款任务，但仍不算已经付款。

### 6.7 付款执行

`finance-payment.html` 能展示付款主体、付款账户、供应商收款账户、原币、本币、银行结果、回单、预付和集团财务核算系统（项目内简称“NC”）状态，适合作为出纳主入口。

确定问题：

1. 页面不接收已审批付款申请的共同记录，固定付款行与申请页编号、金额和业务并不一致。
2. 提交银行时即生成付款凭证编号，而银行尚未确认成功，业务时点过早。
3. 线下登记付款和上传回单只改当前行，不形成付款单、银行流水、应付核销或供应商预付余额。
4. 上传回单后把付款标成“已付款”，但回单仍待核销；付款成功和回单核对的业务事实混在同一行。
5. 付款失败后重新付款会清空并覆盖原银行流水、回单和凭证状态，无法审计每次尝试。
6. 付款账户可以在操作中直接改写，没有按付款法人自动带出默认账户、财务改选权限和修改记录。

付款成功必须以银行或已审核的线下付款事实为准。每次银行提交和返回分别保留；失败重试生成新的执行尝试，不覆盖原记录。付款成功后，普通付款生成应付核销，预付款生成供应商预付余额。

### 6.8 回单核销

`finance-remittance.html` 统一展示付款回单、客户退款回单和付款退回到账，作为出纳回单工作区是可行的。

但上传、匹配和确认核销都只改当前行，不回写付款、应付、预付或资金账户；确认核销时直接拼出凭证号。页面支持按单据号、付款号、退款号、退回号和业务号定位，却不支持其他页面实际传入的 `remittanceNo` 参数，因此预付和付款退回页的“查看回单”链接不能自动定位目标记录。

回单是付款证明和核对依据，不应重新决定付款金额。核销应将一张回单匹配到已有付款执行结果，保留账户、币种、原币、本币、银行日期和差异；有差异时进入异常处理，不覆盖原付款。

### 6.9 预付管理

`finance-prepayment-offset.html` 已表达预付款来源、合同、应付、账单、分摊、冲抵、转用、退回、余额和凭证，覆盖面较完整。

确定问题：

1. 余额变化没有独立流水，页面根据当前累计值临时拼接历史。
2. 金额解析去掉币种，处理结果统一用人民币格式；美元、欧元等原币预付可能被无提示地当成人民币处理。
3. 本次冲抵、转用或退回未校验不能超过可用余额；页面只把结果截为零，超额动作仍可能被记录。
4. “关闭余额”可以在余额非零时直接关闭，剩余资产既未转用、退回，也未确认损失。
5. 转用目标为自由文本，没有校验同一供应商、付款主体、币种、合同授权和目标团期是否有效。
6. 转用、退回和冲抵只改当前预付行，不生成目标预付、付款退回、应付核销或结算调整。

预付必须按原币和本币双金额维护。任何冲抵、转用、退款和损失都形成独立余额变动；非零余额不能直接关闭。

### 6.10 付款退回

`finance-payment-return.html` 已区分供应商退款、银行退回、预付退回和保证金退回，并展示原付款、应付、预付和业务影响，页面定位正确。

但匹配、确认和冲销都只改当前行。所谓恢复应付、恢复预付或影响结算只是文字，没有改变对应余额。页面没有读取网址参数，其他页面传入 `returnNo` 后不能自动定位目标退回单；其回单链接又传递回单页不支持的 `remittanceNo`。

正式处理必须先确认资金实际到账，再形成付款退回记录；原付款保留，按原付款性质恢复应付或预付，并另行处理供应商折让、不可追回成本和重新付款。

### 6.11 旧付款聚合页和兼容入口

`finance-payment-management.html` 不在现行财务菜单中，只把付款申请、付款执行、回单和退回汇总成旧入口，其固定数据与现行明细页不一致，应归类为历史聚合页，完成引用检查后归档或删除，不能作为报表来源。

`fulfillment-supplier-fees.html` 和 `fulfillment-payment-apply.html` 只是跳转到团期结算的兼容入口。在路由统一前可以保留，但不应被当成独立业务对象或独立数据源。

## 八、五类财务结果的承接判断

| 财务需要的结果 | 当前能展示 | 当前能否可信生成 | 主要缺口 |
|---|---:|---:|---|
| 团队实际成本 | 是 | 否 | 成本总额与明细不一致，修改覆盖历史 |
| 供应商结算价/账单确认额 | 是 | 否 | 账单不能多团分配，挂接时复制账单为系统成本 |
| 正式应付 | 是 | 否 | 没有共同应付记录、确认与调整明细 |
| 已付款 | 是 | 否 | 付款执行、银行结果和回单没有共同记录 |
| 待付款 | 是 | 否 | 无法由有效应付和核销明细复算 |
| 可申请金额 | 是 | 否 | 未扣审批中、已批待付和争议冻结 |
| 供应商预付余额 | 是 | 否 | 余额无流水、外币丢失、可超额、可带余额关闭 |

## 九、确定缺口与改造方案

### 9.1 P0：先建立共同业务记录

至少分别保存并关联：

- 实际成本明细和成本确认记录；
- 供应商原始账单、账单行和账单分配明细；
- 账单差异及认可结果；
- 应付确认、应付调整和应付余额；
- 付款申请及其应付或合同节点占用明细；
- 每次审批结果和额度释放记录；
- 每次付款执行尝试、银行结果和付款单；
- 付款回单和应付核销；
- 供应商预付及每一笔分摊、冲抵、转用、退款和损失；
- 供应商退款和付款退回；
- 成本、应付、预付和付款调整。

所有生效记录保留原值，通过后续调整或冲销改变累计结果。

### 9.2 P0：统一关联对象和主体

每笔成本和供应商财务记录至少能回到：

- 团期、航次、班期、项目、订单、服务单、采购批次或资源批次；
- 供应商、采购合同和真实费用项目；
- 采购签约主体、成本承担主体、付款主体和进项收票主体；
- 原币、汇率、本币以及各自确认日期；
- 供应商账单、发票、付款申请、付款、回单和后续调整。

跨主体代付必须保留业务主体对供应商的原应付，同时形成资金主体与业务主体之间双方对应的内部应收和内部应付，不能把付款主体直接改成采购主体。

### 9.3 P0：停止推算财务事实

正式报表不得读取以下值：

- 按比例虚构的订单收入；
- 根据文字猜测的币种和汇率；
- 按成本占比推算的已付金额；
- 页面手填且无法回到明细的实际成本总额；
- 为了展示完整而临时拼出的应付、付款、预付和凭证编号；
- 旧聚合页和兼容页的固定示例。

缺少来源时应显示“待确认”或进入异常，不得自动补成可报表金额。

### 9.4 P0：用明细计算余额

应付未付、可申请、预付余额和已付金额必须使用第五章公式，且能下钻到每一条发生、占用、核销、释放、退回、调整和冲销。

付款申请提交时占用可申请金额；驳回、撤销和关闭时释放；付款成功后把占用转为付款核销。预付冲抵只减少预付和应付，不重复产生资金支出。

### 9.5 P1：供应商返点和折让

当前只有账单页的“供应商承担优惠 500 元”等固定示例，没有正式返点能力。需要区分：

- 账单当期折让：直接减少本次账单确认额和应付；
- 销量返点：按合同期间和达量结果确认，可能冲减采购成本或形成其他处理；
- 市场支持或联合营销承担：按协议进入订单、渠道或供应商结算；
- 已结算后返点：通过成本调整和补充结算进入新期间，不覆盖原结算。

返点适用范围、含税口径、确认时点和跨期处理仍需财务确认，但系统当前缺少正式记录已是确定问题。

### 9.6 P1：异常管理

需要统一形成可下钻的异常结果，而不是把各页红色标签拼在一起。首批异常至少包括：

- 成本明细未确认、成本总额与明细不平；
- 供应商账单待识别、待挂接、重复、未分配和差异超期；
- 应付来源缺失、应付金额差异、可申请金额不足；
- 付款账户异常、付款失败、回单缺失或金额不一致；
- 预付未分摊、长期未冲抵、余额超期和非零关闭；
- 回团后未完成成本确认或结算；
- 团队收入小于有效实际成本形成的负毛利。

异常列表只负责定位和下钻，实际处理仍回到成本、账单、应付、付款或预付原页面。

## 十、页面改造顺序

1. 先重构共同成本、账单、应付、付款和预付记录及编号关系。
2. 改造团期结算：业务只维护和确认真实成本，移除财务推算值。
3. 改造供应商账单：支持账单行多团分配、独立成本对照、重复检查和差异记录。
4. 改造应付：用确认和调整记录计算有效应付、未付和可申请金额。
5. 打通业务付款申请、财务复核、审批中心和付款执行，处理占用及释放。
6. 改造付款执行和回单：保存每次银行结果，付款成功后生成核销或预付。
7. 改造预付和退回：所有余额变化有明细，外币不丢失，非零余额不能关闭。
8. 最后建设团队成本、供应商往来、预付账龄、待付和异常分析。

## 十一、验收场景

后续实施至少用以下数字案例验收：

1. 一个团期三个供应商，分别有预估、实际成本、账单、应付和分期付款，总成本与明细一致。
2. 一张供应商账单覆盖三个团期，认可金额等于已分配加未分配，各团只取得自身成本。
3. 一个成本范围由两张账单支撑，同一成本不得重复计入。
4. 外币账单和付款使用不同汇率，原币核销正确，本币差额另行记录。
5. 先预付 300,000 元，后形成应付 500,000 元，冲抵后待付为 200,000 元，不能重复计算已付。
6. 付款申请 100,000 元审批中后可申请金额相应减少；驳回后恢复；付款成功后转为付款核销。
7. 银行付款失败后重新付款，保留两次执行记录，只有成功一次进入已付。
8. 供应商退回 20,000 元，能回到原付款并正确恢复应付或减少预付。
9. 资源数量减少后形成可追回款、不可追回损耗和预付转用，三者分别进入余额和成本。
10. 回团后补账使团队由正毛利变负毛利，保留原结算并形成调整和异常。

## 十二、仍需财务确认的规则

- 各产品实际成本成立的具体时点，哪些业务允许账单未到先暂估；
- 供应商账单确认、服务确认和合同付款节点分别在何时形成应付；
- 付款前合同、验收、账单、发票和审批的必备条件及例外；
- 供应商返点的含税口径、确认时点、冲减成本或其他处理以及跨期规则；
- 外币成本、应付、付款和预付所用汇率及汇兑差额规则；
- 预付跨团期、跨项目、跨法人和跨币种转用的限制；
- 跨主体代付的允许范围、内部清算和默认付款账户；
- 无银行接口阶段，什么凭据和什么角色的确认可以认定付款成功；
- “未提交准单”在新系统对应成本确认、供应商账单、航服准单还是其他业务对象；
- 负毛利的计算范围、预警阈值、审批要求和回团后调整期间。

## 十三、本轮最终判断

财务需要的供应商侧逻辑已经在现有业务文档里有较完整框架，不需要推翻重写；需要把“未来规则”与“当前已实现”明确分开。

现有页面能帮助确认角色、入口和操作内容，但不能证明系统已经有财务数据链。正式改造的最小闭环不是一张成本表，而是：真实成本确认、供应商账单核对、应付成立、付款申请占用、付款成功、应付核销、预付余额及全部调整能够使用同一套记录互相核对。

完成这条链后，团队总成本、已付、待付、预付、供应商结算价和成本异常才具备自动报表基础。

## 十四、唯一下一步

进入“回团结算、收入确认、发票、NC与会计期间模块代码—文档成对核对”，重点判断回团事实如何形成业务结算收入和成本、含税与不含税金额如何确认、结算后调整如何进入正确期间，以及业务结果如何生成并追溯集团财务核算系统凭证。
