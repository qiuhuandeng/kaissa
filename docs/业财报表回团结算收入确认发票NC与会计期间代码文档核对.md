# 业财报表回团结算、收入确认、发票、NC与会计期间代码—文档核对

版本：v1.0  
核对日期：2026年9月6日  
阶段定位：阶段2“代码与文档成对核对”的第六个业务模块  
本轮边界：只形成审计结论和改造方向，不修改业务页面

## 一、结论先行

当前原型已经提供回团、团期成本、业务结算、结算调整、发票、NC推送和期间关账等入口，页面覆盖面看起来较完整，但尚不能自动形成财务可信的回团业绩、团队毛利、不含税毛利或会计期间报表。

主要原因不是少一张报表，而是末端链路中的业务事实和财务结果没有真正分开并贯通：

1. 团期“标记已回团”只改变状态，没有记录实际回团日期、确认人、确认时间和更正过程。
2. 团期结算页会用页面总额按比例生成订单收入，用收款金额判断收入依据，用文字猜币种和汇率；业务结算页又使用另一套固定数据。
3. 项目中没有独立的收入确认和成本结转记录。现有页面把应收、实收、业务结算收入、会计收入、实际成本、应付和付款混在结算展示中。
4. 发票页面默认开票、收票或核验完成后生成凭证，结算调整页还把“发票红冲”直接当成收入冲减；这与“开票不等于收入、收票不等于成本”的财务规则冲突。
5. NC页面直接从结算、付款、发票等页面固定行生成任务，没有经过独立的会计事项和财务复核；其中已有借贷不平的示例仍被标记为“校验通过”。
6. 期间关账页按固定数量和提示判断缺口，会把正常未收、未付、预付和未到票一律当成阻断项；关账和反关也只改变当前页面状态，没有与NC账套、审批和调整范围同步。
7. 同一个团期、结算单和金额在团期成本、业务结算、结算详情、结算调整、发票和NC页面中已经出现编号、日期、退款/优惠含义和已付金额冲突。

因此，正确方向不是继续在现有“业务结算”页增加字段，而是建立以下清晰关系：

    实际回团或客户验收
    → 确定本次业务结算范围
    → 汇总有效订单、退款与优惠承担
    → 汇总有效实际成本和结算调整
    → 形成业务结算收入、结算成本与业务毛利
    → 按履约义务、主责/代理、税务和会计期间分别确认收入与结转成本
    → 发票与税额单独核对
    → 已生效的会计结果形成会计事项
    → 会计事项生成并复核凭证
    → 推送NC并接收唯一结果
    → 业务明细账与NC对平后关账

订单口径与回团口径应使用同一笔订单明细，只改变统计日期和纳入条件；不能各做一套订单或各保存一套收入金额。

### 2. 不能合并成一个状态的结果

以下结果必须分别保存，不能都叫“已结算”：

- 已实际回团或已完成验收；
- 业务结算已确认；
- 收入已确认；
- 成本已结转；
- 供应商对账已完成；
- 应付已确认；
- 付款已完成；
- 发票已开、已收或已认证；
- 会计事项已生效；
- 凭证已生成、已复核或NC已接收；
- 会计期间已关账。

## 四、代码事实与问题

### 1. 实际回团事实没有形成

schedules.html 的“标记已回团”只把 executionStatus 改成“已回团”，并把结算状态改成“未结算”，没有采集实际回团日期、确认人、确认时间、完成依据或更正原因。schedules-detail.html 中可维护的是计划回团日期，也没有独立的实际回团确认动作。

影响：

- 无法区分计划8月1日回团与实际8月2日回团；
- 无法按本周、本月实际履约统计；
- 上年下单、本年回团只能靠人工识别；
- 提前、延期、取消出团和回团日期更正没有历史；
- 财务无法证明收入确认和成本结转使用的是哪个履约事实。

证据位置：merchant/tour/schedules.html:6761、merchant/tour/schedules-detail.html:801。

### 2. 团期成本页生成了并不存在的订单和金额

fulfillment-cost.html 的结算收入直接取“实际收入或团期收入”，再按62%和38%拆成两条虚构订单；订单号、客户、收款号也由团号拼接。默认情况下，已收金额又直接取团期收入。币种和汇率通过线路、供应商名称中的“欧洲、邮轮、新加坡”等文字猜测，已付金额在没有付款明细时按成本占比推算。

页面还把业务结算收入计算为“应收减退款”，没有经过履约义务、主责方/代理方、代收代付和税务判断。项目结算提交校验要求“项目订单收款已核对”，容易进一步把是否收款当成能否确认收入的条件。

影响：页面可以演示结构，但任何收入、实收、成本、已付、外币和毛利数都不能进入正式报表。

证据位置：merchant/tour/fulfillment-cost.html:1758、merchant/tour/fulfillment-cost.html:2897、merchant/tour/fulfillment-cost.html:2934、merchant/tour/fulfillment-cost.html:3184。

### 3. 业务结算可以发生在回团之前

业务结算页的固定记录存在明显时间倒置：

- JS20260720001 的结算期间是2026年7月，但页面回团日期是2026年8月1日；
- JS-FIT-20260622004 已在2026年6月结算并锁定，出发日期却是2026年7月5日、回团日期是7月10日；
- 结算调整中多笔调整发生日期早于原团期出发或回团日期，却显示原结算已经锁定。

这不是普通示例日期不美观，而是说明页面没有执行“回团/验收事实—允许结算期间”的控制。结算确认函数只把状态改成已结算、已锁定、NC待推送，并生成一个凭证号，没有检查实际履约、会计期间、来源明细、审批或税务规则。

证据位置：merchant/finance/finance-settlement.html:138、merchant/finance/finance-settlement.html:174、merchant/finance/finance-settlement.html:955、merchant/finance/finance-settlement-adjustment.html:143、merchant/finance/finance-settlement-adjustment.html:154。

### 4. 同一结算对象在不同页面的金额含义冲突

以欧洲十国团期为例：

| 项目 | 业务结算列表 | 结算详情 | 冲突 |
|---|---:|---:|---|
| 结算单号 | JS20260720001 | JS20260624001 | 同一团期出现两个结算号 |
| 回团日期 | 2026-08-01 | 2026-08-02 | 履约日期不一致 |
| 应收 | 448,000 | 448,000 | 一致 |
| 实收 | 441,600 | 448,000 | 不一致 |
| 6,400差额 | 优惠减免 | 退款 | 同一金额含义相反 |
| 已付/待付 | 112,000 / 185,800 | 185,800 / 112,000 | 已付与待付对调 |

因此当前链接即使能打开详情，也不能证明下钻到了同一笔真实业务。

### 5. 没有独立收入确认和成本结转

代码中没有收入确认或成本结转入口。结算页直接展示“结算收入”和“结算成本”，结算成功后直接生成凭证号；NC页又直接接收“结算”“项目结算”“票损成本”等任务。

这会遗漏以下财务判断：

- 时点履约还是时段履约；
- 本次完成哪一项履约义务；
- 应按全额还是净额确认收入；
- 客户款应从合同负债、应收还是合同资产转入收入；
- 团前成本是预付、履约成本资产、暂估成本还是当期成本；
- 本次结转金额、原发生日期和会计日期；
- 跨主体业务由哪个核算主体确认收入与成本。

业务结算可以作为批量复核入口，但不能替代上述财务确认。

### 6. 发票被错误地当成收入、成本和凭证触发器

发票页在销项开票成功、进项核验通过或红冲完成后，统一把NC状态改为“待推送”并生成凭证号。页面没有保存价税合计、不含税金额和税额三者的完整关系，只有一个税率文本。

具体问题包括：

- 销项开票任务以“收款已确认、应收已审核”作为主要匹配条件，但收入和开票时点不应由是否收款单独决定；
- 进项票登记和核验后默认生成凭证，可能重复确认已经通过实际成本、暂估或应付入账的金额；
- 结算调整页的“发票红冲”示例直接减少收入600元。若只是开票信息错误，红票只能调整发票和税额，不应自动改变业务收入；
- 退款、价格调整、税务红冲和会计收入冲减没有分别记录；
- 境外票据、免税、差额计税、不抵扣和进项转出只有选项，没有对应金额和依据。

证据位置：merchant/finance/finance-invoice.html 中的 confirmProcess、merchant/finance/finance-settlement-adjustment.html:187。

### 7. NC页面存在会计结果错误和重复推送风险

NC页没有从独立会计事项生成凭证，而是直接把固定业务任务当成凭证。已有两个严重示例：

- 项目结算写成“借：项目成本1,512,600 / 贷：项目收入1,906,000”，借贷相差393,400，却标记为“校验通过”；
- 普通团期结算写成“借：成本297,800 / 贷：收入441,600”，借贷相差143,800，同样标记为“校验通过”。

页面还通过业务对象文字推断主体公司、部门、产品类型、客户/供应商编码、币种和汇率，并用固定日期2026-07-04推断会计期间。这样可能把9月才履约的邮轮或专列成本提前记入7月。

点击推送会直接改成成功并拼接一个NC返回号，没有“结果待确认”处理、提交记录、查询记录、NC实际接收金额、审核记账状态或原请求内容。选中的复选框也没有清除，批量操作可以再次执行同一行，存在重复写入日志的风险。

证据位置：merchant/finance/finance-nc.html:88、merchant/finance/finance-nc.html:91、merchant/finance/finance-nc.html:493、merchant/finance/finance-nc.html:524、merchant/finance/finance-nc.html:529及 markPushed。

### 8. 关账页没有区分正常余额与关账异常

期间关账页把未认款、待收款、退款、供应商账单、应付差异、回单、预付、结算、发票和NC数量组合成缺口，并用通用方法把大多数非零值直接判为问题。

与财务底座的冲突包括：

- 未到期应收、应付可以作为正常余额跨期，不应一律阻断；
- 合法预付余额和跨月履约成本可以保留，不应因为“未冲抵”自动阻断；
- 尚未到开票或收票节点的余额可以跨期，未收票也不必然阻断业务结算或会计关账；
- 回单不是资金结果的唯一依据，银企直连已明确成功时是否等待回单应按制度配置；
- 业务结算重开不等于会计期间重开。

确认关账只校验一个下拉框文字，反关则直接把状态改为“已反关”和“NC待推送”，没有检查业务系统与NC是否对平，也没有反关审批、允许调整范围、NC期间重开结果和重新关账记录。

从其他页面只传 period=2026-06 时，该页会命中同期间的第一家公司，不能保证打开正确核算主体。

证据位置：merchant/finance/finance-period-close.html:445、merchant/finance/finance-period-close.html:551及 confirmClose、confirmReverse。

## 五、文档规则与文档冲突

### 1. 当前可作为开发基线的规则

《业财底座04》和《业财底座05》已经明确：

1. 收款、开票、付款或业务结算完成，任何一个单独状态都不能替代收入或成本确认。
2. 收入确认以履约事实和会计政策为基础；成本按资源和服务实际发生及与履约的关系确认。
3. 发票只形成发票和税务结果；是否另形成凭证，要先检查前序收入、成本、应付是否已经包含税额，防止重复入账。
4. 业务结算允许保留正常未收、未付和待开发票余额，只阻断无法解释或未经批准的重大差异。
5. 已结算或已关账后发生变化，应保留原记录，通过补充结算、调整或冲销处理。
6. 会计事项是业务结果到NC之间的必要环节；一项经济影响只能入账一次。
7. NC推送超时、结果未知时必须先查询，不得直接生成第二笔凭证。
8. 业务系统关账与NC总账关账分开，二者对平后才算正式关账。

### 2. 需要修订的旧业务文档表述

《财务流程03》大方向可保留，但有两处需要在阶段4修订：

- 文档写“结算通过后，收入、成本和毛利才能进入稳定报表”。这句话只适用于“已确认结算结果”视图，不能把已实际回团但结算未完成的业务从回团业绩中删除。财务回团报表应同时展示暂估/待结算和已确认结果，并把差异单独列为异常。
- 文档写业务系统“不做复杂税务拆分，只提供标签给NC”。财务要求明确要看不含税收入、不含税成本和不含税毛利，因此系统至少必须保存可复算的含税金额、不含税金额、税额、税务处理和计算依据。税额可以由税务规则服务或NC规则返回，但不能只保留文字标签。

### 3. 仍需财务和业务拍板的规则

以下事项已有建议方向，但不能由原型代码自行写死：

- 跟团、邮轮、专列、自由行、单项、研学和MICE分别采用时点履约还是时段履约；
- 主责方或代理方的判断依据以及全额、净额收入规则；
- 各产品的实际成本、暂估、正式应付和成本结转时点；
- 实际回团日期与财务回团确认月份不一致时，回团业绩和会计损益分别落在哪个期间；
- 退款、补差、返点和后补成本在管理报表与法定会计报表中的期间处理；
- 发票是否为付款强控条件，以及不同业务的未到票关账规则；
- 差额计税、免税、进项抵扣、境外凭据和红字发票的详细计算；
- NC凭证按单据还是汇总推送，以及科目、辅助核算和凭证类别；
- 哪些异常必须阻断关账，哪些可审批后带入下期。

## 六、五类财务结果能否由当前模块承接

| 财务目标 | 当前可见能力 | 当前能否自动形成 | 主要原因 |
|---|---|---|---|
| 财务业绩明细底表 | 可见团号、订单、日期、收入成本和凭证入口 | 不能 | 页面不是同一数据，实际回团、收入确认、成本结转、发票税额和会计期间缺失 |
| 订单口径业绩 | 本模块可反查部分订单 | 不能作为完整订单口径来源 | 订单口径需回到共同订单及有效状态；本模块只能补充后续调整结果 |
| 回团口径业绩 | 有计划回团和“已回团”状态 | 不能 | 没有实际回团记录，结算甚至可能早于履约；未结算回团与已确认回团未分层 |
| 产品和渠道分析 | 结算页有对象类型和负责人文本 | 不能 | 产品、渠道、组织和责任归属不是订单发生时保存的共同资料，NC还通过文字猜测 |
| 毛利、预算和异常 | 可展示结算收入、成本、毛利、发票及关账缺口 | 不能 | 金额存在推算和冲突，没有收入/成本确认、税额关系和共同异常记录；预算另缺正式任务 |

结论：当前模块可以作为页面结构原型参考，但不能作为财务报表数据源。

## 七、目标业务逻辑

### 1. 回团口径和订单口径共用一笔明细

同一订单至少保留：

- 原始下单日期和有效状态；
- 对应团期、航次、班期、营期、项目或出行日期；
- 计划回团日期、实际回团日期和财务回团确认月份；
- 订单原金额、有效订单金额、优惠承担、应退、已退和净额；
- 业务结算收入、会计确认收入及各自确认状态；
- 有效实际成本、已结转成本及调整；
- 产品、渠道、门店、组织、人员、预算区域及发生时版本；
- 来源系统、原系统单号和导入批次。

订单口径按下单日期和有效状态统计；回团口径按实际回团日期或经财务批准的回团确认月份统计。两个结果引用同一个订单和同一组调整，不复制订单。

### 2. 回团业绩的两层结果

回团业绩不能等到全部发票、付款和业务结算完成才出现，应分为：

| 层次 | 纳入条件 | 金额用途 |
|---|---|---|
| 已回团待确认 | 已有有效实际回团/验收事实，但业务结算或成本仍有缺口 | 经营进度、暂估毛利、异常清单；必须明确“待确认” |
| 已确认回团业绩 | 业务结算范围已锁定，收入成本规则已确认 | 财务正式周报/月报和稳定毛利 |

会计报表再按会计日期、核算主体和收入成本确认状态取数，不能直接等同管理回团业绩。

### 3. 结算后调整

已结算后的新增退款、补差、成本、返点、汇兑或税额变化必须：

1. 保留原结算金额和原会计期间；
2. 记录新增来源、发生日期、发现日期、业务归属期间和会计入账期间；
3. 区分收入调整、成本调整、税额调整和只改发票信息；
4. 判断补充结算、当前期间调整、冲销重记或经批准重开原期间；
5. 在当前报表显示“原业务期间”和“本次影响期间”，避免把跨期变化悄悄覆盖回历史数。

### 4. 发票、不含税金额和收入成本

每项收入、成本和发票分别保存价税合计、不含税金额、税额、税率/税务处理、币种和换算依据。三者需要核对但不能相互替代：

    业务收入 ≠ 实收 ≠ 销项发票金额
    实际成本 ≠ 供应商账单 ≠ 应付 ≠ 已付 ≠ 进项发票金额
    发票红冲 ≠ 必然冲减收入
    取得进项票 ≠ 再次确认成本

### 5. 会计事项、凭证和NC

每个已生效会计结果先形成一条可追溯的会计事项，再按财务批准的规则生成凭证。推送前至少检查：

- 核算主体、NC账套、会计日期和期间；
- 借贷平衡、原币和本位币；
- 科目、客户/供应商、部门、利润中心、团期/项目等辅助核算；
- 收入、成本、应收应付和税额是否重复；
- 来源是否已冲销、是否已经被NC接收；
- 调整是否关联原会计事项和原凭证。

推送中、成功、明确失败和结果待确认必须分别记录。重推沿用原会计事项和原凭证任务，不能重新产生一笔相同经济影响。

### 6. 期间关账

关账应按核算主体和NC账套执行，至少分为：

1. 业务截止和资金日结；
2. 业务对象结算与未完业务检查；
3. 应收预收、成本应付预付、渠道门店和内部往来月结；
4. 发票税务、外币重估及会计事项检查；
5. 业务系统预关账；
6. NC推送和业务明细账对账；
7. 财务审批、NC关账和业务系统正式关账。

正常余额、正常未达、批准跨期和关账异常必须分开。反关必须经过审批并限定可修改范围；业务结算重开通常先走当前开放期间调整，不能默认反关原会计期间。

## 八、场景倒推结果

| 场景 | 当前原型结果 | 正确处理方向 | 状态 |
|---|---|---|---|
| 当年下单、当年回团 | 只能依赖“已回团”文字和固定结算行 | 保存实际回团事实；订单口径按下单日，回团口径按实际回团/确认月份 | 已确认缺口 |
| 上年下单、本年回团 | 没有专门关系 | 同一订单保留原下单日与本年实际回团日，分别进入两种统计 | 已确认缺口 |
| 提前或延期回团 | 计划日期可编辑，会覆盖原日期 | 计划日期与实际日期分开，变更保留历史及原因 | 已确认缺口 |
| 已回团、结算未完成 | 可能不进入稳定报表 | 进入“已回团待确认”，异常可下钻，不能消失 | 已确认缺口 |
| 已结算后新增成本 | 有结算调整页面，但日期和金额不贯通 | 保留原结算，生成补充成本/结算和当前期间会计事项 | 已确认缺口 |
| 已结算后退款或补差 | 调整页可展示差额但不形成共同记录 | 分开应收/退款、业务收入、税额和资金结果，并记录影响期间 | 已确认缺口 |
| 发票信息错误红冲 | 当前直接减少收入 | 只改发票和税额；有真实价格/退款变化时才另形成收入调整 | 已确认缺口 |
| 主责方全额收入 | 当前按“应收减退款”统一计算 | 按合同责任确认全额收入和对应成本 | 待财务确认具体规则 |
| 代理方净额收入 | 当前没有正式判断 | 客户全额资金与代理佣金收入分开，代收部分形成往来 | 待财务确认具体规则 |
| 含税与不含税毛利 | 当前没有完整税额关系 | 收入、成本、发票各自保存价税关系并按规则计算 | 已确认字段缺口，税务规则待确认 |
| 跨主体履约与结算 | 页面用公司名称文字，没有双方记录 | 分别确定签约、履约、收入、成本和收付主体，内部业务与资金清算分开 | 已确认缺口，正式组合待确认 |
| 跨期调整 | 页面只有“影响某月”的文本 | 同时保存原业务期间、原发生日、调整生效日和会计期间 | 已确认缺口 |
| NC超时或结果未知 | 点击即成功或明确失败 | 保留结果待确认，先查询NC，再决定是否重推 | 已确认缺口 |
| 正常预付或未到票跨期 | 当前可能直接阻断关账 | 按制度识别正常余额、批准跨期或真正异常 | 已确认缺口，阈值待确认 |

## 九、建议的修改页面与流程顺序

### 第一批：先补业务事实和共同关系

1. 团期管控和团期详情新增“确认实际回团/完成履约”，保存实际日期、实际人数、确认人、确认时间、依据和更正记录。
2. 团期成本页停止按比例生成订单、按文字猜币种汇率和按成本占比推算付款；只引用真实订单、收退款、成本、预付及付款记录。
3. 业务结算页按“本次纳入明细”核对，不允许直接修改来源金额；差异退回订单、退款、成本、账单等来源页面处理。
4. 统一结算列表、详情、调整和来源页面的结算编号、业务对象、日期和金额。

### 第二批：补财务确认层

1. 在财务模块建立收入确认工作入口，展示履约依据、收入模式、确认金额、税额、主体和会计日期。
2. 建立成本结转工作入口，区分履约成本、当期成本、暂估、正式应付和后续差额。
3. 业务结算只形成经营结果；收入确认和成本结转分别承接会计结果。
4. 结算调整改为按收入、成本、税额、汇兑和纯发票更正分类，禁止用发票动作自动修改业务收入。

### 第三批：重构发票、NC和关账承接

1. 发票页保存完整价税关系、原票和红票关系、验真认证结果及税务处理，不默认每次开收票都新增凭证。
2. NC页只接收已生效会计事项；主体、期间、科目、辅助核算、币种和税码必须来自正式规则和来源记录，不从名称猜测。
3. 增加借贷平衡、重复接收、结果待确认、冲销和来源反查控制。
4. 期间关账按核算主体和NC账套生成检查结果，区分正常余额、批准跨期和阻断异常，并保留关账检查结果和审批记录。

### 第四批：最后建设回团和会计报表

1. 先基于同一财务业绩明细形成订单口径与回团口径；
2. 回团报表同时展示待确认、已确认和跨期调整；
3. 再形成团队收入、成本、毛利、不含税毛利、预算完成和异常分析；
4. 所有汇总下钻到订单、实际回团、结算、收入确认、成本结转、发票、会计事项和NC凭证。

## 十、验收要求

### 1. 正常场景

选择一笔当年下单、当年回团的标准跟团订单，能够从订单明细依次核对实际回团、业务结算、收入确认、成本结转、发票、会计事项和NC凭证。订单口径与回团口径金额一致但统计日期不同，收入、实收和开票金额可以不同且均能解释。

### 2. 跨年场景

选择一笔上年下单、本年实际回团订单：上年订单业绩保留，本年回团业绩出现；若会计政策要求在本年确认收入和成本，能够落入本年会计期间并反查原订单。

### 3. 调整场景

选择一笔已结算、已推NC后发生供应商后补成本和客户部分退款的团期：原结算及原凭证不变，新调整分别影响收入、成本、税额和资金；报表能同时说明原业务期间与本次会计影响期间。

### 4. 发票场景

验证开票未收款、收款未开票、已确认收入未开票、进项票晚于成本、纯发票信息红冲和退款导致红冲六种情况，不发生重复收入、重复成本或重复税额。

### 5. NC与关账场景

借贷不平、主体缺失、期间关闭、重复推送和结果未知必须阻断或进入明确异常；正常未到期应收、合法预付和未到开票节点余额可按规则带入下期。业务系统与NC未对平时不能正式关账。
