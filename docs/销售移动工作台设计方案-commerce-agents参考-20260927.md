# 销售移动工作台设计方案

日期：2026-09-27。状态：用户已确认并要求独立项目；已于同日完成 caesar-sales-mobile 首轮原型，原凯撒业务页面未改。用户明确以 commerce-agents 的旅游智能体流程、交互和UI为主要参考，可以直接沿用并裁掉不适用功能。本方案面向一线销售顾问，前轮销售总监分析场景另行保留。

## 一、设计判断

以手机完成一笔销售的连续工作：接收客户需求 → 推荐现成产品或制作定制方案 → 客户确认 → 核对开单 → 收款认领／合同／资料 → 出行跟踪与售后。

上游来自销售本人客户、意向需求、公司可售产品和团期、报价与退改规则；下游进入现有凯撒订单、业务审批、计调资源确认、合同、财务认款及售后。销售负责客户需求与订单事实，AI协助整理和编排，计调确认资源，财务确认实收和执行退转款。

设计采用“工作台负责今天的事，客户承接一段销售关系，AI助手推动方案成交，产品提供直接选购，订单承接成交后的办理”。客户已指定线路时可直接从产品预订，不强制先与AI对话；需要定制时进入完整的需求、方案、调整和开单核对。

## 三、五个底部入口

| 入口 | 主要任务 | 页面组成 |
|---|---|---|
| 工作台 | 开始一天、继续未完工作、处理到期事项 | 身份／消息；今天优先事项；继续中的客户方案；接待客户、找产品、快速开单三个快捷入口；本人业绩弱展示 |
| 客户 | 找客户、看需求、继续销售过程 | 我的客户与意向；客户详情内本次需求、方案、跟进、订单；同一客户可以有多次出行需求 |
| AI助手 | 为当前客户找产品、做方案、解释和修改 | 当前客户及需求摘要；对话；产品／对比／每日行程卡；本次方案；开单核对 |
| 产品 | 客户指定产品时直接查找与预订 | 按目的地、出发地、日期、人数、预算筛选；团期／航次／班期；行程与费用；加入方案或直接预订 |
| 订单 | 成交后持续办理 | 我的订单、状态筛选、待处理条件；订单详情聚合收款、合同、游客资料、资源确认及售后 |

“我的”通过顶部头像进入，放账号、所属公司门店、个人业绩及设置；消息从顶部进入。当前方案属于某次客户需求，不作为全局购物车。后台管理和总监经营分析不占用一线销售的底部入口。

## 四、工作台首屏

1. 顶部明确当前销售、公司／门店及消息，避免多身份混用。
2. 今天优先事项按有效截止和业务影响排列，突出具体客户、订单和缺口：保留到期、签署未完成、认款退回、出行资料缺失。可以有客户回访安排，因其属于工作台；不把这类人工作业文字搬入ERP一级业务列表。
3. 保留一至三条“继续方案”，显示客户、目的地、日期、本次进度及上次修改；点击恢复该客户本次需求。
4. 高频入口为接待客户、找产品、快速开单。常规办理直接用表单，AI提供辅助入口。
5. 本人业绩靠后轻量展示；手机首页不承担渠道排名、经营归因、复杂利润和团队管理。

## 五、AI的核心工作区

进入时优先选择已有客户和本次需求，也可临时接待后补客户。页面顶部持续显示“当前客户＋本次出行需求”；从客户或订单进入时自动带入当前对象，切换对象另开或切换对应会话。

对话承担五类连续工作：

1. **整理需求**：销售输入或粘贴客户沟通，AI提取出发地、目的地、日期、天数、人数结构、预算和偏好；不明确的信息继续补问。语音转文字作为输入增强，不作为首轮必备。
2. **找产品／做方案**：标准产品用真实可售日期推荐；定制游用参考项目的每日行程与资源卡形成草案。初步预算与可采用报价分开。
3. **比较与修改**：支持“减少购物安排”“换同级酒店”“节奏慢一点”等；展示变更前后内容和金额影响，保留旧版。仅用于可定制方案，不直接改公司已发布标准产品或已签约订单。
4. **准备客户确认内容**：生成对客行程及报价说明预览，包含版本、适用人数日期、费用包含／不含、有效期及未确认事项。内部备注与成本不进入对客内容；由销售主动选择后发送。
5. **核对开单**：客户确认后引用指定方案与报价版本，检查联系人、游客、日期、人数、金额、签约／收款公司及资源确认方式；销售核对后保存订单草稿或提交，返回实际订单号及状态。

方案状态可采用“需求待补、方案草稿、待客户确认、已确认、已转订单”；这是方案自身进度，不替代订单状态。聊天里的“可以”“就这样”不自动等于客户已确认；销售记录确认依据。多个方案只有选定版本进入开单。

会话与方案必须可恢复；AI中断后能继续已有草稿，业务表单仍可使用。手机键盘不遮挡发送和确认按钮，长行程按天展开，金额和日期保持完整显示。

## 六、两条成交路径与ERP承接

**现成产品：** 客户需求 → 产品搜索／AI推荐 → 选具体日期与规格 → 核对预订 → 保存草稿／提交订单。

**定制方案：** 客户需求 → AI方案草稿 → 资源与价格核对 → 销售修改 → 客户确认指定版 → 核对开单 → 原单团／项目审核和订单承接。

本次用户明确把定制到开单作为销售AI的参考范围，因此前置方案协作属于建议范围；不借此重建供应商询价、采购审批和财务结算。ERP既有“客户方案确认后录入单团项目”的承接仍保持；报价及资源尚未确认时只能保留草稿或按规则待确认，不以AI生成文字代替确认。

开单后进入同一订单详情，采用清晰分区和当前状态主操作：

- 收款：提供订单收款方式或上传凭证、提交认款；显示未收、待复核、已确认及退回原因。凭证上传不等于实收。
- 合同：核对签约信息、生成合同草稿／发起签署、查看结果；签约先后按现有公司规则，不能固定为先付款后签约。
- 资料：复用客户游客资料，补充必要字段及材料；不同产品按材料要求展示。
- 资源与出行：只读确认结果、集合安排和已发布资料；销售可发起需求，确认仍由计调／资源岗位办理。
- 售后：从原订单选择改期、转团、退订等诉求，提交依据并看进度；业务审批、损失确认及财务退款职责保留。

订单AI以“解释当前卡点、核对缺失、整理客户沟通内容”为主。修改已确认服务、价格或合同必须进入原变更流程。

## 七、首轮原型范围与验收建议

首轮完成五入口框架、客户本次需求、AI产品与定制方案、比较修改、开单核对及订单详情。深度做通两条代表场景：标准跟团直接预订、家庭定制方案转开单；邮轮、专列、自由行和服务单按其差异保留后续扩展位置，未实施不报全覆盖。

成交后在手机内至少能演示认款提交／退回补充、合同发起／签署结果、资料补充、资源待确认、售后申请及进度。复杂批量操作、经营报表、资源采购、供应商成本和财务执行留后台。

原型使用独立且一致的样例，不要求当前模拟数据跨端同步，不以短信、微信分享、真实模型、银行／合同接口或应用发布为原型验收前提。正式接入另验客户归属、权限、来源数据、报价重核、重复提交与失败恢复。

必须覆盖：客户切换不串方案、同客不同需求可区分、缺日期／儿童年龄先补问、无可售资源给替代或待确认、报价过期不能直接采用、改方案不覆盖已确认版、开单核对后才有订单、上传凭据保持待复核、AI不可用仍可人工办理、离开页面可恢复草稿、390像素及软键盘布局。
