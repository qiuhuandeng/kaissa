# 业财报表财务分析与报表代码—文档核对

版本：v1.0  
核对日期：2026年9月6日  
阶段定位：阶段2“代码与文档成对核对”的最后一个业务模块  
本轮边界：只形成审计结论和改造方向，不修改业务页面

## 一、结论先行

当前原型不能自动生成财务五类报表，也不能把现有财务报表页视为可信的汇总结果。

页面已经有“经营损益、收款分析、付款分析、往来分析、预付分析、资金余额”六个视图，产品分析、电销业绩、门店工作台和主体工作台也展示了销售额、订单数、收款、毛利、渠道贡献和完成率。这些页面可以说明未来要展示什么，但现在仍是相互独立的演示数据，主要问题如下：

1. 财务报表始终先装入6条固定盈亏数据，再把少量浏览器本地记录拼进去，没有共同财务业绩明细，也没有正式取数范围。
2. 页面中的日期范围没有参与筛选或计算，产品分析的“按下单日期/按出发日期”也没有生效，电销业绩的日期同样没有生效。
3. 经营损益把应收当作收入、把已入账供应商发票和付款都累加为成本；同一成本可能因收票和付款被重复计算。
4. 固定盈亏数据中的“收入”已经是页面展示的结算收入，程序又减一次退款，导致页面加载前后的收入、毛利和毛利率不一致。
5. 往来汇总把“结算净收入”直接当作“已收”，把每笔应付全额当作“已申请”，并把逾期金额统一写成0，不能用于应收应付分析。
6. 产品分析的毛利率和退款率使用各产品比率的简单平均，不按收入、人数或订单数加权；筛选后虽然数字会变化，但仍不具备财务可解释的分子和分母。
7. 主体、门店、渠道和人员业绩分散在工作台、产品分析和电销业绩中，彼此不共用组织、人员、渠道、订单和任务数据。
8. 没有订单口径和回团口径两套业绩，没有周/月/季/年、同比、环比及跨年回团分析，也没有预算版本和订单/回团任务完成率。
9. 没有不含税收入、不含税成本、原币、本位币、汇率、管理口径、会计口径和数据截止时间。
10. “明细”会在缺少来源单据时临时拼出应收、退款和应付编号；其他反查只是把当前表格文字传到目标页，不能证明找到了同一笔业务。
11. 所有导出按钮只显示“已创建”或“已导出”的提示，没有生成文件、任务记录、口径版本、生成时间、定时更新或邮件发送。

因此，不能在现有六个页签上继续堆财务周报字段。正确方向是：先建立统一财务业绩明细，再把“经营业绩分析”和“财务对账报表”分成两类使用场景。

    统一财务业绩明细
    ├─ 订单口径业绩：按下单日期观察新形成的有效订单
    ├─ 回团口径业绩：按实际回团或财务确认月份观察已履约业务
    ├─ 产品、渠道、区域、组织和人员分析
    ├─ 毛利、预算完成和异常分析
    └─ 财务对账报表：收款、付款、应收应付、预付、资金、发票和NC

不同分析使用同一笔订单、履约、收退款、成本和结算关系，只改变统计日期、纳入条件和展示维度，不能分别维护一套固定数字。

### 2. 当前页面边界混在一起

现有财务报表页同时放了经营损益和资金、往来、预付等财务对账视图，却没有订单业绩、回团业绩和预算分析。另一方面，主体、门店、产品和电销页面各自展示一部分经营业绩。

这会造成两个问题：

- 财务和经营管理者找不到一套可以共同核对的业绩分析；
- 同一个“本月销售额、毛利率、退款率、渠道贡献”在不同角色页面中可能来自不同固定数字。

## 四、财务报表页的真实能力

### 1. 当前六个页签

| 页签 | 当前展示 | 真实能力判断 |
|---|---|---|
| 经营损益 | 结算收入、确认成本、毛利、毛利率、发票/NC | 有演示汇总和跳转；金额来源和计算不可信 |
| 收款分析 | 收款单、流水、订单/应收、客户/渠道、金额和NC | 可展示少量浏览器记录；本月汇总和渠道占比仍是固定数字 |
| 付款分析 | 应付、付款、供应商、已付、回单和NC | 可展示少量浏览器付款记录；本月金额和回单率为固定数字 |
| 往来分析 | 应收汇总/明细、应付供应商/明细 | 汇总算法把收入当已收、把应付当已申请，不可用于对账 |
| 预付分析 | 供应商、余额、本月新增和冲抵 | 完全固定，未读取预付管理结果 |
| 资金余额 | 账户/部门、当前余额、收付退和可用余额 | 完全固定，未读取资金池、银行或付款占用结果 |

### 2. 页面已有但可保留的表达

以下页面结构仍有原型价值：

- 财务报表用页签区分收款、付款、往来、预付和资金视角；
- 经营损益展示结算对象、收入、成本、毛利、发票和NC结果；
- 收付款报表保留财务单据号和来源单据号；
- 往来报表提供汇总和明细两层；
- 产品分析能按产品、目的地、负责人和渠道筛选；
- 电销业绩能按销售组、顾问、来源、产品和目的地查看转化；
- 工作台按集团、主体、产品、运营、销售、渠道和门店角色分视角。

这些只能作为未来页面结构参考，不能作为现有报表能力已完成的证据。

## 五、代码事实与问题

### 1. 固定数据与浏览器记录混算，没有共同取数范围

财务报表加载时先无条件写入6条固定盈亏数据，再读取收款、应收、退款、付款、回单、发票、NC、外采、单团项目和单项服务等浏览器本地记录。没有数据时，收款、付款和往来又各自回退到另一组固定示例；预付和资金余额始终使用固定表格。

这意味着：

- 页面不能说明“本次报表包含哪些来源系统、哪些组织、哪些单据状态”；
- 固定数据与用户刚刚在其他页面产生的演示记录会一起进入汇总；
- 同一业务若同时命中固定数据和浏览器记录，可能覆盖或累加在固定金额上；
- 浏览器清空、换设备或换用户后结果不同；
- 页面无法形成正式历史报表或重新生成相同结果。

证据位置：merchant/finance/finance-reports.html:397、572—625、607—805、845—910。

### 2. 日期控件不参与筛选，期间分析实际不存在

财务报表筛选程序只读取搜索框和下拉框，没有读取任何日期输入。产品分析虽然展示统计开始日、结束日以及“按下单日期/按出发日期”，实际筛选只读取产品、目的地、负责人、渠道和状态。电销业绩也只读取销售组、顾问、来源、产品和目的地。

因此页面不能完成：

- 当日、当周、上周、当月、上月、季度和年度汇总；
- 周环比、月环比、月度同比和年度同比；
- 按下单日期、出发日期、实际回团日期、结算确认日或财务确认期间切换；
- 跨年订单、回团后调整和关账后调整的期间解释。

证据位置：merchant/finance/finance-reports.html:516—545；merchant/data/product-analysis.html:376—395；merchant/sales/call-center/performance.html:174—200。

### 3. 经营损益存在重复冲减和重复成本风险

固定行中的收入、成本和毛利本来满足“毛利＝收入－成本”。例如欧洲十国行展示收入441,600元、成本297,800元、毛利143,800元。但同一固定记录又保存退款6,400元，程序加载后计算“净收入＝收入－退款”，再次扣除退款，页面运行后的收入变为435,200元、毛利变为137,400元。

6条固定行的页面合计原为收入3,317,600元、成本2,021,000元、毛利1,296,600元；程序再次扣除52,400元退款后，会变为净收入3,265,200元、毛利1,244,200元。页面源数据与运行结果已经不一致。

同时，程序还会：

- 把应收金额累加到收入；
- 供应商发票“已入账”时把票面金额累加到成本；
- 付款执行时再把付款金额累加到成本；
- 把退款执行金额从收入中扣除；
- 外采、单团项目和单项服务在没有现有金额时直接用页面金额补入收入成本。

成本确认、收票和付款是三个不同事实。把已入账发票和付款都计入成本，会使同一笔供应商成本重复；应收也不能自动等于业务收入或会计收入。

证据位置：merchant/finance/finance-reports.html:572—580、627—650、705—748、798—803、815—842。

### 4. 往来汇总不是由收款核销和付款申请计算

应收汇总直接取盈亏行的收入，并把“结算净收入”当作已收金额，逾期固定为0。外采结算还直接生成一笔“渠道销售汇总”应收，并设置为全额已收。应付供应商汇总则把每笔应付金额同时累加到“总应付”和“已申请”，不检查是否真的存在付款申请。

所以当前往来汇总不能回答：

- 某笔应收被哪些收款核销、何时核销；
- 应收何时到期、逾期多少天；
- 某笔应付已申请、审批中、可申请、已付和待付分别是多少；
- 预付冲抵是否减少了应付余额；
- 调整、冲销和付款退回怎样影响余额。

证据位置：merchant/finance/finance-reports.html:751—765、883—908。

### 5. 明细抽屉会创造并不存在的来源单据

经营损益没有真实收入或成本明细时，程序会用结算单号临时拼出带“AR、RF、AP”后缀的编号，并标记为已确认；发票记录又被追加到“收入与退款”明细中。

这类编号只能帮助演示表格，不能作为财务下钻，因为它们未必对应真实应收、退款、应付或发票记录。发票也只能用于核对票税状态，不能并入收入明细充当收入来源。

证据位置：merchant/finance/finance-reports.html:913—943。

### 6. 产品分析的汇总算法不具备财务口径

产品分析的每一行都是HTML中写死的销售额、人数、订单数、毛利率和退款率。筛选后，销售额、人数和订单数按可见行相加；毛利率、退款率和满意度则对各产品比率做简单平均。

例如一个销售额很大的邮轮产品和一个销售额很小的签证产品会对综合毛利率产生同等权重。退款率也没有说明按退款金额、退款人数还是退款订单数计算。页面虽然标注“预估毛利率”和“按人数计算”，但没有成本金额、退款人数和总人数明细可供复算。

页面的日期和统计口径不生效，导出也只显示提示。它适合作为产品经营原型，不是财务产品周报。

证据位置：merchant/data/product-analysis.html:106—112、314—395、455—457。

### 7. 渠道、门店和人员业绩是分散的固定视图

- 主体工作台固定展示本月订单额、收款、毛利和4大渠道按周柱状图；渠道分析按钮只显示成功提示。
- 门店工作台固定展示本月销售额、订单数、顾问排行和佣金预估。
- 电销业绩固定展示顾问、销售组、来源、产品和目的地数据；日期不生效。
- 产品分析的“负责人”只是产品负责人，不能替代销售人员、销售组或团控人员。

这些页面没有共用订单和历史任职归属，也无法从主体汇总下钻到渠道、门店、销售组、人员和订单。工作台应最终读取同一分析结果，而不是继续维护自己的数字。

证据位置：merchant/dashboard-group.html:49—103、200—230、695—719；merchant/dashboard-store.html:55—125；merchant/sales/call-center/performance.html:20—99、174—234。

### 8. 预算完成率没有任务分母

销售顾问工作台固定显示“本月GMV目标完成率72%”，但项目中没有对应任务、任务类型、年度/月度分解、适用组织、预算区域、版本、生效日期、审批和调整记录。

因此完成率没有可追溯分母，也不能区分订单任务与回团任务，更不能形成个人、销售组、门店和渠道的月度与年度预算完成。

### 9. 金额口径、税务和币种信息缺失

现有报表统一以人民币符号展示金额，没有保存或显示：

- 原币、汇率、本位币和换算时点；
- 价税合计、不含税金额和税额；
- 订单流水、实收、业务考核收入、业务结算收入和财务确认收入之间的区别；
- 预估成本、实际成本和会计成本之间的区别；
- 管理口径与会计口径；
- 调整前、调整金额和调整后金额。

所以F-013不含税毛利不只是少三列，而是收入、成本、税额和会计期间的上游关系尚未形成。

### 10. 反查是网址参数跳转，不是真实逐层下钻

现有报表通过读取当前行文字，把单号、名称和金额拼到目标网址。页面能打开结算、收款、付款、回单、应收、应付和NC入口，但没有共同记录证明目标页确实存在同一笔单据。部分目标参数还会由当前单号临时生成新的付款号或NC凭证号。

真正下钻至少需要：

    图表或指标
    → 维度汇总
    → 财务业绩明细
    → 客户订单和订单明细
    → 团期/项目及实际回团
    → 收款核销、退款和转款
    → 实际成本、供应商账单、应付、预付和付款
    → 业务结算与调整
    → 收入确认、成本结转和发票税额
    → 会计事项、NC凭证和会计期间

证据位置：merchant/finance/finance-reports.html:451—500、913—943。

### 11. 导出、定时更新和发送均未实现

财务报表的“导出、导出Excel、导出明细”，产品分析的“导出数据”和电销业绩的“导出”都只触发页面提示。代码中没有生成文件、下载、导出任务保存、权限检查、脱敏、报表版本、生成时间、定时计划或邮件收件人。

页面也没有“数据截止时间”和“最近更新时间”。当前代码中的日期还同时出现2025年6月、2026年6月和2026年7月，不能说明数字对应哪个截止时点。

证据位置：merchant/finance/finance-reports.html:995—1020；merchant/data/product-analysis.html:455—457；merchant/sales/call-center/performance.html:223—228。

## 七、建议的功能边界

### 1. 数据中心：经营业绩分析

主要服务财务分析、经营管理、产品、销售、渠道和门店负责人。建议在“数据中心—经营分析”形成共同入口，至少包括：

- 业绩总览：订单口径与回团口径切换，日/周/月/季/年及同比环比；
- 产品与目的地：旅游范围、产品类型、业务类型、目的地及产品负责人；
- 渠道与组织：渠道大类、具体渠道、门店、分公司、经营区域和预算区域；
- 人员业绩：销售人员、销售组、产品负责人和团控人员；
- 预算完成：订单任务、回团任务、年度/月度版本及各层级完成率；
- 毛利与异常：业务毛利、不含税毛利、负毛利、成本缺口、未结算和跨期调整；
- 业绩明细：所有汇总共同下钻的订单明细。

角色工作台只读取这些结果并带条件进入分析页，不再独立维护“本月GMV、毛利、渠道贡献和完成率”。

### 2. 财务：财务对账报表

现有财务报表可保留为财务经理和各财务岗位的只读对账入口，但应按真实财务对象重构：

- 收款与未认款；
- 应收余额和账龄；
- 付款执行与回单；
- 应付余额和账龄；
- 预收、预存与预付余额；
- 资金日报、资金周报、头寸和资金计划；
- 发票和税务异常；
- NC推送和业务系统与NC差异；
- 已确认业务结算损益。

“经营损益”可以保留已结算视角，但必须明确这是业务结算毛利还是会计损益，不承担订单业绩、回团业绩和预算分析的全部职责。

### 3. 报表只读，处理回到来源页面

现有“结算、付款、NC”等按钮应改成“查看结算、查看付款、查看NC”等反查语义。异常从报表进入时要自动定位来源记录和缺口，但处理仍在对应订单、履约、财务或预算页面完成。

## 八、统一业绩明细最低要求

统一业绩明细不是把所有金额塞在一个“收入”字段里。每笔订单或订单明细至少要能关联并展示：

| 类别 | 最低内容 |
|---|---|
| 订单 | 订单号、原系统订单号、订单明细、有效状态、下单日期、人数/数量、来源系统和导入批次 |
| 履约 | 团号/项目号、出团日期、计划回团、实际回团、履约状态、回团业绩确认状态和财务确认月份 |
| 产品 | 旅游范围、产品类型、业务类型、产品经营公司、产品负责人、目的地及分区 |
| 销售归属 | 销售人员、销售组、销售部门、门店、分公司、渠道大类、具体渠道、经营区域和预算区域 |
| 金额 | 订单流水、已分配实收、应退、已退、业务考核收入、业务结算收入、财务确认收入、供应商结算价和实际成本 |
| 毛利税务 | 含税收入、含税成本、不含税收入、不含税成本、税额、业务毛利和会计损益 |
| 资金成本 | 应付、预付、预付冲抵、已付、待付、供应商返点和成本调整 |
| 财务结果 | 结算单、收入确认、成本结转、发票、会计事项、NC凭证和会计期间 |
| 变化记录 | 取消、退款、变更、归属纠错、回团更正、结算调整及其生效日期和原因 |

一张订单包含多个产品、多个供应商或多种归属时，应在订单明细和金额分摊层面统计，不能把整单金额重复放到每个分类中。

## 九、每个指标必须公开的口径

未来每个指标和导出文件至少要说明：

- 统计对象：订单、订单明细、团期、项目、收款、结算还是会计事项；
- 日期口径：下单、出团、实际回团、结算确认、财务确认还是会计日期；
- 纳入状态：哪些状态计入，取消、退款、调整怎样处理；
- 金额名称：订单流水、实收、业务收入、财务确认收入或其他金额；
- 含税方式：价税合计还是不含税；
- 币种方式：原币还是本位币，使用什么汇率；
- 归属时点：按业务发生时、回团时还是当前组织；
- 比率分子和分母：毛利率、退款率、回款率和完成率均应可复算；
- 任务版本：预算完成率使用哪一版订单或回团任务；
- 数据范围：法人主体、经营组织、来源系统和权限范围；
- 数据截止时间、生成时间和口径版本。

## 十、改造顺序

### 第一批：先建立可复算的共同数据

1. 完成前六轮已确认的订单、实际回团、归属、收退款、实际成本、业务结算、收入成本确认和期间记录。
2. 建立订单或订单明细到团期、人员、渠道、组织、资金、成本和财务结果的共同关系。
3. 建立来源系统、外部编号、导入批次和防重复控制。
4. 清除报表参与计算的固定兜底数据和根据文字、比例或页面金额生成的财务结果。

### 第二批：建立订单与回团两套口径

1. 订单口径按真实下单日期和有效状态取数。
2. 回团口径按实际回团和财务确认状态取数，同时展示待确认与已确认。
3. 保存跨年订单、回团后调整、原业务期间和本次调整期间。
4. 建立日、周、月、季度、年度、同比和环比的统一期间规则。

### 第三批：建立归属、预算、毛利和异常分析

1. 统一产品、目的地、业务类型、组织、渠道和人员归属。
2. 建立订单任务和回团任务及年度/月度版本。
3. 分开业务毛利、会计损益、含税和不含税口径。
4. 建立未归属、未回团确认、成本缺失、未结算、负毛利、预算异常和跨期调整清单。

### 第四批：建设页面、下钻和交付

1. 重构经营分析和财务对账报表入口。
2. 打通指标、汇总、业绩明细和来源单据下钻。
3. 为角色工作台提供同一口径的摘要和带条件跳转。
4. 实现正式导出、生成记录、口径版本、权限和脱敏。
5. 口径稳定后再实现每日更新、周报生成和邮件发送。

## 十一、文档核对结论

### 1. 可以保留的规则

- 《业财事件表》关于报表必须从已生效业务和财务记录取数，不能从页面状态临时汇总的规则正确。
- 《财务流程03》和《业财底座05》关于资金、往来、结算、异常和管理报表职责的总体方向正确。
- 《财务模块全量审计报告》关于财务报表只读、可反查但不在报表处理源单的方向正确。
- 《页面重构任务卡》要求报表展示期间、组织、产品、金额、统计口径和更新时间，仍应保留。

### 2. 文档已有、代码未实现

- 从已生效单据自动形成财务报表；
- 报表可穿透到同一来源单据；
- 预付余额、账龄和冲抵明细；
- 资金余额、冻结占用、待处理资金和最近同步；
- 统计口径和更新时间；
- 业务系统与NC对账和异常清单。

### 3. 阶段4需要修订的文档表述

- 两份财务培训材料把“系统自动沉淀”和“可以穿透到源单”写成当前已经具备的能力，实际代码不支持，应改为目标流程或补充原型限制。
- 《财务模块全量审计报告》对现有六类报表页面的字段设计有参考价值，但“来源于已结算或已生效单据”的表述是目标状态，不是当前实现。
- 《财务流程03》中的业务结算报表需要与财务五类需求合并，明确订单口径、回团口径、预算版本、不含税毛利和待确认回团业绩。
- 数据中心目前只有产品分析，文档需补充统一经营业绩分析的角色、入口和与财务对账报表的边界。

## 十三、验收场景

后续不能只用一组正常数据验收，至少需要：

1. 正常订单：订单口径和回团口径分别进入正确期间，汇总可下钻到同一订单。
2. 部分退款：订单流水、实收、应退、已退、业务收入和财务收入分别显示，不重复冲减。
3. 跨年回团：上年下单、本年回团同时出现在对应两套口径，组织归属可解释。
4. 已回团未结算：进入“已回团待确认”，不进入“已确认回团业绩”，且不从分析中消失。
5. 回团后补成本：原期间、调整期间、调整前后毛利均可追溯。
6. 一单多产品/供应商：分配金额合计等于订单和成本总额，各分类不重复。
7. 人员调岗和门店迁移：历史业绩按发生时归属保持不变，批准重述另有记录。
8. 预算调整：旧报表保留原任务版本，新报表使用新版本且年度、月度和下级分解可核对。
9. 外币及税务：原币、本位币、汇率、含税、不含税和税额可复算。
10. 正式导出：文件合计与页面一致，记录筛选、口径版本、数据截止和生成时间。

## 十四、仍待财务和业务确认

1. 有效订单范围以及取消、部分退款、全退和跨期退款的冲减期间。
2. 业务考核收入与财务确认收入的正式计算方法。
3. 回团业绩中“已回团待确认”和“已确认回团业绩”的并列展示及合计方式。
4. 周起止日、跨年周、月度同比和调整归属期间。
5. 自营、凯撒甄选、外采和内部共享产品的判断规则。
6. 多目的地产品的主要目的地或金额分配方式。
7. 历史归属按下单时、回团时还是同时提供两套视角。
8. 订单任务和回团任务的下达层级、预算区域、版本和调整审批。
