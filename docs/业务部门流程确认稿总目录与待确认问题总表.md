# 业务部门流程确认稿总目录与待确认问题总表

业务确认推进稿 v1.0  
编写日期：2026年8月1日  
适用对象：项目负责人、业务负责人、产品负责人、销售负责人、门市负责人、产品/计调负责人、外采负责人、邮轮负责人、航服负责人、财务负责人、法务/合规负责人、技术负责人

本文用于把已完成的业务部门流程确认稿整理成一套可推进评审的总控材料。它不是新的业务流程正文，也不是会议纪要，而是用于回答三个问题：

1. 每个部门应该看哪几份文档、主责确认哪些内容、协同了解哪些内容。
2. 哪些跨部门规则必须先拍板，否则后续开发会反复返工。
3. 现有原型已经覆盖哪些方向，哪些缺口需要业务确认后进入开发范围。

本文适合项目组、业务负责人和评审会使用，不作为某一个部门的单独业务确认稿。各部门正式确认以对应的“流程01”业务确认稿为准。

评审时建议同时使用三份辅助材料。端到端业务场景不再单独成文，已经拆入各岗位流程确认稿中，并统一放在“需要业务确认事项”前，作为业务方评审时使用的跨部门协作场景复核章节：

- [业务角色阅读导航与确认范围](业务角色阅读导航与确认范围.md)：先让每个岗位知道自己主看哪份、协同确认哪份、只读哪份。
- [待确认问题决策表](待确认问题决策表.md)：把“是否”“建议”“需要确认”类问题整理成选项、影响、建议口径和拍板人。
- [统一状态字典与流转口径](统一状态字典与流转口径.md)：统一订单、收款、合同、团期、资源、成本、结算、NC 等状态定义。

上述辅助材料只在总目录、评审会和项目组统筹时使用，不放入各岗位流程确认稿的正文导读。各岗位流程稿应先讲正文流程，再用跨部门协作场景说明本岗位操作之后会交给谁、对方怎么处理、什么情况会退回、最终形成什么结果，最后进入待确认事项。

### 2. 外采文档拆分说明

原《外采产品与供应商协同流程01：供应商上线、代理入库、订单确认与结算流程》不是废弃，而是调整并合并为《外采产品部流程01：外采产品引入、代理包装、销售承接与结算流程》，作为凯撒外采产品部的正式业务确认稿。

外采正式确认稿收敛为两份：

- 《外采产品部流程01：外采产品引入、代理包装、销售承接与结算流程》：给凯撒外采产品部确认内部主体互采、体系外供应商产品采购、代理包装、销售承接和结算方向。
- 《体系外供应商端流程01：供应商产品上线、订单确认与对账结算流程》：给供应商运营和供应商端操作人确认中国国旅等体系外供应商怎么上线、确认订单和提交账单。

这两份文件共同属于“外采”业务确认稿系列，和销售流程、产品计调流程、财务流程一样，都是面向业务部门确认的文档。

## 三、跨部门主链关系

### 1. 标准产品主链

```text
产品资料 -> 团期/价格/库存 -> 销售下单 -> 合同/收款 -> 名单材料 -> 履约资源确认 -> 成本确认 -> 结算 -> 财务应付/收款/发票/NC
```

涉及文档：

- 产品计调流程01
- 销售流程01
- 财务流程01
- 财务流程02
- 财务流程03

必须统一的规则：

- 产品层只维护稳定资料，具体价格、库存和成本落到团期或项目团。
- 订单确认、合同生成、收款确认和资料锁定的条件要统一。
- 团期成本一旦由资源方或计调确认，不能由销售侧修改。
- 已结算后发生差异，走二次结算或结算调整，不改原结算。

### 2. 门店销售链

```text
门店开通/权限 -> 产品可售范围 -> 门店下单 -> 合同主体 -> 门店收款/预存 -> 总部认款 -> 履约交接 -> 门店对账/分润
```

涉及文档：

- 加盟门市流程01
- 销售流程01
- 财务流程01
- 财务流程03

必须统一的规则：

- 门店能看什么价格、能优惠多少、能否看结算价。
- 门店合同主体、收款账户、发票主体和分公司主体是否一致。
- 门店预存、客户团款、门店利润必须分开管理。
- 分润结算节点和计算规则必须由门店/渠道与财务共同确认。

### 3. 外采来源关系链

```text
来源判断 -> 集团内部主体互采 / 体系外供应商 -> 代理或共享入库 -> 销售订单 -> 履约确认 -> 内部对账或供应商账单 -> 财务应付/内部往来/NC
```

涉及文档：

- 外采产品部流程01：外采产品引入、代理包装、销售承接与结算流程
- 体系外供应商端流程01：供应商产品上线、订单确认与对账结算流程
- 销售流程01
- 财务流程02
- 财务流程03

必须统一的规则：

- 外采是供给来源和核算口径，不是独立产品类型。
- 集团内部主体互采不走供应商端，内部主体产品仍通过自营产品入口维护。
- A 销售 B 产品时，需要确认 A-B 内部结算模式、合同主体、收款主体和内部往来 NC。
- 体系外供应商产品才走供应商端产品、供给、订单确认和供应商账单。
- B 采购体系外供应商产品后共享给 A 时，A 与 B 内部结算，B 与体系外供应商外部结算，不能混成一条付款链。

### 4. 邮轮专项链

```text
船司/船只/舱型/模板 -> 邮轮产品 -> 航次舱型库存 -> 销售下单 -> 名单资料/房号/登船通知 -> 船方变更/退改扣损 -> 预付分摊 -> 航次结算/二次结算 -> 财务付款/NC
```

涉及文档：

- 邮轮业务流程01
- 产品计调流程01
- 销售流程01
- 财务流程02
- 财务流程03

必须统一的规则：

- 舱型用业务名称，同时保留船方代码和房间数量。
- 多地出发优先以同一航次舱房库存为核心，前后段交通单独处理。
- 销售只能备注房号偏好，房号由邮轮运营或船方确认。
- 船方重大变更必须处理已售订单和合同，不能只改产品页面。

### 5. 航服机票链

```text
航司/航线/协议 -> BSP散票或团队位库存 -> 销售/产品团期绑定 -> 收款或账期 -> 出票/PNR/票号 -> BSP/IATA/B2B对账 -> 票损/退改签 -> 航服准单 -> 产品成本/航服收入 -> 财务付款/NC
```

涉及文档：

- 航服机票业务流程01
- 产品计调流程01
- 销售流程01
- 财务流程01
- 财务流程02
- 财务流程03

必须统一的规则：

- BSP 散票按订单和出票记录管理，不进机票切位库存。
- 团队票出票前必须确认团号一致。
- 航服对内供票时，航服确认收入同步成为产品团期大交通成本。
- 航司订单号、PNR、票号是航服对账和追溯的核心字段。

### 6. 财务收口链

```text
订单应收/收款 -> 成本确认/供应商账单 -> 应付/付款 -> 发票 -> 结算 -> 调整/二次结算 -> NC -> 报表/关账
```

涉及文档：

- 财务流程01
- 财务流程02
- 财务流程03
- 各业务专项流程

必须统一的规则：

- 财务只核对和确认已发生的业务事实，不替业务补录核心事实。
- 应付和预付判断要按付款节点、回团/完成、账期、结算状态组合。
- 发票是否强控付款，需要按供应商和业务类型配置。
- NC 推送失败在财务侧处理，不回滚业务源单。

## 四、P0 跨部门待确认问题

以下问题建议作为确认前必须确认的 P0 问题。若不确认，后续页面和开发边界会反复变化。

| 编号 | 问题 | 涉及部门 | 建议主责 | 影响范围 |
| --- | --- | --- | --- | --- |
| P0-01 | 合同生成条件按订单确认、收款比例、全款，还是按产品/渠道/门店配置 | 销售、门店、财务、法务 | 销售负责人 + 财务负责人 | 销售、门店、收款、合同 |
| P0-02 | 普通订单未收款、收定金、收全款分别是否允许占位、确认和签合同 | 销售、产品计调、财务 | 销售负责人 | 库存、合同、收款 |
| P0-03 | 报名截止后是否自动关闭销售，材料截止后是否锁定客户资料 | 产品计调、销售、门店、邮轮 | 产品计调负责人 | 团期销售、名单材料、售后 |

## 八、确认时的统一确认口径

每份文档确认时，建议业务负责人按以下口径确认，避免只说“已阅”但没有业务约束力：

1. 本文档描述的角色分工符合本部门实际业务。
2. 本文档描述的业务对象、状态和流程可作为系统开发和验收依据。
3. 本文档列出的“需要业务确认的问题”已在评审中逐项给出结论，或明确列为二期待确认。
4. 本文档列出的“原型已覆盖与需要补充事项”可作为后续开发范围拆分依据。
5. 若后续业务提出与本文档冲突的新需求，应以变更形式重新确认，不直接口头覆盖。

## 九、下一步工作建议

完成本文档后，建议下一步做两件事：

1. 按本文档的 P0 问题，整理一张可评审的《P0 业务拍板问题清单》，每个问题只保留“选项、影响、建议口径、拍板人”。
2. 按“原型覆盖与开发缺口总表”，整理《业务确认后开发任务拆分表》，把每个缺口拆到页面、字段、流程、审批、报表和接口层面。

当前阶段不建议继续新增大而全的流程稿。更有效的动作是拿现有确认稿推进评审，让业务先对核心口径给结论。
