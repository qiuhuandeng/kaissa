# 同行供应商结算最终走查与开发交接

日期：2026-09-26。范围：外部同行旅行社供货、集团采购公司承担结算责任的业务原型；复核原结缺01—07及走查01—03。佣金代销另有规则时单独确认，不自动套本采购场景。

本轮重新核对导航、页面加载、业务规则和各岗位操作，复用18套检查统一运行，不用历史测试数量代替本次执行。验收结论见第五节。本轮只增加统一验收入口和交接文档，不新建业务模块，不改并行订单、应收和审批工作线。

## 一、业务流程和岗位交接

采购公司是本笔采购及结算的责任公司，其他集团公司不会因为同属集团就自动有权代付。计调核业务事实，供应商核自己应收的费用，财务核欠款及资金、票据结果。

| 环节 | 谁从哪里办理 | 提交／确认了什么 | 下一岗位及异常去向 |
|---|---|---|---|
| 采购确认 | 供应商订单人员：订单确认 → 本采购单 | 数量、价格、供应商确认号；补差、保留、无法承接或取消损失 | 原条件确认交采购公司计调；补差／损失须计调认可，未认可不覆盖采购价 |
| 实际费用 | 计调：履约中心 → 团期结算 → 供应商对账 → 采购依据 | 实际服务、增减及依据；来单可补实际费用 | 可用于对账；已纳入已提交／已确认对账的原依据不能直接覆盖 |
| 供应商先报 | 供应商结算人员：对账结算 → 提交账单 | 选择已有采购订单费用、账单金额及材料 | 交采购公司计调核对；已有原对账则关联，不再重复建成本 |
| 我方先发 | 计调：供应商对账 → 新建对账 | 采购公司、供应商、费用范围与金额 | 交供应商逐项核对；不替供应商确认 |
| 差异往返 | 供应商原单核对；计调原单处理 | 保留原金额、主张金额、原因及本次认可 | 调整过金额交另一方确认新版；材料不足退原提交人补充 |
| 对账完成 | 双方确认同一版本及明细金额 | 状态“双方已确认”，历史版本保留 | 交财务应付岗；这是账对完，不等于付款或发票完成 |
| 申请与复核 | 计调从原对账详情进入付款申请；财务从成本应付 → 付款申请 | 本单、确认版本、费用、可申请金额和本次申请 | 本例提交为待财务复核；财务复核送审或退原申请人，审批顺序须按公司政策配置 |
| 执行付款 | 资金岗：成本应付 → 付款执行 | 获批付款的公司、账户、金额及银行结果 | 成功计已付，失败保留原单重试，结果未知保持付款中；回单由原回单核销承接 |
| 核票与补票 | 供应商原对账详情补票；发票岗：资金票据 → 发票管理 | 原收票任务、材料版本、购销方、币种、金额及核验依据 | 退回交供应商在原任务补正；上传不算核验通过，核票不改变付款金额 |
| 退款到账 | 供应商原单提交退款凭据；资金岗：成本应付 → 付款退回 | 原付款／预付、应退依据及逐笔实际到账 | 供应商凭据不代表我方到账；资金岗核到账后交应付岗处理余额 |
| 行前预付查看 | 供应商：订单确认 → 本采购详情 → 预付款 | 已发布的预付节点、实际已付、未付、付款中及缺少材料 | 不必等待最终对账；缺材料交采购公司计调，付款异常由资金岗处理，供应商只读 |
| 后补费用 | 计调及供应商：原已确认对账详情 → 后补费用 | 独立增减、原单及版本、依据、异议与新版确认 | 一致交本公司财务结算岗，走原业务结算／结算调整；原账及付款不覆盖 |

两条发起路径没有先后依赖：**供应商先报交计调，我方先发交供应商；双方确认同一金额和版本，才完成这次对账。** 采购订单先于对账存在。

## 二、七项及三个补齐点的交付核对

| 编号 | 当前交付 | 页面／验收证据 | 原型边界 |
|---|---|---|---|
| 结缺01 我方对账工作区 | 新建、草稿、提交、处理差异、重提及历史 | 团期结算供应商对账；对账规则与浏览器 | 不替供应商确认 |
| 结缺02 供应商逐单办理 | 主动提交、关联原单、逐项确认／异议及退回补充 | supplier对账结算；主动账单、对账检查 | 仅本供应商，不串采购公司或费用 |
| 结缺03 采购确认依据 | 回复、补差认可、保留、无位、取消损失 | supplier订单确认、我方采购依据；采购检查 | 不包含新建采购和取消申请发起页重构 |
| 结缺04 实际服务及费用 | 计调确认实际数量和增减；来单补实际依据、旧版保护 | 原采购依据、原对账；采购检查 | 不以报价或客户退款直接覆盖实际成本 |
| 结缺05 双方金额保留 | 差额、部分认可、原账单及确认版本、沿用原应付 | 财务供应商账单、应付管理；对账与款票检查 | 缺失系统成本不当零，也不用供应商金额直接补平 |
| 结缺06 对账交应付付款 | 本单申请、预付冲抵、复核、执行、失败重试及反查 | 原业务付款工作区及原财务页；请款／款票检查 | 当前页办理，不模拟跨页实账 |
| 结缺07 款票和异常结果 | 只读款项、补票历史、退款凭据／到账、预付和后补调整 | supplier原订单／对账及财务原页；收尾／预付／调整检查 | 业务确认、实际付款、票据核验分别记录 |
| 走查01 本单付款申请 | 进入原两页签即带原对账、版本、公司、供应商、订单／团期及费用 | [本单申请验收](对账到业务付款申请本单承接实施验收-20260926.md) | 未确认、旧版及未知单拒绝，不借用其他固定费用 |
| 走查02 对账前预付查看 | 原采购详情可核本单预付安排与实际付款 | [预付查看验收](供应商对账前预付款查看实施验收-20260926.md) | 无发布资料不伪造零元，失败不计已付 |
| 走查03 后补调整对应 | 原单下独立增减、异议重提、供应商确认和旧版记录 | [后补调整验收](同行对账后补费用调整实施验收-20260926.md) | 不覆盖原确认，不直接改变应付或付款 |

财务的后补结算调整保留原工作区方向；本轮动态后补记录不自动生成该页财务单据。正式开发需补持久化和岗位交接，这不是当前原型承诺中的跨端联调验收。

## 三、金额核对及正常／异常案例

以下为独立办理示例，不把各页操作结果串加成一份真实资金台账。

| 场景 | 核对结果及必须保留的区别 |
|---|---|
| 最终对账和可申请 | 101,000应结 − 30,000已冲抵 − 50,000实付＝21,000未付；其中10,000已占用，尚可申请11,000。申请不是实际付款 |
| 部分申请 | 草稿5,000不占用；提交5,000后尚可申请6,000，实付仍50,000。提交11,000后可申请0，重复提交拒绝 |
| 预付冲抵 | 原预付35,000已冲30,000，余5,000；本页再冲5,000后未付16,000、可申请6,000。冲抵不是又一次银行付款 |
| 付款失败及重试 | 获批10,000执行失败不增加已付；重试成功后本页已付60,000、未付11,000。未知结果不得直接算成功 |
| 对账前预付 | CG-C07安排12,000，成功6,000，未付6,000（含付款中3,000）；另3,000有资料缺口。CG-C06实际服务未确认也可查看预付，失败4,000不计已付 |
| 退未用预付 | 原未冲余额5,000，分2,000和3,000实际到账后归零；原应付和尾款实付不变。供应商上传凭据仍不算到账 |
| 原付款被银行退回 | 原付款50,000保留，退回10,000另记；净付40,000、待付31,000、可申请21,000；不混成供应商退未用预付 |
| 补票 | 101,000票面与应结核对，不拿21,000未付余额当票面上限；补正第2版保留第1版和退回原因，核验不改变付款 |
| 后补增加和减免 | 原101,000保留，新增2,000待确认时不计入已确认后补；确认后含后补金额103,000。减免500、主张300、重提第2版分开保存，原款项不变 |
| 双向报账异常 | 同一费用不能重复进入两张有效对账；原单只选部分费用须补齐；跨公司、供应商、协议、币种及旧版办理拒绝 |

## 四、仍需业务与财务确认的政策

| 待确认事项 | 确认责任 | 对开发的影响 |
|---|---|---|
| 业务审批与财务复核先后、退回及重提路径 | 业务负责人、财务负责人、审批管理员 | 本例走待财务复核；普通旧申请有直接审批中的流程，正式实现不能把两者默认拼成同一顺序 |
| 先票后款／先款后票及紧急例外 | 公司财务、采购负责人 | 发票缺失是否挡付款、谁可批准例外，须按公司和协议确定 |
| 预付比例、账期、分期节点及尾款条件 | 公司财务、采购／计调负责人 | 决定付款节点何时可申请，不能把最终对账作为所有行前预付的前置条件 |
| 跨公司代付、冲抵及退款到账范围 | 集团及公司财务 | 没有批准依据不混用公司余额和账户，代付不改变原采购责任 |
| 结算后增减、退款责任、期间和票据处理 | 业务负责人、公司财务 | 业务双方确认差额后，财务另定应付／退款／冲抵、票据及会计期间 |
| 岗位兼任和正式可见范围 | 业务负责人、权限管理员 | 供应商只看本人业务，公司计调和各财务岗位按任职授权，演示身份不等于正式权限 |

以上未定政策不由本次测试批准。真实银行、税控、审批平台、集团核算系统、后台材料存储与跨端送达均未接入；也不以这些生产条件阻塞已约定的页面原型交付。

## 六、面向开发的承接说明

先保留以上业务事实和财务责任，再实现数据保存、接口和权限。原型共享脚本用来说明校验和交互，不直接充当生产后台。

| 要保存的业务记录 | 当前代码定位 | 正式开发必须承接的关系和行为 |
|---|---|---|
| 采购单、供应商回复和计调认可 | `supplier-reconciliation-model.js`、`supplier-purchase.js` | 采购公司、供应商、协议、订单／团期和费用一一对应；报价、提议及已认可条件分别保存 |
| 实际服务依据 | 同上 | 原报价独立保留；实际数量、增减和办理人有依据；已提交／确认的账不直接覆盖 |
| 对账及双方版本确认 | `supplier-reconciliation-model.js`、`supplier-reconciliation.js` | 原费用防重复占用；双方确认针对同一版本；保留原账单、附件、异议、每次提交和确认记录 |
| 业务付款申请 | `supplier-payment-request-model.js`、`supplier-payment-request.js` | 绑定确认版本和具体费用，按实际占用计算可申请；保存草稿与提交分开；退回后原单重提及审批顺序按获批政策实现 |
| 预付款节点和付款记录 | `supplier-purchase-payments.js`及原财务预付／付款页 | 按采购单归属展示；发布安排与实际付款分别取数；不能从对账冲抵金额倒推完整付款历史 |
| 应付、冲抵、付款和收票 | `supplier-finance-model.js`、`supplier-finance-ui.js`及七个财务原页 | 沿用原应付，不因收到同一账单重复入账；付款占用与实际成功、失败、未知结果独立处理 |
| 退款及票据补正 | 同上及对账模型 | 供应商凭据与我方实际到账分开；原款、退回类型、逐笔到账和补正版本分别可追溯 |
| 后补费用 | `supplier-adjustment-model.js`、`supplier-adjustment-ui.js` | 后补记录对应原对账／版本／费用，仅保存差额；确认后按原财务结算调整承接，不重新记录原费用 |

技术实现时还需完成：

1. 以服务端员工任职和供应商身份判断权限，不信任前端传入公司、角色或供应商；每次查询、提交、确认和附件读取都校验范围。
2. 保存记录版本，旧页面提交时拒绝覆盖新版；同一提交、费用占用、冲抵、银行结果和到账匹配建立防重复标识。并发下也不能超额或重复入账。
3. 在一笔成功提交内同时保存业务状态、版本和操作记录，再生成下一岗位可领取的任务；失败可重试，不能出现已改金额但未留下依据。
4. 付款与开票分别接真实结果；结果未知先查询，不直接重发。原型日期、示例账户、固定金额和页面内存应由真实来源替换。
5. 两端共用持久化业务记录，地址中的单号／版本只用于定位，不能视为授权或可信金额；动态付款申请及后补记录必须按原单准确承接，不能套固定样例。
6. 上线前按第二、三节场景补接口并发、身份越权、附件权限、历史迁移和实际财务核对验收；当前浏览器测试不能代替这些验收。

本线原型收尾后，下一步为业务／财务评审第四节政策，并按本交接说明进入正式开发。收到明确政策或具体试用反馈后再定相应修改范围，不自动增建页面或启动生产服务。
