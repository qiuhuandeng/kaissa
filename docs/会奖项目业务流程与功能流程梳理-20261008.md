# 会奖项目业务流程与功能流程梳理

日期：2026年10月8日

当前原型建设建议已进一步落实为[基于现有单团的整体改造方案](会奖项目基于现有单团的整体改造方案-20261008.md)，明确现有页面、具体办理区、业务状态、改造顺序和验收。本稿保留会议证据与业务规则分析，不以本稿早期局部下一步覆盖后续完整方案。

会奖项目需要按“客户项目统筹、具体活动执行、客户与供应商分别结算”组织。客户资料、框架约定和项目组可以维护一次；每场活动的负责人、服务、客户确认依据、成本和完成依据仍须分别保留。客户按场报价时保留分场金额，整体包价时保留整包约定。这样才能同时解决销售重复建团、多人协作困难和项目整体利润难以核对的问题。

本稿依据用户提供的7月28日会议逐字稿及两份理解稿，结合当前单团页面、对应业务文档和会议管理产品的公开能力形成。会议事实、草案设想、产品判断与待确认政策分别表述；本次交付为业务和功能流程分析，不代表页面已经实施。三份材料综合评审及应修订的具体规则见第十三节；第一至十二节保留完整业务流程、角色、现状对照及拟验收场景。

## 二 按业务组织方式区分三种使用场景

| 场景 | 如何组织 | 应保留的操作效率 |
|---|---|---|
| 一次性单团或单场会议 | 一个项目，默认一条执行记录 | 简单项目直接进入本场资料，不强迫用户先建复杂层级 |
| 一个大项目下少量线路或批次 | 一个项目，多条独立线路或执行批次 | 各自维护日期、人员、服务及成本，统一查看客户与整体结果 |
| 年度框架下大量会议 | 一个年度项目，按月或批次组织活动计划 | 批量创建、复制、分配和维护，只处理每场不同的内容 |

政府和企业是客户分类。业务在15:12—15:51明确表示当前基本操作相同，不宜仅据客户类型复制两套流程；特殊采购、合同或验收材料按客户约定补充。

“会议、奖励旅游、团建”等服务内容，应与“单场、多线路、年度多场”这种组织方式分开。发票种类也不能决定采用哪套业务流程。

建议采用以下关系：

```text
客户
  └─ 客户项目：合作范围、合同约定、销售、项目负责人、项目组
       ├─ 活动或线路批次一：日期、地点、负责人、服务、成本、完成依据
       ├─ 活动或线路批次二：日期、地点、负责人、服务、成本、完成依据
       └─ 项目共同费用：尚不能直接归到某一场的真实费用

框架合同／具体合同／客户确认单
  └─ 明确本次委托覆盖的活动、服务和金额
       └─ 项目订单及收款安排

活动的实际服务与采购依据
  └─ 供应商费用、对账及付款安排
```

这里的“活动”指一次需要独立确定日期、责任人、服务范围或完成依据的执行安排。全国路演的一站通常是一场；同一会议的多个会场、酒店或接送批次，通常先作为该场内的服务安排，无须都升级为子项目。是否另拆活动，取决于独立履约和核对需要，不按供应商数量拆。

项目订单回答“客户委托了什么、确认多少钱、怎样收款”；活动回答“何时何地由谁完成什么服务、发生哪些费用”。默认采用简单对应关系，但允许一份客户委托覆盖多场活动。不能强制每场会等于一张销售订单，更不能把应收改名为应付：应收是客户应付给我方的钱，应付是我方应付给供应商的钱，两条责任同时存在。

客户只确认多场整体包价、未约定每场价格时，成交金额留在客户委托或项目，不要求计调编出“客户已确认”的分场价格。若经营分析需要分场收入和毛利，再按批准的分配依据计算，并与客户原始约定区分；没有依据时展示分场成本及“收入未分配”，仍可核对整个项目结果。

## 三 从客户需求到项目收尾的业务流程

```text
客户提出需求
→ 澄清范围、方案与成本测算
→ 客户确认方案、价格和合同条件
→ 项目录入与内部审核
→ 分解活动并确定负责人
→ 资源安排、采购确认及付款申请
→ 活动执行与变更处理
→ 确认服务完成及取得客户验收依据
→ 按约定对客结算、供应商对账
→ 财务核对收付、票据及收入成本
→ 项目复盘与结项
```

这条线表达业务关系，不要求所有动作机械串行。采购订金可能早于执行，客户收款及开票按合同节点发生，供应商尾款可能晚于活动结束；不能把“完成对账”设成所有付款的统一前置。

当前系统规范明确排除完整询报价流程。因此前三步中的洽谈、投标及方案沟通可以在线下进行，系统保存最终确认结果和必要版本。年度项目若只有框架约定，先录入框架和计划；每场进入正式安排前补齐该场客户确认依据。框架存在不代表所有未来活动已经成交。

| 阶段 | 主要角色及高频任务 | 系统应承接的功能和结果 | 异常如何处理 |
|---|---|---|---|
| 需求与方案 | 销售澄清目的、日期、人数、预算、服务范围；计调提供可行性和成本依据 | 保存客户需求与最终方案附件；区分客户预算、对客价格和内部成本预算 | 未确定的内容明确标待确认，不用空金额或零金额冒充已确认 |
| 客户确认及项目建立 | 销售维护客户、签约公司、确认方案、付款条件和合同依据 | 单次项目记录成交金额；年框记录适用期限、服务范围、额度性质及具体委托方式 | 未签合同、客户主体不一致、超出约定范围按公司规则审批，不默认为已成交 |
| 内部分工 | 项目负责人分场、分人；小项目允许本人兼销售和计调 | 批量录入活动、复制模板、分配负责人，指定资源和助理人员 | 无负责人或超出授权范围的活动保留为草稿；转交保留前后责任记录 |
| 活动准备 | 场次计调核对本场日期、地点、人数、服务及预算 | 从客户确认结果形成活动资料，按类型展示行程或会议日程 | 已确认后的日期、人数、金额变更进入变更记录，不覆盖原依据 |
| 资源与采购 | 计调、资源岗确认酒店、会场、交通、设备、搭建等 | 记录服务日期和数量、供应商、确认号、保留截止、退改条件、付款节点 | 资源失效、替换、数量变化要说明对客户服务与成本的影响 |
| 成本预算调整 | 计调说明供应商涨价或新增费用，项目负责人按权限处理 | 保留原批准预算、最新预计、差额及内部处理结果 | 客户价格不变时同样显示成本增加与毛利下降；是否须再审批按公司规则，不以客户原确认替代 |
| 付款准备 | 业务经办依据已记录的采购或费用提出付款申请 | 带入项目、场次、供应商、费用及本次金额，交审批与财务办理 | 预付款、重复申请、付款失败、取消后退款分别保留，不用付款金额代替成本 |
| 执行与变更 | 场次计调、现场负责人完成服务并核对增减项 | 维护名单及适用的分房、接送、会议日程、交付材料、实际数量 | 客户临时加项分别记录“是否已发生”和“客户是否同意加价”；未确认加价不计入已确认成交额 |
| 完成与验收 | 计调确认服务完成，销售或项目负责人取得客户认可 | 记录实际完成日期、客户验收资料及未解决争议 | 某场争议独立保留，不把其他已完成场次全部拖回未完成 |
| 对客结算 | 销售、项目负责人按合同核对服务及增减费用 | 按场、按月或按批生成对客结算明细，关联订单、原确认及变更 | 合并结算仍逐场列示；部分认可、扣款和补充确认可定位到原服务 |
| 供应商对账 | 我方计调核对服务和费用，供应商确认 | 沿用我方发起、供应商确认的对账方向；与客户结算分别处理 | 已付多于最终费用形成待追回款，少付形成后续付款安排，保留原款 |
| 财务与收尾 | 财务核对资金、票据及核算；项目负责人复盘 | 财务确认收入成本，即按履约事实和公司会计政策确认应计入哪个期间的收入及成本；业务查看预算差异与项目结果 | 服务结束、客户验收、业务结算和资金结清分别表达，关闭后补费有依据地调整 |

## 四 年度多场会议应该怎样操作

以“年度服务上限500万元、某月100场、每场2万元”为纯说明例子。这里先假设500万元是合同上限；实际材料没有明确它是否为上限、已承诺采购额或其他金额。

1. 销售建立一个客户项目，录入年度合同及共同资料，不录成500万元已收款或已确认收入。
2. 月度计划由销售、项目助理或获授权计调批量录入。建议提供模板导入、复制上月与表格批量编辑；这是为解决重复建团提出的功能，不是会议已明确要求的文件格式。
3. 每场只填差异内容，例如客户活动编号、主题、日期、城市、人数、服务范围、本场预算或确认金额。系统沿用共同客户和条款，允许必要例外并提示核对。
4. 项目负责人将100场按30场、30场、40场分给三名计调。每人看到自己负责的活动，补充和提交本场服务及费用；销售可查看全项目进度。
5. 客户确认后，具体委托与活动关联；按真实合同形成订单或订单明细。不能让销售为了内部核对再逐场重建相同资料，也不能以人员分配代替客户确认。
6. 如果100场均已确认，每场确为2万元，本批客户确认金额为200万元；在无其他占用且合同采用该占用规则的假设下，剩余额度为300万元。正式占用时点、取消释放规则仍待业务与财务确认。
7. 完成60场时，可以看到这60场对应的客户确认金额120万元，同时保留实际成本、待确认费用、验收和收付状态；不能直接宣布120万元已经完成会计收入确认。
8. 如果客户按月结算，就汇成该月结算单，逐场列清原确认金额、已认可增减项与本次结算金额。一场延期或争议只影响对应部分。
9. 此例按场定价，项目整体结果可按唯一活动的金额及真实共同费用核对。整体包价项目则从客户委托取整包金额，结合活动成本核对，不能漏掉尚未分配到场的金额。月度结算单只是原明细的结算组织方式，不能再加一次成为额外收入或成本。

人员负责的“10万、50万”先作为所分配活动金额的汇总展示。会议没有清楚定义个人采购额度制度，因此不建议直接做员工额度账户、个人资金池或自动扣额度。

## 五 角色与权限

| 角色 | 最常处理的对象 | 应拥有的主要能力 |
|---|---|---|
| 项目销售 | 客户约定、项目订单、收款节点 | 维护已确认方案和价格、关联合同、发起客户变更、开票申请及收款认领 |
| 项目负责人 | 整体项目、活动分工及例外 | 分配场次、协调资源、查看预算和进度、处理跨场变更与结项 |
| 场次计调 | 本人负责的活动 | 维护服务、名单、资源、采购费用、实际完成及结算依据 |
| 资源岗及专项协作人员 | 被分配的酒店、交通、签证、会务等服务 | 维护授权范围内的资源与确认资料，不默认获得所有商业价格及财务权限 |
| 助理 | 活动计划、名单、材料 | 批量维护和整理资料；金额确认、提交及审批权限按任职配置 |
| 审批人 | 本次送审事项及对应版本 | 查看依据、批准或退回，不重复录入业务资料 |
| 财务 | 收款、付款、发票、结算及核算 | 确认资金和税务处理，办理财务单据；项目页提供业务来源及反查 |

一个人可以兼任多个角色，进入项目后按其有效权限直接操作，无须为了同一件事切换销售或计调界面。兼岗不自动取得审批本人申请、认款或付款权限。

项目组使用员工选择、分工、负责场次、参与起止时间和变更记录，支持按项目及人员导出。员工与参会人、游客分别管理；不以自由备注替代可统计的人员资料。参与登记不自动形成奖金或成本；如公司另需人工成本或奖金分摊，应另行确定政策。

## 六 会奖执行需要的服务内容

会奖与普通旅游单团可共用酒店、交通、用车、餐饮、名单等能力；会议执行还需按本场实际服务增加会场时段、布场撤场、设备、搭建、会议日程、讲师或主持及交付材料。这些属于行业补充建议，不能当作会议逐项确认的全部范围。

| 服务场景 | 应记录的关键内容 | 与普通团期的差别 |
|---|---|---|
| 奖励旅游或考察 | 行程、交通批次、住宿、用车、名单、证件、领队 | 继续使用项目团执行；不放入公开散拼售卖 |
| 纯会议 | 时间地点、会场安排、议程、设备、餐饮及交付标准 | 不强制填写旅游线路、出发地、航班或“回团”；以活动完成表达 |
| 含交通住宿的会议 | 到离时间、接送批次、酒店及分房、参会安排 | 同一场可以多人不同出发地和日期，不能只有一个全员往返日期 |
| 多场共用采购 | 共用供应商、服务期间、约定价格、各场使用量 | 合同或账单可以共用，但费用需要说明由哪些场次承担 |

采购不能只记“酒店一项多少钱”。数量和计价单位要适合服务，例如房间乘晚数、场地乘时段、车辆乘天数、设备乘使用天数。对客可以打包报价，内部仍可分项核对成本；对客费用项与供应商费用项不必一一相同。

现场追加费用应保留发生时间、服务内容、实际数量、我方确认人及客户确认依据。紧急处理权限和事后补认时限待公司确定；不能为了等待客户盖章而隐藏已经发生的费用，也不能把所有实际支出自动转成客户加价。

## 七 金额与结算设计

### 需要区分的六种金额

| 金额 | 业务含义 | 不可替代的内容 |
|---|---|---|
| 框架上限或预计合作额 | 年度合作范围或客户可能采购的规模 | 不直接代替成交、应收、实收或收入 |
| 客户确认金额 | 客户已同意的具体服务价款 | 不等于已到账金额 |
| 内部批准成本预算 | 公司允许本项目按何种成本方案执行 | 不等于供应商最终费用 |
| 最新预计成本 | 当前已确定费用，加上仍未确定部分的最新估计 | 同一费用的预算和实际不能重复相加 |
| 已确认实际费用 | 依据实际服务、采购及对账确认的费用 | 不等于已付款；预付也不自动变成实际成本 |
| 实际收款和付款 | 财务核对已经发生的资金 | 不自动代替收入、成本或业务结算 |

报价阶段、执行阶段、结算阶段分别比较最初预算、最新预计及实际结果。预计毛利与确认结果分开，费用缺失时标明缺口，不把空白当零后得出高毛利。

成本预算调整与对客价格变更分开。酒店涨价但客户不同意加价时，仍记录实际采购变化、预计毛利下降及内部处理结果；已经发生的费用如实保留，不能为维持原毛利隐藏成本。超预算审批阈值、紧急采购权限和补认期限待公司确认。

项目共同费用可以暂列项目层。若需要逐场毛利，应按可解释的实际服务量、人数、场次或约定规则分配；具体规则待确认。分配后项目汇总只能计一次，仍未分配的费用也必须进入项目整体结果，不得因没分到某场而漏掉。

### 含税录入与税务结果分别处理

业务维护供应商报来的含税总额，便于与采购及付款核对。发票号码、价款、税额、对应费用及财务核对结果另外记录。进项税额是采购时支付或承担的增值税；其中哪些允许抵扣，还需要符合适用规定。增值税法同时规定扣税凭证要求和不得抵扣情形，因此不能把上传专票当作抵扣完成。[增值税法第十六条和第二十二条](https://zhejiang.chinatax.gov.cn/art/2024/12/26/art_25716_84101.html)

建议区分“业务测算”和“财务确认”的税额及毛利。未取得或未核对发票时保留测算依据和待确认提示，不能展示成正式税务结果。发票识别仅帮助录入，人工税率与票面不一致时先核对；不可静默改掉原成本、付款或历史结算。

纯算术例子：假设一项含税金额1,060元、适用税率6%，价税分离为价款1,000元、税额60元。只有再确认该60元全部允许抵扣且费用处理适用，才可在相应测算中按1,000元处理；不得抵扣部分仍需按财务规则计入成本或费用。6%仅为示例，不是本项目所有服务的税率。

系统不宜使用含义模糊的“税前利润、税后利润”。可以按财务确认口径分别展示含税业务差额与不含税毛利，并明确后者成本中保留的不可抵扣税额。一般计税、差额处理、收取服务费或代收代付等适用条件，均不能由“普票团／专票团”一个选项决定。本稿不批准公司税务政策。

### 汇率的政策与系统责任

汇率政策由财务确定，系统必须能记录不同用途和适用依据：对客固定约定、对供应商固定约定、内部预算测算、实际收付换汇及财务记账可能不同。

每笔外币业务应保留原币金额、采用的汇率、适用日期和依据。固定合同汇率不能被每日参考汇率覆盖；首次付款也不应无条件锁死全项目后续业务。已确认记录需要调整时保留前后结果和原因。具体取哪天、谁有权改、汇差如何处理属于待财务确认事项。

### 完成和结清的状态

场次主流程建议围绕“计划中、待确认、准备中、执行中、已完成、已取消”表达；项目围绕“草稿、进行中、收尾中、已结项、已终止”表达。具体提交审核状态在对应申请中处理。

客户验收、成本核对、收付款和开票各自保留结果及日期，不在主列表并列堆多个状态标签。业务结项是否允许保留欠款或未付尾款，由公司定义；无论采用哪种规则，未结事项都必须继续可查、可追责，不因项目结项消失。

## 八 审批 合同 开票与提醒

审批人按公司、部门、事项、金额及有效任职匹配。找不到人员时应转交配置维护或授权处理，不能仍让业务靠记忆随便选人。兼任两个审批职位时，只有同一版本、同一事项且审批规则允许合并，才可合并处理；职责不同或金额已变更，不能一律跳过。

致远合同承接应保存合同编号、版本、批准结果、签署盖章资料及适用范围。合同已批准可以减少重复合同审批，但仍需核对本项目客户、我方签约公司、服务和金额是否属于该合同。合同内容变更要有对应版本；已批准不代表已签署，已签署不代表已付款。原型阶段可用已审批合同选择与材料登记表达，真实连接另行建设。

开票申请应明确客户、抬头、服务项目、金额、所覆盖活动或结算批次、票面备注、交付对象。票面备注与内部备注分别保留，财务处理时能完整看到；开票项目由财务维护。财务审核通过、正在开票、开票成功和开票失败分别表达，批准申请不直接显示开票成功；成功后可获取电子文件，失败可定位原因及重新办理。

到期提醒应基于业务数据产生：合同收款节点与账期、活动实际完成日、应提交结算的期限、资源保留截止日。规则需明确负责人、提前天数、逾期升级对象和停止条件，具体天数待公司确认。提醒在工作台、消息及项目记录内承接，不把“催客户、联系供应商”放成列表行操作。手机审批优先复用统一审批能力，致远或企业微信承接方式待确认，不另做一套会奖专属审批。

## 九 功能入口与当前系统承接

保留“产品中心—单团项目”作为项目资料及商务统筹入口，在同一入口内支持单场和多场。现有旧会奖地址已经归并，不建议再创建一个重复的会奖一级模块。

项目详情按后续[页面设计讨论稿](会奖项目原型页面设计讨论-20261008.md)收敛为“活动安排、客户约定、项目费用、项目资料”四个页签；活动详情建议为“执行安排、费用采购、客户款项、结算核对、资料记录”五个页签。项目负责人看全项目，销售核对商务约定，计调进入具体活动。费用和款项区域展示业务申请、结果及关联单据，真正的财务确认仍由财务办理。以上为设计建议，页签数量并非财务政策或已实施结果。

履约中心的日常视图按“我负责的活动”组织，支持跨项目按日期查找。旅行类活动继续使用项目团；纯会议采用活动执行内容，隐藏不适用的旅游字段。项目详情中的活动与履约视图指向同一份活动记录，不重复创建两套数据。

列表只放识别和处理需要的字段，例如活动名称、所属项目、日期地点、人数、负责人和主状态。复杂场景可展示“客户确认缺失、成本未确认项数、验收资料缺失”等可核对缺口；完整资料进入详情。批量导入、分配、复制服务高频任务；提醒和沟通记录不占操作列。

## 十 必须用真实操作走查的场景

| 场景 | 应看到的结果 |
|---|---|
| 普通一次性奖励旅游 | 单项目单次执行，不额外增加年框和批量步骤 |
| 五条线路的大项目 | 五名负责人分别操作，客户与整体结果统一查询，每条线路合同依据清楚 |
| 月度百场会议 | 共同资料一次维护，批量创建和分配后各人只补差异内容 |
| 一份客户委托覆盖三场 | 每场能核对服务及原委托；已约定分场金额则逐场核对，整体包价未分配时不编造逐场收入或毛利，合并结算不重复累计 |
| 月度计划重复导入且一场已采购 | 提示重复及差异；不得删除或覆盖已确认服务和采购历史 |
| 客户取消一场但供应商订金不退 | 客户减收与供应商取消损失分开；未确认客户赔付不计已确认金额 |
| 酒店涨价但客户不同意加价 | 客户确认金额保持，成本增加、预算差异与毛利下降可见，内部批准另按公司规则办理 |
| 一张供应商账单覆盖多场 | 各场分配与总账单一致，未分配金额可见，费用不会重复出现 |
| 一场已完成但验收或尾款未到 | 服务完成事实保留，验收及资金分别显示待处理 |
| 票面税率与估计不同且部分费用不得抵扣 | 提示差异，财务确认后调整对应结果，原含税采购额不被改写 |
| 境外合同固定汇率但付款换汇不同 | 各用途金额可解释，原合同汇率和实际支付记录均保留 |
| 负责人转岗且审批人兼两职 | 场次转交留历史，审批按有效任职和职责办理 |
| 项目结项后收到补充费用 | 关联原活动和依据，保留原结算及本次调整，不能直接改旧数字 |

本轮仅核验设计关系与示例算术，以上13类为后续原型验收标准，尚未执行页面或浏览器测试。

## 十一 实施优先级与待确认事项

最先应完成项目与活动关系、批量分配、人员登记、客户确认依据和活动执行内容；随后把成交、成本、变更、客户结算及供应商对账在项目内串成可用入口。税额、汇率、开票和提醒复用统一模块，补会奖条件，不另建重复的财务体系。

当前原型继续承接已确认方案。完整商机投标、供应商在线询比价、客户门户、现场签到系统、奖金计算及真实接口，不因本次业务梳理自动纳入实施。后续可以扩展，但不能让这些扩展掩盖本次核心痛点。

进入页面细化前，需要优先确认以下业务事实：

1. 年框金额的性质：合同上限、最低采购承诺、预计合作额还是已经确定的具体服务价款；如何占用及释放。
2. 实际对客约定：按场、按月、按批还是按整个项目结算；一份客户采购订单覆盖几场；增减项由谁确认。
3. 哪一级需要独立负责人、完成依据和成本结果；是否真实存在需要中间子项目的情形，避免无依据增加层级。
4. 当前毛利表原件及两种真实案例：一份多线路项目、一份年度多场会议，尤其核实税额、共同费用、服务费及外币处理。
5. 财务确认的税务、汇率、成本分配和结项政策，以及到期提醒的具体时限；未确认之前只做明确标注的测算。
6. 致远、统一合同和审批之间的职责：哪个系统保留最终批准及签署资料，变更如何关联原版本。

### 3 三条业务线及相互交接

| 业务线 | 正常流程 | 交给其他角色的结果 |
|---|---|---|
| 对客户 | 明确需求与服务 → 确认方案及价格 → 关联框架或具体合同 → 确认本次委托覆盖的活动 → 处理增减项 → 按场或按月对客结算 | 销售给计调明确的服务范围；给财务客户价款、合同收款节点、开票要求及客户确认依据 |
| 活动执行 | 建立场次计划 → 分配负责人 → 安排行程／会议日程、名单和资源 → 确认采购及执行准备 → 现场交付及记录变化 → 确认实际完成和验收资料 | 计调给销售实际交付与待认可增减项；给财务可核对的完成和费用依据 |
| 对供应商 | 明确服务及数量 → 确认采购价格、取消条款和付款节点 → 按条件申请订金或阶段款 → 核对实际服务 → 供应商对账 → 多退少补 | 业务确认服务与价款，审批人处理申请，财务核验并执行付款，结果回供业务查看 |

这三条线可以同时推进。客户已确认但供应商资源未定、订金已付但尚未执行、服务已完成但客户未验收、客户已开票但尚未付款，都应能够准确表达。供应商对账不是预付款的统一前置，开票、收款也不自动等于收入确认。

项目建立前可以存在询价、投标和方案修改，这是实际业务流程的一部分。当前原型按既有边界只保存最终确认资料，不因本次完整业务梳理自动建设商机投标或完整线上询比价。

### 4 两份稿件还需补充的经营事实

**客户怎样计价。** 总价与分项是展示方式，固定包价与按实际服务结算才会改变增减费用的处理。固定包价项目采购涨价，客户价款通常不会自动增加；按实际数量和约定单价结算，则应保留客户认可的数量与单价依据。按实际采购费用加服务费、仅收代理服务费等若实际存在，应另记录计价约定；不能仅凭“代收代付”文字决定财务收入总额或净额。

**费用是否完整。** 最新预计成本应覆盖已发生、已确定但未发生、尚需采购的预计费用，同一服务按当前有效金额计一次。例如酒店最新确认3万元、已付订金1万元，酒店预计成本仍是3万元，不是4万元，也不是只算1万元。新增的现场费用即使客户尚未同意加价，也不能从内部成本中消失。

**分场毛利是否具备依据。** 直接费用落场次，不能直接归场的共同费用留在项目。管理分析如需分配，应保留分配方法、原总额及未分配余额。项目合计为各场直接费用加共同费用，已分配的共同费用不能再加一次；项目组多人导出也不能使同一活动金额重复求和。

**一个日期不能包办所有期间。** 计划活动日期、实际完成日期、客户验收日期、客户结算日期、实际收付款日期与财务确认期间分别保留。月份筛选应说明按哪个日期；未完成的场次不能仅因月份结束自动转完成，跨年项目也不能重复确认整份框架金额。

**取消后仍有责任。** 客户取消一场时，需要分别判断客户退费、供应商退订、不可退损失、已付待退和未付欠款。活动变成已取消，不删除这些金额和责任；部分场次取消也不应覆盖其他活动的执行结果。

**名单和项目组不混用。** 员工项目组用于分工及贡献登记；参会人／游客用于实际服务。纯会议按需要记录参会名单和服务信息，含交通住宿的活动增加到离、分房、接送和必要证件资料，不能因不是旅游团就一律取消名单。

### 5 两个数值反例

付款例子：假设某项有效付款依据为28,000元，实际已付8,000元，有效申请中尚未支付4,000元，无退款、冲抵或其他限制，则可申请16,000元。新增5,000元申请后，可申请11,000元，实际已付仍为8,000元。审批通过也不增加实际已付；以后真实支付这5,000元时，应同时减少相应在途申请占用，不能两边重复扣。

毛利例子：只演示已经由财务核定税额后的计算，不作为公司税务规则。假设含税客户价款106,000元，财务确认对应不含税收入100,000元；成本甲含税63,600元，其中3,600元经确认允许抵扣；成本乙含税10,900元，其税额不允许抵扣且全额计入本例成本。在无其他费用的假设下，含税业务差额为31,500元，不含税毛利为100,000−60,000−10,900＝29,100元。若机械把成本乙也除以1.09，结果会被高估900元。未核定税额或成本不全时，应标测算或待确认，不能称最终利润。

### 6 建议的交付范围与验证顺序

第一步先把项目、活动、客户具体委托和成员关系讲清楚，并完成单次快速录入、多场批量建档及分配的设计。第二步围绕活动补执行安排、成本预算与实际、变更和客户／供应商分别结算。第三步复用统一财务、合同、审批、发票、汇率、提醒和数据中心能力，补会奖的范围与依据传递。审批去向、付款真实性及变更留痕从第一步就必须成立，不能因为接口安排较晚而忽略这些边界。

原型应按第十节的13类场景验收，并补两个反例：所分配活动对客金额不能冒充个人成本预算；固定包价涨成本与按实际数量结算的对客变更结果必须不同。真实接口、移动推送和自动识别可以另行实施，不作为本次分析完成条件；奖金公式、独立客户门户及现场签到系统也没有因本次梳理自动获批。
