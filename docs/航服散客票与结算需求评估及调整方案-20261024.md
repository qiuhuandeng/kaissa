# 航服散客票与结算需求评估及调整方案

日期：2026-10-24。评估时未修改业务代码；用户随后明确“好的，按你上面的计划分步执行”。**四步方案已确认，第1—3步已实施验收，第4步未实施。** 现行进度见[第3步实施记录](航服确认单与出票资料第三步实施-20261024.md)。以下现状、缺口与“未修改”证据均保留为实施前评估基线，不能用来覆盖最新进度。

本次依据用户提供的23项业务讨论，核对当前菜单、页面及共享脚本，评估现有能力、实际缺口和需要纠正的业务口径。不是按讨论清单直接实施，也不重新设计一套航服系统。集团财务原8批、36项、6场景的历史验收状态不变；本次发现不等于上述新增场景已验收。

## 五、建议执行顺序及确认内容

建议批准以下四步，每次只推进一步并单独验收，不把整份清单作为一次性重做授权。

1. **订单、日报与核单。** 补实际缺少的乘机人／日报字段，统一即时和批量回填的匹配，明确同票多段、多票一单，展示预计与实际成本差异；同步区分内部按团、外部按单的业务结算。先修“金额为什么是这个数、属于哪笔订单”。
2. **取消、退改与原款。** 补零损失／待定损取消、原团损失留痕、原收付关联、统一退款余额和渠道差异；沿现有资金审查继续补机位付款与平台持续充值的原型表达。
3. **确认单与出票资料交付。** 在原导入／出票抽屉补供应商确认单识别复核、文件与票关联、来源销售领取、含服务费的我方报价／结算资料。真实AI、通知服务、银行及航空接口均不是本轮原型完成条件。
4. **基础资料与入口收尾。** 补协议负责人／续约、采购来源叫法；核对直接团队报名和成本入口，再做受影响其他产品的回归。库存与分期付款继续留机位管理，不迁入航线库。

用户已确认的方案原则：

- 保留现有模块、列表办理抽屉和订单六页签；即时登记与批量回填并存。
- 日报保留交易明细并关联订单，不按每行自动创建一张成本订单；确认单与付款允许分次及汇总分配。
- 内部按团、外部按订单确认业务结算；月度对账和实际收付可以汇总但必须分配到明细，结算后调整保留历史。
