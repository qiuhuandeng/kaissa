## 本批修改

销售顾问从产品预订进入下单，核对门店当前授权和名额保留条件；订单详情承接资源、付款和到期处理；合同经办人在合同管理准备、审核及发起签署。计调负责资源确认，公司财务负责确认收款结果，法务负责适用合同条件。

| 页面 | 解决的问题与现在的操作 |
|---|---|
| 销售下单 | 增加草稿、待确认两种处理方式。草稿不占名额；未取得保留结果的待确认订单不开始计时。预留、人工占位读取门店同一份有效时长，时长未定时提示保存草稿或提交待确认。门店暂停、待开通、资质到期、产品类型未授权或产品停售时阻止新提交。选择“确认”不能越过资源与付款检查 |
| 销售订单详情 | 将笼统复核拆成销售授权、资源确认、确认付款条件、名额截止和到期处理，每项显示处理岗位。保留原订单已有截止时间；没有记录时显示待确认。转确认、释放必须检查实际条件，再填写说明。增人重新检查当前门店授权，提交仅表达待资源确认的增人需求，不立即扩大人数或金额 |
| 销售订单列表 | 快捷转确认、释放调用同一套条件检查。清理这两个动作中误用的“关闭订单／财务影响”选项。“合同”直接带本单进入合同管理，取消另一个可直接宣称合同发送成功的处理路径 |
| 合同管理 | 分开准备草稿、提交审核、发起签署与签署完成。检查本单状态、适用模板、签约公司、资料、办理权限及签约付款条件。缺项只能保留草稿；待审核不能直接签署。发起签署需填写有效截止日期，完成后仅显示“签署中”。从订单进入时匹配该订单，未有合同则展示该单草稿，未知资料不套用另一笔合同的“通过”结果 |
| 历史业务 | 暂停门店不能新增订单或人数；订单收款、合同、售后与工作交接入口保留。已确认历史订单可由有权限经办人按原约定补签，不能借补签扩大原人数、产品或金额 |

普通产品价格、实际名额及资源确认继续由原业务模块承接；没有恢复门店价格口径、库存口径、授信或终止功能。

## 到期和签约怎样处理

- **到期未付款：** 先看本单是否已有批准的释放方式。规则未定时交计调核查，不假报已经释放。
- **已经付款、收款待核查、签署中、已签合同或已出票：** 不直接释放，交销售负责人、计调及财务处理。
- **名额释放后才到账：** 款项由财务核查，计调重新确认余位；不能因到账直接把原订单转为已确认。
- **订单确认：** 资源及本单付款节点满足后方可确认；满足节点不代表已收全款。截图、待认款、预存冻结不计为已支付。
- **合同签署：** 按本单签约条件检查，不强制与“订单已确认”互相等待。合同页有一笔约定先签后款的待发送样例，以及观音山暂停门店历史补签样例；它们不代表所有订单都适用先签后款。

## 验收结果

- 11项规则测试通过：当前授权、预留时长、付款节点、北京时间截止、释放保护、迟到收款、历史补签、审核与重复发送、已结束订单增人限制。
- 26组Chrome浏览器检查通过，无页面脚本报错。本地直接打开与随机本地端口各13组，包含下单与草稿、待确认、停售、详情与列表拦截、合同统一入口、到期特殊情况、资料缺失、签署截止、暂停门店补签、本单合同匹配和窄屏核对表。
- 已付款、签署中和已出票的到期场景，由浏览器测试装入独立订单样例，再实际点击“释放”验证拦截；没有将这些测试资料写入公共订单清单。
- 桌面截图核对确认抽屉与历史补签；修复核对表被旧双列表单挤窄的问题。窄屏核对表在自身容器中滚动。未宣称全站或真实后端验收。

复验：[规则测试](../tests/store-order-rules.test.cjs)、[浏览器测试](../tests/store-order-browser.cjs)。截图及结果位于本机 `/private/tmp/caesar-store-order-qa/`，临时目录不作为长期资料。

## 仍待业务给出的规则与原型边界

保留时长、自动或人工释放、延期规则、确认时要求定金还是全款、发起签署的付款条件，继续由销售、计调、财务和法务确认。规则未知时页面明确提示，不能把“月结”或自行选择的收款计划当成付款条件已满足。

本批完成第4组的页面操作和条件表达。门店使用首批共同演示资料；下单沿用已有浏览器订单记录，合同状态和详情中的处理在当前页演示。没有建设实际权限服务、完整公司与产品授权资料服务、自动到期任务、资源锁定、电子签约接口、真实审批或资金执行。正式开发仍须从对应模块取得这些结果；原型通过不表示上述服务已实现。

未修改履约中心独立的团期订单页面，也未改预存、充值扣款、对账或报表工作线页面。

**唯一下一步：** 推进第7组，公司收付款账户与支付商户在财务资金管理统一维护，门店仅选用获准账户，并区分用途、默认变更生效与历史交易保留。
