# 审批上级与部门负责人能力核对

2026-09-24。依据用户提供的四张企微后台截图及当前项目代码，判断增补范围。本次为分析方案，未修改页面或审批规则。截图仅作为交互及功能参考，不据此推断企微全部规则。

## 结论

需要补充四项能力，保留指定成员、公司审批人员和单据负责人。指定部门负责人属于现有能力扩展，指定上级、连续多级上级、连续多级部门负责人属于新增。个人汇报链和部门组织链必须分开，不能将当前上级部门负责人改名后当作直属上级。

| 用户参考能力 | 当前状态 | 建议 |
| --- | --- | --- |
| 指定上级 | 无员工直属上级关系，不能沿员工关系找第 N 级 | 新增；选择某一级，仅该级审批 |
| 连续多级上级 | 无汇报链及按层级展开流程 | 新增；从直属上级逐级到指定终点 |
| 指定部门负责人 | 有本部门及直接上级部门、单人负责人 | 扩展任意层级、同级多负责人、缺层处理 |
| 连续多级部门负责人 | 有组织树，无逐层审批结构 | 新增；逐部门层级审批，同级按或签／会签处理 |

## 当前证据

- `admin/org.html`：组织树含集团、板块、主体、分公司、中心、部门、门市部和门店；`orgTreeData` 的负责人为单个 `owner` 姓名，新增组织负责人为搜索文本输入，未形成可选择多位员工的负责人关系。
- `merchant/system/my-org.html`：本主体组织树、负责人展示及组织调整申请已有，负责人也是单个姓名；适合继续保留查看和申请调整的职责。
- `merchant/system/staff-management.html`：新增／调整任职已有主体、部门、主任职／兼任、生效日期及履历，没有直属上级或汇报关系。多任职基础可复用，但还不能决定每个任职对应哪位上级。
- `admin/employees.html`：主要维护员工账号、组织、岗位、角色和权限，没有个人汇报链；岗位名称不能用来推导直属上级。
- `shared/approval-config-model.js`：独立六个部门样例，仅一个 owner；department 查当前部门、superior 查一次 parent。它没有读取两端组织树。例如组织页长线中心负责人为陈琳，审批样例为陈涛，当前不可据组织页面显示判定审批实际取人。
- `shared/approval-rule-run.js`：当前多人办理按单节点成员列表进行全部同意／一人同意／依次审批，不保存部门层级。把各层负责人拼成一个成员列表会丢失层级语义，或签更可能让低层一人同意即完成整条链。
- 原方案曾写申请人部门负责人，而当前实现按单据业务责任部门。本轮明确记录这一差异，不自行改掉已有模板的起点。

## 页面组织建议

审批人来源保持简单的五类：指定成员、申请人上级、部门负责人、公司审批人员、单据负责人。

选择申请人上级后，显示“指定一级／连续多级”；选择部门负责人后也显示这两种方式。这样四张截图对应的能力均可配置，又不需要把已有来源替换或把下拉堆成七项。单据负责人继续按事项是否有真实来源字段显示。

指定一级配置层级，连续多级配置终点。层级按从直属／本部门向上或从最高级向下编号，应明确编号基准；截图的“从上至下”首先是层级定位方式，不能直接推断为倒序审批。建议默认从下至上，连续审批逐层向上；最高级向下编号放更多设置，并用链条预览显示实际参与层级及顺序。

## 组织及任职配套

| 维护位置 | 必要增补 | 职责 |
| --- | --- | --- |
| 员工任职新增／调整及详情 | 当前任职的直属上级、有效期、汇报链预览；限制本人为上级及循环汇报 | 任职管理人员按公司维护，同人兼任可有不同上级 |
| 集团组织架构维护 | 部门负责人改员工选择、支持多人，负责人有效期；保留明确上级组织 | 集团组织管理员维护统一组织关系 |
| 业务端组织架构 | 展示同一组织关系及负责人，调整申请支持多负责人 | 公司组织管理员查看及发起调整，不建立第二套名单 |
| 审批编辑／试跑／模拟办理 | 单级定位、连续层级、同级或签／会签、缺层结果及实际链条 | 审批管理员配置，申请提交后按对应身份和业务责任确定人员 |

原型可用共同示例资料与本页操作演示这些关系，不以后台接口、生产同步或跨模块自动回写为本批完成条件；仍须让组织页与审批试跑引用同一套明确资料，不能各自独立展示不同负责人。

## 必须明确的业务边界

1. 个人上级使用申请人本次发起任职的汇报链；多任职须确定本次身份，不凭账户第一条任职猜测。部门链应可区分申请人所属部门和单据业务责任部门，旧模板保留原起点。
2. 最高层级建议默认截止该责任公司内部。集团根节点、板块节点、租户管理员不是自然的审批上级；跨公司审批需明确配置，不能沿组织树自动跨主体。
3. 连续多级须“本层完成后进入上一层”。同层多人或签／会签与跨层顺序是两项规则，不复用一个整链或签开关。
4. 当前层无人、层级不足、人员失效应明确结果。截图的无负责人向上找可以作为节点选项；整节点为空直接跳过不作为默认，尤其付款不能因组织未维护而自动放行。最终无人交现有异常规则处理。
5. 申请人也是负责人、同一人兼多个层级、代办及退回重提沿用并核对现有自审／重复审批规则，不能直接去重后丢失层级记录。
6. “公司内最高层”“层级不足如何处理”“允许哪些事项空节点跳过”是待确认的组织及审批政策，本轮不当作既定规则。

## 建议实施顺序与验收

先补统一组织负责人资料及任职汇报关系，再扩展部门单级／连续多级，随后增加个人指定上级／连续多级；最后在同一试跑中显示层级与实际人员。沿用现有审批来源，不替换旧模板。

验收包含：只批第三级与连续批至第三级的区别；同级两人或签／会签；中间层无人；链条不足；直属上级循环；兼任及跨公司；本人审批及重复负责人；离职代办；退回重提；旧模板保存复开和历史版本只读。当前仅完成代码及截图核对，未实施、未运行新增业务或浏览器测试。
