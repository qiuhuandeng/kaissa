# 财务流程02：成本应付与付款流程

业务确认稿 v1.0  
编写日期：2026年8月1日  
面向角色：计调/团控、采购/资源调度、成本会计、应付会计、付款申请人、财务复核岗、出纳、财务主管

**核心目标：** 让供应商成本从业务发生、成本维护、账单核对、应付确认、付款申请、付款执行、预付冲抵、付款退回到发票和 NC 的全过程在线上可追溯。业务人员只需按真实业务维护供应商、费用项目、金额和付款依据，系统自动判断这笔钱属于应付还是预付；财务负责核对依据、控制付款风险、跟踪发票和凭证。

## 本文件怎么读

- 业务成本经办、计调、采购、外采、航服和邮轮角色重点看第一至第八部分，确认成本来源、账单依据、预付节点和付款申请怎么发起。
- 成本会计和应付会计重点看第五至第九部分、第十二至第十五部分，确认账单核对、应付/预付判断、发票、预付冲抵和 NC。
- 付款岗和出纳重点看第十至第十一部分、第十四部分，确认付款执行、默认付款账户、回单口径和资金计划。
- 财务主管重点看第七至第十七部分，确认应付预付判断、付款风险、发票强控、端到端场景影响和待拍板事项。

## 第一部分：整体业务流程概览

### 一笔供应商付款在系统里的完整链路

旅游业务中的付款通常不是从财务开始，而是从产品履约和资源采购开始。计调确认地接、酒店、车队、票务、邮轮舱房、专列铺位等成本后，系统形成成本项。供应商提交账单或业务维护付款节点后，系统判断这笔款是已确认应付，还是需要提前支付的预付。业务发起付款申请，财务审核付款依据，出纳执行付款。

标准链路如下：

> 业务确认成本 → 系统形成成本项 → 供应商账单或付款节点进入系统 → 财务核对成本和账单 → 系统生成应付或预付 → 业务发起付款申请 → 审批和财务复核 → 出纳付款 → 发票跟踪 → 凭证和 NC

动态资源预付链路如下：

> 机票切位/邮轮包舱/专列包铺合同 → 一押/二押/尾款付款 → 形成资源预付 → 后续分配到团期或航次 → 预付冲抵应付 → 未使用部分退回或结转

逆向链路如下：

> 客户退款或供应商差异 → 触发供应商追款 → 生成负应付、付款退回或预付退回 → 供应商退款到账 → 财务核销

这条链路的关键是：付款不能只看“业务说要付多少钱”，而要能看到供应商是谁、为什么付、对应哪个团期或资源、是否已经形成应付、是否已有预付可冲抵、发票和账单是否齐全。

## 第二部分：成本从哪里来

### 团期和项目成本

标准跟团、单团、研学、MICE 等业务中，成本一般由计调或项目负责人维护。成本可能发生在团期、项目、订单或具体服务项目上。

常见成本包括：

- 地接服务。
- 国际或国内机票。
- 酒店。
- 用车。
- 餐饮。
- 门票。
- 导游。
- 领队。
- 签证。
- 保险。
- 单项服务。

业务维护成本时，需要说明这笔成本对应哪个团期或项目、供应商是谁、费用项目是什么、金额和币种是多少、付款节点是什么、是否有账单或确认件。

### 动态资源成本

机票切位、邮轮包舱、专列包铺等业务，成本往往先发生在资源采购批次上，而不是某一个具体团期。比如先向航司或票代支付机位定金，后续多个团期逐步占用这些机位。

这类成本应先形成资源预付，再根据团期实际使用情况分摊：

1. 资源采购创建切位、包舱或包铺合同。
2. 系统记录供应商、资源数量、付款节点、定金和尾款。
3. 付款后形成预付余额。
4. 团期使用资源时，系统把预付金额分摊到对应团期。
5. 供应商账单确认后，用预付冲抵应付。
6. 未使用、释放或损耗部分进入损耗确认、退回或结算调整。

因此动态资源的日常操作主入口应在履约或资源调度场景，财务只承接已确认的应付、预付、付款和退回。

## 第三部分：成本类型必须业务化

旧系统里使用“团费”作为成本类型，会导致财务无法判断钱到底付给谁、属于什么成本，也无法满足后续成本分析、税务和 NC 科目要求。新系统应取消笼统的“团费”，要求业务选择真实费用项目。

业务人员不需要理解复杂会计科目，但必须选择能反映业务性质的费用项目，例如：

- 地接服务费。
- 国际机票。
- 国内机票。
- 酒店住宿。
- 用车。
- 餐饮。
- 门票。
- 导游服务。
- 领队费用。
- 签证服务。
- 保险。
- 邮轮舱房。
- 邮轮税费。
- 专列铺位。
- 票损。
- 舱损。
- 铺损。
- 其他明确费用项目。

费用项目应由财务统一维护，成本维护、供应商账单、应付单、付款申请和 NC 映射使用同一套口径。业务页面展示业务人员能理解的名称，财务后台再映射科目。

## 第四部分：外币成本如何处理

境外地接、邮轮、机票、MICE 等业务可能产生外币成本。系统应同时记录原币和本币，不能只保存一个人民币金额。

业务录入外币成本时：

1. 选择币种。
2. 填写原币金额。
3. 系统带出或允许财务确认汇率。
4. 系统折算人民币金额。
5. 后续付款申请和付款执行保留原币、本币、汇率三组数据。

如果合同约定外币报价但人民币结算，例如按美元报价但锁定汇率后用人民币付款，本质上可按人民币成本处理，但需要记录锁定汇率和依据。实际支付外币时，应按原币付款，汇兑损益由财务处理。

## 第五部分：供应商账单如何进入系统

供应商账单是财务确认应付的重要依据。账单可以由供应商上传，也可以由我方导入或录入，还可以来自 BSP、平台或接口同步。

常见账单来源：

- 地接月结账单。
- 酒店房费账单。
- 车队用车账单。
- 航司 BSP 账单。
- 票代账单。
- 邮轮舱位账单。
- 专列铺位账单。
- OTA 或平台服务费账单。

账单进入系统后，系统需要识别或录入：

- 供应商。
- 对方账单号。
- 账单日期。
- 费用项目。
- 原币金额、汇率、本币金额。
- 关联团期、项目、航次、班期或资源批次。
- 账单附件。
- 发票状态。

财务核对账单时，不只是看账单有没有上传，还要看账单金额是否和系统成本一致。

## 第六部分：成本和账单如何核对

供应商账单进入后，系统把账单与业务成本进行匹配。匹配成功后，财务或业务确认差异。

标准核对流程：

1. 系统识别供应商和账单号。
2. 系统匹配对应团期、项目、航次、班期或资源批次。
3. 系统对比账单金额和已维护成本。
4. 金额一致时，财务确认账单。
5. 金额不一致时，进入差异处理。

差异常见原因：

- 供应商多收。
- 系统漏维护成本。
- 业务确认价格和供应商账单不一致。
- 汇率口径不同。
- 重复账单。
- 供应商优惠或减免未体现。
- 损耗、票损、舱损、铺损未确认。

差异处理结果可以是供应商承担、我方认可补差、按系统成本确认、部分认可、退回业务补成本或关闭重复账单。差异处理完成后，才能形成准确应付。

## 第七部分：应付和预付如何判断

业务人员不应自己判断“这笔是应付还是预付”。业务只发起付款申请，系统根据付款节点、回团状态、账期、结算状态和资源类型判断财务属性。

### 已确认应付

一般来说，供应商账单、结算单或回团后成本确认完成，且付款符合账期或结算条件时，系统可形成应付。

应付表示公司已经确认需要支付给供应商的债务，后续进入应付管理、付款申请、付款执行和凭证。

### 预付

预付表示业务上需要先付款，但最终成本或结算尚未完全确认。常见于：

- 出发前必须支付的地接预付款。
- 机票切位定金。
- 邮轮包舱定金。
- 专列包铺定金。
- 保证金。
- 尚未分配到团期的资源采购款。

预付后续必须有去向：冲抵应付、分摊到团期、供应商退回、转到其他资源批次或形成损耗。

### 判断规则需要公司确认

系统可以支持多种判断口径：

- 按回团前后判断。
- 按供应商账期判断。
- 按结算单确认判断。
- 按付款节点判断。
- 按准单或成本确认状态判断。

最终建议采用“付款节点 + 回团/账期 + 结算状态”的组合规则，由财务设定默认口径，特殊供应商或特殊资源可单独配置。

## 第八部分：付款申请怎么发起

业务人员不需要进入多个入口判断预付或应付，只需要从成本项、供应商账单、应付单或资源采购批次发起付款申请。

付款申请应回答以下问题：

- 付给谁。
- 为什么付。
- 对应哪个团期、项目、航次、班期或资源批次。
- 总应付或预付金额是多少。
- 已经付过多少。
- 还有多少可申请。
- 本次申请多少。
- 是否有预付可以冲抵。
- 实际要付多少。
- 付款依据是什么。
- 发票或结算单状态如何。

付款申请里必须区分几个金额：

- **应付金额：** 成本或账单确认的总金额。
- **可申请金额：** 当前还可以发起申请的余额。
- **本次可申请：** 根据付款节点、已付、预付冲抵计算出的本次上限。
- **本次申请金额：** 业务实际申请支付的金额。
- **实付金额：** 扣除预付冲抵或其他抵扣后真正需要付款的金额。

不能把应付金额直接当成本次可申请金额，否则容易重复付款。

## 第九部分：财务如何审核付款

财务审核付款时，不只是看申请金额，还要判断付款是否有依据、是否超过可申请金额、是否符合账期、是否有异常风险。

财务审核页面应能看到：

- 供应商名称和付款账户。
- 供应商账期。
- 付款主体。
- 关联团期或项目。
- 成本项和费用项目。
- 应付、已付、可申请、本次申请、实付。
- 原币、汇率、本币。
- 账单、结算单、付款节点、其他附件。
- 发票状态。
- 团组应收和实收提示。

### 应收实收只提示不强控

付款审核时可以展示团组应收和实收，让财务判断是否以收定支。但系统不应简单强控“没收够就不能付款”。原因是会展、月结、系列团、邮轮、机票切位等业务经常需要先付资源款，强控会卡死正常业务。

因此应收实收在付款审核中作为风险提示，不作为统一硬性拦截。

### 账期自动带出

供应商账期应从供应商档案自动带出，不能靠业务临时填写。财务审核时能看到当前付款是否提前、是否到期、是否超过账期。

## 第十部分：付款执行

审批通过后，付款还没有完成。付款执行由出纳完成。

### 无银企直连的主体

无银企直连时，出纳在线下银行制单付款，然后回系统确认付款。

流程是：

1. 出纳查看已审批付款单。
2. 系统按付款主体带出默认付款账户。
3. 出纳在线下银行完成付款。
4. 出纳在系统点击确认付款。
5. 系统把付款单标记为已付款或已结束。
6. 付款金额进入资金计划和付款执行报表。

系统应支持批量付款确认，但必须保证付款对象、账户、金额和币种清楚。

### 有银企直连的主体

有银企直连的主体可以后续支持系统推送银行制单、银行回传结果和回单。该模式是增强能力，不影响无直连主体先按线下制单流程运行。

### 默认付款账户

付款单不应让业务每次选择付款账号。系统按付款主体维护默认付款账户，财务审核或出纳执行时自动带出。如需临时更换账户，应由财务修改并留痕。

## 第十一部分：付款回单的本期处理口径

付款回单和收款流水不同。收款通常有客户付款流水和订单认款关系，比较容易按流水号匹配；付款常按供应商维度一笔多金额，银行回单未必带业务唯一标识。

因此本期建议按以下口径运行：

- 出纳在线下付款后，在系统确认付款。
- 付款单确认后流程结束。
- 业务若需要银行回单，由财务人工从银行导出提供。
- 系统可以保留回单核销能力作为未来增强或银企直连主体使用，但本期不承诺自动回单匹配。

如果未来启用回单核销，再处理付款回单、退款回单、付款退回、账户异常、手续费、汇兑损益等复杂场景。

## 第十二部分：发票如何跟踪

发票不是付款附件里的一个普通文件。系统需要把供应商账单、发票和其他附件分开。

### 发票登记

发票登记应记录：

- 发票号。
- 开票日期。
- 开票公司。
- 购方公司。
- 发票金额。
- 税额。
- 税率。
- 发票项目。
- 关联供应商。
- 关联应付单、付款单、账单或结算单。
- 验真状态。

### 先票后款和先款后票

不同供应商和业务类型可能不同：

- 常规应付可以要求先有结算单或发票。
- 纯预付通常没有发票，只要求付款节点和依据。
- 境外供应商、邮轮、机票、平台服务费可能按特殊规则处理。
- 先款后票可以允许，但必须进入发票进度表。

### 发票进度表

财务需要能按供应商和主体查看：

- 已付款金额。
- 已开票金额。
- 未开票金额。
- 发票是否验真。
- 发票是否异常。
- 哪些付款先款后票。

这样才能追踪供应商全年收款和开票金额是否匹配。

## 第十三部分：预付、冲抵和付款退回

### 预付分摊

大额资源预付往往先发生在采购批次，后续再分摊到团期。系统需要记录预付余额，而不是付款后就结束。

流程是：

1. 资源采购形成预付节点。
2. 财务付款后形成预付余额。
3. 团期实际占用资源时分摊预付。
4. 供应商账单确认后，用预付冲抵应付。
5. 未使用或减少部分进入退回、转预付或损耗。

### 预付冲抵应付

当供应商账单确认后，原预付可以冲抵应付。系统应展示原预付、已分摊、本次冲抵、冲抵后剩余预付、冲抵后应付余额。

### 付款退回

付款退回可能来自银行退回、供应商退预付款、供应商多收后退回、保证金退回，或者客户退款后触发的供应商追款。

付款退回应按以下流程处理：

1. 创建付款退回单。
2. 关联原付款单、应付单或预付单。
3. 记录退回原因和金额。
4. 匹配供应商退款到账流水。
5. 冲减应付或恢复预付余额。
6. 生成凭证和 NC 记录。

客户退款触发供应商追款时，如果原来是预付，就进入预付退回；如果已经形成应付并付款，就进入负应付或付款退回；如果供应商同意抵扣未来账单，则进入供应商结算差异或结算调整。

## 第十四部分：资金计划

付款申请和付款执行应自动形成资金计划数据。财务不应再靠线下表格重新统计每日、每月要付多少钱。

资金计划应包括：

- 计划付款日期。
- 付款主体。
- 默认付款账户。
- 供应商。
- 金额和币种。
- 业务类型。
- 关联团期、项目或资源批次。
- 审批状态。
- 实际付款日期。
- 差异原因。

资金日报、月度执行表、付款计划表都应从系统付款数据生成。

## 第十五部分：凭证和 NC

付款确认后，系统根据付款单、应付单、预付单、供应商、主体、费用项目、币种和金额形成财务凭证数据。

需要注意：

- 应付付款、预付付款、保证金付款、佣金付款、付款退回不能混成一种凭证口径。
- 有团预付和无团预付可能对应不同科目或辅助核算。
- 付款退回、预付冲抵、负应付应形成后续财务事件，不直接改原付款记录。
- 推送 NC 成功后记录凭证号；失败后保留原因并允许修正重推。

## 第十六部分：财务应付端常见端到端场景

本章只讲供应商侧资金动作会牵动业务确认、财务审核、出纳付款、发票和结算继续处理的场景。付款申请字段、财务审核页面和普通报表，前文已经说明，不在这里重复。财务阅读时重点确认：业务提交后我审核什么，哪些情况退回，付款完成后还要跟踪什么。

### 场景一：供应商账单形成应付

供应商账单通常来自计调、外采、邮轮、航服或供应商端。业务先确认成本或接待事实，系统再形成成本项、供应商账单、费用项目、币种、关联团期/项目/资源批次、差异说明和应付单。

财务审核时，重点看账单金额和系统成本是否一致，费用项目和供应商是否正确，币种和汇率是否合理，附件和业务确认是否完整。如果发现成本未确认、账单差异未处理、供应商账户不完整、发票或凭证不符合要求，财务应退回业务或供应商补充。

业务最终要拿到的是可付款金额。供应商提交账单不等于已经可以付款，必须先经过业务确认和财务审核。

### 场景二：动态资源预付款

航服切位、邮轮包船切舱、专列包列等动态资源，往往需要先按采购合同或付款节点支付预付款。业务在资源采购或付款申请中发起预付，系统记录采购批次、付款节点、资源数量、预付余额和后续分摊规则。

财务审核付款依据后执行付款。付款完成并不是这个场景结束，后续还要按实际使用情况追踪预付如何被团期、航次、班期或客户订单分摊，是否有余额退回、损耗确认或未来账单冲抵。

业务最终要看到预付余额和使用去向。预付款不能只在付款当时记录一次，否则后续结算时无法说明钱花到哪里、剩余多少、损失由谁承担。

### 场景三：客户退款后向供应商追款或扣款

客户退团、退订或投诉后，业务如果判断供应商需要承担责任，需要在供应商追款或付款退回入口发起处理。系统应保留原成本、原付款、预付余额、供应商责任依据、负应付、付款退回或未来账单抵扣记录。

客户侧退款由收款退款流程处理，供应商侧追款由应付流程处理。业务确认供应商责任后，财务根据原付款或预付记录追踪供应商退款是否到账，或者在未来账单中扣减。不能因为客户已退款，就直接改掉原供应商付款记录。

最终要做到客户退款和供应商追款各自清楚。供应商未退款、责任未确认、抵扣账单未落地时，结算毛利仍可能存在差异。

### 场景四：专项供应商账单付款

航服、邮轮、外采、签证、地接等专项供应商账单，需要先由专项业务部门确认业务事实。例如航服确认出票和退改，邮轮确认舱房和船方扣损，外采确认接待人数和供应商差异，计调确认地接和酒店实际使用。

业务确认后，财务再审核账单金额、付款对象、付款主体、供应商账户、发票、合同或账单依据和付款风险。财务不替业务判断“到底接待了几个人”或“票是否已经出票”，这些必须由业务确认后再进入付款。

付款岗最终要拿到的是业务已经确认的付款依据。业务事实未确认、账单和业务记录不一致时，财务应退回来源部门。

### 场景五：出纳付款和回单

付款申请审批通过后，出纳在付款执行入口按审批结果付款，并回填付款账户、付款金额、付款时间、付款状态和银行回单。系统同时更新资金计划、供应商余额、付款状态和后续 NC 处理依据。

付款成功后，业务能看到付款完成；如果银行退回、账户异常、金额失败或回单缺失，出纳需要标记失败原因，并进入付款退回或重新付款流程。财务还要继续跟踪发票、供应商余额和 NC 推送结果。

业务最终要看到的是付款完成或失败原因，而不是只看到“已审批”。审批通过不等于银行付款成功，付款成功也不等于结算已经完成。

## 第十七部分：需要业务和财务确认的事项

1. 成本类型统一枚举，是否彻底取消“团费”。
2. 外币成本汇率来源、取值时点和锁汇场景处理方式。
3. 应付和预付的判断依据：回团、账期、结算、准单、付款节点如何组合。
4. 有团预付和无团预付的科目和 NC 口径。
5. 纯预付是否必须上传结算单，还是只需付款节点和依据。
6. 哪些供应商或业务必须先票后款，哪些允许先款后票。
7. 付款审核中应收实收只提示不强控是否确认。
8. 默认付款账户按主体维护的规则。
9. 本期付款回单是否明确不做自动匹配。
10. 客户退款触发供应商追款时，生成负应付、付款退回还是预付退回。
11. 资金计划表、付款执行表、发票进度表字段模板。
