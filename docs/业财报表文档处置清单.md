## 七、本轮修订状态解释

- `当前已实现`：只有实际代码和正常/异常场景验收都能证明时使用。
- `原型表达`：页面能展示对象或动作，但没有共同数据、真实状态承接或正式计算。
- `正式开发方向`：业务和财务目标已经明确，尚未实施。
- `待确认口径`：原始事实仍需记录，但最终计算、归类或期间规则需要业务或财务拍板。

以后新增或修订业财文档，开头必须说明自己属于哪一种状态；同一规则只能有一个主要维护文档，其他文档通过引用使用，不复制一套容易分叉的正文。

### 3. 文档整理跟着业务复盘走

先盘点所有文件的名称、用途、适用模块、引用方及候选维护主稿，再围绕当前要开发的业务阅读相关正文，不先做全部文档重写。每个模块逐项分为：现行有效、待与原型核对、已被替代、历史证据、未批准建议。含有不同状态的文档按章节判断，不以文件日期新旧一刀切。

开发交付入口只列已核验的现行资料及明确待决项。旧资料保留可检索入口和替代去向；移动前检查文档、生成脚本、测试及入口引用。未被引用只是归档线索，不等于可以删除。每项规则只维护一个正文来源，原型、算例及验收通过编号引用。

### 4. 用业务场景发现模块缺口

场景先按三方面组合选择：产品形态（跟团、邮轮、专列、自由行、单项、项目）、交易关系（自营、外部采购、集团公司互供、同公司部门协作）、变化分支（退改、部分履约、失败、跨期、更正）。不穷举所有组合，优先选高频、金额风险大、多人交接的组合，再用模块覆盖表查遗漏。

既有两期计划记录一期标准跟团、二期复杂业务，并排除研学、营销中心及客户中心；本次不重新扩大范围。订单必要的游客、联系人和付款方仍要检查。已有86场景编码和场景手册作为候选库复用，不能默认全都属于本期、都已批准或都已通过。

建议检查范围如下，表内是待核查问题，不是已确认缺失的功能：

| 业务范围 | 重点核查 |
|---|---|
| 公司、部门、人员与权限 | 哪家公司签约、收款、供货、履约和记账；部门只是经营归属还是另有公司责任；调岗和组织变更如何保留历史 |
| 供应商、产品、团期与资源采购 | 谁维护与确认；日期、价格、数量属于哪一层；资源占用、释放、二次确认及损耗由谁承接 |
| 销售、订单与合同 | 成立条件、定金尾款、游客资料、改价、合同和资源确认先后；没有余位或条件不齐如何处理 |
| 履约、售后与成本 | 部分完成、取消改期、客户应退与供应商应退分别处理；费用依据、分配及成本更正 |
| 收款、预款、应付与付款 | 一款多单、多款一单、超额和重复提交、占用释放、审批退回、结果未知、实际成功与失败 |
| 结算、核算与集团财务系统 | 业务结算与收入成本确认分别负责；内部双方如何核对；跨期调整、凭证重复和关账条件 |
| 报表与系统切换 | 每个核心指标从何种有效记录取得；期间和历史归属；旧单接续、期初余额、失败恢复及同范围对账 |

每个场景至少写清：真实业务故事、参与公司和角色、前置资料、按步骤的操作及页面、每步状态和金额变化、下一岗位收到什么、异常及撤回更正、最终报表和单据预期结果。先给出已确认规则下的独立预期结果，再比较原型或开发结果，避免拿实现本身当正确答案。

推荐首个样板是标准自营跟团：产品团期→下单合同→定金尾款→履约与成本→应付付款→结算核算→经营报表；随后在同一场景上增加部分退款、后补成本和失败重试。第二个样板验证外采二次确认；第三个验证A公司销售、B公司供货及代收。不同公司与同公司跨部门必须分开验证。

| 业务验收案例与预期结果 | 正常、异常、边界及跨期怎样验证，金额如何复算 | 现有场景手册与开发承接表，补当前页面及版本 |
| 待决事项与变更记录 | 什么影响开工/上线，谁决定、何时需要、影响哪些模块 | 现有决策表与总对照表，不另复制答案 |

以上是六类内容，不要求再新增六套大文档。已开发模块先用同一案例比较开发系统、原型及有效规则，再决定修哪一方；不要先要求开发推倒重来。未开发模块达到开工条件后可先实施，不等待全项目原型达到所谓100%。

开发侧还需提交技术设计：数据关系、接口责任、并发名额与金额控制、重复请求保护、审批/付款结果未知后的查询恢复、权限与日志、迁移及回退。产品说明业务结果和禁止事项，开发负责提出实现并评审，不把静态页面代码直接当生产设计。

### 6. 评审、完成标准与持续同步

每轮评审处理一条完整业务：产品负责人演示，业务经办验证可操作性，财务验证金额和责任，开发复述系统承接，测试将结果写成可重复案例。业务与财务各确认自己负责的规则；开发确认实现边界和依赖；项目负责人协调未决事项。不能只收“看过原型、没意见”。

开工条件：范围明确，关键状态/权限/字段来源及金额规则已确认，影响该模块设计的阻断问题有结论，正常与主要异常有预期结果。其他未决项标明依赖边界，不以“可配置”掩盖规则未定。

生产验收条件：实际系统用角色账号跑通已约定场景，数量金额可复算，权限越界受阻，失败和重复不造成多占资源或多记资金；接口、历史接续及同期间同范围财务核对有证据。原型正常可点不替代这些检查。试运行覆盖至少一次完整约定结算/关账周期的验证；无法等待自然周期时先演练，再约定实际周期复核及遗留控制，由双方签认。

完成程度分别记录“原型可演示、规则已确认、开发可承接、开发已验收”，不合成缺乏依据的70%或100%。覆盖率的分母来自已确认本期场景清单；影响金额、公司责任或权限的阻断问题不能被其他已完成项平均掉。

以后一次变更必须同时列出受影响页面、规则正文、验收案例和开发任务；审查四者是否同步，不适用则注明理由。历史记录追加保存，当前正文直接维护现行内容，避免只在文末追加“已修改”却让旧正文继续误导开发。

### 7. 建议的首个交付边界

先完成“一期标准跟团链路的现状与有效资料核对”：选择上述正常业务及关键变化，交付当前页面路径、有效文档目录、流程/规则冲突清单、需业务财务确认的问题和一套可复算验收案例。此时才能判断该链路缺什么，并按影响列开发与原型修改项；不直接启动全系统重构或批量归档。
