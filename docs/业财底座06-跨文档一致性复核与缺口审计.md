# 业财底座06：跨文档一致性复核与缺口审计

> 后续完成情况：本文审计时的场景基线为 74 个。本文识别的 12 类必要场景已补入《业财底座02》，场景总数更新为 86 个；逐场景“主体—单据—余额—结算—会计事项—NC—对账”承接结果见《业财底座07》。

## 一、本次复核的目的

本文不新建一套业务规则，而是检查前五份业财底座是否讲的是同一套账：

1. 交易中的各方身份和核算责任是否一致。
2. 各业务场景中的债权、债务、资金和结算关系是否一致。
3. 业务单据、余额、核销、结算、会计事项和 NC 凭证能否前后承接。
4. 对账和关账能否发现前面各环节的遗漏、重复和差异。
5. 现有 74 个场景是否已经足以支撑全国连锁、多主体和多产品的旅游业务。

本次复核范围：

- 《业财底座01：多主体交易关系与核算责任基线》
- 《业财底座02：全业务场景财务数据链路矩阵》
- 《业财底座03：财务业务对象与数据关系》
- 《业财底座04：会计事项与 NC 凭证规则》
- 《业财底座05：对账关账与异常控制》

## 二、复核结论

### 1. 总体结论

五份底座的主干逻辑已经基本一致，可以作为继续梳理的统一基线：

```text
交易各方及核算责任
→ 业务场景中的债权、债务和资金关系
→ 应收、收款、实际成本、应付、付款、结算等财务单据
→ 会计事项
→ NC 凭证
→ 对账、月结和关账
```

但是，当前还不能直接进入“全部财务规则定稿并交付开发”，原因有三个：

1. 74 个场景在后三份文档中只完成了按大类承接，没有逐场景验证到单据、会计事项和对账规则。
2. 现有 74 个场景未完整包含支付平台扣费与拒付、坏账、押金、领队或项目备用金、客户赔付、共享资源分摊等必然会发生的财务场景。
3. 税务口径、各主体会计政策、NC 科目与辅助核算、合同中的收付和结算规则尚未取得凯撒正式资料。

### 2. 结论等级

| 结论 | 含义 | 当前数量 |
|---|---|---:|
| 已一致 | 五份文档的规则可以相互承接 | 12 组主要规则 |
| 已修正 | 复核中发现明确错误，已直接改正 | 13 项 |
| 必须补齐 | 不补齐就会导致开发遗漏账务或计算错误 | 12 类场景＋1 张逐场景承接表 |
| 待公司确认 | 不能由产品或开发代替财务、税务或管理层决策 | 10 类制度问题 |

## 三、五份文档的责任边界

| 文档 | 只回答什么 | 不代替什么 |
|---|---|---|
| 底座01 | 谁是合同、收付、开票、收入、成本和往来的责任主体 | 不代替逐场景金额计算 |
| 底座02 | 每类业务场景如何产生应收、收款、成本、应付、付款、结算和 NC 影响 | 不代替单据的明细关系 |
| 底座03 | 每个财务单据记什么、何时生效、如何核销和计算余额 | 不代替会计科目判断 |
| 底座04 | 什么经济影响需要入账，如何形成 NC 凭证 | 不代替业务结算和资金对账 |
| 底座05 | 每个环节如何对账，哪些问题阻断结算或关账 | 不代替交易主体和会计政策 |

这五份文档不应互相复制全部内容。正确的使用方式是：从底座02的某一场景出发，回到底座01确定主体，在底座03找到财务单据和余额变动，在底座04找到会计事项和 NC 承接，再用底座05验证能否对账和关账。

## 四、已经一致的主要规则

| 复核项 | 一致结论 | 对开发的含义 |
|---|---|---|
| 主体判断 | 集团、法人、核算主体、经营单元、部门和门店不再混为一个组织字段 | 财务单据必须归属唯一法人和核算主体 |
| 交易各方 | 客户签约方、收款方、开票方、销售方、履约方、采购方和付款方可以不同 | 不得用“订单所属公司”一个字段推导全部财务结果 |
| 业务应收与会计应收 | 业务收款计划和客户债权不必然在同一时点进入会计应收 | 不得以“订单提交”统一生成应收凭证 |
| 收款链路 | 到账流水、认款单、收款单和核销明细是四层不同记录 | 必须支持一笔流水拆给多张应收，也支持多笔流水核销一张应收 |
| 预收与预存 | 预收是待后续明确应收或处理方式的款项；预存是经客户确认、可重复使用的余额账户 | 超收不得自动变成预存 |
| 成本和应付 | 预估成本、实际成本、供应商账单、应付和付款是五件不同的事 | 账单未到可能需要暂估，提前付款应先记供应商预付 |
| 付款链路 | 付款申请、审批、付款执行、银行结果和回单核对不是一个状态 | 审批通过或指令发送成功不能当作已付款 |
| 业务结算 | 结算确认经营结果，不要求所有应收、应付和资金余额清零 | 已结算后的差异通过结算调整处理，不直接改原结算 |
| 业务结果与会计入账 | 收入确认、成本结转、资金收付和往来变动分别形成会计事项 | 不得因一笔实际成本先暂估、后到票而重复记成本 |
| 内部业务与内部资金 | 集团内部产品或服务结算，与代收、代付及资金调拨分别记录 | 前者使用内部业务结算单，后者使用内部资金清算单 |
| 冲销和退回 | 单据错误或重复用冲销；银行已受理后实际退回用付款退回 | 两者影响的资金事实和责任不同，不得共用一个结果状态 |
| 关账顺序 | 先资金日结和业务结算，再财务明细账月结和会计预关账，最后 NC 关账 | 业务系统关账和 NC 总账关账必须分开记录 |

## 五、本次已直接修正的问题

以下问题不需要公司做制度决策，因为原表达会直接导致重复计算、重复入账或单据混用，因此已在前五份底座中修正。

| 序号 | 原问题 | 已统一的规则 | 影响文档 |
|---:|---|---|---|
| 1 | 应收可核销余额在有效应收中已经包含调整，又重复扣减调整 | 可核销余额只以有效应收减已核销、已转销等不再可收部分 | 02、03 |
| 2 | 到账流水可认余额存在重复扣减的风险 | 每笔认款明细只占用一次流水金额 | 02、03 |
| 3 | 实际成本已包含损耗和调整，结算时又加一次 | 先记实际成本原额，再加已确认损耗和增减调整得到有效实际成本 | 02、03 |
| 4 | 业务毛利重复扣除了已经计入成交净额的优惠或渠道扣项 | 业务毛利＝业务结算收入－结算成本；另列的渠道、门店费用再计算结算贡献 | 01、02 |
| 5 | 标准付款链路把实际成本和供应商账单都写成形成应付的必备条件 | 按公司应付政策分为正式应付、暂估应付和待账单核对 | 02、04 |
| 6 | 付款执行和付款回单被压成一步 | 付款申请、审批、资金执行、银行结果和回单核对分开 | 02、03、05 |
| 7 | 客户来款未找到业务归属时，原表达无法承接会计入账 | 资金已实收的可先记待认领款项，后续再按认款结果转入应收、预收或其他款项 | 04、05 |
| 8 | 正式应付确认可能再次借记已经暂估或确认的成本 | 已记成本时只转负债和处理差额，不再全额记成本 | 04 |
| 9 | 客户退款的借方含义中将“减少应收”与借方方向混用 | 退款按原因冲减退款负债、合同负债或预存负债；需恢复应收的按已批调整处理 | 04 |
| 10 | 内部产品或服务结算与纯资金代收代付混在“内部结算”中 | 分为内部业务结算单和内部资金清算单 | 01、03、04、05 |
| 11 | 付款冲销与银行付款退回混用 | 错单、重单用付款冲销；银行实际退款用付款退回 | 03、04、05 |
| 12 | 账单核对单和供应商对账单的边界不清 | 前者核对某张或若干张账单明细，后者确认某对账期间的全部往来和余额 | 03、05 |
| 13 | 收入确认、成本确认与会计事项、成本结转的边界不足 | 业务和财务确认记录保存计算结果与依据，会计事项承接科目和 NC 影响 | 03、04 |

### 3. 开发前必须补的逐场景承接表

每个场景至少需要补齐以下内容：

| 检查项 | 必须明确的内容 |
|---|---|
| 交易各方 | 客户、销售方、收款方、开票方、履约方、采购方、付款方、供应商或内部对方 |
| 业务前提 | 哪个业务事实成立后才能进入财务处理 |
| 应收和预收 | 何时形成、向谁收、金额怎么算、后续如何核销或退款 |
| 收款和资金 | 资金进入哪个账户，谁认款，差额、手续费和未认款如何处理 |
| 实际成本和应付 | 何时确认实际消耗，何时形成债务，账单未到或存在差异时如何处理 |
| 预付和付款 | 付款前提、审批、受款账户、预付冲抵、付款退回和回单核对 |
| 业务结算 | 按订单、团期、航次、班期、项目还是批次结算，结算收入、成本和调整如何算 |
| 发票和税务 | 销项开票主体、进项受票主体、计税口径和可扣减依据 |
| 会计事项 | 哪个主体在什么时点以什么金额入账，如何冲销或调整 |
| NC 承接 | 会计日期、凭证类别、科目、辅助核算、汇总方式和返回结果 |
| 对账与关账 | 与谁对、拿什么金额对、什么差异阻断结算或关账 |
| 数字示例 | 至少包含正常、部分收付、差异、逆向和跨期中实际会发生的组合 |

## 七、现有场景中尚未独立、完整表达的财务场景

### 1. 必须在核心开发前补齐

| 序号 | 需补成完整链路的场景 | 为什么必须有 | 建议纳入的场景组 |
|---:|---|---|---|
| 1 | 银行、支付平台和 POS 手续费，以及净额到账 | 订单收款与银行实到不等，必须分开收入、收款、手续费和平台往来 | CASH / CHANNEL |
| 2 | 支付平台拒付、退票、强制退款和滚存保证金 | 原收款可能被平台后续扣回，不等于财务认款错误或公司主动退款 | CASH / CHANNEL / AFTER |
| 3 | 付款方和客户都无法识别的来款 | 现有场景包含已知客户、未知订单，但未单独处理完全无法认领的资金和长期挂账 | CASH |
| 4 | 客户应收的坏账准备、核销和已核销款项收回 | 企业客户、渠道和门店账期必然产生信用风险，仅有催收和冲减不足以关账 | SALE / SETTLE |
| 5 | 客户押金、供应商履约保证金和渠道保证金 | 押金和保证金的退还条件、冻结和扣罚不同于订单预收或供应商预付 | CASH / COST / CHANNEL |
| 6 | 领队、导游、计调或项目经理借款、备用金、报销和余款退回 | 跟团、MICE、研学和境外业务会发生现场支出，不能一律作为供应商预付 | COST / PRODUCT |
| 7 | 客户赔偿、团期事故理赔和保险赔款收回 | 客户退款、公司承担赔偿和保险公司赔款是三条不同的债权债务与资金链路 | AFTER / SETTLE |
| 8 | 包机、切位、包舱、包列、酒店切房等共享资源在多个团期之间的成本分摊 | 固定采购成本与单个订单、团期不是一对一，未售损耗和后续调整会改变各团成本 | COST / PRODUCT / SETTLE |
| 9 | 取消出团、不成团、不可抗力和无法向供应商追回的成本 | 不能只做客户退款，还必须判断已发生成本、供应商扣损、公司损失和责任分摊 | AFTER / COST / SETTLE |
| 10 | 现金、POS 或银行实缴与系统应收的长短款 | 多门店现金和 POS 日结不可避免地会产生实缴差异，需要责任确认和账务处理 | CASH / STORE |
| 11 | 客户同时是供应商时的债权债务抵销 | 不能直接用应收减应付，必须有双方协议、审批、抵销明细和会计承接 | SETTLE |
| 12 | 应收、合同资产和长期预付的减值 | 业务明细可以对上，但期末仍可能需要按会计政策确认减值 | SETTLE |

### 2. 根据凯撒实际业务决定是否纳入首期

| 场景 | 是否纳入首期的判断依据 |
|---|---|
| 积分、礼品卡、储值卡和会员权益 | 凯撒是否实际发行、是否由多主体共用、是否存在未使用余额 |
| 第三方补贴、平台券和联合促销 | 优惠由凯撒、平台、门店或供应商哪一方承担 |
| 跨主体客户或供应商余额迁移 | 法人调整、组织重组或业务转移时是否允许转移往来余额 |
| 外币现钞和境外现场资金 | 境外团队是否存在领队携汇、换汇、退汇和现场结余 |
| 客户分期付款服务 | 是由凯撒提供信用还是由金融机构一次性结算 |

## 八、税务链路为当前单独的重大缺口

前五份底座已经明确“发票不代替收付和结算”以及“差额计税不等于净额确认收入”，但尚未形成可供开发执行的税务规则。

必须另行补齐：

1. 各法人的纳税人身份、税种、税率和发票范围。
2. 旅游服务差额计税的可扣减费用、依据、金额、币种和归属主体。
3. 出境旅游、境外服务、航空运输代理等业务的免税、零税率或差额政策实际使用范围。
4. 主责方或代理方的会计收入判断与税务计税口径的并行关系。
5. 销项开票时点、税务义务发生时点和会计收入确认时点的差异。
6. 供应商账单、进项发票、境外单据和差额扣减依据的对应关系。
7. 销售、收款和开票由不同主体承担时，是否符合合同和税务要求。
8. 红字发票、退款、价格调整和结算调整的税额转回规则。

在这些规则确认前，开发可以先保留发票和税额明细的承接位置，但不能把某一种计税方式写死为全集团统一规则。

## 九、底座文档与旧业务文档的不一致

底座01—05现在是业财逻辑的新基线。仓库中的页面任务卡、业务流程确认稿、培训文档和页面映射文档仍有以下旧口径：

| 旧口径 | 与新基线的差异 | 后续处理 |
|---|---|---|
| 将“到账流水”页直接叫“收款凭证” | 流水只证明资金进入，认款并经财务确认后才形成收款单 | 页面梳理时统一为到账流水、认款单和收款单三层 |
| 订单提交或认款后直接生成 NC 凭证 | 业务结果应先形成会计事项，再根据核算规则生成凭证 | 将页面的“生成 NC”改为展示会计承接结果，NC 推送回到财务模块 |
| 供应商账单确认后必然生成应付 | 应先核对业务事实，并按公司政策判断正式应付、暂估应付或待补依据 | 应付页面和供应商账单页面按新边界重新审计 |
| “外采就按净额”或“客户付款总额就是收入” | 全额或净额必须逐业务模式判断主责方或代理方 | 产品类型不再直接决定会计收入口径 |
| “已结算”同时表示业务结算、供应商对账、付款完成、凭证已推送 | 这些是四个不同的财务结果 | 各页面只保留当前业务单据的主状态，其他结果作为关联信息 |
| “内部结算”包含一切内部往来 | 内部产品或服务结算与纯代收代付的资金清算不同 | 统一为内部业务结算单和内部资金清算单 |

本次不直接批量修改所有旧文档和页面，因为先要完成逐场景承接和公司制度确认。否则会把尚未确认的会计和税务规则过早写进页面。

## 十、需要凯撒业务和财务确认的决策清单

| 序号 | 需确认问题 | 主要确认角色 | 未确认的影响 |
|---:|---|---|---|
| 1 | 法人、分公司、核算主体、NC 账套和经营单元的正式对应表 | 集团财务、组织管理、NC 管理 | 无法准确确定单据归属和凭证去向 |
| 2 | 客户签约、收款、开票、收入确认可以出现的合法组合 | 业务负责人、财务、税务、法务 | 无法固化销售和收款主体规则 |
| 3 | 供应商签约、采购、收票、付款可以出现的合法组合 | 采购、财务、税务、法务 | 无法固化应付和付款主体规则 |
| 4 | 跟团、邮轮、专列、自由行、单项、研学、MICE、航服和外采的主责方或代理方判断规则 | 财务、审计、各业务部门 | 无法确定全额或净额收入 |
| 5 | 各类成本的实际成本、暂估应付、正式应付和成本结转时点 | 业务成本负责人、应付会计、总账会计 | 无法确定会计日期和月末暂估 |
| 6 | 集团内部产品共享、航服供票、代收代付和资金调拨的定价、开票、往来和清算政策 | 集团财务、资金、税务、内部业务单位 | 无法固化内部双方单据和对账 |
| 7 | 门店的直营、加盟、外部渠道、预存、授信、分润、管理费和账期规则 | 门店管理、渠道、财务、税务 | 无法准确区分自有销售、渠道销售和内部资金 |
| 8 | 银行、支付平台、POS、OTA 和第三方清算的手续费、拒付、退票和保证金规则 | 资金、客户收款、渠道结算 | 无法完成资金对账和渠道对账 |
| 9 | 各主体税务政策、差额扣减、免税范围和发票要求 | 税务、财务、法务 | 无法定税额和发票承接 |
| 10 | NC 公司编码、科目、辅助核算、凭证类别、汇总粒度、开放期间和返回结果 | NC 管理、总账会计、信息技术 | 无法完成正式凭证对应和接口验收 |

## 十一、面向开发的当前准入结论

### 1. 现在可以开始的工作

1. 法人、核算主体、经营单元、部门和门店的基础关系设计。
2. 交易各方的独立记录，但暂不写死凯撒尚未确认的主体组合。
3. 到账流水、认款单、收款单、应收核销和预收余额的基础链路。
4. 实际成本、供应商账单、账单核对、应付、预付、付款和回单的基础链路。
5. 业务结算、结算调整、会计事项、NC 凭证状态和来源反查的通用框架。
6. 资金、客户往来、供应商往来、内部往来和 NC 的对账异常记录。

### 2. 不应过早写死的工作

1. 不得固定为“订单提交就会计入账”。
2. 不得固定为“外采产品一律净额确认收入”。
3. 不得固定为“供应商账单确认就一定产生正式应付”。
4. 不得仅凭开票或收票状态判断收入、成本、应收、应付、收款或付款。
5. 不得在未取得 NC 正式规则前固定科目、辅助核算和凭证汇总方式。
6. 不得把业务结算完成、对账完成、收付完成和 NC 推送完成合并为一个“已结算”。

## 十二、下一步工作顺序

本次审计后，不应直接跳到最终的开发文档和财务场景手册。建议保持原来的梳理节奏，按以下顺序继续：

1. 将本文列出的 12 类必须场景补入《业财底座02》，形成新的完整场景清单。
2. 对全部场景逐个建立“主体—单据—余额—结算—会计事项—NC—对账”承接表。
3. 用真实合同、账单、银行流水、对账表和 NC 凭证反向验证每个场景。
4. 单独完成税务口径和 NC 正式对应规则，将已确认结论回填到各场景。
5. 以确认后的底座为准，再复核现有原型页面、业务流程文档和旧财务事项表。
6. 最后再生成两份正式交付物：面向开发的底层业务和财务规则文档，以及面向财务的全场景收付、核销、结算和入账案例手册。

## 十三、本次审计后的口径约束

1. 文档和页面优先使用客户、供应商、应收、收款、成本、应付、付款、结算、对账、凭证等业务和财务日常用语。
2. 不在业务文档中使用只有开发人员才懂的抽象名称代替真实业务名称。
3. 同一名称在五份底座和后续文档中必须表示同一件事。
4. 一个状态只说明一类业务结果，不用“已完成”或“已结算”包含多个财务环节。
5. 公司制度未确认的内容，必须明确写为“待确认”，不得由系统设计代替财务和税务决策。
