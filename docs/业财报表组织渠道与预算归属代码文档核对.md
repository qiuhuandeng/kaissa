# 业财报表组织、渠道与预算归属代码—文档核对

核对日期：2026年9月6日  
核对阶段：业财报表自动化改造阶段2.3  
本轮边界：只核对代码、页面和文档，不修改业务页面，不把静态原型当成已经落地的数据能力。

## 一、本轮要回答的问题

财务按订单、回团、产品、渠道、区域、人员和预算看业绩时，需要知道一笔业务在发生当时归谁负责、从哪里取得客户、进入哪个预算范围，以及组织或人员后来变化后历史结果是否仍能复算。

因此，本轮不是只检查系统有没有“组织架构”“门店管理”或“渠道来源”页面，而是核对以下四条关系能否共同成立：

1. 销售公司—经营单元—部门—销售组—销售人员。
2. 区域—分公司—门市部—门店，以及门店的直营、加盟、合作或集团内独立法人关系。
3. 渠道大类—具体渠道—店铺/分销商/线索来源—结算对象。
4. 预算区域—任务年度—任务版本—个人/销售组/门店/渠道月度及年度任务。

它位于订单和销售归属的上游：组织、人员、门店、渠道和任务规则先有效，订单确认时再保存当时适用的归属结果；财务报表只能读取已经保存的结果，不能按今天的组织树反推历史订单。

## 三、总体结论

现有原型已经表达了组织、任职、门店、分销、线上平台、佣金和销售业绩的主要业务概念，尤其是员工任职历史、门店报表归属、佣金政策版本等页面，说明产品方向并非空白。

但是，财务目前仍不能依靠这些页面自动生成渠道、区域、人员和预算完成报表。根本原因不是少几个报表字段，而是：

1. 同一组织、人员、门店和渠道资料分散在多份互不关联的固定数据中。
2. 页面保存大多只改变当前页面内容或显示成功提示，没有形成其他页面可共同使用的正式记录。
3. 一些页面有生效日期或历史记录展示，但订单并未保存当时适用的组织、门店、渠道和任职版本。
4. 财务要求的预算区域及个人、销售组、门店、渠道任务没有正式管理入口，也没有共同版本。
5. “渠道”在不同页面指渠道大类、具体分销商、线上平台、线索来源或门店，层级尚未统一。

因此，这一模块的结论是：**业务概念覆盖较多，但共同资料、历史版本和订单发生时归属确认均未落地；F-009、F-010和F-016均为已确认缺口。**

## 四、组织和核算归属核对

### 1. 文档要求

《业财底座01》明确要求区分六类对象：集团和板块、法人主体、核算主体、经营单元、组织部门、门店经营单元。

其中：

- 法人主体承担合同、收付款、发票和对外责任。
- 核算主体承接账簿、会计期间和NC结果。
- 经营单元承接产品、收入、成本、毛利、预算和经营责任。
- 部门承接人员任职、数据权限及收入部门、成本部门等辅助核算。
- 门店必须按法律关系和合作方式分类；门店类型用于交易后不能直接覆盖，应按生效时间保留变化。

### 2. 当前原型已经表达的内容

`admin/org.html` 已展示集团—板块—主体公司—分公司/中心—门市部/部门—门店的层级，并明确：

- 福建凯撒承担合同、财务和数据边界。
- 厦门、泉州等分公司没有独立主体资质时，由福建主体承担责任。
- 产品中心、长线中心等属于业务中心，不等于法人主体。
- 主体停用后，历史订单、合同和收付款保留原主体归属。

`merchant/system/my-org.html` 也把分公司、门市部、门店作为业务组织展示，并在门店卡片中显示主体公司、默认签约主体和默认收款商户。

这些表达符合“业务组织不天然等于法人主体”的方向。

### 3. 当前缺口和冲突

#### 同一组织资料存在多份副本

组织树至少独立写在以下位置：

- 集团端组织页；
- 业务端组织页；
- 门店管理页；
- 集团端导航脚本；
- 业务端导航脚本；
- 集团员工页的组织筛选和表格。

它们不是从同一份组织资料读取，组织名称和编号已经出现差异。例如泉州门店在不同导航和页面使用不同编号；集团员工页使用“福建凯撒国际旅行社有限公司”“欧洲产品部”，组织页使用“福建凯撒”“欧洲部”。集团组织页的数据中还重复出现两条“欧洲部”。

这些差异在静态原型中只是显示问题，但正式报表若按名称归并，会造成同一组织被拆成多组或错误合并。

#### 法人、核算主体和经营单元仍未形成独立清单

集团组织页把“福建凯撒”标为主体公司，也展示统一社会信用代码和默认合同、收款主体，但没有独立维护：

- 法人正式全称和显示简称的对应关系；
- 法人与核算主体、NC账套的生效关系；
- 经营单元与利润、预算责任的对应关系；
- 分公司何时只是业务组织、何时是独立法人或独立核算单位；
- 各关系的生效日期和失效日期。

当前可以说明产品方向，却不能作为财务按公司、部门、利润中心和NC辅助核算取数的共同依据。

## 五、人员任职和销售组核对

### 1. 当前原型已经表达的内容

`merchant/system/staff-management.html` 已经表达较完整的任职业务概念：

- 员工可有主任职和兼任组织；
- 新任职有生效日期；
- 任职调整可选择历史业务保留原组织归属；
- 详情中可查看任职开始、结束和历史任职；
- 调岗时区分历史订单、进行中业务和交接接收人。

这是本轮最接近财务历史归属要求的页面设计。

`merchant/sales/call-center/consultants.html` 也维护了电销顾问的部门、销售组、线索来源、负责产品和目的地范围。

### 2. 当前缺口和冲突

#### 任职历史只是页面表达，没有成为共同来源

任职新增、调岗和授权提交后只显示成功提示，没有生成可被订单、门店成员、呼叫中心和报表共同读取的任职记录。

集团端员工账号、业务端员工任职、门店成员和电销顾问各自维护姓名、组织和角色。它们没有使用同一员工身份和同一任职关系，因此无法可靠处理重名、兼岗、跨门店、跨部门或离职交接。

#### 销售组没有进入统一组织体系

组织树中没有呼叫中心一部、呼叫中心二部和电销组；这些分组只存在于呼叫中心页面。

同一顾问张明在顾问配置页属于“参团游电销组”，在电销业绩页属于“出境电销组”。顾问配置页筛选项是“参团游电销组”，业绩页筛选项却是“出境电销组”。这证明销售组和业绩统计目前分别维护，不能作为同一报表维度。

#### 订单没有保存当时任职

虽然任职页写明“新建订单按当前主任职和销售本人落归属”，但前序订单核对已确认订单只保存销售姓名和门店名称，没有销售人员身份、部门、销售组、任职期间或归属确认记录。

所以当前系统即使将来修改人员组织，也无法证明历史订单应计入原销售组还是新销售组。

## 六、门店和区域归属核对

### 1. 当前原型已经表达的内容

门店管理页已经包含：

- 门店类型、负责人、合作开始、合同到期和地址；
- 所属主体、组织路径、所属分公司/门市部和“报表归属组织”；
- 默认签约主体、支付商户、收款账户和NC辅助核算；
- 可售范围、结算方式、预存、授信、账期和管理费；
- 生效日期、审核和调整入口。

门店详情还表达了档案、销售配置、财务配置和成员变更记录，并说明暂停后历史订单、余额和对账仍可查看。

### 2. 当前缺口和冲突

#### 门店类型尚未形成可追溯法律关系

页面可选自营、合作、加盟和大客户门店，但没有明确每种类型对应哪一种合同、收款、应收和分润模式，也没有门店类型变更的历史版本。

《业财底座01》要求至少区分直营门店、内部承包或非独立门市、外部加盟门店、集团内独立法人门店和外部分销门店。当前页面类型不足以单独判断门店究竟是法人内部经营单元、外部合作方还是集团内部法人。

#### “区域”含义不统一

门店页的组织路径可以得到厦门、泉州等经营区域；分销商页的区域是华北、华东、华南、全国；财务表中的预算区域却是京津冀直营、京津冀加盟、非京津冀等管理口径。

三者分别是组织区域、渠道市场区域和预算分析区域，不能共用一个“区域”字段。当前系统没有预算区域资料，也没有门店或渠道到预算区域的生效映射。

#### 页面固定数据已经出现具体矛盾

观音山门店在组织树中归属厦门分公司和厦门思明区门市部，但佣金政策的门店配置示例将观音山门店区域显示为泉州。该差异证明门店和佣金范围没有读取同一份门店资料。

#### 订单只留下门店名称

门店页已经有主体、分公司、门店类型、报表归属和财务规则，但订单生成时没有保存这些当时有效的结果。财务仍无法按分公司、直营/加盟、区域和预算区域稳定汇总历史订单。

## 七、渠道层级和结算对象核对

### 1. 当前页面中的五种不同“渠道”含义

| 页面 | 当前表达 | 实际业务层级 |
|---|---|---|
| 渠道来源 | 门店来源、分销来源、OTA来源、官网直客 | 渠道大类或订单入口 |
| 分销渠道 | 同行分销商、代理商、大客户渠道、异业渠道及具体合作方 | 具体外部渠道及结算对象候选 |
| OTA店铺 | 携程、飞猪、同程及平台店铺 | 具体平台和店铺 |
| 呼叫中心顾问 | 来电咨询、官网留资、小程序、活动名单、老客回访、门店转接 | 线索来源 |
| 门店 | 自营、合作、加盟等门店 | 销售经营单元或外部合作方 |

这些概念都需要保留，但必须分层，不能全部放在同一个“渠道”维度中。

### 2. 当前原型已经表达的内容

- 渠道来源页已表达订单归属及收款/对账承接方向。
- 分销商页已表达渠道类型、区域、授权范围、结算方式、佣金、账户和对账记录。
- 分销授权有生效日期和失效日期。
- 佣金政策有业务场景、适用对象、结算单位、生效起止日期、状态和版本记录。
- OTA店铺已表达平台、店铺、负责人、结算方式、类目和同步范围。

这些内容可作为以后统一渠道资料和结算关系的页面基础。

### 3. 当前缺口和冲突

#### 财务要求的渠道分类没有完整来源

财务材料需要呼叫中心、体验中心、门店、全员营销、分公司及其他渠道。当前渠道来源列表没有呼叫中心、体验中心、全员营销和分公司；全项目也没有找到“全员营销”的正式页面或资料。

呼叫中心虽有独立业务页，但没有与渠道来源关联。官网和小程序既出现在渠道来源，也出现在呼叫中心线索来源，系统没有说明最终订单应记“官网直客”还是“呼叫中心—官网留资”。

#### 渠道大类、具体渠道和结算对象没有稳定关联

渠道来源页的“适用对象”“订单归属”是可自由输入文本；分销商、OTA店铺和门店也各自维护结算信息。系统没有一条共同关系说明：

```text
本单渠道大类
→ 具体分销商、门店、平台店铺或线索来源
→ 负责的销售组织和销售人员
→ 客户应收对象、收款主体及渠道结算对象
```

分销商有结算账户和佣金，OTA店铺只有结算方式，没有明确销售主体、收款主体、平台往来单位和开票关系。不能用“平台月结”四个字直接生成渠道应收或确认收入。

#### 生效版本没有进入订单

佣金政策和分销授权虽有版本与有效期，但页面内修改只影响本页展示。前序订单核对已确认下单时选择的分销商、分销员和线上平台没有保存，更没有保存当时适用的授权或佣金版本。

渠道改名、停用、换结算方式或换佣金政策后，历史订单仍无法按原规则复算。

## 八、预算区域和业绩任务核对

### 1. 财务材料的明确要求

财务材料不是只要一个“完成率”数字，而是要求：

- 订单口径和回团口径分别配置任务；
- 个人、销售组、门店、渠道分别有月度和年度任务；
- 可按预算区域比较实际与任务；
- 任务带年度或期间版本，调整后保留原版本和调整依据；
- 月度任务合计能与年度任务核对，组织汇总能与下级分配合计核对。

### 2. 当前页面实际情况

全项目没有找到销售业绩预算或任务的正式管理页面，也没有找到预算区域资料。

现有相关内容只有零散展示：

- 顾问详情操作日志写有“修改本季度业绩目标为¥820,000”；
- 集团工作台销售视角显示“本月GMV目标完成率72%”；
- 门店工作台显示本月销售额和顾问排行；
- 电销业绩页可按顾问、销售组、来源和产品分析成交金额；
- 业务角色页文字提到门店店长可看业绩目标。

这些页面都没有任务来源、任务类型、任务金额明细、年度/月度分解、预算区域、版本、生效日期、审批、调整原因或与实际业绩的共同计算口径。

项目中其他名为“预算”的字段主要是客户预算、项目预算成本或AI费用预算，与财务要求的销售业绩任务不是同一件事，不能复用。

### 3. 结论

F-016从“待查文档”改为“已确认缺口”。当前72%的完成率只是固定展示，无法回答分母来自哪一版任务，也无法证明实际金额与任务使用相同的订单有效范围、日期口径、组织归属和渠道范围。

## 九、财务报表所需归属结果

订单确认或导入时，至少要保存以下当时有效的归属结果。这里先写业务含义，不预设数据库名称。

| 归属范围 | 至少保存的结果 | 来源规则 |
|---|---|---|
| 销售责任 | 销售公司、经营单元、销售部门、销售组、销售人员 | 有效人员任职和销售组关系 |
| 门店责任 | 门店、门店类型、所属分公司/门市部、经营区域 | 有效门店档案和组织关系 |
| 渠道责任 | 渠道大类、具体渠道、平台店铺/分销商/线索来源 | 有效渠道资料和订单入口 |
| 财务责任 | 签约销售主体、收款主体、渠道结算对象 | 合同、收款及渠道合作规则 |
| 预算责任 | 预算区域、任务年度、订单或回团任务类型、任务版本 | 有效预算区域映射和任务版本 |
| 追溯依据 | 归属确认日期、适用规则、调整记录 | 订单确认、迁移或批准后的归属调整 |

名称可以随后变更，但历史订单必须继续保留当时名称和当时归属。确需纠正历史业绩时，应形成有原因、审批人、生效范围和前后结果的归属调整记录，不能直接修改原订单。

## 十、需要完善的功能和流程

### 第一批：统一组织和人员资料

1. 集团端只维护一份集团、板块、法人、核算主体、经营单元、部门和门店关系。
2. 业务端组织页用于查看本主体组织和发起调整，不再另写一份组织树。
3. 集团员工账号只负责账号身份和后台权限；业务任职页维护主任职、兼任、销售组和生效期间。
4. 门店成员和呼叫中心顾问引用同一员工和任职关系，只补充本场景权限或线索承接范围。
5. 组织、任职、门店类型及上下级关系均保留生效和失效时间。

### 第二批：统一渠道层级

1. 将渠道来源改为渠道大类资料，明确呼叫中心、体验中心、门店、全员营销、分销、OTA、官网/小程序、企业客户和分公司等正式分类。
2. 分销商、门店、OTA平台店铺、呼叫中心线索来源作为具体渠道或下级来源，不与渠道大类混为同层。
3. 每个具体渠道明确负责销售组织、结算对象、合同模式、收款模式、佣金/服务费规则和有效期间。
4. 订单确认时保存渠道大类和具体渠道，不在报表阶段根据页面入口或当前资料猜测。

### 第三批：建立预算区域和任务版本

1. 建立预算区域清单以及组织、门店、渠道到预算区域的生效关系。
2. 区分订单任务和回团任务，区分金额、订单数或人数等任务指标。
3. 支持个人、销售组、门店、渠道、区域的月度和年度任务。
4. 任务需要草稿、待确认、已生效、已失效等状态，并保留版本、调整原因和审批记录。
5. 年度任务、月度分解和下级分配必须有合计校验；同一范围同一期间不能同时存在两份有效任务。
6. 工作台和业绩页只展示从有效任务计算出的完成率，并可下钻到任务版本与实际订单明细。

### 第四批：订单发生时固定归属

1. 新订单、导入订单和外部平台订单在确认时都形成归属确认结果。
2. 归属结果同时保存销售、门店、渠道、财务责任和预算责任，避免报表时分别拼接。
3. 订单口径按订单发生时归属统计；回团口径是否仍按原订单归属，需财务拍板，建议默认保留原订单归属并另提供“当前组织查看”。
4. 历史数据迁移时，无法确定的组织、渠道或预算区域进入待补清单，不能静默归到“其他”。

## 十一、建议修改的页面和主入口

| 页面或流程 | 建议调整 | 主要使用角色 |
|---|---|---|

预算与任务主入口的最终菜单位置仍需结合公司职责确认。建议由财务预算或经营管理角色负责版本确认，销售、门店和渠道负责人负责分解；各业务工作台只查看结果，不各自维护一套任务。

## 十二、验收场景

1. **员工跨组调岗：** 销售顾问7月从参团游组转入邮轮组，6月订单仍归原组，7月生效后的新订单归新组。
2. **门店组织调整：** 门店从厦门分公司调整到泉州分公司，历史订单仍能按原分公司查询，调整后订单进入新分公司。
3. **门店关系变化：** 合作门店改为加盟门店时形成新版本，旧订单仍按旧合同和结算模式核对。
4. **呼叫中心线索转订单：** 官网留资由呼叫中心顾问成交，订单同时保留渠道大类、线索来源、顾问和销售组，不在官网直客与呼叫中心之间重复计算。
5. **分销订单：** 一张分销订单能下钻到分销商、分销员、佣金政策版本、渠道应收和对账记录。
6. **OTA月结：** 平台、店铺、销售主体、平台往来单位、订单原额、退款、佣金、补贴和实际到账可共同核对。
7. **预算调整：** 年度任务调整后形成新版本，历史已发布周报能说明当时使用的任务版本，新报表使用新版本且月度合计正确。
8. **跨年回团：** 上年订单本年回团时，回团业绩使用的销售组织、渠道和预算区域规则有明确依据，不因当前组织资料改变而漂移。

## 十三、仍需业务和财务确认的问题

1. 凯撒正式法人、核算主体、经营单元、分公司、部门、门市部和门店清单及对应关系。
2. 门店的自营、内部承包、合作、加盟、集团内独立法人和外部分销类型如何映射，是否允许同一门店分阶段变化。
3. 财务要求的渠道大类正式清单，以及官网/小程序由呼叫中心成交时的主渠道和下级来源取值。
4. “体验中心”“全员营销”“分公司渠道”的业务对象、负责人和结算方式。
5. 京津冀直营、京津冀加盟、非京津冀等预算区域的正式定义、适用年度和历史变化。
6. 订单任务与回团任务分别下达到哪些层级，金额、人数和订单数是否都需要。
7. 回团口径按订单发生时归属、回团时当前组织归属，还是同时提供两套分析视角。
8. 已经发布报表后发生归属纠错，是否追溯原期间，还是在批准期间形成调整。

## 十四、本轮结论与下一步

本轮没有修改业务页面。已确认组织、人员、门店和渠道页面具备较丰富的业务原型，但它们是多套独立固定数据，无法向订单提供可追溯的统一归属；预算区域和业绩任务管理则基本缺失。

唯一下一步是核对“收款、应收、退款与资金”模块，重点检查到账流水、认款、收款、应收、预收/预存、退款、转款和资金变动是否使用同一订单关系，能否向财务业绩明细提供可核对的实收与调整数据。
