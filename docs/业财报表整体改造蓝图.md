# 业财报表整体改造蓝图

> 版本：第二版，2026-09-06  
> 用途：把财务五类目标结果、现有原型能力、七轮代码—文档核对证据和后续页面改造收敛到一条实施路线。  
> 当前结论：本项目改的是业务原型和财务报表原型。原型用于表达功能、使用流程、业务规则和数据埋点，不要求页面之间的模拟数据真实形成生产级业财闭环。

## 一、最终判断

现有原型能够说明旅游业务从产品、团期、订单、收付、成本、结算、发票到集团财务核算系统（项目内简称“NC”）的大致页面范围，但**还没有完整表达自动生成五类财务结果所需的功能、流程、字段埋点和报表结构**。

问题不只是缺少五张报表，而是现有页面没有把“某个字段由谁在什么动作产生、何时确认、变化后怎么处理、报表如何使用”表达完整。正确目标不是照搬五份Excel，也不是在静态HTML里把所有模拟数据真正串起来；而是把正式系统将来需要的数据来源、操作入口、字段关系、计算规则和下钻方向设计清楚。

本项目交付收敛为三件事：

1. 原型功能和流程缺口：指出哪些页面缺功能、字段、状态、操作或下一步入口，并完成必要的原型优化。
2. 五类财务报表原型：表达报表字段、筛选、口径切换、汇总、下钻、异常和输出功能，示例数据只用于说明场景。
3. 数据埋点与字段字典：按功能模块说明字段的业务定义、产生动作、维护角色、变化规则、报表用途和计算口径，作为未来正式开发依据。

最终链路应为：

`组织/人员/渠道/产品资料 → 客户订单 → 实际履约与回团 → 收款退款和成本付款 → 业务结算 → 收入确认与成本结转 → 发票/会计事项/NC → 共同业绩明细 → 订单、回团、产品渠道、预算毛利和异常分析`

财务需要的五类结果统一定义为：

1. 财务业绩明细：所有汇总共同使用、可以逐笔核对的明细。
2. 订单口径业绩：按真实下单日期统计当期有效订单。
3. 回团口径业绩：按实际回团和财务确认状态观察已完成履约业务。
4. 产品、目的地、业务类型、渠道、区域和人员分析：使用订单发生时的归属。
5. 毛利、预算和异常管理：区分业务毛利、会计损益、任务完成和待处理差异。

## 二、这份蓝图依据什么

本蓝图依据以下已经完成的核对，不重新凭印象设计：

- 5份财务材料、4个工作簿的93个工作表以及Word正文、表格和内嵌图片。
- 集团端、主业务端、供应商端、客户端和运营平台共237个应用页面。
- 产品与团期、订单与销售归属、组织渠道与预算、收款退款与资金、成本应付付款、回团结算会计、财务分析报表七轮代码—文档核对。
- 《财务五类报表需求基线》和《财务要求—现有功能—缺口—修改对照表》中的F-001至F-020。

七轮核对后的状态是：15项已确认缺口，5项仍需确认具体口径。待确认的5项是F-002有效订单与退款冲减、F-007自营/甄选/外采、F-008多目的地、F-013不含税、F-017期间比较；这些事项的**记录能力缺失已经确认**，只是最终计算规则尚未拍板。

## 五、原型实施顺序

后续原型工作只分四步，不按生产系统建设拆成大量批次：

### 第一步：形成数据埋点与字段字典

从五类财务结果逐字段倒推产品、团期、订单、组织渠道、人员、收退款、成本结算等模块。每个字段写清业务名称、定义、产生页面、产生动作、维护角色、变化规则、报表用途和计算规则。

### 第二步：补齐上游功能和使用流程

只修改会影响财务报表的字段、按钮、弹窗、抽屉、状态、详情信息和下一步入口。重点是业务人员是否知道在哪里维护、确认或更正数据，不要求模拟数据跨页面自动回写。

### 第三步：形成数据中心五类经营报表原型

在数据中心“业绩与经营分析”入口中表达财务业绩明细、订单口径、回团口径、产品渠道人员分析、毛利预算及异常。报表需要有筛选、期间口径、字段说明、下钻方向、数据截止、导出和生成记录，但示例数据只用于演示不同业务场景。该页面已经先于上游功能改造完成第一版，后续以走查结果倒推最小必要上游改造。

### 第四步：原型走查与开发说明收口

按照“报表指标 → 所需字段 → 产生功能模块 → 页面操作入口 → 下钻去向”走查。最终交付缺口清单、字段字典、页面原型和待确认口径，不以模拟数据合计完全一致作为验收条件。

## 六、无需等待即可先改

以下事项不会因为财务选择不同计算口径而失效：

1. 保留能够说明场景的模拟数据，但无依据的收入、成本、已付、应付、币种和汇率不得在文案上冒充真实自动计算结果。
2. 销售订单是客户订单主入口，履约中心的团期订单只表达履约查看场景；原型不要求两处模拟数据实时同步。
3. 将计划出团/回团与实际出团/回团分开，并保留确认和更正记录。
4. 将订单金额、应收、到账、收款、收入、成本、账单、应付、付款、发票和税额分开命名和展示。
5. 订单、到账、退款、账单、付款和NC都预留来源系统、外部单号、导入批次和防重复依据。
6. 页面归属按角色调整：高频团期动作回履约中心，财务确认回财务模块，经营分析回数据中心。
7. 工作台只表达应展示的业绩摘要和带条件入口，不把固定示例值写成真实计算能力。
8. 下钻设计明确目标页面、业务对象和传递条件；原型允许使用示例编号，不要求真实跨页定位。
9. 筛选、导出、推送或生成按钮可以演示目标流程，但应明确结果状态和功能边界，不用一句“成功”代替所需交互。
10. 文档明确区分“当前已实现”“原型表达”“正式开发方向”“待确认口径”。

## 七、需财务或业务确认的口径

## 八、建议的首批页面与流程范围

首批原型改造建议命名为“订单与实际回团的数据埋点表达”。选择它的原因是：下单日期和实际回团日期是两套财务业绩的时间入口，但本批只补功能、字段、状态和操作流程，不建设模拟数据链路。

### 8.1 首批先做的业务结果

1. 下单功能明确客户订单的确认、生效、来源和发生时归属字段应在哪里产生。
2. 销售中心是客户订单主入口；履约中心的订单视角明确只服务团期执行，不再表达第二种订单定义。
3. 团期可确认实际回团，保留实际日期、确认人、时间、依据和更正原因。
4. 履约订单详情不再展示没有真实依据的应付和成本。
5. 页面入口能表达从订单到团期、从团期回到订单的下钻方向和所需条件。

### 8.2 首批涉及的当前页面

| 业务场景 | 当前页面 | 首批改造边界 |
|---|---|---|
| 产品预订 | `merchant/sales/sales-product-quote.html` | 负责选择产品、方案和具体团期，并把对象识别信息带入新建订单；不在本页形成订单和财务结果 |
| 新建订单 | `merchant/sales/booking.html` | 补订单创建、确认生效、来源、原订单号和发生时归属的字段及操作表达；不模拟生成全部财务单据 |
| 订单列表与详情 | `merchant/sales/orders.html`、`merchant/sales/orders-detail.html` | 作为唯一客户订单主入口；区分业务状态、履约状态和财务承接状态 |
| 履约订单查看 | `merchant/tour/schedule-orders.html`、`merchant/tour/schedule-orders-detail.html` | 明确为客户订单的团期履约视角；示例数据可以独立，但字段定义和业务含义必须一致 |
| 团期与实际回团 | `merchant/tour/schedules.html`、`merchant/tour/schedules-detail.html` | 计划日期与实际日期分开；新增回团确认和更正的原型表达 |
| 团期成本表达 | `merchant/tour/fulfillment-cost.html` | 明确预计成本、实际成本、应付和已付的字段来源及下一步；本批不做真实计算和完整成本链 |

### 8.3 首批暂不包含

- 不在本批做真实后端、数据库、NC接口或跨页面生产级自动回写。
- 不要求销售订单、履约订单、团期成本和财务报表的模拟记录自动一致。
- 不在本批完成应收、到账、认款、付款、发票和会计核算全闭环。
- 数据中心五类经营报表页面已独立完成第一版；本批上游页面不再重复建设报表，也不制作五份照搬Excel版式的导出文件。
- 不在未确认口径前写死退款冲减、甄选、多目的地和不含税计算。

### 8.4 首批验收场景

1. 普通订单：下单页能说明订单号、团期、下单日期、来源和归属在哪里形成，履约入口业务含义一致。
2. 跨年订单：页面字段能同时表达上年下单和本年实际回团，两种时间口径不混用。
3. 延期回团：计划回团日不变，实际回团日按确认记录展示。
4. 回团更正：更正抽屉或记录区表达原值、原因、人员和时间。
5. 成本信息：订单和履约详情能区分预计成本、实际成本、应付和已付，并说明进入哪个页面处理。
6. 历史来源：迁移订单字段包含来源系统、原订单号和导入批次，并在字段字典中说明未来防重复规则。

逐页任务、字段范围、状态动作、原型边界和实施顺序以《财务自动化报表第一批原型页面修改清单》为准。代码复核已确认首批为9个页面：产品预订页负责选销售对象，`booking.html`才是真正形成订单的页面，两者不能合并计算为一个页面。

## 十、总体验收标准

原型是否已经完整表达“未来自动生成财务报表所需能力”，按以下结果验收，而不是检查模拟数据是否真正跑通：

1. 功能完整：原型包含产生、确认、更正、查看和异常处理所需的功能入口。
2. 字段完整：字段字典覆盖订单、产品、渠道、组织、人员、日期、金额和来源。
3. 时间可解释：下单、实际回团、结算确认、调整和会计期间分别保存。
4. 金额可勾稽：订单金额、收退款、业务收入、会计收入、成本、应付、付款、发票税额互不替代。
5. 归属可追溯：组织、人员、渠道、产品和预算区域按发生时规则保留历史。
6. 汇总规则可说明：订单、回团、产品渠道、预算和毛利结果均写明所需字段、分子分母和统计范围。
7. 跨期可解释：跨年订单、回团后补成本、退款和返点保留原期间与调整期间。
8. 异常可处理：负毛利、成本缺失、未结算、NC失败等能回到正确来源页面；正常余额不被误报。
9. 会计不越界：开票不等于收入，收票不等于成本，付款不等于应付或成本，业务结算不等于NC入账。
10. 报表原型完整：显示数据截止、口径版本、导出和生成记录的功能表达，正式一致性留给后续系统开发验收。

## 十一、阶段3结论与下一步

阶段3和本次范围纠偏后的结论是：不在原型中实现生产级业财数据闭环。先形成数据埋点与字段字典，再按这份字典补上游功能和流程表达，同时设计五类财务报表原型。

财务业绩明细字段和四类汇总指标已经完成。唯一下一步是根据字段字典生成第一批原型页面修改清单，逐页明确角色、上下游、功能缺口、字段、状态、操作、下钻和验收点，并区分原型必须表达与正式开发能力，再确定最小修改批次。
