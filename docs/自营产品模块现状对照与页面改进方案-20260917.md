# 自营产品：现状对照与模块、菜单、页面改进方案

日期：2026年9月17日。状态：**待用户确认，尚未实施页面改造。**

需求依据：本次用户提供的自01—自36，以及[业务会议需求完整梳理](业务会议需求完整梳理-供应商产品与销售-20260917.md)。现状依据：当前导航、页面代码、共享交互脚本与业务流程文档。本文承接[分模块核对及增改清单](业务需求与现有功能分模块核对及增改清单-20260917.md)，把自营部分细化到页面和操作。

本次为静态功能及流程核对。下面的“已有”指代码中可定位到的结构或处理，不代表真实识别、接口、权限、库存并发或财务取数已经完成；“验收”均指后续实施应执行的场景，本次没有进行浏览器或实账验收。没有修改业务页面，没有生成本地图片。附件中的人员分工、执行要求仅作需求证据。

## 一、结论及本次确认范围

**现有原型主链路和多数菜单已经存在，应保留框架，重点补齐处理过程、纠正错误逻辑和统一字段归属。不能把36条需求都塞进“产品编辑”页，也不需要再建一套采购、佣金、结算、素材或领队模块。**

本方案分13个页面改进单元P01—P13，覆盖36条需求。页面单元不是新增菜单，也不表示13个页面从零建设。

最需要处理的六件事：

1. 产品和线路方案：保留多出发地复制、酒店评分和购物表格，补复制关系、每日多段交通、混合签证和服务类型多选。
2. 团期：把建团、开放报名、对外展示分开；补采购资源选择、渠道配额返还和核心资料变更限制。
3. 规则：现有四类定价、佣金、退改继续使用，补审批版本、命中依据和冲突处理；不擅自确定价格叠加和加盟定价政策。
4. 采购：修复减量为零仍回退原金额、多舱型减量未完整承接等问题，补已分配、已售情况下的影响预览。
5. 结算：去掉按62%/38%编造订单明细的处理；账单核对保留真实差异；复用已有二次结算和批量付款申请。
6. 配套：识别必须经过校对，导出必须产生可用文件；补素材下载、领队历史和评价依据。

用户本次需要确认的是：**页面归属、每页改造内容、实施顺序**。第六节列出的业务和财务政策仍需对应负责人确定，确认页面方案不等于批准这些政策。

### 2. 业务角色和上下游

| 角色 | 进入页面最高频任务 | 上游依据 | 本页完成后交给谁 |
|---|---|---|---|
| 产品经理 | 编制、复制线路，校对资料，提交价格和产品审核 | 目的地资源、地接方案、公司经营安排 | 计调建团、销售展示和预订 |
| 计调／团控 | 开排团期，调整名额，分配资源，确认名单及出团资料 | 已审核产品、有效销售规则、采购资源、订单 | 领队与供应商执行；确认成本交财务 |
| 航服／采购／资源调度 | 分期采购、确认数量、分配和释放资源 | 航司／船司／运营商资料及合作协议 | 团期可用资源、付款申请依据 |
| 销售顾问 | 按适用价格下单，补游客资料，发起改价或退转团 | 有权销售的团期、价格版本和渠道配额 | 履约名单、合同、应收调整和售后 |
| 财务 | 核对账单和成本、预付余额、付款及结算 | 业务确认记录、协议、申请及原币金额 | 财务应收应付、付款和结算结果；后续核算沿原流程 |
| 领队管理员 | 维护证件、经历和档期，选合适人员派团 | 领队档案、团期需求、实际带团和评价 | 团期人员安排、出团资料 |

“应收”指按有效业务依据应向客户收取的款；“应付”指按确认依据应向供应商支付的款；“预付”指提前付给供应商、以后需要抵扣或退回的款。以上三者不能用收款、成本录入或采购金额互相替代。

### 3. 字段放在哪一层

| 层级 | 应维护的内容 | 与本次需求有关的边界 |
|---|---|---|
| 产品 | 产品名称、提供公司、归属部门、目的地、共用素材和说明 | 自营产品提供公司不作为外部采购供应商重新准入 |
| 线路方案 | 出发地、分日行程、参考交通、酒店候选、服务标准、签证和说明 | 同产品可有北京出发、上海出发等方案；复制后保留来源关系 |
| 团期 | 具体日期、采用的方案版本、当期交通、名额、价格、门店、人员和集合安排 | 不重复录入整份行程，不用一次变更覆盖已售团期的旧资料 |
| 采购 | 供应商、公司协议、分期采购数量、资源规格、付款节点、可退条件 | 可被多团使用；资源采购数量不等于最低成团人数 |
| 订单／游客 | 实际销售渠道和人员、成交依据、游客签证方式、证件、退改申请 | 同团可有人自办签证、有人随团办理；退位回原渠道 |
| 结算／财务 | 经确认的金额、调整、账单差异、预付抵扣、付款和二次结算 | 产品参考价、实收、业务收入及财务确认收入分别表达 |

当前页面把方案叫“线路”、旧文档又把长期产品叫“线路”，容易混淆。建议编辑页统一用“线路方案”，如“北京出发·品质款”；保留用户熟悉的“产品管理”菜单，不额外增加一层需要重复建档的产品。

## 二、逐页改进方案

### P01 产品列表：产品中心 → 自营产品 → 产品管理

页面：[产品管理](../merchant/product/products.html)。角色：产品经理；对象：长期产品档案。关联自01、自03、自22、自34。

**现状：** 有产品分类、编辑、复制、渠道发布和排期入口，产品编辑内另有复制线路。不能把列表复制产品和同产品复制出发地方案视为同一动作。证据E01、E02。

**改法：**

- 保留按产品名称／编号、目的地、产品类型、归属公司／部门和主状态查询。主信息列只保留产品识别、出发地概况、方案数量、负责人及主状态等高频字段；不新增采购金额、付款状态、名单缺口列。
- 列表“复制”明确为复制产品；同一产品扩展出发地到编辑页内“复制方案”完成，不要求再建一个无关联产品。
- 列表保留编辑／详情、进入团期等主要入口；渠道发布使用当前产品自己的处理抽屉。方案编辑、交通明细和佣金复杂配置不并列堆到行操作。
- 产品审核和渠道展示分别控制。产品审核通过不自动将所有团期展示到小程序或官网；产品允许展示的渠道为团期展示范围上限。
- 产品详情或编辑素材区提供“选择素材／查看关联素材”，集中管理仍在素材中心，不再复制一个媒体库。

**验收：** 同一产品下能找到北京、上海两条方案及各自团期；产品审核完成但尚未开启小程序的团期，不出现“已发布小程序”的结果。供应商列表保持原状。

### P02 产品编辑：基础信息、线路方案、每日行程

页面：[自营产品编辑](../merchant/product/product-self-edit.html)。直接共用处理见附录E02—E04。角色：产品经理。关联自01—自09。

**保留现有“基础信息／线路配置”两步骨架，建议第二步名称改为“线路方案”。** 方案内保留分区导航；每日交通融入行程，顶部大交通区域收敛为参考交通汇总与选用规则，避免两处重复维护航段。

#### A. 基础信息与多出发地方案

| 现状 | 具体改法 | 操作结果 |
|---|---|---|
| 产品名称已为普通文本，样例已含【】、星号，长度80 | 保留真实业务符号；明确长度提示，保存、预览、导出、手机端显示一致；不把所有特殊字符删除 | 名称如“欧洲（国庆）*纯玩”完整保存；内容按普通文本展示 |
| 共享预设把“福建凯撒”等作为供应商来源 | 自营处显示“产品提供公司、归属部门、产品负责人”；实际地接、酒店、交通供应商在采购／团期服务安排分别引用 | 销售知道哪家公司提供产品；财务知道实际付给谁 |
| 已有复制线路，并询问新出发地 | 改为“复制方案”抽屉，选原方案、新出发地、新名称；默认复制行程、酒店、签证、说明和素材，显示需核对的首尾交通／天数 | 新方案仍属于原产品，保留复制自哪条方案和采用版本 |
| 复制后共用内容关系不清 | 本期采用“有来源关联的副本”，不做无限自动同步；共用内容更新时可勾选应用到哪些未锁定方案并预览差异 | 原方案修改不会悄悄覆盖另一口岸或已售团期；更深共享编辑另确认 |

这里的“有来源关联的副本”为方案建议，满足不用重录且保持关联；不把业务需求解读为必须同步修改所有出发地。

#### B. 每日交通

- 每天行程增加“交通安排”明细：交通方式、航班／车次、起终点、当地出发／到达时间、到达日偏移、参考／待确认说明；支持新增、排序和删除多段。
- 例：D1北京→多哈、D1多哈→巴黎，D2巴黎→里昂火车；不能只用“飞机＋火车”勾选代替两段具体航班和一段列车。
- 产品方案维护参考安排，具体日期和最终票号／确认号在团期交通资源与游客出票记录维护。跨日抵达需明确D2，不把到达时间误算为负时长。
- 既有“大交通”若保留，只展示由每日交通汇总的去返程参考、是否包含、团期需要确认什么；不再维护另一套独立起降时间。

#### C. 资料识别与校对

- 复用现有Word／PDF上传、文本粘贴入口；抽屉按“资料输入→按天及字段校对→应用所选结果”组织。
- 校对区展示原文片段、建议字段、缺失和不确定项；产品名、行程天数、每日段落、酒店、自费购物分别确认。
- 支持只导入行程，不覆盖已维护产品名；覆盖当前资料前给出受影响天数和字段；无有效结果、文件不支持或识别失败时保留原资料。
- 本期原型用明确标识的示例资料演示校对和应用，不再对任意文件报“已识别”；正式文档识别服务另行接入和验收。

#### D. 自费、购物、酒店、签证和服务

| 分区 | 已有基础 | 建议调整 |
|---|---|---|
| 自费／购物 | 已有所属行程、城市／国家、参考价、时长和合同名称，已可加行 | 日期选择跟随实际D1—Dn生成；国家与城市分开选择或明确对应；团期展示换算实际日期；调整天数后处理失效日期。图片识别走同一校对过程；“全程说明”不能代替有实际发生日的项目 |
| 酒店 | 已有住宿类型、评分、星级／档次及多行参考酒店 | 保留并完善酒店库多选和临时文本候选；评分分来源、分值、满分，避免不同平台混比。营地／特色住宿可无星级；参考酒店与最终确认酒店区分。合同展示以业务提供的有效合同模板确认，不宣称已满足未提供的新模板 |
| 签证 | 已有多个国家方案，但办理方式仍单选 | 产品勾选允许“游客自办、随团办理”等方式，分别说明费用和材料；订单按游客选实际方式。自办不自动等于减免签证费，费用是否可退／减交价格和退改规则确定 |
| 导游／领队 | 目前为单选，含“全陪＋地陪”等组合值 | 改为可组合的服务类型：领队、全陪、地陪、司机兼导游、景区讲解等；可填服务天／地区和人数说明，“无”与其他项互斥。这里只定服务标准，不直接选当期人员 |
| 须知／途经城市 | 已有长文本、模板带入及途经城市 | 保留；补分段编辑／手机预览、版本和适用范围。护照、保险、汇率风险等文字由业务审核；模板应用前预览，不自动替业务作承诺 |

**异常处理和下一步：** 未校对识别结果保留为草稿；具体必填项错误定位到当前方案和日期。保存草稿可继续，提交审核按明确校验项提示。审核后的方案交建团引用，不能把参考交通或候选酒店标成当期已确认资源。

**验收：** 复制北京方案为上海方案后D2—D6无需重录；一天两航段与一段列车均可展示；同团两人自办、三人随团办理；营地无星级可保存；购物D8在行程改为7天时提示重新选择。

### P03 销售政策：定价、佣金、退改及审批

页面：[定价策略](../merchant/product/product-pricing.html)、[佣金政策](../merchant/channel/commission_rules.html)、[退改规则](../merchant/resource/refund-rules.html)、[审批](../merchant/approval/approvals.html)。角色：产品定价人员、授权负责人／审批人。关联自13—自15、自32。

**现状：** 定价页已有淡旺季、早鸟／尾单、人数和出发地模块及审批状态；佣金页已有门店、分销商、销售顾问选项、版本、适用产品和结算单位；退改已有独立入口。“按团期结算”不是已经能选择某个具体团期适用。证据E05。

**定价页：**

1. 每套规则明确适用公司、产品／方案／团期、渠道、有效期、审批版本。填写四类条件继续用现有模块，不另加四个菜单。
2. 增加“价格试算”：选择出发日、报名日、人数、出发地及销售渠道，逐条显示基础价、命中项、排除原因和最终报价；人数指单笔订单人数还是整团人数必须可分清，业务未定前不默认。
3. 价格概念分别显示：产品部门批准的标准售价、建议零售价、渠道结算价、订单实际成交价。渠道结算价不能叫供应商采购成本，建议零售价不默认成为强制最低价。
4. 待确认的叠加顺序不能写成系统固定算法。多条命中且无批准规则时显示“价格规则冲突，待确认”，保留各自结果供审核；不要静默任选一条。
5. 已批准规则修改形成新版本；团期选择生效版本，已成交订单保留当时价格依据。适用价格条件变化不反向重算历史成交价。

**佣金页：** 在已有适用对象选择上补产品／指定团期、指定渠道／门店／顾问的完整选择与当前适用范围摘要；区分佣金受益人和销售渠道；明确计提基数、金额或比例、生效时间、退团和应收调整的处理依据。同一订单多政策命中时提示冲突，优先级和能否并享待确认。销售顾问激励不能因名字相近就与加盟分润合计。

**退改页：** 保留独立模板及审批版本，线路和团期可引用；团期例外需说明适用范围和批准依据。佣金政策只引用退改后的处理依据，不在退改模板内维护佣金比例。

**审批承接：** 来源页显示草稿／审批中／退回／已生效及版本；审批人看变更前后、影响范围、意见。实际外部审批服务未接入时只演示来源与处理结果，不能宣称已同步到真实审批系统。

**验收：** 相同条件试算与订单引用一致；一个政策能明确选到某个团期和顾问；审批中不能当成有效售价；退团时能找到当时佣金和退改版本。加盟自主定价与折扣审批按第六节确认结果再实现。

### P04 建团和批量排期：履约中心 → 团期管控

页面：[团期管控](../merchant/tour/schedules.html)的批量开团、[新建团期](../merchant/tour/team-create.html)。角色：计调／团控；关联自10—自12、自22。

**改法：**

- 批量生成继续用日期范围、星期或节假日，新增／保留可勾选的日期预览、手工排除、重复团期提醒。确认后显示创建成功、跳过及失败日期；不把节假日样例当成每年自动更新的正式日历。

- 最低成团人数是产品经营规则。采购来源已有经批准的建议值时可带入，否则从方案／销售规则取值或人工填写；不从“可分配30座”自动算出“最低30人”。

- 团期维护出发地、集合时间地点、计调、领队安排、允许销售门店及采用的规则版本；集合事项可待补，何时必须完整按出团准备要求校验。
- 新建默认内部筹备。销售开放控制能否报名；小程序／官网等展示开关控制在哪里被客户看到。展示开关初始关闭；保持与产品渠道授权一致，允许内部销售但暂不公开展示的场景。

**操作后：** 生成待发布团期并保留所选方案与采购分配依据；交团控检查价格、名额和销售范围。原型只演示当页结果与合理承接入口，不假造银行或跨系统动作。

**验收：** 国庆日期生成7天、排除2天，只生成5个日期；两团合计分配不超过同批可用量；不绑定交通可保存内部团期，页面不报资源确认完成。

#### 两项必须补的限制

**渠道库存：** 团期总量之内分别表达直营、代理、线上平台配额；订单留原占用渠道。取消或释放经相应业务处理后归还原渠道，即使原渠道停售也不自动混到其他渠道；是否转为公共可分配量需要单独调配动作。共享可用池是否允许及如何使用待业务确认，本期不能将“渠道独立”实现为每个渠道都可售总名额。

**核心变更：** 草稿且无关联订单／费用时可按权限编辑；已进入销售，尤其有订单、占用或成本时，日期、方案和核心交通需先看影响范围。建议“新建目标团期→选择需要转团订单→售后审批和资源重分配”，保留原团。整团迁移能否自动承接旅客、合同、款项待确认。仅时刻变化且无费用变化的例外单独标“待确认”，不能默认允许直接改，也不能永久一律禁止。

**验收：** 总量30，直营10／代理8／平台12；代理取消2位只恢复代理2位。销售中有成本的团不能在普通编辑里覆盖出发日期；时刻例外有单独确认路径。出团包可看到同一游客的签证和资源匹配缺口。

### P07 单团项目：快速建团和询价两条路径

页面：[单团项目](../merchant/tour/product-custom-list.html)、[项目详情](../merchant/tour/product-custom-detail.html)、项目确认后进入[新建团期](../merchant/tour/team-create.html)。关联自21。

**现状：** 项目列表已支持线下成交录入、确认材料；详情区分线下确认及意向来源，新建团期仍有“已锁定报价”提示。不能断言所有单团必须从零询价，也不能把“跳过询价”解释成跳过确认。证据E09。

**建议明确两个场景：**

- **客户已确认，快速建团：** 新建项目时选“已有确认方案”，录客户、日期、人数、行程／标准、确认金额或其待定状态、负责人及客户确认材料。已有最终报价可作为确认依据，不要求重新跑多轮询价。进入建团仍需满足已确认的项目条件；若只获准内部筹备，则生成内部待完善项目，不冒称成交或已形成应收。

### P08 交通采购：分期、分配和数量变更

页面：[交通采购](../merchant/tour/resource-procurement-inventory.html)，由机票切位、邮轮包舱、专列包铺菜单进入各类型。角色：航服／采购／资源调度。关联自11、自23—自26。

**现状：** 已有三类资源、分期付款、分配到团期、释放、数量变更和费用调整。业务文档要求到期提醒后人工发起申请，会议希望节点自动形成申请，两者存在明确待定项；当前数量变更为零会回退原付款金额，且只有单一子类型直接更新总量。证据E10。

#### 分期采购和付款计划

- 保留一押、二押、三押／尾款，允许增减阶段；每阶段明确数量确认日、有效数量、付款到期日、比例或固定金额、累计还是本次付款、原币和条款。
- 免费退回比例必须显示计算基数和截止日，区分“退还名额”和“发生损耗”，不可用一个“可损比例”同时表达无损退位和实际损失。
- 付款节点展示计划金额、已申请、已付、本次可申请及数量变更影响。已付款记录保持原值，变化用补款／退回／后续抵扣建议表达，不能直接改历史付款额。
- “到期自动形成申请”保留为待确认模式：自动生成草稿还是自动送审、哪一状态启动、防重复、金额变更怎么处理需确认。原型可先完善“核对节点→发起申请”；任何模式都不等于自动付款。

#### 可分配数量与变更

| 处理场景 | 页面必须呈现 | 建议行为 |
|---|---|---|
| 正常分配 | 采购规格、当前有效总量、已分配、未分配、本次分配、目标团期 | 本次不得超过该规格可分配量；记录采购来源与目标团期 |
| 采购后绑定既有团期 | 团期日期及缺口、候选采购日期／航段、分配数量 | 在团期或采购分配抽屉完成同一类分配，展示对应来源；不要求重新建团 |
| 减量仍覆盖已分配 | 前后总量、未分配减少量、付款节点差额 | 确认后只更新受影响的资源和数量示例，已售明细保持 |
| 减量低于已分配／已售 | 每个受影响团期、渠道和已售数量，缺口、可能费用 | 给出冲突清单，进入重新分配／补采购／退转团待处理；未经批准策略不自动减掉已售名额或随机挑团 |
| 减至零 | 未付款节点计算为零；已付金额和可能退款／损失分别列出 | 零是有效结果，不回退旧金额；已有占用时走冲突处理 |
| 邮轮／专列多类型 | 各舱型／铺型原数量、新数量、单价及单位 | 按明细重算，不能用一个平均价覆盖所有舱型，也不能只更新合同总量 |

采购数量、未分配、分配到团期、订单占用是不同层次。已分配数量中已包含对应团期的已售占用，采购可分配量不能再重复减一次已售。免费退回和损耗也需说明是否已经从有效总量扣除，避免二次扣减。

邮轮采购按间／舱房，专列按铺／座，机票按座；人数换算、入住、儿童占位、实名分配等沿产品类型规则另核实，本方案不把采购三类视图视为全部售卖规则设计完毕。

**验收：** 100座已分配60，变为80时未分配为20；变为50需显示10座分配缺口，不能静默抹掉；无占用减为0时未付节点为0。两个舱型分别减量时数量、单价和总额都能对上。

### P09 团期结算与业务付款申请

页面：[团期结算](../merchant/tour/fulfillment-cost.html)、[付款申请入口](../merchant/tour/fulfillment-payment-apply.html)。角色：计调／成本经办。关联自27—自29、自31、自32。

**现状：** 付款申请菜单实际跳转同一页面的付款视图，并非另一套完整页面；已有批量申请、成本、预付分摊、二次结算。收入明细按62%/38%拆分并拼接订单号，是必须修改的错误示例。证据E11。

**结算详情：**

- 用明确的示例订单、应收调整、认款、退款及成本记录替代固定比例拆分；每行有来源编号、日期、公司、金额和状态。原型可用独立算例，但不能反推编出貌似真实的订单明细。
- 分开显示原成交金额、已生效增减项、当前应收、已确认收款、已退款、净收款、未收金额、已确认成本。收入确认金额和业务毛利按确定口径展示，未定项标注待确认，不把实收直接当收入。
- 成本按供应商、服务范围／成本类别、数量、原币、汇率、本币、确认状态和来源显示；地接、酒店、机票等多供应商分别承接，产品提供公司不成为所有外采费用的默认收款人。
- 结算提交前核对缺失依据和差异；未收齐尾款或未付款不自动等于不能做业务结算，是否阻断要依据批准条件。

**二次结算：** 保留已有入口；展示原结算号及版本、本次新增应收／成本／更正、调整依据、本次差额、调整后累计结果。原结算只读，审批退回只影响本次调整；不能将二次结算再复制整团全部金额。

**付款视图：**

- 业务经办按供应商、团期／项目、成本类别、可申请状态筛选成本明细，选择多项后预览分单。全团未最终结算也可在单项成本满足批准条件时发起；“录入了成本”不等于已批准可付款。
- 批量申请按付款公司、供应商、币种及有效协议等必要条件分组，不把不同公司／币种简单合成一个金额；显示已付、已申请占用、可用预付抵扣及本次申请，防重复。
- 提交后显示申请记录和审批阶段，财务复核／执行入口进入对应财务页面；不要在业务成本页显示“付款完成”。

**验收：** 两笔明确订单合计10万元、已生效减少5000元时，当前应收为95000元；已收10万元、已退5000元时净收款95000元，退款不再额外扣一次收入。原结算后补成本3000元，本次只结算差额3000元并保留原结果。

### P10 财务承接：账单、预付、付款和汇率

页面：[供应商账单](../merchant/finance/finance-supplier-bills.html)、[付款申请](../merchant/finance/finance-payment-apply.html)、[预付管理](../merchant/finance/finance-prepayment-offset.html)、[业务结算](../merchant/finance/finance-settlement.html)；配置参考[财务设置](../merchant/finance/finance-currency.html)。角色：财务。关联自23、自27—自31。

**账单核对：** 当前确认挂接／核对处理中存在把供应商账单金额写为系统成本、将差异置零的逻辑。改为并排展示业务确认成本、供应商申报额及差异；挂接只建立对应关系，不确认金额相等；差异经退回补成本、补资料或批准调整处理后再确认。示例：业务成本80000元、账单82000元，应保留2000元差异及处理记录。

**预付管理：**

- 复用现有预付账户／抵扣能力，明确纯预付可暂不绑定团期，大额预付须有供应商、付款公司、协议、币种、用途及批准依据；后续在实际成本或结算中选择抵扣。
- 详情显示已付、已抵扣、冻结／申请占用、可用余额；一次多团抵扣须展示每团金额、成本依据和合计，不能超过同一可用余额，也不能把预付款再次作为成本增加。
- 转用记录明确原用途、目标用途、金额、原因和批准结果；跨公司／跨币种的调拨与换汇不能默认等同同账户内部改用途，按待确认政策处理。

**付款申请与业务结算：** 承接业务申请来源、供应商有效协议、账期和收款账户审核结果。预付申请与成本付款分别显示依据；新申请未批准不改变已付结果。原供应商详情保留使用，供应商列表继续维持用户回撤后的状态。

**币种与汇率：** 保留原币金额、币种、折算本币金额；补汇率来源／日期／采用值／审批依据，采购估算、申请折算与实际支付记录分开。汇率缺失不能按1处理，未批准算法不能自动形成汇兑差额记账。具体来源、时点、费用承担和核算方法见第六节。

**本期不扩改：** 银行接口、自动付款、回单核销或NC推送逻辑。NC是现有财务核算系统，业务批准结果由原财务流程承接，本方案不另造核算闭环。

### 应保留的边界

- 供应商列表维持用户回撤后的原状，已有供应商详情与审批承接保留；自营页面选择公司协议时使用这项成果，不恢复此前列表改造。

- 团期订单独立；产品分析沿数据中心现有菜单和只读原则；并行门店专项不动。
- 邮轮、专列保留类型区别；自由行和单项服务不因自营共用脚本就被强套团期／领队结构。
