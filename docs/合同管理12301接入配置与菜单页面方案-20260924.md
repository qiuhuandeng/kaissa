# 合同管理12301接入配置与菜单页面方案

日期：2026-09-24。状态：第1步配置、第2步销售办理及第3步审批／变更／归档原型已完成。用户明确以原型页面功能完整为目标，后端接通不在本任务范围。验收见[第1步](合同12301配置原型第一步实施验收-20260924.md)、[第2步](合同12301销售办理原型第二步实施验收-20260924.md)、[第3步](合同12301审批变更归档原型第三步实施验收-20260924.md)。

本版回应用户“只知道要接12301，希望明确如何接、如何配置和使用、在哪个菜单页面增改”的要求。用户补充：目前没有登录网址或合作方资料，先完成方案。本文是合同工作线最新方案，接入方式仍待平台资料核实；不要求用户先理解技术参数，不重新启动平台选型。

## 一、结论与接入方式

建议采用“本系统管理订单和合同办理，12301承接其开放的签署及监管服务”的方式。销售日常在本系统核对、送审、发起及查结果，游客在平台提供的签署页面完成签约，管理员负责平台开通和授权配置。

目前只能确定接入目标，不能宣称已经取得接口。先核实公司取得的是完整电子合同服务，还是仅合同编号／备案接口；如果只有备案接口，尚缺正式签署能力，必须由平台明确现有签约服务的衔接方式，不能在原型中用“已签署”补齐这一环。推荐先核实12301现有签署能力的直接接入，不预设另购一家电子签服务。

正式使用时的业务路径建议为：

**订单资料 → 本系统合同草稿与预览 → 按规则内部审核 → 正式提交平台／发起签署 → 游客及我方完成平台要求的签署 → 核对签署、备案和文件结果 → 订单展示合同覆盖。**

本地生成草稿与平台创建合同必须分开。在确认现行接口行为前，将可能发送短信、占用正式编号或启动签署的调用放在“发起签署”步骤，不能在销售点预览或内部审核前调用。若平台还要求审核，单独显示“平台审核中”，本系统审核通过不能冒充平台审核通过。

本次范围为公司与游客／企业客户的旅游销售合同，不将供应商采购协议、劳动合同或全部企业协议自动纳入12301。

## 二、公开资料已确认什么、尚未确认什么

文旅部政务服务门户提供全国旅游监管服务平台及旅行社入口，开通核实应从该官方入口或公司已确认的服务联系人开始，不依赖旧教程中的邮箱、域名或承诺时限。[文旅部政务服务门户](https://zwfw.mct.gov.cn/)

12301公开操作手册包含多人签署、企业授权代表签署、补充协议、合同审核及签章备案；描述了创建合同后向游客发送短信。因此这些并非凭空设想的业务功能，但手册是平台网页操作说明，不等于这些能力全部向本项目开放。[12301电子合同和权限系统操作指南](https://static.12301.cn/econtract/doc/旅行社电子合同和权限系统操作指南.pdf)

监管统一编号、电子签署和签后备案是不同事项，应分开承接。[文旅部《旅游电子合同管理与服务规范》解读](https://zwgk.mct.gov.cn/zfxxgkml/zcfg/zcjd/202310/t20231011_949067.html)

尚未取得：本公司授权范围、现行接入申请要求、接口文档、测试方式、收费约定、各接口开放能力与实际返回样例。具体认证方式、签署渠道、时效、补充／解除及企业合同支持范围均以这些资料为准。不要把原型中已写的微信、邮件、自动盖章、回调或到期重发当成平台承诺。

## 三、先去哪里开通，再由谁配置

| 顺序 | 谁办理、在哪里 | 需要完成什么 | 办完后得到什么 |
|---|---|---|---|
| 1 | 公司合同负责人，在官方旅行社平台或向已核实的服务联系人办理 | 核对已有旅行社账号、经营公司、许可证、分社／门店关系和合同使用情况，优先复用已有资质 | 确定有哪些签约公司、谁管理账号、目前采用何种合同服务 |
| 2 | 公司平台管理员，在12301侧办理 | 按平台当前流程完成企业资料、电子合同用章及相关账号权限；核实原有授权能否给新系统使用 | 企业及用章可用的确认依据，不是上传印章图片就视为开通 |
| 3 | 公司负责人配合开发方，向平台申请系统对接 | 说明凯撒系统、签约公司、业务范围和所需功能，取得现行接口资料及开通结果 | 接入凭据、服务范围、测试安排及技术联系人；是否分公司独立申请由平台确定 |
| 4 | 技术管理员，在集团后台“系统配置 → 接口配置” | 配置连接，关联各签约公司及可用授权，核实查询、签署、备案和文件能力 | 可核对的接入状态；连接成功不等于公司可以签约 |
| 5 | 公司运营／法务及审批管理员，在业务端设置与审批页面 | 配置模板、附件、适用规则、审批流程；门店只选择获准范围 | 销售打开订单时能得到正确公司、合同模板和处理规则 |
| 6 | 业务及技术共同在获准测试方式下验收 | 完成一份完整合同，再核对多人、补充协议、失败、超时、文件和多公司隔离 | 验收通过后开通对应公司的正式使用，保留操作记录 |

业务负责人提供公司清单、现有合同样本和平台联系人即可；申请材料、参数配置和联调由技术人员协助完成。实际手机号接收短信、正式签约等动作必须纳入获准测试安排。

## 五、按页面说明怎么配置、具体增改什么

### P01：接口配置——接得通、哪家公司能用

现状：已有“合同签章”面板，仅含通用接口地址、应用编号、默认印章和接收结果地址，顶部固定显示正常，测试可直接提示通过。这不能说明12301已接通。

**连接配置子Tab：** 显示服务“12301电子合同”、当前接入阶段、平台确认的服务能力、接口版本及技术联系人。提供保存、核对连接、查看结果。没有资料时显示“待开通／待配置／未验证”，原型测试必须标记演示；成功时记录检测时间、实际检测项目，不把网络可达等同签约可用。

技术管理员专用区按平台文档填写测试／正式环境（若平台提供）、接口地址、接入编号及认证凭据；需要平台通知结果时才显示相应地址。凭据与销售页面隔离，已保存值不作为普通业务字段展示。不要把平台网页登录账号密码等同接口凭据。

**公司签约配置子Tab：** 一行一家实际签约公司，展示公司名称、许可证、平台企业关联、电子合同用章、授权范围及可用结果。点击“配置”打开当前公司的抽屉，选择其可用接入授权、适用组织／门店和经办人关系，查看平台审核要求及支持模板范围。凭据可能覆盖一个或多个公司，以平台授权为准；不能假定全集团共用一个账号或一个章。涉及平台经办人账号的要求，按现行接口确认后关联，不先给每名员工复制一个平台账号。

公司、模板、规则三项必须分别可用；任一不足就指出缺项。平台印章的申请／备案优先在平台完成，本系统读取或登记核验结果及证据；不提供一个上传PNG图片便“生成有效电子章”的假流程。

**对接记录子Tab：** 技术管理员按公司、合同、时间、业务步骤和结果查创建、签署查询、备案查询及文件获取记录；异常详情展示最近结果、原因、已核对情况及允许的处理。超时先查询，未经确认不再次创建正式合同。销售只在合同详情看业务可理解的原因，不看密钥或原始请求数据。

### P02：组织架构——公司资料只维护一次

在主体公司资料及编辑入口补旅行社许可证号、签约联系地址和电话等模板必需资料，复用现有公司全称、统一社会信用代码及法人。合同使用的投诉联系资料按正式模板要求维护。

平台企业关联、用章及授权结果在公司详情只读展示，去P01办理配置。经营公司／分支机构与实际签约公司分别表达：门店名称不能自动作为有资质的签约公司，集团也不能自动成为全部合同签约方。

### P03：合同模板——确定用什么合同、谁可以用

保留现有模板列表及编辑页面，增加或完善：适用签约公司、业务范围、客户类型、平台合同类型和版本、必需签署方、允许的多人方式、条件附件、有效日期与启停状态。

原来的“12301映射”改成可核对的对应关系与检查结果。哪些采用平台标准文本、哪些允许自定义条款或上传文件，必须区分，不能本地编辑任意条款后直接标“平台已匹配”。接口字段对应等内容留在管理员配置区，销售只看到合同名称、版本和适用条件。

补“示例预览／检查”入口，使用明确示例核对正文、行程、费用及附件。正文引用本次固定版本，停用模板只限制新合同，不破坏旧合同查阅。企业旅游合同可配置企业授权代表方式；是否覆盖具体MICE定制文本由平台及法务确认。

### P04：基础参数——确定什么时候允许签

新增“合同规则”分类及配置抽屉，不另建“合同设置”菜单。每条规则明确适用公司、业务类型、渠道／门店范围、启用日期及负责人。配置内容为：

- 允许生成草稿的订单阶段，以及发起签署前需要满足的订单、游客和行程条件。
- 是否要求内部审核、引用哪条已启用的合同审批流程；审批人维护仍在P08，不在此再维护一套。
- 发起签署的付款条件：按批准政策选择先签后收或引用已配置的付款节点，不默认全款，也不将“先交团费”当作无金额条件的有效规则。
- 默认合同模板选择范围、允许的签署方式；规则要求不能超出P01授权和P03模板能力。

公司规则作为基准，门店只能在授权范围内引用已批准的差异规则；同一订单匹配多条矛盾规则时提示管理员处理，不默默选择一条。未获批准的政策显示待确认，不作为正常可用规则。

### P05：门店销售设置——门店选择获准的公司和规则

既有“默认签约主体、合同模板、合同控制”升级为可核对的选择：可用签约公司、适用模板、合同规则、是否允许本店发起签署。禁用或未授权项不能选，已失效的旧选择必须显示原因，不能悄悄换成另一家公司。

详情“销售与合同”只读显示这些配置及生效情况。不在门店重复保存平台凭据、印章或一套自由付款规则。原收付款、保证金、预存等财务设置不改。

### P06：订单列表和详情——销售从订单开始

保留订单入口。列表的生成／查看合同动作按订单及合同阶段显示；新建草稿必须带入当前订单，不能无关联随意填写金额和游客。

订单详情的合同区补“签约准备”：签约公司、适用模板、必要游客资料、合同附件及本单签约条件。缺项提示对应来源及处理入口，销售补游客资料，模板问题交配置人员，金额或行程不在合同页另造一套。

合同摘要分别显示有效主合同份数、覆盖游客／应覆盖游客、必要签署完成情况和当前约定金额；主合同、补充协议和历史版本分组。3人共签1份要显示覆盖3人；主合同1万元、已确认生效的增补1千元，当前约定金额为1.1万元；待签变更不提前覆盖原约定。提供准确进入本订单合同的入口。

### P07：合同管理——销售的日常办理页

**列表：** 按主状态组织，主合同／补充协议／解除文书与多人合签／按人分签分开；修复日期搜索，支持订单、客户、合同编号及签约公司查询。主状态一个，签署进度和备案异常用简短文字，完整原因放详情。固定右侧操作列，长表在容器内横向滚动。

**合同草稿／生成抽屉：** 核对订单及签约公司、游客及实际签署人、金额分配、正文与附件。提供保存草稿、完整预览和提交审核；规则允许无需内部审核时进入待签署。原“订单变量”改为“合同内容”或“订单信息”。此步不承诺已向12301创建正式合同。

**发起签署／签署进度抽屉：** 明确本次文件版本和需要签署的人员，发起前重新检查公司、模板、审批和签约条件。显示提交中、平台待审核（若要求）、已取得签署入口、部分完成、全部完成或失败。二维码／链接按平台返回展示；重发通知与重新创建合同分开，不能每次重发都创建新合同。签署短信等渠道按实际支持提供，不默认勾选微信、邮件。

**合同详情抽屉：** 显示签约双方、订单／项目、正文附件、逐方签署、我方签章、监管编号／查验、备案结果、文件与历史记录。签署成功与备案成功分别展示；无结果显示待核对，不能点击一次就造成功。文件能实际查看／下载，有明确待签稿、正式签署版及历史版区别。

**变更／解除抽屉：** 引用已确认的订单或售后调整，展示变更前、调整额、变更后与受影响游客；选择补充协议或平台允许的重新签约方式，重新审核及签署。新增版本不继承旧签名，也不直接替代原有效约定。对未签撤销、已签协商解除、其他依法处理分别说明依据和平台结果；内部审批通过不直接标已解除。原合同及附件保留。

**企业归档抽屉：** 保留已有线下上传、双方盖章和授权核对。适用电子模板及公司授权均可用时可走电子签约；否则按批准方式线下办理。销售提交、审批人审核、归档结果分开；替换文件未审核通过时保留旧有效版本。

发起签署、编辑、详情等按主状态固定出现；催签、联系客户等过程动作不进入列表操作列。低频变更可统一放详情主入口，列表不再并排放多套补充／新版本按钮。

### P08：审批中心——谁审核、审核通过后做什么

审批配置增加或细化合同首次签约、合同变更、撤销／解除、企业线下归档事项的流程，按公司和场景配置是否适用、审批岗位和退回要求。不是规定所有合同都必须走相同审批，也不是让销售逐单选择是否审核。

待我审批及审批详情展示本次版本、签约公司、游客范围、正文／附件、变更对照和来源依据。通过只表示本次内部申请通过，后续等待平台受理、必要签署或归档；退回要能回到正确草稿修改。若审批由致远等外部系统执行，既有审批中心承接其流程及结果，不另立一套审批引擎。

修正当前合同作废样例中“原合同不可下载”的说明，改为历史文件按权限可查、不能继续用于新的签约。平台另有审核时，在合同详情显示外部审核状态和处理入口；能否通过接口审核待核实，不演示未经授权的自动放行。

### P09：售后与单团项目——提供来源，办理仍回合同

售后详情增加或整理“合同处理”区域：关联原合同、已确认的游客／日期／金额变化、建议处理类型及进入对应合同的入口。售后通过不直接视为合同解除，也不因合同解除自动执行退款。

项目详情的“项目合同／企业合同”明确签约方式、企业客户、授权代表、项目确认金额和对应模板。已有线下文件维护可保留，审核统一承接P08；电子签署进入P07。移除按MICE类型一律固定线下的判断，也不把所有企业服务合同强行纳入旅游电子模板。

### P10：权限和操作审计——控制谁能做什么

后台角色补12301连接、公司关联和对接记录权限；业务角色分别配置合同查看、生成、发起签署、文件下载、变更／解除申请、模板维护和审批权限。按公司、门店／部门、本人范围控制可见合同，不能共享一个平台账号就默认可看全集团合同。

操作审计补连接／授权配置变更、模板版本、发起、变更、解除及敏感文件访问的记录；技术对接错误在P01查看。这里只补合同相关权限项及样例，不重构角色系统。

## 六、配置完成以后，业务人员怎么用

| 使用人 | 日常路径 | 操作结果 |
|---|---|---|
| 销售顾问 | 订单管理 → 订单详情 → 生成合同 → 核对及预览 → 按规则提交审核 | 得到与订单对应的合同草稿或待审核记录 |
| 审批人 | 审批中心 → 待我审批 → 合同事项 → 审核或退回 | 本系统记录本次版本的内部审批结论 |
| 销售顾问 | 合同管理 → 待签署 → 发起签署 | 正式提交平台，取得平台受理／审核／签署入口结果 |
| 游客或获授权代表 | 平台提供的短信链接／二维码等入口 | 在平台完成身份核验、查看全文及签署；不需要登录销售后台 |
| 销售顾问 | 合同管理 → 签署进度／详情 | 查看谁未完成、我方签章、备案与文件；异常按原因处理 |
| 销售顾问／项目负责人 | 订单或售后／项目确认变更 → 对应合同详情 → 变更或解除 | 产生独立变更办理记录，保留原合同及处理依据 |
| 技术管理员 | 接口配置 → 12301电子合同 → 对接记录 | 处理授权、平台异常和结果未知问题；不代替游客签字或业务审批 |

游客认证、手写签名及平台电子章不在本原型中自建；最多演示“打开平台签署页”的入口及结果返回。平台链接未提供前明确是演示，不绘制假扫码图当作可用链接。

## 七、验收和实施顺序

每一步只推进有边界的一组页面。用户已授权执行，随后明确目标为原型功能完整；三步均已完成页面与交互验收，当前原型按本方案收尾。

1. **配置原型：P01—P05及对应P10权限项（本轮已完成）。** 先让人能看懂如何开通、公司如何关联、模板与规则在哪维护。正常及未开通、缺许可证、公司不匹配、用章不可用、模板未支持、规则冲突都需可演示。
2. **销售办理原型：P06—P07（本步主流程已完成）。** 从订单草稿到发起、部分签署、完成、备案待处理和文件获取；验证不在预览／审核前通知游客，超时不重复创建。
3. **审批与变更承接：P08—P10剩余内容（已完成）。** 补审批退回、平台审核待处理、补充协议、解除、企业线下及替换版本；复核直接入口。多人覆盖、金额及旧版留存必须验算。
本工作线在第3步页面功能与交互验收后收尾。正式接口实施仅为未来开发参考，不属于本次步骤、不计为原型遗留缺口，也不以账号、接口或测试环境阻塞原型。

方案阶段已核对导航、相关源代码及公开资料，当时未改页面。用户授权后的第1步已修改10个HTML和配置专用共享资源，完成23组规则及31组浏览器检查；仍未使用公司账号或实际调用平台。历史功能缺口逐条证据见[前版11项核对](合同管理12301对接原型增改方案-20260924.md)，本版补齐前版未说清的后台配置、公司资料、规则入口、角色与平台审核边界。

试用收尾：已按菜单与样例完成试用并修复发现问题，见[试用修复验收](合同12301原型菜单试用与修复验收-20260924.md)。后续按具体业务反馈调整页面，无待实施第4步；账号与后端接通不属于本原型任务。
