# 业财场景确认手册00：编写规范与内容标准

版本：v1.0  
固化日期：2026年8月23日  
适用范围：后续全部《凯撒旅游全业务场景业财链路与结算核算确认手册》及其开发、测试承接文档  
规范来源：用户确认的场景账本要求、《业财底座01—07》及《业财场景确认手册01》的已确认格式

## 一、必须长期记住的工作目标

前置《业财底座01—07》解决的是系统底层规则是否完整、是否重复、是否矛盾；《业财场景确认手册》解决的是财务能否对一笔真实业务从头验算到底。

财务确认系统是否正确，必须能够回答：

- 某个客户通过哪个门店或渠道购买了什么产品；
- 合同由哪个公司签订；
- 客户把钱付给了哪个公司或平台；
- 产品由哪个公司组织和履约；
- 资源向谁采购、成本由谁承担、款由谁支付；
- 各法人分别形成多少应收、实收、预收、收入、成本、应付、预付、实付和内部往来；
- 业务结算后哪些余额应当为零，哪些余额可以正常保留；
- 哪些经济事项进入哪个法人对应的 NC 账簿；
- 业务系统、银行、往来单位和 NC 最终是否对平。

每个场景必须成为一本能从订单或合同开始，一直算到结算、NC 和期末余额的“小账”。文档同时作为财务确认材料、后端业务规则来源和测试验收依据。

## 二、强制使用业务和财务语言

文档面向业务、财务、产品、开发和测试共同阅读，必须优先使用真实业务或财务叫法，不造技术名词。

应使用：

- 客户应收、客户实收、客户预收、客户预存；
- 供应商实际成本、供应商账单、应付、预付、付款；
- 门店代收应缴、门店预存、门店分润；
- 渠道应收、平台佣金、平台补贴、平台结算差异；
- 内部应收、内部应付、内部结算、内部资金清算；
- 订单、团期、航次、班期、项目、营期、服务单、采购批次；
- 会计事项、会计日期、NC 凭证、对账、关账、冲销和跨期调整。

不得用不能被财务直接理解的抽象词代替真实关系，例如用“统一余额池”“交易中台对象”“结算引擎节点”“资金归集对象”等词掩盖谁欠谁、因为什么欠、余额是多少。确需说明开发实现时，放到后续技术设计，不进入财务确认正文。

## 三、文档组织原则

### 1. 按现实业务故事组织

不得按收款模块、应付岗位、门店页面、NC 模块或数据库对象组织主文档。必须按现实中发生的一笔业务组织，例如：

> 北京直营门店销售一个福建公司自营团，客户订单 100,000 元，先付定金 30,000 元、后付尾款 70,000 元；公司预付地接社 20,000 元，回团确认实际成本 60,000 元；最终分别计算收入、成本、毛利、应收、实收、应付、实付和 NC。

### 2. 区分完整主场景和变化分支

现有 86 个场景编码不得机械写成 86 篇平行文章。

- 完整主场景：从订单或合同开始，贯穿收款、履约、成本、结算、会计事项、NC 和对账。
- 变化和异常分支：在主场景对应节点说明一笔款多订单、多人付款、多付、退款、拒付、银行退回、补成本、坏账和跨期等变化。

86 个编码必须全部被承接并可追溯，但允许一个完整案例组合多个编码。

### 3. 客户链和供应商链独立

客户退款与供应商追款是两条独立链：

```text
客户应退、客户已退、客户未退

供应商应退、供应商已退、供应商未退

两者差额、承担主体、归属订单/团期/门店/责任部门或公司损失
```

不能因为供应商尚未退款就不确认客户退款责任，也不能因为客户退款尚未执行就不记录供应商应退款。

### 4. 多法人必须逐家算账

多主体场景不得只给集团合计。每个法人分别列收入、成本、应收、应付、实收、实付和期末余额，再列集团抵销和集团对外结果。

基本关系：

```text
内部提供方应收 = 内部接收方应付

内部提供方收入 = 内部接收方成本（按集团确认的同一内部结算口径）

集团合并经营结果 = 对外收入 - 对外成本 - 对外费用/损失
```

### 5. 业务结算不等于余额清零

业务结算确认的是本次应计入多少收入、成本、损耗、费用和调整。只要有真实依据且满足制度条件，下列余额可以在结算后正常保留：

- 尚未到期或已批准账期的客户应收；
- 尚未支付的供应商应付；
- 尚待后续订单使用或退款的客户预收、预存；
- 尚待后续服务冲抵或退回的供应商预付；
- 尚未完成划拨的内部代收代付往来；
- 有清楚原因和处理期限的银行、平台或内部在途款。

不得为了显示“已结算”而强制把真实余额改成零。

## 四、全业务场景覆盖要求

完整手册至少覆盖以下九组现实业务。具体案例可组合，但不得漏掉任何所列业务条件。

### 第一组：同主体直接销售

1. 标准跟团订单一次收清或分定金、尾款、补差收款。
2. 企业客户先出团后付款。
3. MICE 项目阶段收款和验收。
4. 一笔客户款支付多张订单。
5. 一个订单多个付款方。
6. 客户多付转预收或预存。
7. 已知客户但暂不明确订单。
8. 完全无法识别付款方和客户的来款。
9. 外币订单和外币收款。
10. 现金、POS、交款、缴存及长短款。

必须验证：

```text
订单金额 → 业务应收 → 到账流水 → 认款 → 收款单 → 应收核销
→ 预收/预存 → 收入确认 → 团期或项目结算 → NC
```

### 第二组：门店销售

1. 直营门店销售和现金收款。
2. 直营门店实收、POS 清算、银行入账长短款。
3. 加盟门店获客、总部直收、门店分润。
4. 加盟门店充值预存并按结算价下单。
5. 加盟门店代收客户款后上缴。
6. 加盟门店账期采购。
7. 集团内独立法人门店采购集团产品。
8. 门店订单退款并退回预存。
9. 门店月度对账、管理费、佣金和分润。

必须分别计算客户价、总部结算价、门店分润、门店预存、门店代收应缴、总部对门店应收或应付、门店期末余额和双方 NC 账套。

### 第三组：OTA 和外部分销

1. OTA 代收和月结，扣佣金后净额打款。
2. OTA 直接退款后向凯撒扣款。
3. 平台承担优惠或平台与凯撒共同承担优惠。
4. 外部分销商账期采购及逾期。
5. 支付平台拒付、强制退款和滚存保证金。
6. 平台账单、系统订单、银行到账差异。

必须证明：

```text
平台有效订单金额
- 平台退款
- 平台佣金
- 凯撒承担优惠
+ 平台承担补贴
- 拒付
- 滚存保证金
= 平台本期应汇款

平台本期应汇款 - 实际到账 = 平台结算差异
```

### 第四组：普通供应商成本和付款

1. 服务完成、账单确认、应付和付款。
2. 服务已完成但账单未到，按制度暂估。
3. 账单先到但业务事实未确认。
4. 一张账单跨多个团期、多张账单组成一个成本范围。
5. 预付后冲应付，预付多于最终应付时供应商退款。
6. 部分付款、分批付款、外币付款和银行退回。
7. 先票后款、先款后票。
8. 客户与供应商为同一往来单位时抵销。
9. 供应商押金和保证金。

必须持续区分：

```text
实际成本 ≠ 供应商账单 ≠ 应付 ≠ 付款 ≠ 发票

有效实际成本
= 实际成本原额 + 已确认损耗 + 成本增加调整 - 成本减少调整

应付未付余额
= 有效应付 - 付款核销 - 预付冲抵 - 供应商应退款抵减 - 已批准往来抵销
```

### 第五组：旅游专项产品

1. 邮轮包船/切舱的分批预付、销售、退舱和舱损。
2. 专列包列/包铺的销售、释放、铺损和成本分摊。
3. 团队机票切位/包机的押金、二押、尾款、出票和票损。
4. 包机或共享固定资源跨多个团期分摊。
5. BSP 散客票的订单、票号、日报、IATA 账单和付款。
6. B2B 航司平台充值、出票、退票和余额恢复。
7. 自由行采购批次向多个订单分摊成本。
8. 单项服务费与代收代付款分开。
9. 研学学校与家长混合付款。
10. MICE 阶段收入、阶段成本和追加服务。
11. 领队、导游、计调或项目经理借款、现场支出、报销和还款。
12. 共享资源跨团期分摊和调整。

邮轮、专列、机票等固定资源案例必须算出合同总额、分批预付、已售成本、可退资源、不可退损耗、最终账单、应付、预付冲抵、剩余付款、结算毛利和 NC。

### 第六组：集团多主体复杂交易

1. 同一法人不同经营单元协作。
2. A 公司销售 B 公司自营产品。
3. A 公司销售 B 公司包装的外部产品。
4. 航服公司向集团内产品公司供票。
5. 集团资金公司代业务公司收款或付款。
6. A 收款、B 履约、C 开票等主体不一致异常。
7. 独立法人门店采购集团产品。
8. 内部交易双方月份或汇率不同。
9. 体系外外采的主责方全额模式和代理方净额模式。
10. 内部产品结算与内部资金代收同时发生。
11. 集团内部月末对账和合并抵销。

### 第七组：客户售后和业务取消

1. 未收款减价/取消、已收款部分或全额退款。
2. 原路退款、退款转预存。
3. 同主体或跨主体转团、转款。
4. 客户退款同时向供应商追款，且二者金额不同。
5. 邮轮改退舱、专列改退铺、机票退改签和票损。
6. 取消出团、不成团、不可抗力。
7. 客户赔偿、事故理赔和保险赔款。
8. 退款执行或供应商付款后被银行退回。

### 第八组：团期、项目和业务结算

1. 普通团期正常结算，允许保留有依据的未收、未付和暂估。
2. 邮轮航次、专列班期、自由行订单、MICE 项目、研学营期和单项服务结算。
3. 供应商、OTA、渠道、门店和集团内部周期结算。
4. 已结算后补成本、客户退款或供应商退款。
5. 关账后跨期调整。
6. 应收、合同资产和长期预付减值。
7. 坏账核销和已核销款项收回。

### 第九组：NC、对账和关账异常

每个主案例尾部必须验证：

1. 业务单据生效但未满足入账条件。
2. 会计事项已形成但未生成凭证。
3. NC 推送失败、已接收未记账、已记账后发现错误。
4. 原期间已关账后的处理。
5. 业务系统与 NC 余额不一致。
6. 内部一方已入账、另一方未入账。
7. 银行与收款、账单与应付、结算收入成本与 NC 不一致。
8. 期末正常未收、未付、预收、预付。
9. 必须阻断关账和批准后可带入下期的差异。

## 五、每个案例的固定十段式模板

### 1. 业务故事与采用条件

说明谁买了什么、谁销售、谁履约、谁收付款，何时采用本场景，什么条件下必须换用其他场景。

### 2. 参与公司和责任

至少列明客户、产品、订单金额、销售主体、签约主体、收款主体、履约主体、采购主体、付款主体、开票主体、产品来源、主责方/代理方判断、结算对象和会计期间。

### 3. 金额条件

列出客户原价、优惠、补退差、有效交易金额、内部结算价、供应商成本、收付款计划、实际收付款、税费及期初余额。不得只给最终合计。

### 4. 主体和债权债务图

使用 Mermaid 同时画出业务结算关系和实际资金关系，节点使用真实业务名称，边上标明金额。不能只画页面或单据流转。

### 5. 按日期发生的完整链路

固定列出：日期、业务事实、形成的财务单据或数据、各余额变化、是否具备入账条件。必须覆盖订单/合同、收款、履约、成本、应付、付款、发票、结算和 NC。

### 6. 金额计算

逐步列公式，至少计算：

```text
客户有效应收
= 订单原始金额 - 客户优惠 + 补差 - 退差/取消

应收未收余额
= 有效应收 - 收款核销 - 预收核销 - 预存扣款 - 往来抵销 - 坏账核销

应付未付余额
= 有效应付 - 付款核销 - 预付冲抵 - 供应商应退款抵减 - 往来抵销

结算贡献
= 结算收入 - 结算成本 - 单列损耗 - 渠道/门店费用 ± 其他已确认调整
```

### 7. 各主体分别看账和资金结果

单主体列期末应收、预收、应付、预付、银行净变化、收入、成本和毛利。多主体必须并列每个法人和集团合并结果。

另列资金动作：付款方、收款方、应付金额、实付金额、未付或未清金额，证明业务已结算但资金可以尚未结清。

### 8. 发票、会计事项与 NC

按“业务事实 → 会计事项 → 核算主体 → 会计日期 → 入账条件 → NC 凭证类别 → NC 返回状态”描述。发票作为并行核对线，不能代替成本、应付、付款或收入事实。

正式科目编号、税码、辅助核算和凭证类别必须在取得凯撒 NC 资料并经财务确认后补入，不得虚构。

### 9. 结算和最终对账结果

至少列订单有效应收、客户实收、客户未收、实际成本、应付、实付、预收预付、内部往来、收入、成本、毛利、内部抵销差异、NC 未推送或失败金额和期末正常余额。

### 10. 财务确认问题与变化分支

把尚未取得的正式制度写成明确问题；列出退款、补差、多付、拒付、银行退回、补成本、跨期等变化应承接的案例或规则。不得把未确认政策伪装成已经确定的系统逻辑。

## 六、每个案例必须通过的检查式

```text
客户侧：有效应收
= 已核销收款 + 已核销预收/预存 + 已批准抵销/核销 + 期末待收

供应商侧：有效应付
= 已核销付款 + 已冲抵预付 + 已批准抵销 + 期末待付

资金侧：原始资金流水
= 已确认的全部资金分配 + 未认领余额 + 已确认退回/转用

经营侧：结算收入 - 结算成本 - 单列费用/损失
= 结算贡献

内部交易：内部提供方应收 = 内部接收方应付

集团合并：集团对外收入 - 集团对外成本 - 对外费用/损失
= 集团合并经营结果
```

任一公式不平，案例不得标记为财务可确认。

## 七、图表使用规则

每个主案例最多使用：

1. 一张主体与债权债务图；
2. 一张按日期的时间链路表；
3. 一张资金和余额结果表。

多法人场景可增加一张各主体损益和内部抵销表。图表必须帮助看清金额关系，不为装饰而添加。

## 八、与业财底座01—07的一致性规则

后续写作前必须读取本规范，并按需反查 01—07：

- 主体责任和主责/代理判断：底座01；
- 86 个场景和金额口径：底座02；
- 单据、核销和余额：底座03；
- 会计事项、会计日期和 NC：底座04；
- 对账、结算、关账和异常：底座05；
- 缺口和未决政策：底座06；
- 每个场景的主体—单据—余额—结算—会计事项—NC—对账承接：底座07。

若案例与底座冲突，不能静默选择一个版本。应先判断是案例错误还是底座规则需要修订，并同步修改所有受影响文档。

## 九、税务和 NC 的表达边界

在未取得正式资料前：

- 案例金额按含税业务金额展示；
- 说明需要拆分收入、税额、差额扣除和进项，但不虚构税率或金额；
- 不虚构 NC 科目编码、税码、辅助核算编码或凭证类别；
- 必须写清核算主体、经济影响、会计日期依据和来源单据；
- 对主责方全额收入、代理方净额收入和旅游服务差额计税分别判断，三者不得混为一谈。

## 十、完整性与验收要求

每次新增或修改案例后必须检查：

1. 35 个端到端案例目录是否完整，86 个原场景编码是否全部覆盖。
2. 场景名称、编号和口径与底座02、07是否一致。
3. 每个案例是否具备固定十部分，不能只写业务流程或最终分录。
4. 所有金额能否从原始数据逐步算到期末余额。
5. 多主体内部应收应付、内部收入成本是否成对。
6. 客户侧、供应商侧、渠道/门店侧和资金侧是否分别核对。
7. 结算后保留余额是否有真实原因、责任人、后续处理和账龄。
8. NC 推送失败、冲销、跨期和关账后的处理是否有承接。
9. 是否使用业务和财务语境，是否出现不必要的技术抽象名词。
10. 尚未取得的财务、税务、NC 制度是否明确标记“待确认”。

## 十三、订单金额颗粒度和多主体结算深化规则

后续所有订单案例，尤其是“一个主体销售另一个主体产品”的案例，不能只列客户售价、内部结算价和外部成本三个结果数。必须继续拆到以下层次。

### 1. 每一个金额都要回答五个问题

```text
这笔金额因什么业务产生
谁应当支付
谁应当取得
计算依据来自哪份合同、产品约定、活动规则或审批结果
最终在哪张订单、团期、结算单、收付款和 NC 事项中承接
```

不能存在只有“结算价”“返点”“优惠”名称，却无法说明付款方、收款方和依据的金额。

### 2. 一张订单必须保留全部价格层次

至少区分：

- 对外展示价；
- 客户合同金额；
- 客户应付金额；
- 客户现金实付金额；
- 优惠券、积分及其他抵扣；
- 每项优惠的承担公司、部门、渠道或供应商；
- 销售方可取得的销售差额、佣金或分润；
- 销售主体与产品主体之间的结算金额；
- 产品主体应取得的内部结算金额；
- 采购或平台管理部门按约定取得的返还；
- 外部供应商最终应付金额；
- 各法人收入、成本、毛利和各部门管理贡献。

名称相同的“结算价”必须同时写明交易双方，例如“A 公司应付 B 公司的内部结算金额”“B 公司应付外部供应商的采购结算金额”，不得只保留一个无交易双方的结算价。

### 3. 跨法人业务必须形成三段可独立追溯的订单关系

以 A 销售 B 外采产品为例：

```text
A—客户：客户销售订单和客户应收收款
A—B：内部采购/供应订单和双方内部应付应收
B—外部供应商：外部采购订单、成本、应付和付款
```

三段关系使用同一业务关联号连接，但各自合同对方、订单金额、应收应付、收付款、发票和 NC 主体不同。系统采用一张还是多张数据表不属于财务确认内容，财务确认的是三段关系不能混账。

### 4. 全额上缴后返还和扣除后净额上缴必须分开

门店、代理人或销售渠道可能采用两种资金方式：

- 全额上缴后返还：客户款全额进入收款主体，再根据结算结果向销售方支付佣金或差额；银行有一笔全额流入和一笔返还流出。
- 扣除后净额上缴：销售方先保留协议金额，只把净额汇给收款主体；应收通过“净到账 + 已批准佣金/差额抵销”结清，不能虚构全额银行到账。

订单必须保存采用方式、规则来源、销售方应得、实际保留/返还和未清金额。

### 5. 公司法定利润和部门管理贡献必须分开

跨法人交易按每个法人确认收入、成本、往来和 NC；同一法人部门之间的销售差额、采购返还和员工奖励只用于内部经营考核，除非真实形成费用或人员应付，不得伪造法人间收入应付。

```text
公司法定经营结果 → 进入 NC
部门管理贡献 → 管理报表和绩效分配
员工奖励 → 经批准后形成薪酬或费用事项
```

### 6. 团期归属与付款批次不能混为一谈

- 多个销售订单可以归入同一产品主体、同一出发日期的同一团期结算；
- 不同出发日期或不同履约团期不能为了操作方便合并成一个新团期；
- 多个团期的应付可以在付款时批量支付，但每笔付款分配必须回到原团期和原应付；
- 销售主体团期号、产品主体团期号和外部供应商团号可以不同，但必须保留一一对应或明确分配关系。

### 7. 业务结算、双方对账、应付成立和付款必须分开

产品主体完成团期结算，是确认收入、成本和经营结果；A、B 双方对账，是确认内部结算金额；内部应付成立，是 A 已承担对 B 的付款义务；付款申请和银行付款，是后续资金执行。

正常无差异业务可以按集团批准规则在回团后自动发起结算或生成对账结果，但不能因自动化而跳过金额来源、异常冻结、付款审批和 NC 检查。是否需要销售方逐单确认、回团后几天自动结算、争议金额是否冻结，必须作为集团制度参数确认，不得由案例自行假定。

## 十四、参考《表结构》后的场景分析模板升级

后续新增或重写详细案例，统一采用 [财务场景分析与案例编写模板](第三方模型项目资料/06-财务场景分析与案例编写模板.md)。该模板参考项目提供的《表结构 (1).docx》，以“场景设定—价格拆解—分阶段流程—公司和部门结果—合同资金发票会计核对”为主线。

本文件第五部分的固定十段式仍用于既有手册的目录追溯；新详细案例按以下十三部分展开：

1. 场景在业务全景中的位置；
2. 业务场景设定；
3. 参与方、合同关系和责任；
4. 完整价格体系和成本结构；
5. 业务关系、债权债务和实际资金三张图；
6. 分阶段完整流程；
7. 每阶段余额变化；
8. 团期、项目及各往来方结算；
9. 各法人公司和部门结果；
10. 合同、业务、资金、发票和会计五条线核对；
11. 会计事项和 NC；
12. 最终对账和反算检查；
13. 变化分支、备选方案和财务确认结论。

参考文档的表达结构可以采用，但其中具体会计结论不能直接视为凯撒已确认政策。所有金额必须通过公司结果、部门抵销、资金反算和跨主体往来四重检查；同一笔供应商扣点、管理费、优惠或佣金不得既冲减成本又重复确认收入。
