# 财务流程01：收款应收与退转流程

业务确认稿 v1.0  
编写日期：2026年8月1日  
面向角色：销售顾问、门店销售、财务收款岗、认款复核岗、应收会计、退款会计、出纳、财务主管

**核心目标：** 让客户从下单、付款、认款、合同、退款、转款到财务入账的全过程都在线上可追溯。销售只负责说明“这笔钱属于哪个客户、哪张订单”，财务负责确认“钱是否真实到账、能否入账、差额如何处理”。系统要减少线下查流水、发截图、手工表格认款，同时保证未到账、未复核、跨主体、重复认款等风险不会进入财务账。

## 本文件怎么读

- 财务收款岗和认款复核岗重点看第一至第六部分，确认到账流水、认款、无流水收款单、现金、外币、OTA 和易宝静态码处理。
- 应收会计重点看第二至第四部分、第七至第八部分，确认订单应收、阶段应收、预收和预存如何形成。
- 退款会计和出纳重点看第九至第十一部分，确认退款、转款、凭证和 NC 如何处理。
- 销售和门店只需重点看第四部分、第五部分、第九至第十部分，确认自己怎么发起认款、退款和转款。

## 第一部分：整体业务流程概览

### 一笔客户收款在新系统里的完整链路

客户报名或签约前，系统先根据订单、项目或门店业务生成应收。客户付款后，钱先进入公司银行账户、聚合支付账户、平台账户或现金账户。系统把这些到账记录汇总到资金流水池。销售在订单上发起认款，告诉系统这笔到账流水对应哪个订单、哪几个客户、哪几笔应收。系统先自动匹配，无法确认的再交给财务复核。

完整链路如下：

> 订单/项目生成应收 → 客户付款 → 到账流水入池 → 销售认款或系统自动认款 → 系统匹配流水和应收 → 财务自动确认或人工复核 → 应收核销 → 合同条件判断 → 生成收款凭证 → 推送 NC → 报表对账

如果客户后续退团、改期、换团或转给其他人，流程不再回头改原收款，而是从订单售后发起退款或转款：

> 售后申请 → 选择原收款 → 审批 → 财务退款/转款执行 → 应收冲销或新订单认款 → 凭证和 NC → 报表留痕

这个流程的关键不是“销售提交了一张收款单”，而是系统最终能回答四个问题：

- 钱是否真的到了公司账户。
- 这笔钱被认到了哪个客户、订单、合同或项目。
- 如果退款或转款，原收款和新去向是否能追溯。
- 财务凭证和 NC 是否只基于已确认的资金事实生成。

## 第二部分：下单后应收如何形成

### 标准散客和门店订单

销售或门店完成产品预订后，系统根据订单成交价、人数、付款计划和费用项目生成应收。普通跟团游可能是定金加尾款，邮轮可能按舱型、成人儿童、港务税费拆分，自由行或单项服务可能直接生成全款应收。

订单应收至少需要让财务看到：

- 客户是谁，订单号是什么。
- 产品、团期、航次或项目是什么。
- 本次应收金额、已收金额、待收金额。
- 应收来源是团款、补差、升舱、单房差、签证保险、单项服务还是其他费用。
- 财务主体和收款主体是谁。
- 收款到期日和当前收款状态。

销售可以看到业务需要的收款计划，财务可以从应收管理看到完整应收和认款记录。

### 项目团、MICE 和单位客户

单团、MICE、研学或企业客户通常不是一次性收全款，而是按合同节点收款。例如先收项目首款或确认款，再收进度款，最后收尾款。系统应按项目阶段生成应收，而不是只用一个订单总额。

业务流程是：

1. 项目负责人建立项目订单，录入客户、项目总价、收款计划和确认材料。
2. 系统按阶段生成应收，例如首款、进度款、尾款、追加服务款。
3. 客户付款后，销售认款到具体阶段。
4. 财务复核时可以看到该阶段对应的合同、客户确认方案、确认金额或内部审批依据。
5. 项目结算时，系统按阶段还原收入和已收款。

如果一个单位客户同时替多个客人付款，系统不能只按“一个订单一个付款方”处理。一个订单里可以有学校付款、学生个人付款、家长代付等多付款方场景，财务最终应能追溯每一笔钱对应的客户或客人。

## 第三部分：客户付款的几种业务场景

### 场景一：订单活码支付

订单活码是最自动化的场景。系统为订单生成专属付款码，客户扫码付款时，支付平台会把订单号、金额、支付流水实时回传系统。系统知道这笔钱属于哪个订单，所以可以自动生成认款并核销应收。

这类收款的业务结果是：

- 销售不需要再手工上传付款截图。
- 财务不需要逐笔查流水。
- 订单应收自动减少。
- 如满足合同放行规则，合同入口自动放开。
- 收款凭证按已确认收款生成。

### 场景二：固定码、门店码或工位码支付

固定码只绑定公司主体、门店或收款账户，不绑定具体订单。客户扫码后，系统知道钱到了，但不知道属于哪张订单。

流程是：

1. 客户通过固定码付款。
2. 支付平台把到账流水写入资金池。
3. 销售或门店在收款认领页面搜索这笔流水。
4. 销售选择对应订单，填写本次认款金额，上传客户付款凭证或说明。
5. 系统校验金额和应收余额。
6. 匹配无误的自动确认，存在付款方不一致或差额的进入财务复核。

固定码适合门店现场收款，但必须通过认款把资金和订单绑定，否则财务只能看到一笔未识别流水。

### 场景三：客户对公银行转账

单位客户、单团客户、渠道客户常用对公转账。系统处理方式取决于银行是否直连。

如果银行已做银企直连，客户转账后，流水会自动进入资金池。销售认款时可以直接勾选流水，系统按流水号、付款方、金额匹配。

如果银行未直连，财务需要从银行后台导出流水并导入系统。流水导入前，销售可能已经拿到客户付款截图并急着出合同，这就进入“无流水先做收款单”的特殊模式，见第五部分。

### 场景四：现金收款

现金不天然产生银行流水，但系统不能让现金收款停留在线下。门店或柜台收到现金后，应登记一条现金收款记录，相当于系统里的现金流水。

现金收款建议按以下流程处理：

1. 销售或门店登记现金收款，选择订单或客户。
2. 系统记录收款人、门店、金额、时间和现金凭证。
3. 出纳或财务确认现金实缴。
4. 财务确认后才核销应收。
5. 未实缴或未复核的现金，不生成正式入账凭证。

现金收款不是银行流水，但它必须像银行流水一样有收款记录、复核记录和后续去向。

### 场景五：外币收款

会展、MICE 或境外项目可能收到外币。外币收款需要同时记录原币和本币。

系统处理时应记录：

- 原币币种和金额。
- 到账账户。
- 到账日期。
- 采用汇率。
- 折算人民币金额。
- 手续费。
- 汇兑差额。

如果银行已经把外币折算成人民币入账，就按人民币流水处理；如果公司实际收到外币，则认款和退款都要保留原币口径。销售不能自行调整汇率差异，汇兑损益由财务处理。

### 场景六：OTA 和平台月结

OTA 月结不是普通“客户付款后马上到账”的流程。携程、飞猪、小红书等平台可能先确认订单、先占位或先要求合同，平台到月底或次月才打款。有些平台还会在结算时扣服务费、佣金、退款和活动差额。

OTA 月结流程应单独处理：

1. OTA 订单进入系统，形成订单应收或渠道应收。
2. 订单是否可以先出合同，按 OTA 专项规则判断，不套普通收款规则。
3. 平台出月结账单后，业务或财务上传账单。
4. 系统按平台订单号匹配系统订单。
5. 平台一笔打款可以拆到多个部门、多个订单。
6. 财务核对平台实结金额、扣费、退款抵扣和系统应收。
7. 核对完成后，系统核销应收并生成凭证。

OTA 的核心不是“销售上传水单”，而是平台账单、订单明细和最终到账之间要能对清楚。

### 场景七：易宝台牌和第三方静态码

易宝台牌、部分第三方静态码可能存在交易号不唯一的问题。客户截图上的单号、平台导出的商户单号、银行或平台到账单号可能不是同一个编号。

系统要按以下原则处理：

- 如果能取得唯一交易号，销售认款和平台流水导入都使用该交易号匹配。
- 如果只能取得非唯一商户单号，系统只能辅助匹配，不能自动确认。
- 财务复核时按金额、时间、付款方、平台商户信息和截图判断。
- 平台退款如依赖账户余额，财务需预留退款资金或制定归集规则。

## 第四部分：销售如何认款

销售认款的本质是告诉系统“这笔钱属于谁、认到哪里、认多少”。销售不决定财务入账，只提交业务归属。

### 普通认款流程

1. 销售进入订单详情或收款认领页面。
2. 系统展示订单应收、已收、待收和付款计划。
3. 销售搜索到账流水，可以按流水号、金额、付款方、交易号、到账日期查找。
4. 销售选择流水，填写本次认款金额。
5. 销售上传付款凭证，补充付款方、交易号或代付说明。
6. 系统校验金额不能超过订单应收余额，也不能超过流水可认余额。
7. 系统提交认款单，进入自动确认或财务复核。

### 一笔款分配到多个订单

客户可能一次转一笔总款，用来支付多个订单。系统不应要求财务把一笔银行流水拆成多条假流水，而应在认款时拆分。

例如客户一次转账 100,000 元：

1. 销售选择这一笔 100,000 元流水。
2. 分配给订单 A 30,000 元、订单 B 40,000 元、订单 C 30,000 元。
3. 系统记录原流水已认 100,000 元，可认余额为 0。
4. 三张订单分别生成认款记录和应收核销记录。

如果本次只认 60,000 元，剩余 40,000 元保留在资金池中，后续继续认款或转预收。

### 一个订单分多次收款

一个订单可以多次收款：定金、尾款、补差、升舱、单房差、单项服务等都可以形成不同应收和认款记录。订单详情里应看到每笔收款的状态，而不是只看到一个总已收。

财务需要能反查：

- 认款单号。
- 对应到账流水。
- 本次认款金额。
- 付款方式。
- 财务确认时间。
- 是否已生成凭证。
- NC 状态。

## 第五部分：无流水先做收款单

在未实现银企直连或财务尚未导入流水的情况下，销售可能已经拿到客户付款截图，但系统资金池暂时查不到流水。这个场景必须在业务效率和财务安全之间做平衡。

建议系统支持“先做收款单、后关联流水”的模式，但收款单在未关联真实流水前只能是待核对状态。

业务流程如下：

1. 客户付款后，销售拿到付款凭证。
2. 销售在订单上提交收款单，填写金额、付款方式、付款方、交易号或截图。
3. 系统标记为“待核对”，不核销应收，不生成凭证，不推送 NC。
4. 财务或出纳查银行确认到账，或导入银行流水。
5. 系统按流水号、金额、付款方、交易号匹配待核对收款单。
6. 财务确认关联后，收款单转为正式认款，核销应收。
7. 如果始终找不到流水，财务退回销售或关闭收款单。

这个模式必须有三条底线：

- 未关联流水的收款单不能入账。
- 未关联流水的收款单不能重复占用同一笔资金。
- 后续关联流水时，系统必须检查该流水是否已经被其他认款使用。

合同是否允许基于“待核对收款单”先放行，需要公司单独确认。如果财务要求严格模式，则只有已关联流水并复核通过的收款才算合同放行依据。

## 第六部分：财务复核怎么处理

系统能自动确认的收款尽量自动确认，财务只处理异常。

### 自动确认场景

以下情况可以自动确认：

- 订单活码支付，订单、金额、流水已绑定。
- 流水号或交易号唯一匹配，金额一致，付款方与客户或单位客户一致。
- 固定码支付能通过交易号、金额和订单信息唯一匹配。

自动确认后，系统直接核销应收、更新订单收款状态，并生成收款凭证待推 NC。

### 人工复核场景

以下情况进入财务复核：

- 付款方与客户不一致，例如亲属代付、公司代个人付。
- 金额一致但同金额流水有多笔。
- 销售上传凭证不清晰。
- 交易号不唯一。
- 未找到流水。
- 一笔款跨多个部门、多个订单或多个客户。
- 现金、外币、OTA 月结、易宝台牌等特殊场景。
- 认款金额大于当前应收，需要转预收、预存或生成补收应收。

财务复核时，要能看到订单、应收、销售凭证、候选流水、付款方、金额差异和系统校验结果。

复核结果包括：

- **确认通过：** 核销应收，生成凭证。
- **退回补充：** 销售补资料或改认款对象。
- **保留待认：** 钱到了但暂不清楚业务归属。
- **转预收：** 钱到了但暂不能核销具体应收。
- **转预存：** 客户、门店或渠道确认留存余额。
- **生成补收应收：** 业务确认应收增加，例如补差、升舱、单项服务。

## 第七部分：合同与收款的关系

合同放行不是单纯财务规则，它会影响销售转化、门店现场签约、法务合规和财务风险。系统应支持按主体、渠道、产品类型配置不同合同放行规则。

财务在本流程中只确认一个口径：

> 只有自动确认或财务复核通过的认款，才是“已确认收款”。未关联流水、待核对、待复核、退回补充的收款单，都不能作为正式入账依据。

合同放行可以有几种模式：

- 已确认收款达到订单金额一定比例后允许发合同。
- 订单确认后允许发合同，收款由应收管理跟踪。
- 全款确认后允许发合同。
- OTA、加盟门店、呼叫中心按不同规则配置。

具体采用哪种模式，需要公司统一确认。

## 第八部分：预收和预存

### 预收

预收是钱已经到账，但暂时不能核销到明确应收。常见场景包括：

- 客户提前打一笔总款，订单还没完全确认。
- 单位客户先付款，后续拆分到多个订单。
- 客户多付。
- 销售暂时无法提供完整业务归属。

预收后续只能走四个方向：

- 转订单应收核销。
- 转客户预存。
- 退款给客户。
- 继续保留待认。

预收不能在线下表格单独维护，必须进入系统余额和明细。

### 客户预存

客户预存表示客户确认把余额留在公司，后续可用于报名或退款。客户预存常见来源：

- 订单取消后客户不退现金，留作下次使用。
- 超收金额客户确认留存。
- 客户提前打款形成余额。

客户预存账户要记录充值、扣款、冻结、退款、调整和余额。

### 门店预存

门店预存是门店先向公司充值，后续下单时按规则冻结或扣款。

流程：

1. 门店提交充值申请并上传凭证。
2. 财务匹配到账流水。
3. 财务确认充值入账。
4. 系统增加门店预存余额。
5. 门店下单时按结算方式冻结或扣减余额。
6. 月度门店对账汇总充值、扣款、退款转预存、管理费和期末余额。

## 第九部分：客户退款流程

### 退款从哪里发起

退款应从订单售后发起，由销售或售后人员选择原订单、退款原因、退款金额和退款对象。财务不应直接从流水上手工退钱，否则订单、应收和售后原因无法追溯。

### 退款必须带出原收款

客户可能分多次付款，也可能一笔付款分给多个订单。因此退款时，系统必须带出原收款记录，让业务和财务明确退的是哪笔钱。

退款页面应展示：

- 原认款单。
- 原到账流水。
- 原付款方式。
- 原收款金额。
- 已退金额。
- 可退金额。
- 本次退款金额。
- 原收款账户或平台商户信息。

销售或售后选择要退的原收款记录，系统控制累计退款不能超过可退金额。

### 退款方式如何确定

退款方式原则上跟原收款方式绑定。

- 线上支付、小程序、微信、支付宝：接口支持时原路退回。
- 银行汇款：优先带出原付款账户或客户确认账户。
- 易宝、第三方台牌：按平台商户订单号到平台退款，系统带出原商户信息。
- 现金：按公司现金退款规则，由财务或出纳复核。
- OTA：按平台逆向流程或月结账单抵扣处理。

业务人员不应随意修改退款方式。确需改账户或非原路退回时，应走审批并留原因。

### 客户退款与供应商追款解耦

客户退款依据客户合同，供应商退款依据供应商合同，两者不是同一条法律关系。新系统不能简单要求“供应商款追回后才退客户”，但也不能让供应商追款丢失。

建议流程：

1. 客户申请退款。
2. 系统检查订单是否已有供应商预付或付款。
3. 如果没有供应商预付，按普通客户退款执行。
4. 如果已有供应商预付，系统同时生成两条流程：
   - 客户退款流程：财务按客户合同执行退款。
   - 供应商追款流程：系统生成负应付、付款退回或预付退回任务，提醒计调/采购跟供应商追款。
5. 供应商后续退款到账后，财务核销追款任务。
6. 客户退款单和供应商追款单互相关联，后续结算和报表都能追踪。

客户退款不默认等待供应商退款到账。是否某些产品必须等供应商退回后才能退客户，需要公司另行规定。

### 退款后的财务结果

退款确认后，系统应自动处理：

- 原订单已收金额减少或应收冲销。
- 退款单形成财务凭证。
- 如果原收款已推送 NC，后续生成退款或冲销凭证，不直接改原凭证。
- 如果退款转客户预存，则增加客户预存余额。
- 如果退款失败退回公司账户，应回到退款退回处理，不能作为普通销售认款。

## 第十部分：订单转款流程

转款是把一个订单已确认收款转到另一个订单，不是客户重新付款。常见于团取消换团、客户改期、邮轮航次调整、本人不去转给家人、门店或销售录错订单等。

### 转款基本流程

1. 销售在原订单售后中发起转款。
2. 选择原订单的一笔或多笔已确认收款。
3. 填写本次转出金额。
4. 选择目标订单。
5. 系统检查主体、门店/分销商、客户是否一致。
6. 符合自动放行条件的，直接进入财务确认。
7. 不符合自动放行条件的，走业务审批和财务审批。
8. 审批通过后，财务或出纳确认转款。
9. 原订单减少可用收款，目标订单自动生成认款。
10. 转款记录进入凭证、NC 和转款报表。

### 转款管控规则

转款的风险在于把 A 客户的钱转给 B 客户，或把一个主体的钱转到另一个主体。建议规则如下：

- 跨主体不允许。系统应直接限制目标订单范围。
- 同主体、同门店/分销商、同客户，可以自动放行。
- 同主体但客户不同，可以申请，但必须说明原因并审批。
- 同主体但门店或分销商不同，可以申请，但必须审批。
- 判断同客户时，以真实姓名和证件号为准，不能只看姓名。

转款前必须补齐客户实名信息。如果订单只写“王先生”或“客人甲”，系统不能判断是否同一客户。

## 第十一部分：凭证、NC 和资金报表

### 收款凭证

只有确认通过的认款才生成收款凭证。待核对、待复核、退回补充、保留待认都不生成正式凭证。

### 退款和转款凭证

退款执行、转款确认、退款失败退回、转预存都应形成独立财务事件。系统不能直接修改原收款凭证，而应通过退款、冲销、转款或调整凭证体现。

### 报表

财务日常至少需要：

- 到账流水明细。
- 认款明细。
- 未关联流水收款单。
- 未认流水余额。
- 应收账龄。
- 退款执行明细。
- 转款明细。
- 预收预存余额。
- 资金日报、周报、头寸和资金计划。

报表的意义不是重复录表，而是从系统业务事件自动生成。

## 第十二部分：财务收款端常见端到端场景

本章只讲客户侧资金动作会牵动销售、门店、合同、履约和结算继续处理的场景。普通认款字段、流水字段和复核页面，前文已经说明，不在这里重复。财务阅读时重点确认：我确认或退回一笔钱以后，订单、合同、退款、转款和对账分别会发生什么。

### 场景一：客户付款后认款

客户付款后，系统可能自动识别，也可能由销售或门店手动提交认款。订单活码支付可以直接匹配订单；固定码、银行转账、第三方支付或门店预存扣款，则需要销售或门店选择订单、填写金额并上传凭证。

认款进入财务视角后，财务重点核对是否真实到账、金额是否一致、付款方是否合理、交易号或流水是否匹配、订单应收是否足够核销。通过后，订单收款状态更新，合同放行条件和履约条件随之变化；退回时，销售或门店需要补充凭证、改正金额或等待真实流水入池。

业务最终要看到的是订单收款状态明确更新。付款方不一致、金额差异、无流水、凭证不清时，不能只靠客户截图放行，应按复核规则处理。

### 场景二：无流水先提交收款单

有些场景下，客户已提供付款截图，但银行或第三方流水还没有进入系统。销售可以先提交待核对收款，系统保存付款截图、金额、客户和订单关系，但这笔钱在财务确认前不能作为正式已收款处理。

财务需要等待银行流水导入或到账通知进入系统，再把真实流水与待核对收款关联。找到真实流水并确认后，才核销订单应收、生成入账依据并进入后续 NC；如果一直找不到真实流水，财务应退回销售核实客户是否实际付款。

这个场景需要业务和财务共同确认：待核对收款是否允许影响合同放行、占位或确认书。财务默认口径应是未找到真实到账前不正式入账、不推 NC。

### 场景三：客户退款

客户退款一般由销售或门店从订单售后发起，售后审批通过后进入财务退款。系统会关联原订单、原收款、客户账户、可退金额、扣损依据、退款方式和审批记录。

财务审核时，不只看售后金额，还要核对原收款是否存在、退款对象是否合理、客户账户是否一致、扣损是否已经由业务确认、是否存在未完成转款或未核销应收。审核通过后，出纳执行退款并回填结果；如果涉及供应商责任、可追款或付款退回，则交给应付流程另行处理。

销售最终要看到退款完成、失败或被退回的原因。原收款未选、账户不一致、扣损未确认、审批依据不完整时，财务应退回而不是直接付款。

### 场景四：转团、改期或转款

客户不退钱，而是把原订单收款转到新订单时，销售或售后发起转款申请。系统会记录原订单可用收款、目标订单应收、转款金额、转款原因和审批记录。

财务审核重点是主体、客户、门店、金额和业务原因。通过后，原订单减少可用收款，目标订单增加收款并核销应收；如果还需要补差或退差，则继续生成补收或退款事项。跨主体、跨客户、跨门店转款风险更高，需要更严格审批和凭证。

业务最终要看到新订单收款承接完成，原订单账务不再挂着未说明余额。转款不能绕开退款审批，也不能把一笔客户款随意转给无关订单。

### 场景五：OTA 或渠道月结收款

OTA 或渠道月结不是单看客户是否付款，而是要把平台订单、系统订单、平台账单和实际到账放在一起核对。渠道运营或财务上传平台账单后，系统会形成渠道应收、平台扣费、平台退款和实结金额。

财务核对时，重点看平台订单号是否匹配系统订单，退款是否与系统售后一致，平台扣费和活动差额是否有依据，实际到账是否与账单实结一致。差异需要渠道运营解释或调整，不能只按到账总额冲掉全部应收。

渠道最终要看到的是应收是否核销、差异是否处理、月结是否完成。平台订单号不准、退款未对齐、扣费口径不清时，财务无法完成结算。

### 场景六：门店预存、扣款和退款转预存

门店充值、订单扣款、退款转预存都会影响门店预存账户。系统需要记录充值到账、订单扣款、冻结解冻、退款转预存和余额变化，并在账期结束后形成门店对账单。

财务先确认充值是否真实到账，再确认订单扣款和退款转预存是否有订单和审批依据。账期结束后，门店确认对账单，财务复核后生效，结算岗再按确认结果处理分润或余额调整。

门店最终要看到可用余额和对账结果。客户个人预存和门店预存是否分开、退款是否允许转预存、预存余额是否可以跨主体使用，需要业务和财务确认。

## 第十三部分：需要业务和财务确认的事项

1. 未关联流水的收款单是否允许提交，是否允许影响合同放行。
2. 哪些收款可以自动确认，哪些必须财务复核。
3. 付款方不一致时，需要销售提供哪些代付说明。
4. OTA 月结是否允许未到账先出合同，适用哪些平台。
5. 易宝或第三方平台能否提供唯一交易号。
6. 现金收款由谁登记、谁复核、是否缴存后才确认。
7. 外币收款和退款使用哪个汇率口径。
8. 客户退款是否默认不等待供应商退款到账。
9. 供应商追款进入负应付、付款退回还是预付退回。
10. 转款自动放行是否采用同主体、同门店/分销商、同客户三条件。
11. 收款报表、退款报表、转款报表和资金日报字段模板。
